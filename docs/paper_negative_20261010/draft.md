## 摘要

長對話的 KV cache 要放哪一層：快而小的 CPU 記憶體、慢而大的 SSD，或者不存、回來時重算。近年有系統在**寫入當下**就決定，常用的依據是 chunk 在對話裡的位置。讀取端也已經會自己調整：Cake 還原時讓 GPU 從前面重算、I/O 從後面載入，兩邊在中間會合。我們問：讀取端會自適應時，寫入時放置還重要嗎？

我們在一張 AMD MI300X 上，用 Llama-3.1-8B、自管 KV 的 harness（還原後逐位元比對）、限速的 CPU／SSD 層和一個與 GPU 對過的模擬器，把寫入時放置和它的「延後雙胞胎」比。延後雙胞胎＝同一條規則，改在滿了才做、背景做、預先清理，或者乾脆寫穿。

結果有三點，另加一個真實系統的觀察。
- **Cake 只在一段頻寬帶裡明顯有用。** 在我們的 harness 上，32K token、層頻寬 0.33–3.73 GiB/s 時，Cake 比「只算」「只載」中較快的再快 1.38–1.93 倍；11.6 GiB/s 時只快 5%〔實測 A0 ✅F5〕。harness 的重算比預設 vLLM 慢約 1.7–2 倍〔實測 F1；算術〕，所以這條帶子的絕對位置〔待重量〕：重算越快，帶子越往高頻寬移。
- **寫入時放置從沒在 GPU 上同時贏過全部延後雙胞胎 ≥5%。** 第一階段 17 組設定、消融 16 組比較、模擬唯一存活者的 5 個 seed，全部沒過〔07 §8.4；實測 B2 ✅F5；實測 R1GPU ✅F5〕。原因是位置資訊在淘汰時一樣拿得到。延後版唯一會輸的區域是「SSD 持續寫不完，而且寫入佇列有上限」。用 10 個全新 seed、事先登記、程式凍結重跑併發模擬：沒有持續排隊（ρ_KV<1）的 216 格裡，兩個寫入時候選都 0 格通過〔模擬 F6 ✅F5〕；過載角落原本 5 格，只有 1 格重現（10 個 seed 裡 7 個，中位 +14.2%，回來請求 TTFT 中位 11.2 s），而且改看平均或 p90 就不贏〔模擬 F6 ✅F5〕。單卡、實測參數下 ρ_KV 最高 0.99〔模擬 D1SW ✅F5〕；真實 vLLM 0.28 在 133,504 個要存的 block 裡跳過 0 個〔實測 D2 ✅F5〕。
- **哪個延後策略贏，主要由使用者回來的順序決定**，不是由硬體常數決定：同樣的硬體條件只換回來順序，模擬裡只有 17／64 組的贏家不變〔模擬 D3 ✅F5〕。
- **真實系統的觀察（工程陷阱，不是寫入時放置的證據）**：vLLM 0.28 在 ROCm 上只要設定任何 KV connector，就把 attention 從 ROCM_ATTN 換成 TRITON_ATTN；同一個 33K prefill 的 attention kernel 從 1.367 s 變 3.277 s〔實測 F1 ✅F5〕。開 CPU 卸載後新請求慢 96%，3／3 個 seed 重現〔實測 F1 ✅F5〕。把 KV 拆成 K、V 兩個 view 註冊，可以無損地拿掉 45–74% 的多出時間〔實測 F1 ✅F5〕；上游還沒修〔原文 vLLM #60316；F1 §5.1〕。

最後我們整理出三條評估「提早決定」型設計的方法：延後測試；模擬篩選的門檻要大於模擬器對策略的相對偏差；比較「卸載 vs 不卸載」時要鎖同一個 attention 實作。

## 1 引言

**本節要講的**：在我們測過的範圍內，讀取端會自適應時，「寫入當下就決定 KV 放哪一層」沒有不可取代的價值。我們先講問題，再講為什麼值得寫成一篇論文，最後列貢獻和範圍。

### 1.1 問題

使用者和 LLM 的長對話會「離開再回來」。回來時，之前算過的 KV 要嘛還存在某一層，要嘛要重算。

- **層**：GPU 記憶體放不下的 KV，可以放 CPU 記憶體（快、小），或放 SSD（慢、大），也可以不存、回來時重算。
- **讀取端已經會自己調整**：Cake〔原文；卡片 D6_Cake〕還原時，GPU 從第一個 chunk 往後重算，I/O 從最後一個 chunk 往前載入，兩邊在中間會合。前段越便宜重算，後段越值得載入。
- **一個自然的想法**：既然前段反正會被重算，那**寫入時**就把前段放到慢的層（或不存），尾段放 CPU。我們把這叫 S5。
- **已有人這樣做**：Krul 在寫入時決定每層前段不存、讀取時重算〔原文 p.8–9；卡片 A_Krul〕；TierKV 在 prefill 後依位置把 token 分三層〔原文 p.4；卡片 A_TierKV〕；Lachesis 在寫入前依壽命決定放 HBM 或 HBF〔原文 p.2；卡片 A_Lachesis〕。
- **但它們幾乎都沒和「同一條規則，延後才套用」比過**〔Lit-A §0；lit_A_summary.md〕。

所以問題是：**讀取端會自適應時，寫入時放置還重要嗎？**

### 1.2 為什麼重要

- **寫入時決定有成本**：要在寫入路徑上加邏輯、加預測器，甚至改資料路徑。如果延後版拿得到同樣的好處，這些成本就白付了。
- **反過來，如果有一個區域只有寫入時做得到**，系統設計者需要知道它在哪裡、多常出現。
- **經典儲存文獻有類似的結論，但 KV 不一樣**。Gill（FAST'08）比過「資料經過時就決定放哪層」和「逐出時才往下搬」：搬移免費時最多只差 4–5%，頻寬受限時是 3.42 對 5.05 ms〔原文 p.13；卡片 B_PROMOTE〕。KV 有兩個不同的地方：丟了可以重算，而且讀取端會依頻寬自己調整。在我們查到的前作裡，沒有人在這個組合下量過〔Lit-A §0；查不到不等於沒有〕。

### 1.3 我們做了什麼

- 三輪 GPU 實驗：第一階段（07）、消融（09）、破解第 1 輪（12）。每輪開跑前都寫死判準。
- 一次 zero-context 反方審查（REDTEAM_round1.md）：抽查 24 個數字，5 個有錯，已更正〔12 §9〕。
- 八個方向同時探索（D1–D8），各自事先登記判準。
- 五個後續工作（F1–F4、F6）：真實 vLLM 變慢的原因、能耗、反量化成本、資料稽核、併發模擬用新 seed 重跑。

### 1.4 貢獻

1. **Cake 的頻寬帶（§4.1）**：在 MI300X、Llama-3.1-8B、32K token、我們的 harness 上，Cake 只在約 0.3–4 GiB/s 的層明顯有用（1.38–1.93 倍）；6.98 GiB/s 時快 17%，11.6 GiB/s 時快 5%〔實測 A0 ✅F5〕。帶子的絕對位置〔待重量〕（§3.1）。
2. **延後測試的結果（§4.2）**：寫入時放置在所有 GPU 比較裡都被延後雙胞胎追平。原因可以說清楚：寫入時用到的資訊（位置），淘汰時一樣拿得到。
3. **贏家由回來順序決定（§4.3）**：同樣的硬體常數，只換使用者回來的順序，最好的策略就換人。所以「事先用 κ 算出誰會贏」做不到。
4. **「沒有空閒」的區域在實測參數下不會持續出現（§4.4）**：這是延後版唯一會輸的區域。用新 seed 事先登記重跑後，沒有持續排隊時寫入時決定 0／216 格通過〔模擬 F6〕；持續過載的角落只剩 1 格、只在中位數上贏〔模擬 F6〕。
5. **方法上的教訓（§5.3）**：延後測試；模擬篩選要有足夠的門檻；事後加對手的偏誤要照實報告、並用新 seed 事先登記重跑；量測時要確認引擎實際選了哪個 kernel。
6. **一個真實系統的工程發現（§4.6）**：vLLM 0.28 在 ROCm 上開 KV connector 會換掉 attention kernel，這才是「開卸載反而變慢」的主因；有一個無損的修法〔實測 F1〕。這不是寫入時放置的證據，但它影響任何「卸載 vs 重算」的量測。

## 2 背景

**本節要講的**：本文用到的四個概念各是什麼：KV 分層、Cake 還原、κ、延後雙胞胎。

### 2.1 KV 分層

- **chunk**：512 個 token 的 KV。Llama-3.1-8B（BF16）每個 token 的 KV 是 128 KiB，所以一個 chunk 是 64 MiB〔07 §2.1〕。
- **層**：
  - GPU：只放正在服務的請求（刻意製造容量壓力，07 §10 L5）。
  - CPU：pinned DRAM。
  - SSD：本地 SSD 或 NFS。
  - 不存：回來時重算。
- **回來請求的 TTFT**：使用者回來時，從送出到第一個 token 的時間。包含還原舊的 KV，加上 prefill 新的部分。本文的主要指標是**回來請求 TTFT 的中位數**〔07 §8〕。

### 2.2 Cake 雙向還原

- 還原 n 個 chunk 時，GPU 從 chunk 0 往後重算，I/O 從 chunk n−1 往前載入，兩條線在會合點 b 碰頭〔Cake 原文；卡片 D6_Cake〕。
- 前 b 個 chunk 被重算，後 n−b 個被載入。**b/n** 是「被重算的比例」。
- 重算第 i 個 chunk 的時間 f(i) 隨位置線性上升：在 MI300X 的 harness 上，第 1 個 chunk 28.9 ms，第 80 個（40K）98.8 ms，斜率 0.888 ms／chunk〔實測 C1；絕對值〔待重量〕〕。越後面越貴，這正是 Cake 的前提。
- 會合點可以事先算：用演算法 1（f(i) 加上層頻寬）預測，28／28 格和實測差 ≤1 個 chunk〔實測 A0；07 §3.3〕。

### 2.3 κ：重算和載入的成本比

- **本文的定義**：κ(i)＝f(i)÷ℓ，ℓ 是從某一層載入一個 chunk 的時間。κ 和位置 i、和層都有關。
  - CPU 層（35.4 GiB/s）：ℓ＝1.76 ms，κ(0)＝28.9÷1.76≈16.4〔算術，由 C1、C0〕。載入比重算最便宜的 chunk 還便宜 16 倍。
  - CPU 層用 vLLM 實測的速度（3.69 GiB/s）：ℓ≈16.9 ms，κ(0)≈1.7〔算術，由 KS〕。
  - NFS 層（0.331 GiB/s）：ℓ＝188.8 ms，κ(0)≈0.15〔算術，由 C1、C2〕。重算比較便宜。
  - 這三個值都用 harness 的 f(i)。重算快 1.7–2 倍的引擎上，κ 會小 1.7–2 倍〔算術，由 F1；待重量〕。
- **κ 決定 b**：κ 很大時 b 很小（幾乎全載入）；κ 很小時 b 接近 n（幾乎全重算）；κ 接近 1 時 Cake 最有用。重算變快＝κ 變小（也就是 ℓ÷f 變大）＝b/n 變大。
- **定義要統一**（F4 稽核的結論）：`main.tex` 的 MI300X κ 是「重算÷傳輸」、在 vLLM 上以每 token 平均量的；harness 的是逐 chunk 的時間比。F4 認為兩個值都是真的，只是量的是不同軟體路徑：vLLM 的 CPU 卸載比 memcpy 慢 8.9 倍〔DATA_AUDIT 摘要〕。F4 建議統一成「同一引擎、同一後端，重算÷取回，並附平台、模型、長度、路徑」〔DATA_AUDIT §4〕。F1 另外發現，MI300X 上 vLLM 一開卸載就換 attention kernel，所以 vLLM 量到的 κ 混進了 kernel 的差（§4.6）。**本文不引用 `main.tex` 的任何 κ 數值**；3090 的 κ 來源每一列都在整機 HEAVY 爭用下量，F4 判「有疑慮」〔DATA_AUDIT §1〕。

### 2.4 寫入時放置，和它的延後雙胞胎

**寫入時放置**：寫入當下就依位置決定放哪一層。本文的候選：

| 代號 | 寫入時做什麼 | 淘汰時 |
|:--|:--|:--|
| S5 | i<b（以 CPU 速度算的會合點）放 SSD，其餘放 CPU | 依位置，前段先走 |
| S5L | 同 S5 | 最久沒用的 session，從前段開始搬 |
| S5P | 同 S5 | Pensieve 的保留值 V＝f(i)÷閒置時間 |
| S5c | 全部放 CPU，**另外**把前段先複製一份到 SSD | 前段先走；有副本的直接丟 |

（定義：`03_strategies.md`、08 §4。併發模擬另有 S5T、S1D，見 §4.4。）

**延後雙胞胎**：同一個效果，不在寫入當下決定。這是本文的核心對照組〔10 §2〕：

| 類型 | 意思 | 代號 |
|:--|:--|:--|
| 延後版 | 同一條規則，等 CPU 滿了才套用 | S4B（S5L 的延後版）、S4+（S5 的延後版） |
| 背景版 | 同一條規則，每輪結束後在背景先做，保持 CPU 至少空 25% | S4W |
| 預先清理版 | 照淘汰順序，先把一部分 chunk 複製到 SSD，CPU 那份留著 | S4C |
| 寫穿版 | 每一層都寫一份，不做決定 | S1（寫穿＋LRU）、S2b（寫穿＋依位置淘汰） |
| 讀取時版 | 讀取時才決定 | Cake 本身（所有策略的還原都用 Cake） |

不看位置的簡單策略也一起比：S4（只寫 CPU，滿了照 LRU 搬）、S4+P（Pensieve 式淘汰）、S4L（LRU session、從前段搬）〔08 §4〕。

## 3 方法

**本節要講的**：數字從哪裡來、哪些可信、哪一句原本說錯了、判準怎麼定。

### 3.1 GPU harness

- **自管 KV 的 Llama 前向**：重用 Hugging Face 的權重和 RoPE，注意力和 KV 緩衝自己管〔07 §2.1〕。這樣才能逐 chunk 計時，讓 Cake 的「前段重算、後段載入」真的並行。
- **正確性**：
  - 重算兩次的 KV 逐位元組相同；GPU→pinned→GPU 往返逐位元組相同〔實測 07 §2.2〕。
  - 每次實驗都把還原後的 KV 和存的那份逐位元組比，所有實驗 `kv_bad`＝0〔07 §2.2；09 §1；12 §5.4〕。
- **雜訊底線**：同一設定重複量，δ＝6.2%（95% CI 半寬÷中位數，四組取最大）〔實測 C4〕。雜訊主要來自會合點在相鄰兩個 chunk 之間跳動。

**更正：harness 的重算比預設 vLLM 慢約 1.7–2 倍〔算術，由 A0、F1〕，不能說「不是稻草人」。**
- **原本的說法**：第一階段拿 harness 的整段重算和 vLLM 0.28 比，8K 慢 46%、16K 慢 10%、32K 快 18%，所以「計算端相當，f(i) 不是被做弱的稻草人」〔07 §7〕。本草稿的第一版照抄了這句話。
- **為什麼不成立**：那次的 vLLM（C6）開著 OffloadingConnector。vLLM 0.28 在 ROCm 上只要設定任何 KV connector，就把 AMD 的 ROCM_ATTN 從候選拿掉，改用慢的 TRITON_ATTN；C6 的 server log 寫的就是 `Overriding with TRITON_ATTN`〔實測 C6 的 `vllm_server.log`；程式碼 `platforms/rocm.py:482-485`；F1 §3.1、§6.1〕。也就是說，對照組是被拖慢的 vLLM。
- **和預設 vLLM（ROCM_ATTN、不開 connector）比**：8K 首輪 0.318 s、33K 首輪 2.244 s〔實測 F1，3 個 seed〕；harness 的整段重算是 645 ms（8K）、3,759 ms（32K）〔實測 A0〕。harness 慢 2.0 倍與 1.7 倍〔算術〕。
  - 兩邊設定不完全一樣：harness 的「只算」多算了 256 個新 token；vLLM 這次用 `max_num_batched_tokens`＝8192，C6 是 server 模式〔F1 §6.1〕。所以 1.7–2 倍是近似值。
  - 逐 chunk、帶長前綴的比較，方向看引擎而定：vLLM 0.19.1（沒有這個換 kernel 的邏輯〔程式碼；F1 §6.1 第 3 點〕）的引擎時間戳，算一個新 chunk 是 harness 的 1.53 倍；扣掉一筆和上下文長度成正比的開銷後，邊際時間只有 harness 的 0.26–0.28 倍〔實測；12 §4.2–4.3〕。
- **這對本文的影響**（細節在 §4.1、§4.2、§7）：
  - harness 的 f 偏大 → κ 偏大 → 算出的 b 偏小 → 寫入時「可以決定的東西」被低估。**這個偏差的方向對寫入時放置不利，也就是偏向本文的結論。**
  - 所以 Cake 頻寬帶的絕對位置、κ 的數值、會合點 b 都標〔待重量〕。
  - 結構性的主張（延後追得上）在重算變快時證據最弱，見 §4.2 的敏感度分析。

### 3.5 延後測試

**定義**〔10 §2〕：一個寫入時的想法 X，要在 GPU 實測、≥3 個 seed 上，**同時**贏過它的每一個延後雙胞胎（延後版、背景版、預先清理版、寫穿版、讀取時版）各 ≥5%，才能說「寫入時決定有效」；≥15% 算強。只贏過一部分的，寫成「某某規則有效」，不能寫成「寫入時」有效。

**為什麼要這樣比**：寫入時決定有用，只可能是因為四種東西之一〔10 §2〕：
- N1 寫完就消失的資訊；
- N2 延後要多付的稀缺資源；
- N3 延後需要空閒時間，但沒有；
- N4 寫成什麼形式，決定讀取時能做什麼。
位置不屬於 N1：淘汰時一樣看得到。

**這個判準是怎麼來的（照實寫）**：它不是一開始就有。08 的第一次模擬掃描裡，S5L 贏了不看位置的策略；看到之後才加了 S4B（S5L 的延後版）〔08 §8〕。之後才把它寫成通用的延後測試（10 §2）。第 1 輪之後，所有方向都在開跑前把它寫進判準〔11；D1–D8 各自 §2〕。

## 4 結果

### 4.1 Cake 只在一段頻寬帶裡明顯有用（帶子的絕對位置待重量）

**本節要講的**：讀取端的 Cake 確實有用，但好處強烈依賴層的頻寬。這決定了「前段該不該去慢的層」這個問題什麼時候才有意義。下面的數字都是在 harness 上量的，重算比預設 vLLM 慢（§3.1），所以帶子的**形狀**可信，**絕對位置**〔待重量〕。

**32K token 的 TTFT 加速**（對「只算」「只載」中較快的那一個；S0＝全部存在限速的 SSD 層；每格 6 次的中位數）〔實測 A0 ✅F5；絕對位置〔待重量〕〕：

| 層頻寬（GiB/s） | 0.331（NFS 參數） | 0.815 | 2.91 | 3.73 | 6.52 | 6.98（本地 SSD 參數） | 11.6 |
|:--|--:|--:|--:|--:|--:|--:|--:|
| Cake TTFT（ms） | 2,723 | 1,952 | 972 | 833 | 566 | 565 | 409 |
| 加速 | 1.38× | 1.93× | 1.50× | 1.39× | 1.24× | 1.17× | 1.05× |

（「只算」32K 是 3,759 ms〔實測 A0〕。）

- **在 0.33–3.73 GiB/s 之間，Cake 快 1.38–1.93 倍**〔實測 A0 ✅F5〕。最大的好處在 0.815 GiB/s，也就是載入時間和重算時間差不多的地方。
- **頻寬越高，好處越小**：6.98 GiB/s 快 17%，11.6 GiB/s 快 5%〔實測 A0 ✅F5〕。最短 × 最快那一格（4K、11.6 GiB/s），Cake 還比只載慢 5.6%（78 對 74 ms）〔實測 A0；07 §4〕。這是 28 格裡唯一的例外。
- **context 越長越有效**：對「只算」的加速，7／7 個頻寬都隨長度變大〔實測 A0；07 §4〕。
- **和原文一致**：Cake 原文 Table 6 的 GQA Llama-3.1-8B 在 32 Gbps 時是 0.98 倍〔Cake 原文 Table 6，引自 07 §4；卡片 D6_Cake〕。
- **MHA 模型的好處較大，但只有公式值**：LongAlpaca-7B（MHA，KV 是 Llama 的 4 倍）在 3.69 GiB/s 時，公式算出 2.10 倍；同一個公式給 Llama 1.45 倍，而 A0 實測只有 1.39 倍，所以公式偏高〔算術 KS；12 §4.1〕。LongAlpaca 的 GPU 實測 NOT_MEASURED。

**重算變快時，帶子往哪裡移**：Cake 最有用的地方是「載入一個 chunk ≈ 重算一個 chunk」。重算快 1.7–2 倍時，要達到同樣的平衡，層的頻寬也要高 1.7–2 倍〔算術，假設每個 chunk 的 f 都等比例變快；待重量〕。所以在較快的引擎上，Cake 有用的帶子會往高頻寬移，原本「≥7 GiB/s 好處 <20%」的說法也要重量。

**真實 vLLM 的 CPU 層落在「載入≈重算」附近**：
- vLLM 0.28 的 CPU 卸載在 MI300X 上跑到 4.02–4.11 GiB/s，而裸 PCIe 的 pinned H2D 是 52.9 GiB/s〔實測 C6、C0〕。
- 用預設的 ROCM_ATTN 重算、用修好的路徑從 CPU 載入（同一個 kernel）：chat 回來請求載入約 16K token 要 1.678 s，重算 1.460 s，載入**慢 15%**；doc 載入約 33K token 2.049 s，重算 2.272 s，載入只快 10%〔實測 F1，seed 1〕。
- 〔判讀〕在真實引擎上，CPU 層正處在載入和重算差不多的地方，也就是 Cake 最該有用的地方。但 vLLM 0.28 不做 Cake，它只會二選一。

**但頻寬要在目標軟體上量，不能用裝置頻寬算**：用校準頻寬預測真實裝置上的 Cake 加速，誤差中位 25.1%（9 格）〔實測 C7；D3 §4.1〕。

**小結**：在 harness 上，Cake 讓「前段重算、後段載入」在 0.3–4 GiB/s 的層上值 1.38–1.93 倍〔實測 A0〕；帶子的絕對位置隨重算速度移動〔待重量〕。在 CPU 速度（35.4 GiB/s）下，b 只有 0–3 個 chunk〔07 §8.3〕，「寫入時把前段放到別處」幾乎沒有東西可以決定。

### 4.2 寫入時放置在每一個 GPU 比較裡都被延後雙胞胎追平

**本節要講的**：三輪 GPU 實驗，沒有任何一個寫入時策略同時贏過全部延後雙胞胎 ≥5%。贏的永遠是「規則」，不是「寫入時」。最後一段看重算變快時這個結論還站不站得住。

**第一階段：寫入時和延後只差寫入那一步，結果一樣。**
- S5 和 S4+ 的唯一差別是「寫入當下就依位置放」還是「滿了才依位置搬」。所有設定的差距都在 −3.0%～+0.3%〔實測 B ✅F5〕。
- 原因：在 CPU 速度下，κ(0)≈16（§2.3），算出來的 b 只有 0–3 個 chunk〔07 §8.3〕。S5 寫入時幾乎把所有 chunk 都放 CPU，之後的行為就和 S4+ 一樣。
- 容量緊時，依位置淘汰本身就不好：25% 容量時，LRU 類策略比依位置的 S5 快 12–33%〔07 §1 結論 5〕。依位置淘汰會把每個 session 的前段都擠到慢的層，包括馬上要回來的那個。

**08 消融：贏的是「b 規則」，不是「寫入時」。**
- 模擬裡最有希望的設定（doc＋hold＋CPU 3.69 GiB/s＋NFS＋50% 容量，seed 0）上 GPU：S5L 比最好的不看位置策略快 18.9%，但只比 S4B 快 0.7%〔實測 B2 ✅F5〕。S4B 就是「同一條 b 規則，滿了才套用」。
- 換一個 seed，這條規則本身也不穩：seed 1 時寫穿 S1 最好，S5L 慢 6.8%〔實測 B2 ✅F5〕。
- hold 下真正有用的是「早點寫到慢的層」，寫穿就做得到：chat＋hold＋25% 時，S1 是 1.555 s，S5 是 3.450 s〔實測 B2 ✅F5〕。
- 「四個條件」（快的層 ≲4 GiB/s、空間緊、搬移卡在請求路徑上、淘汰看閒置時間）在 G1 設定裡同時成立過，還是沒過。缺的第五個條件是「這個決定延後做不到」〔09 §0；FULL_REPORT §3〕。

**第 1 輪：模擬裡唯一能上 GPU 的存活者，GPU 上 0／5。**
- 存活者：Llama、doc、free、CPU 11.6 GiB/s、本地 SSD、50%。模擬預測 S5L 快 7.6%（0.416 對 0.451 s）〔模擬 SIMR1；12 §5.2〕。
- 事先固定只看 S5L，不在每個 seed 挑最好的寫入時策略〔11 追加 4〕。
- GPU 上 5 個 seed 都沒過；S5L 和 S4B、和最好的不看位置策略都在 ±3.5% 內〔實測 R1GPU ✅F5〕。
- S5L 確實贏我們做的背景版 S4W（8.0–16.8%）和預先清理版 S4C（3.3–30.9%）〔實測 R1GPU ✅F5〕。這只表示這兩個對照組做得比 S4B 差，不改判定。
- 模擬為什麼說存活：模擬器對 S5L 偏樂觀約 4.6%，對 S4B 偏悲觀約 1.1%，相對偏差和預測的優勢差不多大〔12 §5.4 ✅F5〕。
- LongAlpaca 的 4 個存活者沒上 GPU：doc 負載的回來請求超過它 32,768 token 的上限；hold 那組又處在 NFS 寫入過載〔12 §5.3；RT §2〕。

**另一個方向：寫入時的決定用的是當下的假設，之後會過時。**
- 寫入時決定「前段不存」，GPU 忙時要付代價：一開始不寫前段的 S3，在 GPU 忙時比 S0 慢 13–66%（16K 以上）〔實測 A1；07 §5〕。
- S5 的 b 是假設 GPU 閒算出來的。NFS、GPU 很忙、32K 時，S5 是 546 ms，全放 CPU 是 400 ms，慢 37%〔實測 A1；07 §5〕。
- 延後的決定可以用淘汰當下的資訊，所以不吃這個虧。

**SSD 寫入量也沒有贏**：寫入時策略「TTFT 在最好的 5% 內、而且 SSD 少寫 ≥20%」的設定只有 2／23（8.7%），判準是 ≥20% 的設定，所以殺掉〔實測重分析 H1；12 §3〕。在 5% 帶內寫得最少的，最常是延後的 S4（10／23）〔H1；12 §3〕：延後本身就少寫，只有被擠出 CPU 的才寫 SSD。

**重算變快時呢？（模擬敏感度，照實寫）**

- **只改重算成本一個因子**（f×0.25–2）：寫入時策略都贏不到 5%〔模擬 SIM08；09 §3〕。
- **但組合起來就不一樣**。08 的 390 格組合掃描裡，同時贏過「最好的不看位置策略」與 S4B 各 ≥5% 的 8 格，有 7 格是 f×0.25 或 ×0.5〔模擬 SIM08；09 §3〕。依 f 拆開（F5 從 `sim_sweep_gain.csv` 重算）：

| f×0.25 | 3 | +15.4% | 2 |

- **換 5 個 seed 檢查穩定性**：09 用「5／5 個 seed 都要過」，結果 30 個設定 0 個過〔09 §3〕。但如果用第 1 輪的規則（≥3／5），F5 從 `sim_probe.csv` 重算是 **3／30 個設定存活**：兩個是 CPU 11.6＋hold＋doc＋NFS＋f×0.5（4／5、3／5），一個是 CPU 11.6＋free＋doc＋本地 SSD＋f×0.25（3／5）〔模擬 SIM08；F5 重算 ✅F5〕。反方審查也指出這兩輪的 seed 門檻不一致〔RT §1.2 f〕。

- **判讀**：重算越便宜，寫入時放置越接近贏；f×0.5（大約就是「harness 換成預設 vLLM 的速度」）在 free 下仍然 0 格通過、最大領先 3.3%，但在 hold 下有存活者。所以「延後追得上」在較快的重算下大致成立，但證據只有模擬，而且正是最弱的一塊〔待重量〕。要補的是：在較快的重算下，用完整的雙胞胎集合（含 S4W、S4C、admit-first）和 ≥3／5 規則重跑，存活者再上 GPU。

**小結**：三輪共 38 組 GPU 比較（17＋16＋5）〔算術〕，寫入時放置沒有一次同時贏過它面對的全部延後雙胞胎 ≥5%。第一階段的對照組還沒有 S4B、S4W、S4C；加上它們只會更難通過。這個結論是在偏慢的重算下量的；重算變快時，模擬裡有少數存活者，還沒有 GPU 確認。

**(d) 真實 vLLM 0.28：CPU 滿了不丟新的，它會重試。**

- CPU 只有工作集 25% 時也是 0／200,256〔實測 D2 ✅F5〕。

- CPU 下面接一層 NFS 時，CPU 曾被「寫往下一層」完全鎖住（不能淘汰的比例 100%），但最後只跳過 0.21%〔實測 D2 E2 ✅F5〕。

- 只有一個 seed。主指標 0.0% 離門檻很遠，照事先規則不補 seed〔D2 §7〕。

**(e) OS 層：作業系統本身就是一個延後寫入的緩衝。**
- LMCache 的本地磁碟後端和 SGLang 的 `file` 後端預設用一般的 buffered 寫入〔程式碼；D7 §4.1〕。
- buffered 寫完 30 s 後，自己的檔 100% 還在 page cache（本地 16,384／16,384 MiB、NFS 4,096／4,096 MiB）；本地的 dirty 資料在寫完 30.24 s 後才寫到磁碟〔實測 D7〕。
- 寫到 12 GiB dirty 都沒有掉崖（p99÷中位數 1.50）〔實測 D7〕。照算術，這個 container 要 dirty 到約 63 GiB 才會開始擋寫入者〔算術；公式憑記憶，未查證；D7 §4.3〕。
- 延後版「之後再丟 page cache」很便宜：0.52–3.09 s 就把 4–16 GiB 還回來〔實測 D7〕。

**小結**：
- 單卡、實測的層參數下，持續寫不完（ρ≥1）沒有出現；在沒有持續排隊的格裡，事先登記的新 seed 重跑 0／216 格通過〔模擬 F6〕；真實 vLLM 存不進去會重試；OS 本身也會吸收幾十 GiB 的寫入突發。
- 寫入時放置唯一贏的地方，是「ρ_KV≈2.1、佇列有上限、TTFT 已經 10 s 以上」的模擬角落，只有 1 格穩定重現、只在中位數上贏〔模擬 F6〕，而且用的是假設的頻寬。
- **多卡同時卸載時，每張卡真正分到多少 SSD 寫入頻寬：NOT_MEASURED**（這台只有一張卡）。這是本文結論最可能翻轉的地方之一（另一個是重算變快，§4.2）。

- 事先登記的判定看用哪一組延後版：照文字列的 7 個，SSD 寫入差距中位 86.8%、89.2%（有看頭）；照程式裡放的 25 個（多了「完全不寫 SSD」），差距 0%（死路）〔模擬 D4〕。兩個都列出。
- **延後測試**（事後加的對照組 KEVa）：同一份「誰會被重用」的知識，延到淘汰時才用，在 CPU 11.6 GiB/s＋本地 SSD 與所有 NFS 格，TTFT 和 SSD 寫入都和寫入時用**完全相同**〔模擬 D4〕。CPU 比 SSD 還慢的那一組（3.69 GiB/s）不同，但差別來自規則，不是時機〔D4 §4.6〕。
- 有差的只有 CPU 很小時（≤工作集 10%）：知道誰會被重用，就完全不用寫 SSD〔模擬 D4〕。這是「准入預測」的問題，flash cache 領域有前作，新穎性要另外查〔SUMMARY §3C〕。

**D5 的細節**：Gemma-3-12B 在 32K 時，滑動視窗層有 81% 的位元組用不到〔算術 D5〕；但 SGLang 和 vLLM main 已經做了分層感知卸載〔程式碼；D5 §0〕。P/D 分離在 25 Gbps 時，逐 chunk 管線只露出 0.59% 的傳輸時間〔算術 D5〕。MLA 讓 b/n 變得很小（DeepSeek-V3 在 3.69 GiB/s 時 0.047）〔算術 D5〕。只有混合 SSM 的「每一層存多密的檢查點」沒人做，而且只對分叉型工作有意義〔D5 §0〕。

**D6 的細節，含 F3 的結果**：
- Cake 的還原時間只看「各精度各載入了幾個 chunk」，和它們在哪個位置無關〔算術 D6〕。所以依位置挑精度沒有額外好處，均勻降精度本身才有用，而那是 Cake 原文 Table 6 做過的〔原文 p.6–7；卡片 D6_Cake〕。
- D6 的事先判準：INT8 反量化 ≤1 ms／chunk 就判死路；≥3.5 ms 才有「混入 BF16 分擔反量化」的空間〔D6 §6〕。
- **F3 量到**：INT8→BF16 反量化一個 64 MiB chunk，最快的正確實作 0.031 ms（中位數；快取冷）；最慢的 plain torch 寫法也只要 0.184 ms〔實測 F3 ✅F5〕。FP8、INT4 是 0.026、0.027 ms〔實測 F3〕。照 D6 的判準，**D6 判死路**。
- D6 原本引用的「INT4 0.814、FP8 0.087 ms／chunk」**不是反量化 kernel 的時間**，是 warm TTFT 的差；每組只有 3 個樣本，INT4 那組還換了 attention kernel（TRITON_ATTN 對 ROCM_ATTN）〔實測 F3，查 20260915-124058 的 stdout 與 server.log〕。這兩個數字本文不用。

### 4.6 真實系統：vLLM 0.28 在 ROCm 上開 CPU 卸載會換掉 attention kernel，這才是變慢的主因

**本節要講的**：這是一個真實系統的量測發現和工程陷阱，**不是**寫入時放置的證據。D2 看到開 CPU 卸載反而變慢；F1 用 3 個 seed 重現，並找到原因：不是搬資料，是 attention kernel 被換掉了。它對本文的意義有兩個：第一階段的「harness 不是稻草人」說錯了（§3.1）；任何「卸載 vs 重算」的量測，都要鎖同一個 kernel。

**設定**：vLLM 0.28.0、Llama-3.1-8B、OffloadingConnector＋CPU（工作集約 50%）、16 個 session × 4 輪、輪與輪之間沒有空檔，照 D2〔F1 §2.1〕。

**(a) 重現：3 個 seed 都變慢**〔實測 F1 ✅F5；比例為算術〕：

| 格（事先選定的主指標） | seed 1：關 → 開 | seed 2 | seed 3 |
|:--|:--|:--|:--|
| chat 併發 1（回來請求 TTFT） | 0.826 → 1.542 s（+87%） | 0.877 → 1.734 s（+98%） | 0.825 → 1.531 s（+86%） |
| doc 併發 1（新請求 TTFT） | 2.242 → 4.398 s（+96%） | 2.244 → 4.394 s（+96%） | 2.244 → 4.403 s（+96%） |
| doc 併發 16（回來請求 TTFT） | 43.69 → 66.95 s（+53%） | 43.68 → 66.94 s（+53%） | 43.69 → 67.02 s（+53%） |

**(b) 原因：換 kernel，不是搬資料。**
- vLLM 0.28 在 ROCm 上只要設定任何 KV connector，就把 AMD 的 ROCM_ATTN 從候選拿掉；這台沒裝 aiter，只剩 TRITON_ATTN〔程式碼 `platforms/rocm.py:482-485`、`rocm_attn.py:212-215`；F1 §3.1〕。這和卸載有沒有真的搬資料無關。
- **消融**：完全不開卸載、只把 kernel 換成 TRITON_ATTN，就解釋了多出時間的 106%（doc 新請求）、105%（doc 併發 16）、83%（chat）〔實測 F1 ✅F5，3 個 seed 中位數〕。
- **profiler**（同一個 33K prefill，只看 GPU kernel 時間）：attention 從 1.367 s（ROCM_ATTN）變 3.277 s（開卸載，TRITON_ATTN）；不開卸載的 TRITON_ATTN 是 3.650 s；矩陣乘法都是約 0.75 s，沒變〔實測 F1 ✅F5〕。
- 「真的搬資料」只佔多出時間的 11%–33%（seed 1，用「connector 開著但一個 byte 都不存」拆）〔實測 F1 §4.2〕。D2 量到「等寫入≈0」也對得上。

**(c) 修法：把 KV 拆成 K、V 兩個 view 註冊給 connector，就能用回 ROCM_ATTN。**
- 多出來的時間拿掉 74%（doc 新請求）、67.5%（doc 併發 16）、45%（chat）〔實測 F1 ✅F5，3 個 seed 中位數〕。
- **無損**：KV 來回逐 block 位元組比對 511／512 相同，和上游原本的路一樣；不拆的負對照 0／512、輸出被弄壞，證明檢查抓得到錯〔實測 F1 §4.5〕。
- 剩下的時間全是搬資料，而且跟 copy 次數走：每次 D2H copy 約 6 µs GPU 時間，資料減半時間幾乎不變〔實測 F1 §4.3〕。再把位址相連的 copy 合併，拿掉的比例到 70–79%（seed 1）〔實測 F1 §4.6〕。
- **上游沒修**：vLLM main（2026-10-10）和 v0.31.0 都還在排除〔原文，F1 用 curl 核對；F1 §5.1〕。上游知道這個機制（issue #60316，講的是 PD／decode／MI355X），維護者回覆 ROCM_ATTN 支援 connector「may not be on the roadmap in the near future」〔原文 #60316；F1 §5.1〕。「CPU 卸載＋prefill＋MI300X＋退到 TRITON_ATTN」這個組合沒查到有人報過〔F1 §5.1；查不到不等於沒有〕。

**(d) 從 CPU 載入，可能比重算還慢。**
- 同一批回來請求、同一個 kernel（ROCM_ATTN）比：chat 從 CPU 載入約 16K token 要 1.678 s，重算 1.460 s，**載入慢 15%**；doc 載入約 33K token 2.049 s，重算 2.272 s，載入只快 10%〔實測 F1 §4.4，seed 1〕。
- 用 TRITON_ATTN 比（上游原本的路），doc 載入 1.092 s、重算 4.679 s，載入快 4.3 倍〔實測 F1 §4.4〕。所以「卸載值不值得」的答案，在這台機器上取決於 kernel 選擇和 copy 次數，不是頻寬。

**(e) D2 的兩個舊觀察，一個是假象，一個重現。**
- **假象**：D2 寫的「doc 併發 1 回來請求快 2 倍（2.26 → 1.11 s）」是雙峰中位數造成的。回來請求的 TTFT 分兩群（GPU 命中約 0.1 s、沒命中約 2.2 s），中位數落在哪一群看命中率有沒有剛好過 50%：seed 1 是 0.132 → 0.128 s，seed 2 是 2.260 → 1.111 s〔實測 F1 §4.1〕。不能當結論。
- **重現**：接一層慢的 NFS 時，vLLM 仍然寧可等，也不重算。重跑一次，回來請求最久等 89.3 s（scheduler 延後 88.2 s），24 個裡 6 個超過 10 s；同一段 33K 重算只要 2.24 s（ROCM_ATTN）或約 4.4 s（TRITON_ATTN）；等待是重算的 20–40 倍〔實測 F1 §4.7 ✅F5；倍數為算術〕。這個 run 也是 TRITON_ATTN；fs 在 NFS 上，不代表本機 NVMe。
- **量測的乾淨度**：25 個正式 run 裡 19 個被 gpu_guard 標記，全是自己行程結束時的 pid −1 假警報；接受規則是事先沿用 D2 的〔F1 §7〕。

**小結**：
- 真實系統的卸載不是免費的，也不會依 κ 選「等」或「重算」。
- 在 MI300X＋vLLM 0.28，「開卸載 vs 不開」的比較同時改了兩件事（搬資料、換 kernel），而主因是後者。
- 對本文：第一階段的 vLLM 對照（C6）無效（§3.1）；建議見 §5.2 第 2 點。這些都不支持、也不反對寫入時放置。

## 5 討論

### 5.1 寫入時放置什麼時候會重要

**本節要講的**：我們的結果沒有說寫入時放置**永遠**不重要。下面是它可能重要的條件，每一條都標了目前的證據。

1. **持續寫不完，而且寫入佇列有上限（N3）**。
   - 證據：F6 重現的 1 格（ρ_KV≈2.1、TTFT 中位 11.2 s，只在中位數上贏）〔模擬 F6〕；Gill 頻寬受限時 3.42 對 5.05 ms〔原文 p.13；卡片 B_PROMOTE〕；Tachyon 的失效條件〔原文 p.2；卡片 B_Tachyon〕。
   - 缺的：多卡同時卸載時，每張卡真正分到的 SSD 寫入頻寬（NOT_MEASURED）；真實服務會不會在 TTFT 十幾秒的地方運作，還是早就做准入控制了（未查）。
2. **重算比 harness 快很多**：模擬裡 f×0.25–0.5 時有少數存活者（§4.2），沒有 GPU 確認〔待重量〕。
3. **寫完就消失的資訊（N1）**：例如混合 SSM 模型 prefill 過程中被覆蓋的中間狀態〔Marconi 原文 p.5–6；卡片 A_Marconi_補充〕。但這不是位置，而且整段還原時 Cake 不需要中間狀態〔12 §6.3〕。只剩分叉型工作有意義〔D5 §0〕。
4. **只有寫入當下走得了的資料路徑**：寫入時決定前段不進 CPU，就能讓 GPU 直接寫 SSD；延後版的資料已經在 host。這台機器沒有本地 NVMe、也沒裝 hipFile，NOT_MEASURED〔D7 §4.6〕。
5. **換一把尺：能耗**（F2；這也不是寫入時放置的論點，而是「還原時要不要用 Cake」的論點）。
   - MI300X 上 GPU 重算時 726.4 W，等資料時 168.9 W，比值 4.30〔實測 F2 ✅F5〕（D8 原本猜 1.6–3.2）。
   - 所以在 CPU 層（35.4、11.6、3.69 GiB/s）和本地 SSD 層，**最省 GPU 能量的是「只載入」**，比時間最佳的 Cake 少用 62–70% 的 GPU 能量，但還原要慢 4–43%〔實測 F2 ✅F5〕。在 NFS 層，能量最佳和時間最佳一樣，都是 Cake〔實測 F2 ✅F5〕。
   - 換成錢：用每度電 0.10 美元〔假設〕、PUE 1.3〔假設〕，GPU 租金要低於每小時 0.14–1.35 美元，選「省電」才划算〔算術 F2〕。所以只有在「電是瓶頸」或「GPU 等的時間本來就沒別的事做」時，這個差別才重要〔F2 §4.7〕。
   - 前作：HotCarbon 2026 在 H200 上量過「卸載比重算省能量」（扣掉閒置功率的邊際能量，KV 使用率 p95 >90% 時省 14.4–31.9%）〔原文 p.3；F2 §5〕；新的只是「部分重算的切點」在快的層很耗電。
   - 限制：只有一個 seed（每格 5 次）；只量 GPU 卡，主機 DRAM／PCIe／SSD 的功率在這個 container 讀不到〔F2 §7〕；用的是 harness 的重算，換成較快的 kernel，每個 chunk 的重算能量也會變〔判讀；待重量〕。
<!-- F2_RESULT: filled from docs/research_20261010_followup/F2_energy_kappa.md -->
6. **SSD 寫入額度**：用時間當指標時 H1 被殺掉（§4.2）；但延後本身就少寫。要比的對手是頻率准入和容量條件准入〔12 §3；Lit-A §1〕。
7. **反方向的證據**：寫入時的決定用的是當下的假設（例如 GPU 閒），之後會過時（§4.2，GPU 忙時慢 13–66%〔實測 A1〕）。延後版用的是淘汰當下的資訊。

### 5.2 給系統設計者的建議

**本節要講的**：根據 §4，KV 分層系統可以先做下面幾件事，再考慮寫入時放置。

1. **先做讀取端自適應。** Cake 式的「前段重算、後段載入」在 harness 上、0.3–4 GiB/s 的層值 1.38–1.93 倍〔實測 A0；絕對位置待重量〕。在真實 vLLM 上，CPU 層的載入和重算差不多快（chat 16K 載入比重算慢 15%，doc 33K 快 10%〔實測 F1〕），正是兩邊一起做最有用的地方；vLLM 0.28 目前只會二選一。
2. **比較「卸載 vs 不卸載」或「載入 vs 重算」時，兩邊鎖同一個 attention kernel，並看 log 確認引擎實際選了哪個。** 在 ROCm＋vLLM 0.28，開 connector 會把 ROCM_ATTN 換成 TRITON_ATTN，量到的主要是 kernel 差〔實測 F1；F1 §6.1 第 2 點〕。
3. **在目標軟體上量有效頻寬，不要用裝置頻寬。** vLLM 的 CPU→GPU 是 4.1 GiB/s，裸 PCIe 是 52.9 GiB/s〔實測 C6、C0〕；而且它主要受「每次 copy 的固定成本 × copy 次數」限制〔實測 F1〕。用校準頻寬預測真實裝置上的 Cake 加速，誤差中位 25.1%〔實測 C7；D3〕。
4. **把位置規則放在淘汰時，並且讓新進來的 chunk 也算淘汰候選。** D1 裡，就是這個語意讓延後版追上寫入時版（5／192 → 0／192）〔模擬 D1AN、D1AF〕；F6 用新 seed 確認〔模擬 F6〕。
5. **預設用寫穿＋LRU 就很強。** 第一階段 17 格裡，最好的策略比業界預設 S1 快 ≥5% 的只有 1 格（FIFO 干擾、25% 容量）〔實測 B；D3 §4.3 ✅F5〕。D1 加了併發之後，S1 仍是最常出現的最緊對手（192 格裡 51 格）〔模擬 D1X4〕。
6. **CPU 滿時，丟前段比丟尾段好。** 會溢出的格裡，「依位置先丟前段」比 LMCache 式「存頭丟尾」中位快 11.3%，比 vLLM 式「整批不存」快 9.4%〔模擬 D1OV〕。這個好處就是 Cake 的好處（只出現在 NFS）。它要讀取端支援「前段不在、後段命中」〔RT §3.1〕。
7. **用多個回來順序或真實 trace 評估，平均和中位數都報。** 贏家會隨 seed 換人（§4.3）；回來請求的 TTFT 常常是雙峰，中位數會騙人（§4.6(e)）。
8. **任何「提早決定」的新設計，都先過延後測試**（§3.5）。

### 5.3 方法上的教訓

**本節要講的**：這個負面結果的過程中，有四件事值得別人照做，也有兩件事我們做得不好。

1. **延後測試**（§3.5）。寫入時的想法要和「同一條規則延後套用」比，而且延後版要用和候選**一樣**的接納語意（新 chunk 能不能被淘汰）。D1 的事先判定就是因為延後版的語意不同才誤判（§4.4）。
2. **模擬篩選的門檻要大於模擬器對策略的相對偏差。** 模擬器整體很準（50 格裡 47 格誤差 ≤10%），但對 S5L 和 S4B 的相對偏差約 5–6 個百分點；預測的 7.6% 優勢在 GPU 上消失〔12 §5.4〕。我們之後把門檻提高到 10%，或者每個存活者都上 GPU〔D1 §2.5；12 §8〕。seed 門檻也要前後一致（09 用 5／5、第 1 輪用 ≥3／5，結論會不同，§4.2）。
3. **事後修正過的判定，用新 seed、事先登記、程式凍結重跑一次。** F6 就是這樣做的：判準寫在開 agent 之前、程式 sha256 跑前跑後核對、seed 是沒看過的；先逐列重現舊結果（103,680 列相同），再跑新 seed〔F6 §2–3〕。它確認了主張，也把過載角落從 5 格縮到 1 格。
4. **單位要用資料自己驗算。** 匯入 Mooncake trace 時，D4 用「`len(hash_ids)`＝ceil(輸入長度÷512)」驗算，三個 trace 都 100% 吻合〔trace D4〕。專案先前把 512-token 的 block 當成 16-token，整批結果作廢重跑過〔CLAUDE.md 規則 6〕。
5. **我們做得不好的（一）：事後加對手幾乎都朝「讓寫入時輸」的方向。**
   - 08 的 S4B、第 1 輪的 S4C、D1 的四段追加、D4 的 KEVa，都是看到候選贏之後才加的〔08 §8；11 追加 2；D1 §2.8–2.11；D4 §4.6〕。
   - 反方審查的原話：「每次 S5 贏，就加一個專門針對它的對照組；S5 輸的時候，從來沒有人反過來檢查對手是不是人工現象」〔RT §1.2〕。

## 6 相關研究

**本節要講的**：前作分成五類。沒有一篇在「讀取端會自適應」的條件下，把寫入時放置和它的延後雙胞胎系統性地比過。這是本文唯一的定位。

**讀取端自適應還原**
- **Cake**（ICML'25）：GPU 從前面重算、I/O 從後面載入，在中間會合；假設 KV 事先全部存好，沒有寫入策略〔原文；卡片 D6_Cake、D8_Cake_補充；07 report/related_papers_update.md a1〕。本文的所有策略都用 Cake 還原。
- **CacheFlow**：用動態規劃決定每個請求、每個層區塊重算哪些、載入哪些；決定都在讀取時〔原文 p.1；卡片 D5_CacheFlow〕。
- **KVPR**、**HCache**：用離線 profile 決定重算／傳輸的切點〔原文；卡片 D6_KVPR、D6_HCache；D3 §5〕。HCache 在寫入時依層決定存 hidden state 或 KV，量過「依 token 位置切」比「依層切」慢 7–12%〔原文 p.12；卡片 A_HCache_補充〕。
- **Pensieve**（EuroSys'25）：空間不夠時，優先從閒置對話的**開頭**逐出，回來時重算；保留值＝重算成本÷閒置時間〔原文 p.6–7；07 related_papers_update.md a2〕。它就是「前段不存」的**延後版**，而且已經發表。本文的 S4+P 照它的保留值做。
- **AsymCache**：逐出時同時看重用機率和隨位置上升的重算成本，用 MSA kernel 支援不連續的命中〔待查：沒有卡片，只有反方審查附的連結〕。

**寫入時決定放置或准入的 KV 系統**
- **Krul**：寫入時依「重算 vs 載入平衡」決定每層前段不存，讀取時重算；有損（跨層共享）〔原文 p.8–9；卡片 A_Krul；venue 未查證〕。
- **TierKV**：prefill 後依位置分三層，尾段放 flash；單請求、有損〔原文 p.4；卡片 A_TierKV；PDF 頁首寫 EuroSys'27，未在 ACM DL 核對〕。
- **Lachesis**：寫入前依 agent harness 給的壽命放 HBM 或 HBF，HBF 壽命變 1.19–3.13 倍〔原文 p.1、p.9；卡片 A_Lachesis〕。
- **EfficientAgent**：有壓力時整個請求的新 KV 都不存；同一條准入規則在容量不夠時重算少 36%，容量夠時重算變 4.3 倍〔原文 p.5、p.7；卡片 A_EfficientAgent〕。
- **HyMCache**：寫入緩衝滿了就跳過寫入，讀取壓力下跳過 >15%〔原文 p.6、p.10；卡片 A_HyMCache〕。
- **Where Should the KV Cache Live?**：好處主要來自容量，不是放置策略；它的策略都是延後版〔原文 p.1、p.3；卡片 A_WhereKVLive〕。
- **真實系統**：vLLM、LMCache、SGLang HiCache、Dynamo 在 CPU 滿時預設丟掉或不存，不等 SSD；往 SSD 都是寫穿〔程式碼；H0_offload_blocking.md；12 §2〕。CachedAttention（ATC'24）有水位線式的背景淘汰〔原文 p.7；卡片 A_CachedAttention_補充〕。Mooncake（FAST'25）〔lit_A §4 已核對 venue〕。
- **和本文的差別**：上面這些寫入時的系統，幾乎都沒有和「同一條規則延後套用」比過〔Lit-A §0〕。本文就是補這個比較。

**經典儲存與記憶體分層**
- **Gill, FAST'08**：PROMOTE（經過時就決定放哪層）對 DEMOTE（逐出時才往下搬）；頻寬不限時最多好 4–5%，其他 trace 平均 0.3–1.5%；頻寬受限時 3.42 對 5.05 ms；「idle time should never be considered free」〔原文 p.3、p.13；卡片 B_PROMOTE〕。本文的 §4.2、§4.4 是它在 KV＋讀取端自適應下的對應。
- **Wong & Wilkes, ATC'02**（DEMOTE）〔卡片 B_DEMOTE〕。
- **Tachyon, SoCC'14**：能重算，持久化就能變成背景、可放棄的工作；寫入速度超過磁碟頻寬時背景版失效〔原文 p.2、p.6；卡片 B_Tachyon〕。
- **TPP, ASPLOS'23**：把回收水位線和配置水位線分開（背景提早搬），就修好配置突發〔原文 p.7–8、p.10–11；卡片 B_TPP〕。和 D1「只挑尾段的預先清理追得上」一致。
- **Nomad（OSDI'24）、CacheLib（OSDI'20）**：clean 的資料逐出免費〔卡片 B_Nomad、B_CacheLib〕。KV 寫穿之後永遠是 clean。

**卸載的損益平衡、能耗與特性分析**
- **Understanding Bottlenecks …KV Offloading**（MLSys'26）：定義 κcrit，在 H100／B200 上是 1–76〔原文 p.1–2；D3 §5.2〕；卸載服務時 GPU 平均只用 TDP 的 22–28%〔原文 p.8；F2 §5〕。
- **py-kvcache**：重算或載入的損益平衡隨硬體與負載變，效能「not only on device bandwidth」〔原文 p.1–2、p.8；D3 §5.2〕。
- **LMCache**：低頻寬時，只有 context 長度超過交叉點才該載入〔原文 p.15；D3 §5.2；venue 未查證〕。
- **Energy Characterization of KV Cache Offloading Under Agentic Workloads**（HotCarbon 2026，依網址；PDF 頁腳是 ACM SIGENERGY Energy Informatics Review）：H200＋vLLM，卸載比「被搶佔後重算」省 14.4–31.9% 能量〔原文 p.3；F2 §5，F2 讀了全文〕。
- **MatKV**（arXiv 自述 ICDE 2026）：H100 上量了能量跟著時間走；沒有部分重算〔原文 p.9–10；F2 §5〕。
- 讀取端的「κ／頻寬→載入、重算或 Cake」地圖，前作已經做得比我們廣（多硬體、多模型）〔D3 §5.2〕。本文不主張這張地圖是新的。

## 7 限制

**本節要講的**：這些結論不能推廣到哪裡。

1. **一台機器、一個 GPU 寫入端模型。** 只有 Llama-3.1-8B（GQA）有寫入端的 GPU 實測。MHA 模型會讓 b/n 變大（LongAlpaca 在 3.69 GiB/s 時 0.59，Llama 0.31）〔實測 KS〕，但 LongAlpaca 只有模擬，而且模擬情境超過它的 context 上限〔12 §5.3〕。
2. **harness 的重算比預設 vLLM 慢約 1.7–2 倍**（整段 prefill：8K 2.0 倍、32K 1.7 倍〔算術，由 A0、F1〕）。第一階段說「不是稻草人」，是因為對照的 vLLM 開著 connector、被換成了慢的 kernel（§3.1）。影響：
   - κ、b、Cake 頻寬帶的絕對位置都〔待重量〕。
   - 偏差方向是讓寫入時「可以決定的東西」變少，也就是偏向本文的結論。
   - 模擬裡重算變快（f×0.25–0.5）時，有少數設定讓寫入時放置存活（3／30 個設定，≥3／5 規則〔模擬 SIM08，F5 重算〕；§4.2），沒有 GPU 確認。
   - 要補：在 harness 換用和 ROCM_ATTN 同等速度的 attention，或在預設 vLLM 上逐 chunk 量 f(i)，再重跑 A0 和第 1 輪的確認。
3. **層是限速器。** SSD 層的參數取實測最慢值×0.9；真實裝置的寫入懸崖、page cache、檔案系統開銷都不在模型裡〔07 §10 L2〕。限速器和真實裝置的比值，在 NFS 只載時最高 2.66〔實測 C7；07 §3.1〕。NFS 參數代表「慢的 NFS」，不是 NFS 的平均。
4. **GPU harness 一次服務一個請求。** 併發只在 D1、F6 模擬，沒有 GPU 驗證。D1 的事先判定是在看到結果之後修正對手才翻轉的；F6 用新 seed 事先登記確認了修正後的結論（§4.4），但仍然是模擬。**這是反方審查認為最強的拒稿理由**（附錄 A）。
5. **多卡同時卸載的 SSD 頻寬沒有量。** 這是寫入時放置唯一可能贏的區域之一（§4.4(c)）；而且那裡只有 1 格穩定、只在中位數上贏。
6. **Python harness。** 兩條線是兩個 Python 執行緒；不限速時會互相干擾（CPU 真實錨點每 chunk 3–4 ms，限速時 1.77 ms）〔07 §10 L3〕。生產系統不會有這個開銷。
7. **工作負載是合成的。** 8 個 session × 最多 4 輪；回來順序由 seed 決定〔07 §10 L4〕。D4 用了 Mooncake 的真實 trace，但那是一次一個請求的快取模擬。
8. **樣本小。** 判定用中位數，每個 seed 只有 7–24 個回來請求（第 1 輪）〔12 §10〕。D2 的「丟資料」只有一個 seed；能耗（F2）只有一個 seed、只量 GPU〔F2 §7〕。
9. **A0 有一格例外**（4K × 11.6 GiB/s，Cake 慢 5.6%）〔實測 A0〕。
10. **hold 和 free 都不是真實系統的預設**〔12 §2〕。真實系統是「放不下就丟」，D1、F6 的模型才有。
11. **文獻**：部分 API 被限流，有些引用的 venue 沒有查證（Krul、Lachesis、EfficientAgent、LMCache）；AsymCache 沒有卡片〔待查〕。投稿前要跑 `citation-audit`。
12. **原始論文的數字正在稽核，本草稿不依賴它們。** F4 逐一核對了 `main.tex` 的 241 個數字：一致 95、不一致 59、找不到來源 17、來源有疑慮 70〔DATA_AUDIT 摘要〕。有疑慮的包括 κ 的頭條數字（3090 在整機 HEAVY 下量）、oracle 修正前的 headroom、平台 B 的品質主張，以及卸載組和 INT4／INT8 混進了換 kernel 的效果〔DATA_AUDIT 摘要〕。本草稿只用第一階段（2026-10-08）以後、每列都有 run_id 的資料，以及 F1–F3、F6 的新量測；`main.tex` 的 κ、headroom、品質數字一個都沒用。

### A.3 綜合判讀

- **最站得住的部分**：§4.3（贏家隨 seed 換）；§4.4 裡「沒有持續排隊時寫入時決定不贏」（F6 事先登記確認）；§4.6 的工程發現（3 個 seed、消融、profiler、修法都有）。
