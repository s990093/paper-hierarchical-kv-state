# 方向草稿：以 Cake 為基底，延伸到「要不要存、存在哪、依位置決定」

> 狀態：想法階段，還沒有任何實驗。10/4 加入討論補充（§10）與「怎麼做成研究貢獻」（§11）。
> 標註：〔原文〕論文原句；〔AMD 實測〕MI300X 量到的；〔算術〕用公式和實測常數算的，不是量測；〔推論〕我的判讀。

## 1. 要解決什麼問題

- 長上下文輸入時，prefill 階段產生 KV cache 的運算量很大，是推論的主要瓶頸〔Cake 原文〕。
- prefix caching 把算過的 KV 存起來重用，可以省掉重複運算〔Cake 原文〕。
- 但 GPU 和 CPU 記憶體放不下那麼多 KV，所以大量 KV 只能放在容量大、頻寬低的磁碟或遠端儲存。依 AttentionStore 的評估，約 80% 的快取命中發生在磁碟層〔Cake 原文引用 AttentionStore〕。
- 從這類儲存讀回大量 KV 會產生嚴重的 I/O 延遲，拉長第一個 token 出來的時間（TTFT）〔Cake 原文〕。
- 過去的系統不是只靠重算，就是只靠 I/O 載入，沒有把兩種資源同時用上〔Cake 原文〕。

## 2. Cake 做了什麼

- **做法**：同一段上下文，GPU 從最前面的 chunk 往後重算，I/O 從最後面的 chunk 往前載入，兩邊實際跑到哪就在哪會合。
- **為什麼這樣分**：越後面的 token 重算越貴（要看的前文越長），而載入一個 token 的成本跟位置無關。所以便宜的前段交給 GPU 算，昂貴的後段交給 I/O 載〔Cake 原文〕。
- **效果**：TTFT 平均比只算或只載快 2.6 倍〔Cake 原文〕。

## 3. Cake 沒處理的地方

1. **假設 KV 早就全部存好**〔原文：「we precompute and store all requests' KV cache in advance」〕。它只處理「已經命中之後怎麼最快拿到」，不處理：
    - 這段 KV 要不要存；
    - 存在哪一層（GPU、CPU 記憶體、SSD）；
    - 存進去要花多少寫入頻寬、佔多少空間。

    詳細分析見 §3.1。
2. **只有一個儲存層，而且是模擬的**。I/O 時間是依頻寬算出延遲再暫停傳輸，沒有接真實裝置〔原文〕，也沒有 GPU／CPU／SSD 多層的情況。
3. **沒有「依位置決定存放」**。它的機制本身已經說明「前段會被重算」，卻仍然把整段的 KV 都存著、準備載入。
4. **沒有退路**。兩邊快慢差很多時仍硬分工；GPU 只剩 12.5% 可用時，比單純載入還慢 25%〔原文 Table 5，Llama3.1-70B、32 Gbps〕。作者把「估計機制」和「退回單一路徑」列為未來工作〔原文〕。
5. **context 只到 16K**（4K–16K 的合成 prompt）〔原文〕。

### 3.1 為什麼「假設全部存好」是問題

**Cake 的評估怎麼做**：每個請求的 KV 事先算好、全部放進儲存，再量讀取時的 TTFT〔原文〕。這個設定等於假設三件事：容量無限、寫入免費、只有一層。真實系統裡三者都不成立。

**不考慮的後果**〔推論，待實驗驗證〕：

1. **容量：存了不會讀的東西，擠掉會讀的東西**。
    - 快取層的容量是固定的。每段 context 都全存，能放進去的 context 數量就變少，命中率下降；沒命中的請求只能整段重算，TTFT 回到最差情況。
    - Cake 讀取時，前段大約 1/(1+κ) 本來就會被重算。如果只存後段的 κ/(1+κ)，同樣容量最多能多放 (1+κ)/κ 倍的 context〔算術，上限：假設讀取時的會合點正好落在寫入分界〕：
        - κ ≈ 0.72（搬得慢）：最多約 2.4 倍；
        - κ ≈ 11.65（搬得快）：最多約 1.09 倍。
    - 這個上限要容量吃緊才兌現。容量夠大時，全存也不會擠掉任何東西，這一點就不成立。
2. **寫入頻寬：寫入和讀取搶同一條路**。
    - 存 KV 要經過 PCIe，寫進 SSD 還要吃 SSD 頻寬。這條路同時也是別的請求載入 KV 的路。
    - Cake 的 TTFT 不含寫入成本，因為 KV 是事先寫好的。實際上線時，前段那 1/(1+κ) 的寫入量可能永遠不會被讀回，卻會拖慢其他請求的載入。
    - 次要影響：SSD 寫入量直接消耗壽命。
3. **只有一層：最貴的後段，從最慢的地方載入**。
    - Cake 只從單一儲存層載入。最後幾個 chunk 重算最貴，若 GPU 或 CPU 還有空間，放在那裡可以直接用或更快載入，但 Cake 的設定裡沒有這個選項。

**考慮之後為什麼比較好**：讀取時的會合點已經告訴我們「哪一段會被重算、哪一段要被載入」。把同一條規則提前到寫入時用，前段不存（省容量、省寫入），後段依重算成本放到對應的層（越貴放越快的層）。寫入不需要另一套規則，只是把 Cake 讀取時已知的資訊提早用上。

**反面（這樣做可能變差的情況）**：
- 讀取時頻寬或算力變了，會合點往後移，原本沒存的前段就要多重算，TTFT 可能變差（見 §7 第 4 點）。
- 共用的前段（系統提示）不存，可能害到別的請求（見 §7 第 3 點）。
- 模型撐得住 INT4 時，容量壓力本來就小，第 1 點的效益會被吃掉（見 §7 第 1 點）。

**要用什麼實驗證明**：

| 實驗 | 要回答的問題 | 做法 | 看什麼 | 什麼結果代表這點不成立 |
|---|---|---|---|---|
| E1 容量 × 命中率 | 全存是否真的擠掉會讀的 KV | 模擬器＋真實 trace（Mooncake，block 為 512 token），掃快取容量；比較「全存＋Cake 讀取」與「依位置寫入＋Cake 讀取」 | 命中率、TTFT p50／p99、整段重算的請求比例；分 κ 小與 κ 大兩組 | 在合理的容量範圍內，命中率或 TTFT 改善 < 5% |
| E2 寫入干擾 | 寫入是否拖慢其他請求的載入 | MI300X＋vLLM `OffloadingConnector` 實測：一邊有請求在寫 KV，一邊有請求在載入 | 每個請求的寫入位元組、載入請求的 TTFT 變化 | 寫入同時進行時，載入請求的 TTFT 沒有可量到的變化 |
| E3 多層 vs 單層 | 多一層是否值得 | 總容量固定，比較「只有 SSD」與「CPU＋SSD」，以及後段留 GPU 的情況 | TTFT、各層的使用量 | 多層與單層的 TTFT 差距在量測誤差內 |
| E4 穩健性 | 會合點移動時會不會變差 | 讀取時把頻寬或可用算力調低或調高（例如 ±50%），寫入時的決定不變 | TTFT 相對全存的最差情況；退路觸發的次數 | 擾動下 TTFT 常比全存差，而且退路救不回來 |

E1 是主實驗，E2 到 E4 補充。E1 不成立的話，這一點就不能當成主要動機。§8 的第一步就是 E1 的最小版本。

## 4. 因為這些缺點，會導致什麼

**核心觀察**：Cake 讀取時，前段大多是用重算補回來的。所以**前段的 KV 就算存了，很多時候也不會被讀到**〔推論〕。這會造成三個浪費：

1. **浪費儲存容量**：前段 KV 佔著位置，排擠了真正需要被載入的後段。在容量有限的快取層，這直接降低命中率。
2. **浪費寫入頻寬與 SSD 壽命**：每一段 KV 都要寫進 SSD，但其中前段那部分可能永遠不會被讀回。
3. **快的層放錯東西**：最該留在快層的是「重算最貴」的後段，但現在的系統依「最近有沒有用」決定（LRU），不看位置。而且 vLLM、SGLang 逐出時是從尾巴先丟〔vLLM 文件〕，剛好把最貴的那段先丟掉。

**前段會被重算多少？**〔算術，一階近似〕
- 依 Cake 的會合邏輯，被重算的前段比例大約是 1/(1+κ)，κ ＝ 重算成本 ÷ 傳輸成本（CacheFlow 寫出了同一個切點公式）。
- 我們在同一張 MI300X 上，只換模型或長度，κ 就在 0.72 到 11.65 之間變動〔AMD 實測〕。換算下來：
    - 搬得慢（κ ≈ 0.72）：約 58% 的前段會被重算，這部分根本不必存；
    - 搬得快（κ ≈ 11.65）：只有約 8%。

**所以這個方向的效益是平台與模型相依的**：搬得越慢（越接近 SSD 或遠端儲存），能省的越多。

## 5. 所以想做什麼

把 Cake「讀取時」的雙向還原，延伸成**一套貫穿寫入、放置、逐出、讀取的位置感知（block 級）策略**，涵蓋 GPU／CPU／SSD 三層，context 拉到 32K–128K。

![架構圖：以 Cake 為基底的位置感知 KV 分層](../figures/fig_cake_extension.png)

**怎麼讀這張圖**：(A) 由左到右是一個 chunk 的生命週期：寫入、存放、讀取。三欄共用同一組儲存層。紫框是本提案新增或修改的部分，藍框是 Cake 原有，綠框表示資料已在 GPU。

- **(A) 左：寫入路徑（新增）**。prefill 算完 KV 後，逐個 chunk 比較「重算成本 R(p)」與「各層的載入成本」。R(p) 隨位置變貴，所以：
    - 前段重算便宜，不存；
    - 中段放 SSD，後段放 CPU；
    - 最後幾格重算最貴，留在 GPU，再依品質預算 ε 選 BF16、FP8 或 INT4。
- **(A) 中：六態儲存層**。GPU 一層再分 BF16／FP8／INT4 三種精度，加上 CPU、SSD 與「不存」，共六種狀態，每個 chunk 只處於其中一種。FP8 與 INT4 的品質影響依模型與任務而定。
- **(A) 右：讀取路徑（Cake 的雙向還原，改造後）**。三條來源各自接到一個讀取動作：
    - 已在 GPU 的直接可用（FP8／INT4 需反量化）；
    - 放在 CPU 或 SSD 的，由 I/O 從後段往前載入。Cake 原本只從磁碟載，本提案改為多層；
    - 不存的前段，由 GPU 從前段往後重算，這部分 Cake 原本就有。
    三者在「會合」後開始 decode。另外新增退路：一邊明顯較快時，只走那一邊。
- **左右怎麼接起來**：寫入時「不存」的前段，正好是讀取時 GPU 本來就會重算的那段；寫入時放到 CPU 或 SSD 的後段，正好是讀取時 I/O 要載入的那段。
- **(B)** 重繪自 Cake 論文 Fig. 2，用 12 個 chunk 對比兩種做法：
    - Cake：12 格全存磁碟，讀取時前 6 格重算、後 6 格從磁碟載；
    - 本提案：前 6 格不存，後 6 格依序放 SSD、SSD、CPU、GPU-INT4、GPU-FP8、GPU-BF16。讀取時前 6 格同樣重算，SSD、CPU 的格子由 I/O 載入，GPU 上的格子直接可用。
    紅色虛線是「寫入分界 ＝ 讀取會合線」：兩種做法的會合點相同，但本提案 I/O 要搬的格數變少、來源也更快。

原始檔：`figures/fig_cake_extension.svg`（可編輯）；產生腳本：`figures/specs/make_fig_cake_extension.py`。12 個 chunk 與分界位置是示意，實際分界由實測成本決定；圖中各層只標相對快慢，不標具體頻寬。

### 核心圖：同一條逐位置規則，寫入分界 ＝ 讀取會合線

![逐位置決策：寫入分界等於讀取會合線](../figures/fig_cake_staircase.png)

- **(a)** 每個 chunk 有 6 種狀態，不是只有 3 種：GPU 內的 BF16、FP8、INT4（用品質換空間），以及 CPU、SSD、不存（無損，但要用時付代價）。INT8 可視為精度的另一階。
- **(b)** 同一條逐位置規則：重算成本 R(p) 隨位置變貴，跟各層的載入成本比較。重算比較便宜的不存；越貴的放越快的層（SSD → CPU → GPU）。留在 GPU 的，再依品質預算 ε 選 BF16、FP8 或 INT4。左右不是兩套規則。
- **(c)** 寫入時，每一格選一種狀態，六種狀態都會出現。
- **(d)** 讀取時跟 Cake 一樣：藍色階梯是 GPU 重算的前緣，橘色階梯是 I/O 載入的前緣。已經在 GPU 的格子直接可用，不必搬。兩條前緣會合的位置（紅色虛線），正好是 (c) 的寫入分界。
- 分界會隨實測成本移動；精度能不能降，取決於模型與任務。

產生方式：`python3 figures/specs/make_fig_cake_staircase.py`（輸出 `figures/fig_cake_staircase.svg`）；配色用色盲友善的 Okabe–Ito 色系；圖中數值為示意。

| 時機 | Cake | 想做的 |
|---|---|---|
| 寫入時 | 全部都存 | 依位置決定：前段（反正會被重算的）不存或只存在便宜的層；後段存在能快速載入的層 |
| 放在哪 | 只有一層儲存 | GPU／CPU／SSD 三層，依「這段重算多貴、載入多快」決定 |
| 逐出時 | 不處理 | 從前段開始逐出（跟 Pensieve 同方向），不從尾巴丟 |
| 讀取時 | 雙向並行，沒有退路 | 雙向並行，但成本用實測（包含每筆搬運的固定成本），並在一邊明顯比較快時退回單一路徑 |
| 長度 | 4K–16K | 32K–128K |

**「token 層級」要講精確**：實際系統以 block 為單位（vLLM 預設 16 token），所以這裡的「token 層級」是指「依 block 在序列中的位置」決定，不是逐個 token。

**多輪對話的額外好處**〔推論，需要驗證〕：如果每一輪只是在後面追加內容，會合點只會往後移。那麼前面那一段在之後每一輪都會被重算，從一開始就不必寫入。這個論證成立的前提是：讀取時的算力與 I/O 速度大致不變、重用是「往後追加」、引擎支援非前綴命中。

## 6. 最接近的前作與差別

| 論文 | 已經做了什麼 | 我們多了什麼 |
|---|---|---|
| Cake（ICML'25） | 讀取時雙向並行 | 寫入與放置也依位置決定；多層；實測成本；退路 |
| CacheFlow（arXiv 2604.25080） | 推出最佳切點公式 ℓ ＝ L × T_io ÷ (T_comp + T_io) | 把切點用在寫入端，並證明多輪下會合點單調後移 |
| Pensieve（EuroSys'25） | 從對話開頭逐出，丟掉的要用時重算 | 加入 SSD 層與寫入決策；以 SSD 取回成本決定 |
| HCache（EuroSys'25） | 在「層」的維度決定哪些層不必存，要用時重算 | 改在「位置」的維度決定，而且不限 MHA |
| AsymCache（arXiv 2606.02964） | 用位置線性成本做逐出 | 寫入與多層放置 |
| py-kvcache（arXiv 2609.11744） | 依硬體量出損益平衡長度，短的不存也不載 | 以 block 位置判斷，而不是整段前綴長度 |
| SGLang HiCache／Dynamo KVBM | 依「用過幾次」決定要不要寫 | 依「位置與成本」決定 |

**新穎性判斷**：部分已知，算窄新。每個零件都有人做過，空白在「寫入時、依位置、多層、多輪下單調」這個組合〔9/24 查新〕。動手前要再做一次查新。

## 7. 會被問到的問題與風險

1. **INT4 會不會讓這件事沒必要？** 我們量到，模型撐得住 INT4 時，空間壓力會大幅下降，放置策略只剩 2–3.5% 的空間〔AMD 實測，初步〕。這個方向的效益要在「不能降精度」或「壓力很大」的情況下才明顯。
2. **搬得快的平台上效益很小**：κ 大時，被重算的前段只有約 8%〔算術〕。
3. **共用的前段**：系統提示這類開頭常被很多請求共用，而且很熱。前段不存，可能害到別的請求，要另外處理。
4. **會合點會動**：Cake 自己說，會合點會隨當下的算力與 I/O 變化〔原文〕。寫入時的決定必須能容忍讀取時的變化。
5. **要改引擎**：vLLM 和 SGLang 只認「從頭開始的連續前綴」命中。前段沒存的話，後段在原生查找下永遠不會被算成命中，所以要做「區段命中」。
6. **SSD 結論目前不確定**：MI300X 容器沒有本地 NVMe，SSD 路徑的實測速度不能代表一般伺服器。可改用 CPU 記憶體＋限速器模擬（見 §10.5）。
7. **量化會抵銷這個方向的效益**：量化讓會合點往前移，「不存」的前段跟著變短（見 §10.6）。
8. **GPU 忙的時候，前段不存會變差**：會合點往前移，沒存的前段只能硬算（見 §10.7）。

## 8. 第一步（約一週，只用模擬器）

1. 在現有模擬器加一個模式：「區段命中＋雙向還原＋依位置寫入」，成本常數用 MI300X 實測值。
2. 比較四種做法：
    1. 現狀：全存＋LRU；
    2. Cake 式：全存＋雙向讀取；
    3. Pensieve 式：前段逐出；
    4. 提案：依位置寫入＋雙向讀取＋前段逐出。
3. 量：寫入位元組、各層容量需求、TTFT，以及跟 oracle 的差距。
4. **判準**：
    - 提案相對 Cake 式，在 TTFT 不變差的前提下，寫入量或容量需求能省一個有意義的比例（例如 ≥ 30%）→ 做引擎原型；
    - 否則放棄，結果寫進分析型論文當「何時不值得做」的一個例子。

## 9. 能不能建立在 Cake 上發表（2026-10-01 評估）

可以。建立在前作上是常態，Cake 本身也是建立在 AttentionStore 上。問題不在能不能，而在會不會被判定為「Cake 多加一步」。目前有三個風險：

1. **自己的初步數據不支持（最嚴重）**。模型撐得住 INT4 時，INT4 單獨就拿走 oracle 空間的 91.8%／103.9%，放置策略只剩 2–3.5%〔AMD 實測，初步〕，低於 `< 5%` 的 NO-GO 線。必須先證明在「不能降精度」或「壓力很大」的情況下，空間明顯大於 5%。
2. **新穎性窄**。零件都有人做過（見 §6），空白只在「寫入時 × 依位置 × 多層 × 多輪」的組合。組合型貢獻需要一個洞見撐住；候選是「寫入分界 ＝ 讀取會合線」，要有成本模型推導與實測驗證。上次查新是 9/24，動手前要重做。
3. **硬體條件**。MI300X 沒有 NVMe，SSD 路徑實測 1.3–3.2 GB/s（overlay）。SSD 層要嘛換有 NVMe 的環境，要嘛在論文中明說是以量到的常數模擬。模擬的做法見 §10.5。

**最少需要**：
1. Oracle go/no-go：模擬器加入本提案模式，用 MI300X 實測常數，與 Cake／LRU／Pensieve 比較；`< 5%` 就停。
2. 反例：找出 Cake 全存磁碟、或 LRU 從尾巴丟，實際造成命中率下降的 workload，並量出差距。
3. 真實 I/O：Cake 原文的 I/O 是模擬的，以 vLLM 真實搬運量測本身就是差異點。
4. 重做查新。

**投稿場所**：Oracle 尚無結果，依 CLAUDE.md「9 月底沒有 Oracle 就放棄 MLSys 這一輪」，MLSys 2027（10/30）不實際；目標改為 EuroMLSys 2027（約 2 月，6 頁）。

## 10. 10/4 討論補充

> 來源：10/4 的想法筆記，以及要問老師和學長的問題。講到 Cake 的地方都已對照本地 `papers/cake2025.pdf`；跟原文對不上的地方直接標出來。

### 10.1 這個方向在 L0–L5 的哪裡

```
L5  誰在用、用多久？    ← 使用方式與契約
L4  怎麼找到筆記？      ← 命中規則      ← 連帶：前段不存，就要支援「區段命中」（§7 第 5 點）
L3  怎麼搬筆記？        ← 傳輸          ← 連帶：雙向載入、限速、每筆固定成本
L2  筆記放哪裡？        ← 放置          ← ★ 本方向的核心
L1  筆記寫多細？        ← 精度／格式    ← 連帶：依位置量化（§10.6）
L0  要存的是什麼筆記？  ← 物件種類      ← 不碰（dLLM、hybrid 見 §10.8）
```

- **為什麼選 Cake 當底座**：它在 L2 的演算法清楚、乾淨（前段算、後段載、中間會合），而且已經同時用上重算和載入兩種資源。本方向只是把同一條規則往前延伸到寫入、往外延伸到多層。
- **方法組成的目標**（自訂）：約三分之一用經典演算法或 OS 技巧，一定要有 DL。對照目前的設計〔推論〕：
    - 經典／OS 的部分已經有：雙指標會合（Cake）、依取回成本決定留誰（GreedyDual-Size 這類成本感知替換）、Amdahl 上限與 rent-or-buy（故事 6）。
    - DL 的部分還沒有。候選：預測「這段 context 會不會再被讀」，或「讀取時會合點會落在哪」。
    - ⚠️ CLAUDE.md §8：Oracle 出來之前不訓練任何模型。DL 元件要等 E1 判定 GO 之後才能做。

### 10.2 跟 L2 共同問題的關係（可以跟老師講的）

| L2 的共同問題 | 證據 | 這個方向怎麼處理 |
|---|---|---|
| 把傳輸當成「大小 ÷ 頻寬」 | 兩個平台都量到，傳輸速度由軟體路徑決定（故事 2） | Cake 的限速器正是「大小 ÷ 頻寬」。我們模擬時，延遲要加上每筆固定成本（§10.5） |
| 假設量化和放置互補 | 全部改 INT4 加原廠 LRU，就拿到最佳放置 92–104% 的好處〔AMD 實測，⚠️ 初步，腳本未入庫〕 | 這是本方向最大的威脅（§9 第 1 點）。E1 要在「不能降精度」的設定下做 |
| 結論互相矛盾 | Strata 說長 context 重算不划算；MTDS 說命中很長時不載反而快 | 矛盾很可能來自各自的傳輸實作〔推論〕。用 κ（§10.4）把兩篇放在同一條軸上 |
| 沒辦法互相比 | 32 篇用了 64 種 baseline，任兩篇之間 72.6% 沒有共同對手；重點五篇都沒報變異或信賴區間（`ADVISOR_REPORT_20260930.md` §3） | 固定一組對手：只算、只載、LRU、Cake、Pensieve；每個設定重複量，報信賴區間 |

**結論**：L2 的「招式」確實擠滿了，還空著的是「判準」：什麼條件下聰明的放置才值得做（故事 6）。這是分析型的貢獻，不是再做一個新策略。本方向怎麼接到判準，見 §11。

### 10.3 長 context：要用到 CPU 層，前段不存也不便宜

- Cake 的實驗只有 4K–16K，而且只從一個模擬的儲存層載入〔原文〕。短 context 確實用不到 CPU 層；長 context 時，後段重算很貴，從慢的 SSD 載入也慢，中間就需要 CPU 層〔推論〕。
- 建議的分層（跟 §5 的圖一致）：
    - 後段 → GPU／CPU：重算最貴，要用時直接可用或很快載入；
    - 中段 → SSD／NFS：Cake 式，跟 GPU 重算並行；
    - 前段 → 重算（或不存）。
- ⚠️ **前段不存，在 500K 時並不便宜**：前 10% 就是 50K token 的 prefill。原筆記寫「約 9 s」，但 repo 裡找不到對應的 run，先標 **NOT_MEASURED**。評估要看整段的累積時間，不能只看單一 chunk 的成本（見 §10.4）。
- ⚠️ **500K 只能量時間**：Qwen2.5-7B-1M 的 noDCA 變體上限是 262,144；512K 是外推，RoPE 超界，品質無效（`results/m1_capacity/capacity.csv`）。
- 實驗不一定要把 GPU VRAM 撐爆：只要前綴之後會被重用、GPU 又留不住，就會走到載入或重算〔推論〕。
- **「長 context 只靠 Cake 不夠」要講精確**。原筆記寫「long context 會變成 compute only，GPU 使用率上升，所以不能只靠 Cake」。但 Cake §5.3 量到的方向相反：序列越長，相對只算的加速越大，因為後段越貴、越該交給 I/O〔原文〕。比較準的說法是：
    - 長 context 時，Cake 會把更多 chunk 交給 I/O。I/O 慢（例如 AMD 的儲存）時兩邊都慢，這時才需要更快的 CPU 層〔推論〕；
    - 重算用的是服務其他請求的同一張 GPU（§10.7）。GPU 越忙，Cake 越接近只載〔推論〕。

### 10.4 兩種成本怎麼比：都換成等效吞吐

- **問題**：重算的單位是「秒／chunk」，載入的單位是「GB/s」，沒辦法直接比。
- **解法**：都換成「每秒能產出多少 GB 的 KV」。Cake Fig. 3 就是這樣做：重算的等效吞吐 ＝ KV 大小 ÷ 重算時間〔原文〕。
    - Cake 量到（LongAlpaca-7B，32K，chunk 512 token）：A100 約 3.3 GB/s、H100 約 4 GB/s、NVMe SSD 約 4 GB/s、網路約 1 GB/s、HDD 約 200 MB/s〔原文 Fig. 3〕。
- **跟 κ 是同一件事**：κ ＝ 重算時間 ÷ 傳輸時間 ＝ 載入頻寬 ÷ 重算等效吞吐〔算術〕。
- **重算的等效吞吐隨位置下降**：越後面越貴，所以每個 chunk i 有自己的等效吞吐 S ÷ c(i)（S 是每個 chunk 的 KV 位元組數，c(i) 是第 i 個 chunk 的重算時間）。
- ⚠️ **分界要用累積時間定，不是逐格比較**。兩邊是並行的，會合點 m\* 是「前段累積重算時間 ＝ 後段累積載入時間」的位置：Σ_{i≤m\*} c(i) ≈ (N − m\*) × 載入一個 chunk 的時間〔算術〕。逐格比較（某一格重算比載入便宜就不存）會得到不同答案：例如每一格重算都是載入的 2 倍時，逐格規則會說「全部都該存」，但並行時 GPU 仍會分擔前 1/3〔算術〕。§5 圖 (b) 的「逐位置比較」要照這個累積的意思讀。

### 10.5 實驗方法：Cake 的「模擬 I/O」是什麼，我們怎麼做

- **問**：Cake 說 I/O 是模擬的，那是建一個模型來跑分嗎？
- **答**：不是。GPU 重算是真的在跑（vLLM chunked prefill），只有 I/O 端換成限速器：依 chunk 大小和頻寬算出延遲，延遲到了才把資料交給 GPU〔原文，實驗設定〕。
- **Cake 掃的兩個軸**〔原文〕：
    - I/O 頻寬（Table 2）：7 Gbps（Google Cloud 一般 egress）、25 Gbps（Google Cloud tier-1 egress）、32 Gbps（Lambda Lab SSD 讀取）、56 Gbps（Samsung 980 Pro 讀取）、100 Gbps（InfiniBand RoCE）。
    - GPU 使用率：用 vLLM 的 token budget 比例定義。例如 budget 512、Cake 的請求用 256，就是 50%。掃 12.5%／50%／87.5%／100%。
- **SSD 要多快 Cake 才划算？** 原文沒給門檻，只說兩邊速度相當時最划算（對只算、只載都約 2 倍）；一邊快超過 10 倍時，相對快的那邊幫助有限〔原文 §5.2〕。換成 κ：每個 chunk 成本固定時，Cake 相對較快那條路的加速是「1 ＋ 慢的那邊速度 ÷ 快的那邊速度」，κ ＝ 1 時最大，等於 2〔算術，一階近似〕。
- **AMD 的儲存其實落在 Cake 掃的範圍內**〔算術〕：MI300X 量到的 SSD 路徑 1.3–3.2 GB/s（§9 第 3 點）約等於 10–26 Gbps，介於 Cake 的 7 與 32 Gbps 之間。真正不同的是 GPU：MI300X 重算比 A100 快，等效吞吐較高，同樣頻寬下 κ 比較小，I/O 相對更慢〔推論，待量〕。
- **我們的做法**：
    - SSD 太慢或沒有本地 NVMe 時，用 CPU 記憶體當後端，再加限速器模擬不同速度的 SSD／NFS／網路。這跟 Cake 的方法一樣，可以直接掃 Cake 的 7–100 Gbps，結果能跟 Cake 對照。
    - ⚠️ 限速器不能只算「大小 ÷ 頻寬」。我們量到每筆搬運有固定成本（§10.2 第一列），延遲要寫成「每筆固定成本 ＋ 大小 ÷ 頻寬」，固定成本用實測值。
    - ⚠️ 跟 §9「真實 I/O 是差異點」有衝突：SSD 也用限速的話，就不能說「全部用真實搬運」。折衷：CPU 層用 vLLM 真實搬運，只有 SSD／NFS／網路用限速，論文裡寫清楚哪些是模擬的。
    - ⚠️ 限速器（虛擬 I/O 時鐘）不含 PCIe 競爭，也看不到寫入對讀取的干擾。所以 E2 一定要真機量，不能用限速器代替；這一點要寫進限制。
- **規模**：Cake 只到 16K。我們要到 128K，時間量測再延伸到 500K（品質無效，見 §10.3）。

### 10.6 量化：會合點往前移，不是往後

- **問**：如果用自己的量化方法、又不掉精度，可以把 I/O 往後拉嗎？
- **答**：方向對，但說法要改：會合點是**往前**移。量化讓每個 chunk 變小，I/O 載得更快，能負責更多 chunk，GPU 要重算的範圍就縮短。用 κ 講：傳輸時間下降 → κ 變大 → 被重算的前段比例 1/(1+κ) 變小〔算術〕。
- ⚠️ **Cake 已經做過「量化＋Cake」**：§5.5 Table 6 接上 8-bit 與 3-bit（KVQuant），精度越低，相對只算的加速越大（32 Gbps：1.59 → 2.12 → 3.73 倍）〔原文；2×A100、100% 使用率、16K、LongAlpaca-13B〕。所以這件事本身不新。
- **可能新的部分**〔推論〕：依位置決定精度，只量化要被 I/O 載入的後段，並依品質預算 ε 選精度。
- 要注意三件事：
    1. **跟本方向互相抵銷**：量化讓會合點往前，「不存」的前段變短，§3.1 能省的容量和寫入跟著變小。這跟 §7 第 1 點（INT4 讓放置只剩 2–3.5% 的空間）是同一個現象。
    2. **定義要改**：目前的六態裡，CPU 與 SSD 是無損的位元組搬移（CLAUDE.md §0）。量化後再存到 CPU／SSD，等於新增「CPU-INT4」「SSD-INT4」這類有損狀態，品質要重新量（M5）。「不掉精度」也要在 LongBench／RULER 上量過才算。
    3. **反量化有成本**，要算進讀取時間。

### 10.7 GPU 服務和 KV 重算要一起考慮

- 重算用的就是服務其他請求的那張 GPU。Cake 的處理方式是：decode 優先，其次是沒有快取的 prefill，最後才是有快取的 prefill，自己只用剩下的 token budget〔原文，設計章 Part 3〕。
- **對本方向的影響**〔推論〕：「前段不存」等於把那段的成本固定交給 GPU。GPU 忙的時候（例如 Cake 的 12.5% 設定），會合點往前移，有一部分前段本來該由 I/O 載入，但已經沒存了，只能硬算，TTFT 變差。E4 要包含 12.5%／50%／87.5%／100% 四種使用率。
- 反過來，GPU 越忙，存起來的後段越有價值。所以寫入規則可能要看「讀取時預期的 GPU 負載」，不能只看寫入當下〔推論〕。

### 10.8 要問學長的

1. **dLLM 會不會有這個問題？**
    - 初步判讀〔推論〕：Cake 的前提「越後面越貴」來自因果注意力（後面的 token 要看前面全部）。dLLM（例如 LLaDA）用雙向注意力，每個位置都看整段，重算成本不再隨位置變化；而且後面的字一改，前面的 KV 也跟著變，快取只是近似（`PAPERS_BY_LEVEL.md` 附錄）。所以「依位置決定」的基礎可能不成立。
    - 已有工作：GroupKV（dLLM 長 context 分層卸載）、BiCache（只有淺層的前綴 KV 能重用）。
2. **hybrid 模型大家也在做，要不要碰？**
    - 初步判讀〔推論〕：hybrid 模型只有 attention 層的重算成本隨位置變貴，線性層是固定的，所以「越後面越貴」的斜率變小，依位置分層的好處可能變小。另外它多了一份固定大小的 recurrent state，只在特定位置存才有用（`ADVISOR_REPORT_20260930.md` L0），存放規則跟 KV 不同。
    - 已有工作：Marconi、Sparse Prefix Caching、DASC、Tail-Replay（`PAPERS_BY_LEVEL.md` L0），已經不是空白。

## 11. 這算研究貢獻嗎？怎麼做成研究貢獻（10/4）

### 11.1 判斷

**§5 現在的寫法是「方法提案」，還不算站得住的研究貢獻。** 用「研究問題、新意、預期貢獻」三個問題檢查：

| 問題 | §5 現在的答案 | 缺什麼 |
|---|---|---|
| 研究問題 | Cake 假設全部存好，浪費容量和寫入 | 前提還沒量過（§3.1 全是〔推論〕或〔算術〕）；我們自己的初步數據還說 INT4 會把空間吃掉（§9 第 1 點） |
| 新意 | 寫入時 × 依位置 × 多層 × 多輪 | 每個零件都有人做過，只剩組合（§6）；組合型貢獻需要一個洞見撐住 |
| 預期貢獻 | 一個新策略 | 只能說「更快、更省」，說不出「在什麼條件下有效、為什麼」 |

**能變成研究貢獻的版本**：把問題從「再做一個放置策略」改成「**重算＋載入並行（Cake 式）在什麼條件下有效、什麼條件下失效？能不能只量幾個常數，就事先預測？**」這就是故事 6 的「判準」，落在一個具體機制上。依位置寫入（§5）變成從判準推出來的設計結論，用 E1 驗證；不成立的話，也是判準的一個資料點，不會白做。

工程（在 vLLM 裡做 Cake 式載入器、限速器）還是要做，但它是驗證的手段，不是貢獻本身。

### 11.2 研究問題、新意、貢獻（草稿）

- **研究問題**：在真實硬體與長 context 下，Cake 式的雙向還原什麼時候有效、什麼時候退化成只算或只載？會合點和加速比能不能事先預測？預測出來的會合點，能不能直接拿來決定寫入時存哪些、存哪層？
- **新意**（相對 Cake 與 CacheFlow）：
    - Cake 只在 4K–16K、A100／H100、模擬 I/O 下量，結論只有「兩邊平衡時最好」〔原文〕；
    - CacheFlow 有切點公式 ℓ ＝ L × T_io ÷ (T_comp + T_io)，從形式看是假設每個 token 成本均勻〔推論，⚠️ 待讀原文確認〕；
        - ⚠️ 10/4 讀了 v2 全文（2026-09-26）：公式已改成階梯式 DP，有線上量測的成本與預測準確度，這一條新意大半已被做掉。只有「寫入時的決定」沒有處理。見 `WRITE_PROBLEM.md`。
    - 我們的模型多了四個因子：隨位置變化的重算成本 c(i)、每筆搬運的固定成本 α、KV 精度 b、GPU 可用比例 g，並在兩個平台上用「事先預測、事後比對」驗證。
- **預期貢獻**：
    1. **失效地圖**：在真實平台上量出 Cake 式還原退化的區域，並把現有論文的評測設定放上同一張圖；
    2. **可預測的成本模型**：用 c(i)、B、α、b、g 事先算出會合點與加速比，跟實測比對；
    3. **設計結論**：寫入分界 ＝ 預測的會合點；量化讓分界往前移；GPU 越忙，前段越不能不存。用 E1 決定這條結論值不值得做成原型。

### 11.3 成本模型（先寫下來，再量）

符號：N 個 chunk；c(i) 是第 i 個 chunk 用整張 GPU 的重算時間（實測）；g 是 GPU 可用比例；S(b) 是精度 b 下每個 chunk 的 KV 大小；B 是來源層的頻寬；α 是每筆搬運的固定成本。

- 載入一個 chunk 的時間：ℓ ＝ α ＋ S(b) ÷ B
- 會合點 m\*：讓 max( Σ_{i≤m} c(i) ÷ g , (N − m) × ℓ ) 最小的 m
- 預測的 TTFT：上式在 m\* 的值
- 預測的加速比：只算的時間 Σ c(i) ÷ g、只載的時間 N × ℓ，各自除以預測的 TTFT
- 多層：已經在 GPU 的 chunk，ℓ ＝ 0（FP8／INT4 加反量化時間）；CPU、SSD 各用自己的 B 與 α

〔算術，一階近似。用到兩個假設：GPU 可用比例對重算時間是線性的；搬運與計算完全重疊。這兩個假設本身要驗證。〕

### 11.4 10/4 提的四點，各要補什麼

| 提的點 | 判斷 | 要補的 |
|---|---|---|
| **可量化的失效條件**：AMD＋慢 NFS 下 r 很小，Cake 收益趨近 I/O-only | ✅ 這是「既有方法在特定條件下失效」的證據 | ⚠️ r 沒有定義。若 r ＝ I/O 等效吞吐 ÷ 重算等效吞吐，r 小代表 I/O 慢，Cake 應該趨近**只算**；若 r 指 GPU 可用比例，r 小時才趨近**只載**。兩種失效都要量，論文要先定義 r。另外，Cake 自己已經標出極端情況（一邊快 10 倍以上；12.5% 時比只載慢 25%）〔原文〕，所以新意不是「Cake 在極端會失效」，而是「真實平台落在失效區」 |
| **可預測的成本模型**：用 c(i)、B、量化 bit 數事先預測會合點與加速比 | ✅ 最核心，也是 L2 擠滿之後的空缺 | 加上 α 和 g（§11.3）；跟 CacheFlow 劃清界線；驗證要「事先預測」，例如用 16K–32K 擬合 c(i) 去預測 128K，或沿用 3090 上的模型形式、只換 MI300X 的常數去預測。誤差門檻要在量之前寫下來 |
| **系統性掃描**：16K → 128K → 500K、MHA vs GQA、頻寬、GPU 使用率、精度與品質 | ✅ 論文都沒掃 | 每個軸先寫出模型預測的方向（見下），掃描是在驗證預測，不是收集數字，不然就變回工程。全因子組合太多，用模型挑「預測會翻轉」的點去量。500K 只能量時間（§10.3） |
| **誠實的限制**：虛擬 I/O 時鐘不含 PCIe 競爭 | ✅ | 再加兩項：寫入對讀取的干擾（E2 必須真機量）；在一兩個點上比對「限速器」與「真實搬運」，把差距寫出來 |

各軸的預測方向（「往前」＝ 會合點往序列開頭移，GPU 算得比較少）：

- context 變長 → 後段更貴 → 往前（與 Cake §5.3 一致）
- GQA（KV 比較小）→ 載得快 → 往前（與 Cake §5.4 一致）
- 頻寬變大 → 往前
- GPU 可用比例變小 → 往前
- 精度變低 → 往前，但品質可能掉

### 11.6 用現有常數先算一次：找到的問題（10/4）

> 〔算術〕不是量測。把 M4 已經在用的實測成本常數（`results/m4_oracle_mi300x/cost_model_b-*.json`、`results/m4_oracle/cost_model.json`）代進 §11.3 的模型。指令：`python3 code/cake_predict.py`；輸出：`results/cake_predict/cake_predict.csv`、`cake_predict_robust.csv`（run_id `20261004-140033-cake-predict`）。一階近似：搬運與計算完全重疊、g 對重算時間線性。重算擬合只到 64K（llama8b 32K），**128K 以上全是外插**；載入成本是整段讀回的攤提值，沒有分出每筆固定成本 α。

**找問題的方法**：拿一個設計背後的假設（Cake 的、或我們自己的），把實測常數代進去，看它在哪裡不成立。先用算術（不用 GPU）找出「預測會出事」的點，再去量那幾個點。

**問題 1：Cake 的好處只在一個帶狀區域**（相對較快那條單一路徑的加速）

| 條件 | MI300X，SSD 路徑 | MI300X，CPU 路徑 | 3090 |
|---|---|---|---|
| 16K，GPU 全空 | 1.68–2.15 倍 | 1.34–1.75 倍（Qwen3-MoE 1.09 倍） | CPU 1.14 倍；SATA SSD 2.12 倍 |
| 128K，GPU 全空（外插） | 1.37–1.71 倍 | 1.21–1.41 倍 | CPU 1.11 倍；SSD 1.60 倍 |
| 16K，GPU 只剩 12.5% | 1.10–1.22 倍 | 1.01–1.11 倍 | CPU 1.02 倍；SSD 1.16 倍 |

- context 越長、GPU 越忙、搬運路徑越快，Cake 越接近「只載」，好處縮到 1.0–1.2 倍。最划算的反而是兩邊速度相當的情況，例如 MI300X 的慢 SSD 路徑在 16K–64K。
- 這修正了 §10.5 的擔心：AMD 的 SSD 慢，正好落在 Cake 最划算的區域。好處小的是快的 CPU 路徑（Qwen3-MoE 37.8 GB/s、3090 的 CPU 層）。
- 兩個平台落在不同區，所以判準有區分力；§11.5 階段 3 的停損，預測上會通過。

**問題 2：「前段不存」很脆弱**（§5 原本的設計）

寫入時假設 GPU 全空，算出會合點，前段不存；讀取時 GPU 變忙，沒存的前段只能用剩下的算力硬算。相對「全存＋Cake」的 TTFT：

| 讀取時 GPU 可用比例 | MI300X（SSD 路徑，16K） | MI300X（SSD 路徑，128K，外插） | 3090（CPU 路徑，16K） |
|---|---|---|---|
| 50% | 慢 1.44–1.60 倍 | 慢 1.67–1.80 倍 | 慢 1.87 倍 |
| 12.5% | 慢 3.94–5.24 倍 | 慢 5.39–6.37 倍 | 慢 7.12 倍 |

- 所以寫入分界不能用「GPU 全空」的會合點，要用讀取時悲觀的 GPU 比例。這樣一來，能不存的前段只剩約 9–18%（16K）、4–13%（128K）〔算術，g＝12.5%〕，比 §4 估的上限小很多。
- 這是本方向目前最大的問題，也可能是貢獻本身：**寫入時的決定必須考慮讀取時的 GPU 負載**。現有工作（Cake、CacheFlow）都在讀取時才決定，沒有遇到這個問題。

**問題 3：專案本身的缺口**

- MI300X 的 M2 原始檔沒有進 git：`RUNLOG_MI300X.md` 列為產出檔的 `cost_constants_mi300x.csv`、`recompute_fit_mi300x.csv`、`retrieval_cost_b-*`、`recompute_position_b-*` 都不在 repo，`cost_model_b-*.json` 指向 MLSteam 上的路徑。違反 CLAUDE.md §1 第 3 條，要從 MLSteam 推上來。
- `RUNLOG_MI300X.md` M2 表的斜率單位寫成「µs/千 token」，用 P\* ＝ 3,396 token 反算，應該是「ms/千 token」（＝ µs/token）。
- 重算成本有兩套：M2 的分塊法與 M3 校準的擬合（故事 6 已指出結論會隨量法改變）。這裡用的是 M4 採用的 M3 版本；階段 1 要決定以哪個為準，並量到 128K 以上。
- 「搬運與計算完全重疊」還沒驗證；vLLM 目前沒有 Cake 式載入器。

**下一步要量的點**（預測差異最大的地方）：MI300X Qwen2.5-7B 慢 SSD 16K（預測約 2.1 倍）、Qwen3-MoE CPU 16K（預測約 1.09 倍）、GPU 12.5%（預測 ≤ 1.22 倍）、以及問題 2 的「前段不存＋GPU 變忙」。四個點的實測跟預測對得上，就是 §11.2 的貢獻 1 和 2；問題 2 成立，就是貢獻 3 的核心。
