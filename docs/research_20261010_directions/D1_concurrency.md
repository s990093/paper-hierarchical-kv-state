## 1. 問題是什麼、要證明什麼

**問題**：之前所有「寫入時決定 KV 放哪一層」的測試，都是一次只服務一個請求。反方審查說：這樣延後的做法（滿了才搬、背景搬）永遠有空檔，當然追得上。

**要證明的**：很多請求同時進來、SSD 寫不完、CPU 裡的 chunk 被「寫往 SSD 中」鎖住、CPU 滿了又沒東西可丟的時候，**延後的做法會不會輸**？如果會，「寫入時就決定」才有用。

**白話名詞**：
- **chunk**：512 個 token 的 KV，64 MiB。
- **Cake 還原**：使用者回來時，GPU 從前面重算、I/O 從後面載入，兩邊在中間碰頭。所以**前段**的 chunk 存不存都差不多（反正會被重算），**尾段**才值得存。
- **b_c、b_s**：從 CPU 載入（快）或從 SSD 載入（慢）時，前面大約幾個 chunk 會被重算。SSD 越慢，b_s 越大。
- **寫穿**：寫進 CPU 的同時也寫一份到 SSD。真實系統（vLLM、LMCache、SGLang、Dynamo）預設都這樣做（H0）。
- **ρ（寫入負載）**：想寫進 SSD 的速度 ÷ SSD 寫得動的速度。ρ≥1 就是「寫不完，一直排隊」。
- **溢出規則**：CPU 滿了、又沒有能立刻空出的格子時，新的 chunk 要丟哪些。whole＝整批不存（vLLM）；tail＝存頭丟尾（LMCache）；pa＝依位置，先丟前段。
- **延後測試**（10 §2）：寫入時決定的做法，要同時贏過「同一條規則、等滿了才做」「背景做」「預先清理」「寫穿」「讀取時（Cake）」這些版本，才算「寫入時」有用。

### 2.2 策略

寫入時（新 chunk i；b_c＝以 CPU 速度算的分界、b_s＝以 SSD 速度算的分界，都用這一輪結束後的長度）：

| 策略 | 寫入時 | 淘汰順序 | 淘汰的 chunk 沒有 SSD 副本時 | 類別 |
|:--|:--|:--|:--|:--|
| S1 | CPU＋寫穿 SSD | LRU session | 丟掉 | 寫穿（對照） |
| S2b | CPU＋寫穿 SSD | 位置最前的先 | 丟掉 | 寫穿（對照） |
| S4 | CPU | LRU session | 搬到 SSD | 延後（對照） |
| S4+ | CPU | 位置最前的先 | 搬到 SSD | 延後（對照） |
| S4B | CPU | i<b_c 的先（LRU），再 LRU-前段 | 搬到 SSD | 延後版 S5L（對照） |
| S4W | 同 S4B，加背景：每輪後讓 CPU 至少空 25% | 同 S4B | 搬到 SSD | 背景（對照） |
| S4C | 同 S4+，加預先清理：淘汰順序最前面 25%×cap 先寫一份到 SSD | 同 S4+ | 搬到 SSD | 預先清理（對照） |
| S4PD | CPU，沒有 SSD | Pensieve：V＝f(i)/閒置時間，最小的先 | 丟掉 | Pensieve 式延後丟棄（對照） |
| S4BT | CPU | LRU-前段 | i<b_s 丟掉，i≥b_s 搬到 SSD | **候選規則的延後版**（對照） |
| S4WT | 同 S4BT，加背景：每輪後讓 CPU 至少空 25% | LRU-前段 | 同 S4BT | **候選規則的背景版**（對照） |
| **S5T** | i<b_c 不存；b_c≤i：存 CPU；i≥b_s 另外寫穿 SSD | LRU-前段 | 同 S4BT | **候選（寫入時）** |
| S5L | i<b_c 直接寫 SSD（經 CPU 暫存），其餘 CPU | LRU-前段 | 搬到 SSD | 次要（只報告，不進判定） |

- 「搬到 SSD」：送一筆 SSD 寫入，寫完才空出那格；寫入佇列滿了就跳過這個 chunk，看下一個。
- 「丟掉」：立刻空出那格，資料沒了，回來時重算。
- 鎖住（寫入中）的 chunk 跳過，不能淘汰。
- 讀取時版（Cake）內建在所有策略的還原裡。

### 2.3 為什麼選 S5T 當候選（事先講清楚）

- S5L 會把 i<b_c 的前段寫到 SSD；這些 chunk 在任何版面都會被 Cake 重算，寫它們只是浪費 SSD 頻寬。在寫入排隊的區域，S5L 機制上就吃虧，用它當候選，輸了也說明不了什麼。
- S5T 是「寫入時決定」在 N3 區最有機會贏的版本：寫入當下就只把會被讀回的尾段（i≥b_s）送去 SSD，總寫入量少，而且一產生就開始寫，不必等滿了才搬（延後版搬移要 I/O，排隊時搬不出來）。
- 對手包含它自己規則的延後版（S4BT）與背景版（S4WT），符合 10 §2「同一條規則，延後／背景套用」。

### 2.5 判定規則

- **指標**：回來請求（round ≥2）TTFT 的中位數（含排隊）。另外報平均、p90、p99、溢出丟棄比例、GPU 使用率、寫入負載 ρ。
- **ρ 的定義**：
  - ρ_KV＝這個工作負載產生的新 KV 位元組 ÷（SSD 寫入頻寬 × 這次模擬的總時間）。和策略無關，代表「全部寫穿要多少頻寬」。
  - ρ_peak＝每 30 s 視窗的同樣比值，取最大。
  - ρ_strat＝這個策略實際送到 SSD 的寫入 ÷（SSD 寫入頻寬 × 總時間）。
- **候選固定**：S5T＋pa 溢出。**不在每個設定挑最好的寫入時策略**。
- **對手**：S1、S2b、S4、S4+、S4B、S4W、S4C、S4PD、S4BT、S4WT。每個對手在每個 seed 取三種溢出規則裡**最好的**（對候選比較嚴）。
- **一格（設定）通過**：5 個 seed 裡至少 3 個，候選的中位數比**每一個**對手都快 ≥10%（快＝對手中位數 ÷ 候選中位數 − 1）。門檻從 5% 提高到 10%，因為模擬器對 S5L 偏樂觀約 5 個百分點（12 §5.4）。
- **判定**：
  - **有看頭**：至少一格通過，而且那一格是穩定的：ρ_KV < 1 且 GPU 使用率 < 0.95。
  - **可能**：有格通過，但都在不穩定區（ρ_KV ≥1 或 GPU ≥0.95）；或者沒有格通過，但有穩定的格在 ≥3／5 個 seed 贏所有對手 ≥5%。
  - **死路**：沒有任何一格在 ≥3／5 個 seed 贏所有對手 ≥5%。
- **不管結果如何**，這只是〔模擬〕；任何正面結果都要 GPU 確認才算數（不在本 agent 範圍，GPU 只有 D2 能用）。

### 2.9 追加 2（**事後**，2026-10-10T05:50:56Z；看過追加 1 的結果之後、跑追加 2 之前寫的）

**追加 1 的結果**（run `20261010-054959-d1-analyze-posthoc`）：加了 S4BD、S4WD、S1D 之後還有 3 格通過（都是 3.69、NFS、doc）。我看了第 1 格的明細：S1D 的 service 中位數和 S5T 一樣（0.879 s），差在排隊。差別的來源是：

- 我的 drop 模型「先淘汰、再收新的」：新 chunk 不是淘汰候選。所以延後版（S4BD、S1D）即使規則是「先丟 i<b_c」，新進來那個 session 自己的前段還是會先占 20 格，擠掉別的 session 有用的 chunk；要等下一次淘汰才丟。
- **這和 m7 原本的語意不同**：`BState.after_round` 是「先放進去、超過容量再淘汰」，新 chunk 也是候選。我在 drop 模型裡改成先淘汰，是為了處理鎖，但順帶讓所有延後版吃虧。

  - 這是「丟哪一段」的決定，本來就只能在寫入當下做。但它的好處就是 Cake 的好處（反方審查 §3.1 第 4 點）。
  - 上面是「先淘汰再收」的語意。改成 admit-first（新的也算候選）之後，**丟的量不變，只是換了名字和順序**：S1 在 NFS＋doc 一樣是 59% 的格、平均丟 8.8% 的新 chunk，但記成「淘汰新 chunk」，而且照淘汰順序丟（LRU 順序下新 chunk 的前段先丟，等於內建 pa）〔模擬 20261010-055231-d1-admitfirst〕。
  - 所以 admit-first 讓所有策略（含 S5T）都自動用「先丟前段」處理新 chunk；這是追加 2 的對手追上來的原因之一。

## 5. 延後版／更簡單的做法＋前作

**追得上的延後版（本次模擬）**：

| 寫入時的決定 | 追得上的延後版 | 證據 |
|:--|:--|:--|
| 前段（i<b_c）不存 | 淘汰時先丟前段，**新進的 chunk 也算候選**（S4BD／S1D＋admit-first） | 追加 2：0／192 |
| 尾段寫入時就寫穿 | 背景預先清理，**只挑尾段**（S4CT／S4CT50） | 追加 4：0／192、0／96 |
| 兩個都做（S5T） | 上面兩個＋寫穿 S1 | 追加 4：0／192；S1 是 51 格裡最緊的對手 |
| 丟哪一段（溢出時） | 沒有延後版；但避免溢出就不用丟 | 4.7 |

**前作**（都已在 repo 的卡片或摘要核對過原文；本 agent 沒有再開原文）：
- **Pensieve**（Yu、Lin、Li，EuroSys 2025，arXiv 2312.05516；`lit_A_summary.md` 第 123 行，PDF 頁首核對）：空間不夠時先丟閒置對話的前段、回來重算。就是「前段不存」的延後版。
- **Gill, FAST '08**（`cards/B_PROMOTE.md`）：頻寬不限時「經過時決定」只比「逐出時才搬」好 ≤5%；頻寬受限時 3.42 ms 對 5.05 ms〔原文 p.13〕。我們的結果一樣：只有持續頻寬受限的角落，寫入時決定才贏。
- **Tachyon, SoCC '14**（`cards/B_Tachyon.md`）：背景 checkpoint 能成立，是因為「most data has time to be checkpointed due to the bursty behavior」〔原文 p.6〕；反過來「if data is written faster than the available disk bandwidth」就會失效〔原文 p.2〕。4.6 的角落就是這個條件。
- **TPP, ASPLOS '23**（`cards/B_TPP.md`）：配置突發時，把回收水位線和配置水位線分開（背景提早搬）就修好了〔原文 p.10–11〕。和本次「只挑尾段的預先清理追得上」一致。
- **H0**（`H0_offload_blocking.md`）：真實系統預設都寫穿；CPU 滿了就丟（vLLM 整批跳過、LMCache 存頭丟尾）。
- 「持續寫入超過 SSD 頻寬時，依位置挑尾段寫穿」這個組合有沒有人做過：**沒查**〔未查證〕。

## 6. 如果要繼續：下一步、成本、最大風險

**我的建議：D1 這個方向停。** 把結果寫成負面結果的一節，回應反方審查最強的拒稿理由：

> 加了併發、寫入排隊、鎖、放不下就丟之後，只要延後版用同一條位置規則（而且新進的 chunk 也能被淘汰），延後測試仍然成立。唯一的例外要求 SSD 的**持續**寫入量超過頻寬（Tachyon 的條件），而一張 GPU 在量到的層參數下到不了那裡。

**如果還是要追 4.6 的角落**：

| 步驟 | 成本 | 會殺掉它的結果 |
|:--|:--|:--|
| 1. 量真實多卡機器上，每張 GPU 同時卸載時分到多少 SSD 寫入頻寬（取代 local8 的假設） | 半天，需要多卡機器（這台只有 1 張） | 分到的頻寬讓 ρ_KV<1 |
| 2. 看 D2 量到的真實 vLLM 丟資料頻率 | 0（等 D2） | 很少丟 |
| 3. 那個角落 TTFT 中位數 2.6–34 s：先確認真實服務會不會在那裡運作（還是早就擋請求了） | 讀文件 | 有准入控制就不會在那裡 |
| 4. 重新事先登記（候選 S1D、16 個對手、qmax、ρ≥1 的格），再上 GPU | 模擬 1 天＋GPU 1–2 天 | GPU 上 <10% |

**最大風險**：
- 那個角落是過載的人工現象：drop 模型「完全不等」對延後版最不利；真實系統的新 KV 可以在 GPU 上多留一下。
- 模擬器對策略之間的相對差不準（12 §5.4：S5L 偏樂觀約 5 個百分點）；S1D 沒有任何 GPU 驗證。
- doc 負載回來請求的 TTFT 是兩群（排在大 prefill 後面或沒有），中位數很敏感：同一格（3.69、nfs、doc、bursty、0.05、0.125）裡 S1D 的 seed 中位數從 1.01 s 跳到 17.55 s〔模擬 20261010-055748-d1-an-x4〕。
