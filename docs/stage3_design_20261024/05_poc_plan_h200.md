## 0. 一頁摘要

- **核心主張**：寫入端只存一份「可以分層讀」的格式，所有決定都移到讀取那一刻。
  - **當下的 GPU 資源**決定用什麼方式、分多少 SM 去還原（方向 B，**主線**：新意最穩，查新沒找到聯合規劃，也沒有 GPU 共用系統把 KV 還原放進 SM 分配）。
  - **新問題**決定每一塊讀多清楚（方向 A，**副線**：表示法已被 ReadKV 等在 decode 時發表，但上檔空間最大）。
  - 兩者共用一個能外推的還原成本模型（方向 C，基礎）。
- **先篩再做**：四道便宜的閘（A0、B0、C0、D0）先跑，約 40–55 GPU 小時〔估計〕。11/17 依事先寫死的條件決定哪些方向繼續。
- **主實驗**（11/18–12/13）只做通過的方向；**消融與擴大規模**（12/14–12/31）回答審稿人一定會問的四件事：同位元組、只靠選擇、只靠規則、規模。
- **深度學習**的部分（學出來的挑塊器、學出來的 codec）只在 A0 的上界通過之後才做（CLAUDE.md §8：Oracle 出來之前不訓練）。

## 4. 篩選閘 A0（方向 A 的上界）：「全部粗、少數細」到底能拿回多少

### 4.1 問題

在同樣讀取位元組下，「全部塊讀粗版、只把少數塊升級」能不能比「每塊同樣壓縮」好？先用**知道答案的挑法（oracle）**看上界；上界不夠大就停。

### 4.2 配置

- **base（每塊都讀）**，兩個家族：
  - LR：3a X4 每個倍數的最佳配比，取 16×、24×、32× 三級（例：Qwen 32× `xl:k11:v17+K4V2`，Llama 32× `xl:k9:v14+K4V2`）。
  - K2：逐 token 2-bit K＋低秩 V。理由（2604.08426，V8 核對）：§4.1 低秩 K 壓縮在 context-intensive 任務上即使多載 10 倍 token 也追不上 full attention；§4.3 逐 token 2-bit K 做選擇勝過低秩代理。倍數對齊 LR 的三級。
- **refinement（只讀挑中的塊）**：兩種目標，INT4（3.2×）與 BF16。
- **升級比例 ρ**：1/16、1/8、1/4。
- **挑法**（每種都在同一題、同一個 base 上配對）：
  - ORACLE：用新問題、在原始 BF16 KV 上的真實 attention 挑（不可部署，是上界）
  - EXACT-Q：用**精確**的新問題 query（從 BF16 prefill 取）、在 base 的 K 上打分。這是 ReadKV／Fathom 的設定，用來和下一列對照
  - BASE-ATTN：用新問題、在 **base** KV 上跑 prefill，query 本身也來自粗 KV（可部署）。**和 EXACT-Q 的差＝「query 不精確」造成的損失，沒有前人量過**（L8a §0 第 6 點）
  - KSCAN-2b：逐 token 2-bit K 掃描（FIER／YAKV／Fathom 式）
  - QUEST-512：C1b 的摘要（已知不準，當對照）
  - WRITE-TIME：寫入時就依重要性決定哪些塊精修（AnchorKV／MiKV 式）
  - RANDOM、RECENT（最後幾塊）
- **對照組**（L8a §6 列的審稿人必要對照）：
  - 均勻壓縮 U(r)：r＝3.2×、8×、12×、16×、24×、32×
  - **同碼、查詢無關**：同一個漸進碼、同樣的讀取預算，但每塊讀一樣深（ReadKV 的對照）
  - **全部依序精修到期限為止**（不挑塊）
  - **丟塊**：同一個挑法、同一個 ρ，但沒挑中的塊直接不用（＝C1b）。用來分開「挑得準」和「不丟」兩件事
  - 全部 BF16 載入、Cake（A2 才量時間）
- 塊 0（sink 與任務說明）一律讀 refinement，位元組算進去。

### 4.3 演算法 A（漸進式還原），論文體

**輸入**：下層存的每一塊 j 的 base_j 與 refine_j；新問題的 token；讀取位元組預算 R（或時間期限 D）；挑法 S。
**輸出**：GPU 上可用的 KV，每塊是 base 或 refined。

1. 讀所有塊的 base；塊 0 讀 refined。
2. 把 base 解碼放進 GPU 的 KV。
3. 用這份 KV 跑新問題的 prefill（只算問題的 token），記錄每一塊在所有層、所有 head 得到的 attention 總量 a_j。
4. 依 a_j 由大到小，把塊加進升級清單，直到 refinement 的位元組用完預算 R。用時間期限時，改成預估的讀取時間到 D 為止。
5. 讀清單裡每塊的 refinement，解碼後覆蓋 GPU 上對應的塊。
6. 丟掉第 3 步產生的問題 token KV，用升級後的 KV 重跑問題的 prefill，然後開始生成。

變體（A2 才做）：
- 和 Cake 結合：會合點以前的塊直接重算（本來就是 BF16），步驟 1–5 只作用在要載入的那段。
- 和打字預取結合：步驟 1–2 在使用者打字時先做；按下送出才有步驟 3–6。

### 4.4 量法

- 先 teacher forcing（TF）篩選：每個模型 96 題 × 約 90 個配置（規模同 X4a），量答案的 log-prob 掉多少。
- TF 挑出每個模型最好的約 12 個配置，跑生成答對率：192 題新問題＋150 題第 2 輪。
- **位元組帳**逐塊記：base、refinement、索引、塊 0。平均位元組比＝讀的位元組 ÷ BF16。

### 4.5 判準（草案，開跑前凍結）

- **GA0-GO**：兩個模型中至少一個，存在某個 (base, ρ, 目標) 使得 ORACLE 版：
  - 平均位元組 ≤ BF16 的 1/12；
  - 對 E0 的 CI 下界 ≥ −2；
  - 而且比位元組 ≥ 它的最好均勻壓縮 U(r) 多 ≥2 個百分點（配對 CI 下界 >0）。
  - 另一個模型方向相同（點估計 >0）。
- **GA0-STOP**：每個格子的 ORACLE 版比同位元組的均勻壓縮都好不到 2 個百分點 → 方向 A 停，寫成負面結果：「在 8–32 倍的範圍內，KV 的重要性不夠集中，挑塊升級拿不回均勻壓縮的損失」。
- **GA0-SEL**（只在 GO 時看）：BASE-ATTN 拿到 ORACLE 好處的比例。≥70% → 不需要學的挑塊器；50–70% → 做 A-DL1（學的挑塊器）；<50% → 先做 D0 的原生索引，不行就停。
- **GA0-DROP**（分開兩件事）：同一個挑法下「變糊」比「丟掉」好 ≥5 個百分點 → 「不丟」本身有貢獻。

### 4.6 成本〔估計，NOT_MEASURED〕

TF 每個模型約 4–6 GPU 小時；生成每個模型約 6–8 GPU 小時；合計約 20–30 GPU 小時。品質實驗不量時間，可以和別人的 job 同時跑。

## 5. 篩選閘 B0（方向 B）：在像真實服務的背景下，還原的各種做法被拖慢多少

### 5.1 問題

O8 的翻轉只在純 matmul 背景下出現；O9 的「讓 SM 給還原」只在 MPS 下量過。真實的服務背景（decode、chunked prefill、混合批次）下：(a) 各種還原做法被拖慢的倍數，(b) 最快的計畫會不會變，(c) 分 SM、改 stream 優先權能換到多少，代價是背景慢多少。

### 5.2 格子

- **還原的基本動作**（32K、64 塊、兩個模型）：
  1. copy engine 一次搬連續的 pinned 記憶體
  2. 逐塊 copy、批次 copy
  3. SM 驅動的 zero-copy gather（同 vLLM #42212 的做法）
  4. INT4 反量化（融合 kernel）
  5. 低秩重建（矩陣乘）＋INT4
  6. 重算一個塊（fa3）
  7. 端到端：Cake、全部載入、漸進式（A）
- **背景**：閒；decode B＝8／32／128；chunked prefill；混合批次；**prefill 節點**（連續的 chunked prefill、不混 decode：P/D 分離部署裡回來的請求在這裡還原，[08](08_kill_argument.md) §1.2）；matmul（舊）；HBM 複製（舊）。
- **動作集分兩組報**：全部動作；只用生產格式（BF16、FP8、INT4，以及 SM90 上軟體反量化的 NVFP4）。後者回答「沒有低秩重建時，爭用還會不會改變排序」。
- **共用方式**：同 process 雙 stream（還原 stream 設高優先權／一般）；MPS 不限；MPS 背景限 87％／75％／50% SM；有 green context 就加。
- 每格量：還原時間（中位數、P95，≥6 次）；**背景吞吐的變化**（還原期間背景每秒 token 數 ÷ 單獨跑）。
- 量法的骨架：Paragon（ASPLOS'13）的「敏感度 × 壓力源」。每種背景是一個壓力源，每種還原動作量它對每個壓力源的敏感度；結果是一張干擾矩陣（L8b §0 五）。
- 同時記錄 vLLM #42212 的靜態選路（payload <28 KiB 且 n≥16 時走 SM kernel、固定 12 個 SM）在同一格的表現，當工程上的現行做法。

### 5.3 判準（草案）

- **GB0-FLIP**：在任一種像真實服務的背景下，至少 2 條（模型 × 下層）線的最快端到端計畫和「閒」時不同，而且差 ≥10%。
- **GB0-SHARE**：某個 SM 比例或 stream 優先權設定，讓還原快 ≥30%，背景吞吐少 ≤10%。
- 兩條都不成立 → B 不做線上選擇器，降級成路 2 論文裡的一節量測（「真實背景下還原的干擾矩陣」）。
- 只有 SHARE 成立 → B1 只做「還原給多少 SM」，不做格式選擇。
- **GB0-STATIC**：如果最好的 SM 比例在每一種背景下都相同（差 ≤1 級），固定預留就是答案 → 主張改成「該預留多少」的量測，不做線上規劃器（[08](08_kill_argument.md) §1.2 第 1 點）。

### 5.4 成本

約 6–10 GPU 小時，**量時間、獨佔**（同時間不跑我們自己的其他 job）。

## 6. 篩選閘 C0（方向 C）：能外推的還原方式預測模型（只用 CPU）

### 6.1 問題

G5b 在 32K 準（平均離最好 0.4%），但在 64K／128K（2.7%，最差 20%）、H200 忙時（11.5%）、換 attention kernel（1.21 → 1.33）都會錯。能不能用少數幾個物理量，寫出一個換長度、換負載、換平台、換 kernel 都準的模型？

### 6.2 演算法 C（還原方式預測），論文體

**輸入**：塊數 N；每塊位元組 s；下層有效頻寬 B；重算第 i 塊的時間 f(i)＝f₀＋α·i（依模型、kernel、平台校正）；目前負載下的兩個倍數：重算 m_c、搬運 m_l。
**輸出**：選 Cake 或全部載入；Cake 的會合點 b\*；預估時間。

1. 對每個候選會合點 b，Cake 的時間 T(b)＝max(m_c·Σ_{i<b} f(i), m_l·(N−b)·s／B)＋c₀。
2. 取最小的 b\*；T_cake＝T(b\*)。
3. 全部載入的時間 T_all＝m_l·N·s／B＋反量化時間（也乘負載倍數）。
4. 選時間小的那一個。
5. （可選）用歷史上「預估 vs 實測」的誤差，學一個小的殘差修正（梯度提升樹，特徵只用 N、B、m_c、m_l、kernel、格式）。

### 6.3 資料與檢驗

- 資料：MI300X `m10_restore2`（32K–128K）、H200 `m10_restore2_h200`（report_13）、ICPE P0-1 (b) 的 fa3 格子、P2 的新 seed（11/2 前收齊）。
- **只在沒看過的格子上評分**（四種切法，各自報）：
  - 用 32K 訓練、64K／128K 測；
  - 用閒時訓練、忙時測；
  - 用 MI300X 訓練、H200 測（兩邊各自的微基準先把常數換掉）；
  - 用 sdpa 訓練、fa3 測。
- 指標：選錯的代價（選的 ÷ 最好 −1），平均與最差。

### 6.4 判準（草案）

- **GC-GO**：四種切法的平均代價都 ≤1%、最差 ≤5%（G5b 對照：2.7%／20%、11.5%）。→ 當 A、B 的成本模型；寫成路 2 的一節「什麼時候該重算」的可預測準則。
- **GC-PARTIAL**：只有部分切法過 → 寫清楚它在哪裡失效（例：時間片共用時）。
- 成本：只用 CPU。之後 C1 在 H200 用 4 GPU 小時、獨佔，量 12 個新格子做最後檢驗。

## 7. 篩選閘 D0（方向 D，探索）：模型自帶的稀疏注意力索引，能不能當還原時的挑塊器

依 [L8d](lit/L8d_native_sparse_index_restore.md)：無損版（只讀 indexer 選中的）已被 Janus（2609.36938）做掉，所以 D0 只當 A 的一種挑法來篩。

- 模型：MiniCPM4.1-8B（InfLLM-v2，64-token block，BF16 16.4 GB，1 張 H200）。稀疏路徑只有 HF transformers ≥4.56＋`infllmv2_cuda_impl`（feature_infer 分支）或 CPM.cu；vLLM／SGLang 只跑 dense（L8d §5）。同一份權重可切 dense／sparse，所以原生索引、完整 K 上界、Quest 能在同一份 KV 上比。
- 量法 1（先做）：把「問題的每個 token × 每層 × 每個 KV head」選中的塊取聯集，換算到 512-token 粒度，看聯集佔全部塊的比例。這沒人量過（L8d §0 限制 ii）。
- 量法 2：同 C1a，答案所在塊的 recall@k（k＝1/8、1/4 的塊數），比原生索引、Quest-512、完整 K 上界。
- **GD0**：聯集佔比 >80% → 「只讀被選的」省不了位元組，D 只剩 A 的挑法角色；recall 離完整 K 上界超過 10 個百分點 → 停。
- 成本約 4–8 GPU 小時（品質，不量時間）。
- 注意：換了模型，結果不能直接和 Llama／Qwen 的 A0 比，只能比「挑法離上界多遠」；逐層相依（第 ℓ 層的 indexer query 來自第 ℓ−1 層）讓「一次決定、一次讀回」不能直接套用。

## 8. 寫入端檢查 W0：降級時才壓縮，來得及嗎

- 量：一個 32K 請求在 (i) 16 個 CPU 核、(ii) GPU 側 stream 上，壓成 base＋refinement 的時間；用事先校準的基底（3a 38k：和每題 SVD 分不出差，Llama 同位元組 +0.4 [−1.7, +2.6]）。
- 和「降級的需求速率」比：最壞情況是 HBM 滿了、每秒要降多少 GB。
- **GW0**：CPU 壓縮速度 ≥ 需求速率 → 「降級到慢層時才壓縮」成立，寫入不碰 GPU；否則要在 GPU→CPU 卸載時就壓，而這一步也會受方向 B 的干擾影響，要算進 B0。

### 演算法 B（資源感知的還原計畫），論文體

**輸入**：候選計畫集合 P（還原方式 × 格式的解碼路徑 × 搬法 × 給還原的 SM 比例）；每個計畫的資源需求向量 d_p＝(tensor core 時間, SM 運算時間, copy engine 位元組, HBM 位元組)，由 B0 量出；當下各資源的剩餘比例 r；對其他請求的拖慢上限 Δ。
**輸出**：選定的計畫，以及還原途中是否要改計畫。

1. 探測：每隔 T 毫秒，用引擎自己每一步的時間膨脹率，加上一個極小的探測 kernel，估計 r。
2. 對每個計畫 p，預估時間 t_p＝max_k d_p,k ÷ (容量_k × r_k)，加上固定開銷（瓶頸型的 roofline）。Cake 類計畫的會合點用同樣的速率，依演算法 C 重算。
3. 由 B0 的干擾矩陣查出 p 對背景的拖慢 s_p。
4. 在 s_p ≤ Δ 的計畫中，選 t_p 最小的。
5. 還原途中每完成 k 塊重新探測一次；速率變化超過門檻 θ，就只對剩下的塊重新規劃。

## 12. 風險與對策

| 風險 | 會發生什麼 | 對策 |
|:--|:--|:--|
| A0 的上界不夠大 | 8 倍均勻壓縮已經接近無損（Qwen −0.7），能拿回的只在 ≥16 倍 | 事先寫死 STOP；負面結果本身回答「KV 的重要性有多集中」，可以併進路 1 或路 2 的量測段 |
| BASE-ATTN 挑不準 | 在糊的 KV 上算的 attention 排序跑掉 | A0 同時量 ORACLE 與 BASE-ATTN 的差；不夠再試 D0 原生索引、A-DL1 |

| Slurm 看不到鄰居 | 時間數字被同節點別人的 PCIe、記憶體流量污染 | 配對比較、順序隨機、每點 ≥6 次、`squeue -w` 快照；NFS 量測避開尖峰並記錄 |
