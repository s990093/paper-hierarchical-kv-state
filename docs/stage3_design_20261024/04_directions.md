### 為什麼 B 當主線、A 當副線（10/24 查新之後改的）

- 原本把 A 排主線，是因為它可能同時做到老師三準則的 ② 和 ③。L8a 查到 ReadKV 等已經在 decode 時做到這兩點，A 的新意降成「把它帶到讀回邊界，並量 query 不精確的損失」。
- B 的組合沒有前作，SM 分配這一軸在 12 個 GPU 共用系統裡都沒有；而且 B 正是你原本提的「還原時依當下頻寬、GPU 負載、長度決定」。
- B 過閘的機率也比較高：H200 MPS 的數據裡，背景讓出 13% 的 SM（只用 87%），Cake 從 0.397 s 變 0.127 s（快 3.1 倍），背景吞吐只少 9%（O9），已經接近 GB0-SHARE 的門檻（這是合成背景，真實背景要 B0 量）。A 的上界則可能卡在 2 分的邊緣（[05](05_poc_plan_h200.md) §12）。
- **A 留著，因為它的上檔空間最大**：如果 A0 通過，同答對率下慢層讀的位元組可能少一半以上。兩者也接得起來：在 B 的框架裡，「每塊讀多深」就是計畫的另一個維度。
- 最後誰當論文主軸，由 11/17 的篩選結果照 [05](05_poc_plan_h200.md) §1.1 的決策表決定。

## A　漸進式還原：依新問題決定每一塊讀多清楚（副線）

**一句話**：存一份可以分層讀的 KV；使用者回來時，全部塊先讀粗版，再用新問題挑出少數塊升級。**漏選只會變糊，不會答錯。**

**起（大家以為）**：要少搬就得二選一。
- 一條路是**均勻壓縮**（KVTC、xKV、CacheGen、KVServe）：每塊同樣倍數，倍數高了全部一起糊。
- 另一條路是**選擇性載入**（Quest、IMPRESS、ShadowKV、LOCKS）：選對就省，選錯的塊就不見了。
- 兩條路的前提都是「每一塊的精度，要嘛寫入時定，要嘛讀取時只有載／不載兩種」。

**承（我們量到）**：
- 均勻壓縮：8× 接近無損，到 24–32× 掉 4–8 分（O5）。
- 選擇性還原：Quest 放回一半就掉 8–12 分；但用完整 K 挑，Qwen 只放回 1/4 也不掉（O4）。所以**重要的塊很少，但漏掉一塊就錯**。
- 重要性在寫入時猜不到（只比隨機好 11–24 分），問題來了才猜得到（O3）。
- 跨層低秩的基底有序、可截斷，而且可以事先校準（O6）：天生就是「先讀前 r 個成分，需要再補」的格式。

**轉（為什麼）**〔判讀〕：attention 對多數塊只需要「大致的位置與量級」，讓 softmax 的分母和背景脈絡正確；只有少數塊需要精確的內容。把沒挑中的塊丟掉，會同時破壞這兩件事；只讓它變糊，只會小幅影響分母。

**合（所以提出）**：
- 寫入端：降級到慢層時，存成 base（例：32 倍）＋refinement（INT4 或 BF16）。
- 讀取端：照 [05](05_poc_plan_h200.md) §4.3 的演算法 A：全部讀 base → 用 base 跑新問題 → 依 attention 挑塊 → 只讀挑中塊的 refinement。
- 和已有的東西接起來：
  - 和 Cake 接：前段本來就重算成 BF16，只有後段需要分級讀。
  - 和 3b 的打字預取接：打字時先讀 base；按下送出、有了新問題，才決定補哪些塊（O12）。

**老師的三準則**：
- ② 讓取捨消失：選擇性還原的「省 vs 漏」不再是取捨，因為漏了只是糊。
- ③ 換抽象層：問題從「寫入時給每塊多少位元」（一次定死、要猜未來），變成「讀取時在預算內挑要升級的塊」（背包問題，資訊齊全）。

**貢獻（如果 A0／A1 通過）**：
1. 一個量測：KV 的重要性在新問題下有多集中（oracle 上界隨模型、長度、倍數怎麼變），以及在粗版上算的 attention 能不能挑對。
2. 一個機制：讀取時、跨下層、多輪的漸進式還原，同位元組下比均勻壓縮好、沒有選擇性還原的懸崖。
3. 一個設計原則的實證：「寫入只存可分層讀的格式，決定延到讀取」。這延續路 1 的負面結果，把它變成正面的設計。

**前人與新穎性**（[L8a](lit/L8a_progressive_query_aware_restore.md) 全文查新後**下修**；詳見 [03](03_competitors.md)）：
- **表示法本身已經被發表，不能當新意**：
  - ReadKV（arXiv 2610.11245，2026-10-08）：每個 K／V 存成 8-bit 漸進碼；decode 時由 query 決定 K 每個 channel 讀幾位，再用重建 K 的注意力決定 V 每個 token 讀幾位；沒讀的保留。Discussion 提到可延伸到慢速層（L8a §0 引 p.15）。
  - Xie et al.（2503.18869）：記憶體控制器把 KV 存成 bit-plane；分頁混用 BF16／FP8／FP4 只出現在一個動機用的困惑度實驗（V8 更正：原文沒有 Quest 排名、沒有「排名外不讀」）。只算 bit-plane 存放的前例。
  - Fathom（2609.17652）：host memory 上的 bit-plane K，由每個 query 決定讀幾個 plane，但只用來選 top-k。
  - AnchorKV（2608.02901）、MiKV：每個 token 都留粗表示、只精修一部分（「沒有位置離開 softmax」）；選擇在寫入時（prefill 結束）就定。
  - CacheGen §9（p.12）早就提出「像 SVC 一樣漸進串流 KV」當未來工作。
  - 所以**不能宣稱「首次提出漸進式 KV 讀回」或「不丟塊」**。
- **還剩的缺口**（L8a §0 第 4 點）：所有這些都在 decode 時、HBM／DRAM／host memory，而且 query 都來自精確的 prefill 或精確的 decode。沒有人在**多輪讀回的那一刻**，用**新問題在粗版 KV 上跑 prefill 得到的注意力**，決定從**慢層（SSD／NFS）**替哪些**塊**補讀精修層，並在 **TTFT 期限**內和**重算（Cake）**一起排程。
- **最乾淨的新知識**：「query 本身是在粗 KV 上算出來的」時，挑塊的 recall 會掉多少。第 ℓ 層的誤差會傳到第 ℓ+1 層的 query，沒有任何論文量過（L8a §0 第 6 點）。
- **設計上的警告**（L8a §0 第 5 點）：只放低秩係數的 base，在高資訊密度任務上可能挑錯（2604.08426 §4.1：ShadowKV 的 rank-160 SVD K 壓縮，多載 10 倍 token 仍追不上 full attention；§4.3：逐 token 2-bit K 做選擇勝過低秩代理；Fathom Table 7：塊 landmark 在 128K 掉 0.130）。逐 token 的低位元 K 排序比較準。→ A0 要加一種「逐 token 2-bit K＋低秩 V」的 base。

**下修後的定位**〔判讀〕：A 的貢獻從「新表示法」變成「新邊界上的機制＋一個沒人量過的現象」：
1. 量測（R1）：在粗 KV 上跑新問題，挑塊的準確度會掉多少；KV 的重要性在讀回邊界有多集中。
2. 機制（R2，限定在讀回邊界）：從慢層、以塊為單位、有期限、和 Cake 合用的查詢導向精修。
3. 老師的三準則裡，② 和 ③ 在 decode 時已經被 ReadKV／AnchorKV 做到；我們只能說「把它們帶到讀回邊界，而且在那裡要解決 query 不精確的問題」。新意從「中高」降為「中」。

**方法組成**（使用者要的「約 1/3 經典、要有 DL」）：
- 經典：漸進式編碼（successive refinement、嵌入式編碼、可分層影片編碼 SVC）；有期限的背包問題與 anytime 演算法（時間到就停，拿到的永遠可用）。
- DL：學的挑塊器（A-DL1）；選做：殘差向量量化的 codec（多層 codebook 天生是漸進的）。
- 系統：分級讀取的位元組帳、和 Cake 的三線管線、vLLM 的降級時壓縮。

**最小證偽**：A0 的 oracle 在同位元組下比均勻壓縮好不到 2 個百分點 → 停（GA0-STOP）。

**風險**：
- 8× 均勻壓縮已接近無損（Qwen −0.7），好處可能只在 ≥16 倍、慢層、長 context、Llama 這些區域。
- 在糊的 KV 上算的 attention 可能排序跑掉（GA0-SEL 量）。
- decode 途中 attention 會漂移，可能需要生成時再補（C1b 的補載補回 1–14 分，可以借用）。

## B　資源感知的還原：還原成本是現場的資源向量（主線）

**一句話**：還原的每種做法吃不同的 GPU 資源；當下誰在搶哪一種，決定哪個計畫最快、要分多少 SM 給還原。

**起（大家以為）**：還原成本是硬體的常數，離線量一次就好。
- HCache 用離線 profile 定切分；Tutti 用離線的 slack 表；KVServe 把 GPU 負載當誤差慢慢吸收；Cake 只調切點、不換格式。
- 原始 Tiara 的主張「κ 跨硬體變 32 倍」也是把 κ 當成每張卡一個數。這一點 FSL-26-02 已經說過。

**承（我們量到）**：
- 同一張卡上，κ 隨負載變，而且各種做法變得不一樣多：重算 ×1.97，反量化 ×2.4–3.8，低秩重建 ×2.8（O7）。
- 最快的格式在算力型背景下翻轉（3／6 條），在頻寬型背景下不翻（0／6）（O8）。
- H200 上用 MPS 空間共用時：背景佔滿 SM，Cake 要 0.397 s；把背景限在 75% SM，Cake 變 0.076 s，背景吞吐剩 0.78（O9）。
- 時間片輪流和空間共用的結論完全不同（02 §2）。

**轉（為什麼）**〔判讀〕：搬運主要吃 copy engine 和 PCIe；反量化吃 SM 的運算與 HBM；低秩重建與重算吃 tensor core。背景是 decode 時搶 HBM，是 prefill 或大批次時搶 tensor core（[圖 3](figures/fig3_resource_vector.svg)）。這就是 roofline 的瓶頸觀點：哪個資源被佔，用那個資源的做法就變貴。

**合（所以提出）**：
- 把還原計畫寫成「資源需求向量」，用輕量探測估當下各資源還剩多少，選瓶頸時間最小、又不拖慢別人超過上限的計畫（[05](05_poc_plan_h200.md) 演算法 B）。
- **SM 分配本身是計畫的一部分**：給還原多少 SM，和選哪種格式、哪個切點一起決定。

**老師的三準則**：① 量到「同一張卡的 κ 隨現場資源變、而且排序會翻」，推翻「離線量一次」的假設。

**貢獻（如果 B0／B1 通過）**：
1. 第一份「真實服務背景 × 還原動作」的干擾矩陣（H200，同 process 雙 stream 與 MPS 兩種共用）。
2. 一個瓶頸型的還原計畫選擇器，把 SM 分配也納入。
3. 對前人的更正：還原的最佳做法不是平台常數。

**前人與新穎性**（L7b＋[L8b](lit/L8b_contention_aware_restore.md) 全文查新；詳見 [03](03_competitors.md) §2）：
- **整個組合沒查到**：用當下量到、按資源拆開（SM／tensor core、HBM、copy engine／PCIe）的爭用，**聯合**選 recompute／load 切分、格式的解碼路徑、copy engine 或 SM 搬運、SM 配額、多個還原的順序。「算力型背景翻、頻寬型背景不翻」也沒人報過（L8b §0 一）。
- **但每一軸都有局部前例，主張要避開**：
  - Cascade（arXiv 2608.06557，UBC＋Azure Research＋NVIDIA）：用每個請求的延遲預算決定從各層搬回多少位元組、其餘重算（§IV-C Eq. 6–7）；負載只看 active decode 數（§IV-B），爭用塞進離線固定的係數 γ（Eq. 3）；沒有格式、路徑、SM；主要結果來自模擬器。
  - Bidaw（FAST'26）：依「等待時間／KV 大小」排讀取順序（§3.2）；把重建 KV 的運算放在低優先權 stream，**理由是假設 SM 有空閒**（§4 p.10）。我們量到忙時這個假設會壞（低秩重建慢 2.8 倍）。
  - vLLM PR #42212（已合併）：依 payload 大小在 copy engine 和 SM kernel 之間選路，門檻 28 KiB、固定用 12 個 SM，都是靜態常數。
  - py-kvcache（arXiv 2609.11744）把「動態估計與爭用」列為未來工作（§10.2 p.22）→ **有被搶先的風險**。
  - KVServe：GPU 負載只用 EWMA 殘差吸收；HCache、Tutti：離線定一次；ShadowServe、KVCodec：用硬體隔離避開。
- **SM 分配這一軸最乾淨**：L8b 查的 12 個 GPU 空間共用系統（LithOS、Orion、REEF、Paella、MuxServe、semi-PD、Bullet、MuxWise、NanoFlow、POD-Attention、RAPID-Serve、Hummingbird）**沒有一個把 KV 載入、還原或反量化放進 SM 分配**（L8b §0 三）。
- 主張只能寫成：「還原成本不是硬體常數，是隨當下爭用類型而變的資源向量；最好的計畫會翻轉」。不能寫成「第一個做載入／重算切分」或「第一個做 SLO 感知的還原」。

**方法組成**：
- 經典：roofline／瓶頸分析；Bubble-Up（MICRO'11）、Paragon（ASPLOS'13）的「敏感度 × 壓力源」框架（L8b §0 五：Paragon 用 10 種壓力源各一個微基準），正好對應「每種還原格式 × 每種資源壓力」的矩陣；DMA 對 programmed I/O 的老取捨（L8b 引 arXiv 2409.08141：約 1 KiB 以下 PIO 勝過 DMA），對應 copy engine 對 SM 驅動的搬運。
- DL：選做，用引擎的遙測學干擾倍數，和解析模型比。
- 系統：同 process 雙 stream、stream 優先權、MPS／green context 的 SM 分配。

**最小證偽**：B0 在真實背景下既沒有翻轉、分 SM 也換不到 ≥30% → 降級成一節量測（GB0）。

**風險**：
- 真實服務的背景大多是 decode（頻寬型），翻轉可能不出現。這時只剩 SM 分配。
- Slurm 下看不到同節點別人的負載。
- 線上探測本身有成本。

## C　能外推的還原方式預測（基礎元件）

**一句話**：用每塊位元組、下層頻寬、重算曲線、兩個負載倍數，預測該用 Cake 還是全部載入；換長度、換負載、換平台、換 attention kernel 都要準。

**起**：Cake 讓兩條線自己跑到會合；G5b 用 32K 的量測估兩種做法的時間。

**承**：G5b 在 32K 平均離最好 0.4%，但 64K／128K 平均 2.7%、最差 20%；H200 忙時 12 格錯 10 格（11.5%）；換 fa3 之後 1.21 → 1.33（O10）。

**轉**〔判讀〕：G5b 少了三個變數：長度（重算是 O(i) 遞增）、負載（重算和搬運被拖慢的倍數不同）、kernel（斜率 0.473 → 0.210 ms／塊）。

**合**：[05](05_poc_plan_h200.md) 演算法 C。只在沒看過的格子上評分。

**三準則**：不強；這是「可預測的準則」型貢獻（使用者 10/4 說想做的那種），也是 A、B 的地基。

**貢獻**：一個外推驗證過的「什麼時候該重算」的準則。可以併進路 1 的討論，或路 2 的一節。

**前人**：Cake 的會合點是自然形成的，沒有估計器；CacheFlow 有 DP 但假設互不干擾；FSL-26-02 有 1,764 組硬體的模型但沒有負載。

**最小證偽**：四種切法平均 ≤1%、最差 ≤5% 不成立 → 寫清楚在哪裡失效。

## D　模型自帶的稀疏注意力索引當挑塊器（探索）

**一句話**：新一代模型訓練時就學會挑塊；把它的索引借來當還原時的挑塊器，可能補上「便宜的索引挑不準」這個洞。

**起**：選擇性還原要有索引；便宜的（Quest 摘要、共用基底的低秩 K）都不準（C1b、LOCKS、YAKV）。
**承**：完整 K 的上界很好（O4），差在索引。
**轉**〔判讀〕：DeepSeek 的稀疏注意力（DSA）、NSA、MiniCPM4 的 InfLLM-v2 都有訓練過的選塊機制，而且索引很小。依 [L8d](lit/L8d_native_sparse_index_restore.md) §2：DSA 每 token 每層 132 B（約 BF16 MLA KV 的 11.5%），InfLLM-v2 40 B（約 3.9%），放得進 GPU。

**L8d 查新之後，D 要收窄**：
- **無損版已被做掉**：Janus（arXiv 2609.36938，2026-09-29）用模型自己的 indexer、從 SSD 只讀要用的條目、多輪 append prefill；用較早層的 hidden state 預測（recall >96%），漏掉的再補讀，整體無損。對「原生稀疏模型的無損還原」是**完全重疊**（L8d §0、§3）。〔待 verifier 抽查〕
- **三個硬限制**（L8d §0）：
  - 逐層相依：第 ℓ 層的 indexer query 來自第 ℓ−1 層的輸出，所以「先算好要讀哪些塊、再從 NFS 一次讀回」不能直接套用。
  - 粒度：DSA 是 token 級 top-2048，InfLLM-v2 是 64-token block；換到我們的 512-token block 後，union 可能接近全部 block。這沒人量過。
  - Llama、Qwen 這類 dense 模型沒有原生索引。
- 原生 indexer 本身也不是精確 top-k 的好近似：DeepSeek-V3.2-Exp 在 HELMET 128K 上和逐 head 精確 top-k 的重疊平均約 60%（L8d §0 引 Native Top-k study §3 p.5）。

**合（收窄後）**：D 不再當獨立方向，改當 A 的**挑法之一**，並且只在 Janus 沒做的地方：
- 沒被選中的塊用粗版讀，而不是不讀（＝A 的分級）；
- 低於 exact union 的有損預算，以及它的品質–位元組曲線；
- 512-token、NFS 粒度下 union 有多大。
- 模型：MiniCPM4.1-8B（InfLLM-v2，BF16 16.4 GB，1×H200；同一份權重可切 dense／sparse，所以原生索引、完整 K 上界、Quest 能在同一份 KV 上比）。稀疏路徑只有 HF transformers＋`infllmv2_cuda_impl` 或 CPM.cu，vLLM／SGLang 只跑 dense（L8d §5）。
**最小證偽**：D0 先量 512-token 粒度下 union 佔全部塊的比例；>80% → 「只讀被選的」省不了位元組，D 只剩 A 的挑法角色。recall 離完整 K 上界超過 10 個百分點 → 停。
**風險**：換模型後和 Llama／Qwen 的結果不能直接比；HF 路徑比 vLLM 慢，只能量品質、不能量時間。

## E　高併發時的降級還原（延伸）

**一句話**：很多人同時回來時，先給每個人粗版、有空再補細版，用一點品質換掉排隊的尾巴。

**起**：尾延遲靠排程（SRPT、優先權）或擴容解決。
**承**：p99 的 98% 是排隊（O11，模擬）；I3g 的 NFS 層，回來那一輪 P95 到 105 秒（實測）。
**轉**〔判讀〕：A 讓每個請求有兩個可交付的版本（粗版、細版）。排隊時先交付粗版，等於把服務時間砍掉一大截。這是 web 系統的 brownout：高負載時暫時關掉可選的內容。
**合**：兩級的 I/O 佇列（所有人的 base 優先，refinement 次之）＋品質預算。
**三準則**：② 讓「尾延遲 vs 品質」從全有全無變成可調。
**前人**（L8b §0 六）：有依大小或 slack 排還原順序的（Bidaw 的 HRRN、Cascade 的最少剩餘預算優先、Nuska、TokenFlow）；有依負載降品質的（MorphServe 高負載時換量化層、OrbitFlow 延後大請求）。**沒查到依當下爭用改還原格式或精度的 brownout。**
**最小證偽**：在同樣的品質預算下，p99 改善 <15% → 不做。
**風險**：**同一個問題在不同負載下答案不同**，違反「快取命中和不命中輸出相同」的產品承諾。所以只當延伸，主設定一律固定預算。
