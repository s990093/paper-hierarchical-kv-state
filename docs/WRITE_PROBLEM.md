# 寫入問題：寫入時決定「不存」，要看讀取時的 GPU 負載

> 狀態：問題定義＋文獻核對，還沒有實測。2026-10-04。
> 標註：〔原文〕論文原句或原表；〔算術〕用實測常數代公式算的，不是量測；〔推論〕我的判讀。
> 上游：`DIRECTION_CAKE_EXTENSION.md` §11.6 的問題 2。

---

## 1. 一句話

Cake 和 CacheFlow 都在**讀取時**才決定哪一段重算、哪一段載入，所以 GPU 忙不忙，讀取當下就知道。如果把這個決定提前到**寫入時**（前段不存，省容量和寫入），寫入時並不知道之後讀取時 GPU 會多忙。GPU 一忙，沒存的前段只能用剩下的算力硬算，TTFT 會變差好幾倍。

## 2. 問題長什麼樣

- **讀取時**（Cake、CacheFlow）：GPU 從前面重算，I/O 從後面載入，在兩邊累積時間相等的地方會合。GPU 越忙，會合點越往前，重算的部分越少。
- **寫入時**（本方向 §5 的原始設計）：用「GPU 全空」算出會合點，會合點之前的前段不存。
- **出事的情況**：讀取時 GPU 只剩一部分（例如在服務別人的 decode）。這時最佳的會合點應該更前面，但前段已經沒存，I/O 載不到，只能全部由 GPU 重算。

## 4. CacheFlow 全文精讀（arXiv 2604.25080 **v2**，2026-09-26）

Nian、Shen 等，UIUC（Fan Lai 組）＋CMU。PDF：`papers/cacheflow2026.pdf`（不進 git）。程式碼：「upon acceptance」才釋出〔原文〕。

### 4.1 它做了什麼

把 KV 還原看成「在 token、層、GPU 三個維度上平行執行」的問題〔原文〕：

1. **Token 維度**：跟 Cake 一樣，前段重算、後段載入、中間會合。
2. **層維度**：前面幾層重算整段，後面幾層載入，在某一層會合（類似 HCache）。好處是 kernel launch、權重搬移這類固定成本每層只付一次。短 prefix 時層維度較快，長 prefix 時 token 維度較快（Llama-3.1-8B，交叉點約 36K）〔原文 Fig. 2〕。
3. **兩者合起來是「階梯」**：每個層區塊 i 重算前 j_i 個 chunk，j_1 ≥ j_2 ≥ … ≥ j_L。全部相等就是 token 維度，前幾層全算、其餘全載就是層維度〔原文 式 1〕。
4. **GPU 維度**：模型切在多張卡上時，在切點多存一份「邊界 activation」，下游的卡就不必等上游，可以同時還原〔原文 §3.1〕。
5. **批次感知的 DP 規劃器**：D_i[x] ＝ 前 i 個層區塊「省下 x 位元組傳輸」所需的最少重算時間；最後挑讓 max(重算時間, 剩餘傳輸 ÷ B) 最小的 x。同一套 DP 可以把一整批請求的所有（請求, 層區塊）放在一起規劃，讓它們共用 GPU 與 I/O〔原文 式 3–5〕。
6. **重算成本用線上量測**：從最近的服務紀錄收集 f(j)，沒看過的長度用內插〔原文 §3.2〕。
7. **hybrid 模型**：Qwen3.5 的 GDN 層有固定大小的 recurrent state。只重算一部分的話，最後的 state 還是要載入，除非整段重算〔原文〕。128K 時，full-attention 層的狀態比 recurrent checkpoint 大 125 倍（Qwen3.5-35B-A3B）與 250 倍（Qwen3.5-9B）〔原文〕。
8. **理論**：DP 跟理想最佳解的差距是 O(1/N)。Qwen3.5-9B、10 Gbps 時，差距最多 19.5 ms，占 32K／64K／128K 的 6.52%／3.26%／1.63%〔原文 Prop. 1〕。

### 4.2 實驗設定與結果〔原文〕

- **平台**：A100、H100（單卡與多卡）；vLLM v0.29.0＋LMCache v0.5.5rc5。
- **模型**：Llama-3.1-8B、Qwen3.5-9B、Qwen3.5-35B-A3B、Qwen3.5-122B-A10B。
- **負載**：LMSYS-Chat、SWE-Bench、OSWorld 2.0；線上用 Mooncake 的到達時間。
- **頻寬**：80／40／10 Gbps，預設 10 Gbps。原文沒說是真實裝置還是限速。
- **對手**：vLLM（只算）、LMCache（只載）、Cake。
- **結果**：
    - TTFT 平均快 2.24–3.00 倍，TTLT 快 1.64 倍；
    - 資源使用：GPU 89%、I/O 89%（LMCache 的 GPU 只有 1%，vLLM 的 GPU 98%）；
    - 對 Cake：40 Gbps 快 2.63 倍、80 Gbps 快 2.40 倍；H100 快 2.69 倍、A100 快 2.07 倍；batch 1／4／8 都約快 2.8–2.9 倍；
    - **預測準確度**：92% 的重算預測、98% 的載入預測誤差在 10% 內；95% 的還原，重算與載入在 10% 內同時完成；
    - 規劃器成本：中位數占 TTFT 的 0.019%，p99 占 0.34%。

### 4.3 它沒處理的地方

| 項目 | CacheFlow | 證據 |
|---|---|---|
| **要不要存（寫入時決定）** | ❌ 沒有。假設所有狀態都存好、可以載入；被逐出的狀態在 DP 裡設成無限大成本，只能重算 | 〔原文 式 3 下方、附錄 A.1「target caches are loadable」〕 |
| 讀取時 GPU 被其他工作佔用（decode、沒快取的 prefill） | ⚠️ 只處理「同一批正在還原的請求」之間的競爭；理論假設「一個計算資源、一個載入資源，互不干擾」 | 〔原文 附錄 A.1〕 |
| 一次還原過程中資源變動 | ⚠️ 只靠線上量測的 f(j) 慢慢適應；沒有像 Cake §5.6 那樣測資源波動 | 〔原文 §3.2〕 |
| 傳輸的每筆固定成本 | ❌ 載入時間 ＝ 位元組 ÷ B。固定成本只在「計算」那邊討論（用來支持層維度） | 〔原文 式 2、§3.1〕 |
| 多個儲存層 | ❌ 只有一個載入頻寬 B | 〔原文 式 2〕 |
| KV 精度（量化） | ❌ 量化只在相關工作提到 | 〔原文 §2〕 |
| 非 NVIDIA 平台 | ❌ 只有 A100、H100 | 〔原文 §4.1〕 |
| 何時不值得做 | ❌ 所有設定都報加速，沒有失效區 | 〔原文 §4〕 |

另外，CacheFlow 還**多存**東西（邊界 activation），方向跟「少存」相反。

## 5. 對我們方向的影響

**被拿走的**〔推論〕：
- 「讀取時的雙向還原＋可預測的成本模型」：CacheFlow v2 已經有階梯式 DP、線上量測的成本、批次規劃，還報了預測準確度。`DIRECTION_CAKE_EXTENSION.md` §11.2 的貢獻 2（可預測的成本模型）大半已經被做掉。
- hybrid 模型的還原：CacheFlow 已經處理 Qwen3.5 的 GDN。§10.8「要不要碰 hybrid」又多了一個已有的工作。

**還空著的**〔推論〕：
1. **寫入時的決定**：存不存、存哪一層。CacheFlow 只在讀取時規劃，被逐出的狀態只能被動重算。
2. **寫入決定對讀取時 GPU 負載的穩健性**：本文件 §3 的問題。CacheFlow 的理論假設資源互不干擾，沒有碰到。
3. **多層＋每筆固定成本＋精度**：CacheFlow 只有一個 B，傳輸是「位元組 ÷ 頻寬」，正好是 L2 共同問題的第一條。
4. **失效地圖與非 NVIDIA 平台**：CacheFlow 全部設定都報加速。

**建議**：
- 把**寫入問題**當主軸：「讀取時的規劃（Cake／CacheFlow）已經很好；但寫入時要存什麼，取決於讀取時會有多少 GPU。」
- 讀取端直接把 CacheFlow 當成上界和 baseline，不要自己再做一個讀取規劃器。它的程式碼還沒釋出，所以實驗上先用 Cake 式 token 維度實作，論文中說明 CacheFlow 的層維度會讓寫入問題變成二維（哪些 token × 哪些層不存），這是延伸。
- 預測模型降為工具，不當主要貢獻；主要貢獻是寫入規則及其穩健性。
