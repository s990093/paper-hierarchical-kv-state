## 一頁看懂

1. **場景**：使用者和聊天機器人或 agent 對話，兩則訊息之間常隔幾秒到幾分鐘。這段時間，服務端把這段對話的 KV cache 移出 GPU，放到 CPU 記憶體或更慢的儲存。使用者再發問時，KV 要先回到 GPU，畫面才會出現第一個字。一段 32K token 的 Llama 對話，KV 有 4.0 GiB [M1]。
2. **三個問題，一個接一個**：第一，不加任何預測時，KV 該怎麼送回、存成什麼格式？答案會不會因情況改變？第二，GPU 同時在跑別的工作時，要保留多少 GPU 給送回？第三，在前兩題的固定做法之上，再加預測或更複雜的機制，還能省多少？
3. **方法**：一張 H200、兩個 7–8B 模型、三份真實的使用紀錄（trace）；「值得做」的門檻在看到數字前就登記。送回方式與格式直接在 GPU 上量（32K token 的一次送回）。GPU 共用與預測用模擬計算，再在 GPU 上跑一個縮小版檢查：不算排隊時間時，實測÷模擬＝0.911–0.987，模擬給的排名和實測相同 [B6]。
4. **該怎麼送回**：放在慢速儲存層（本文的 b32、b48、NFS 級）時，INT4 加 Cake 最快，比次好的做法快 11.0–40.7% [M1]。放在 CPU 記憶體時，關鍵是 4 位元的資料怎麼解壓：整段讀完再一次解壓，整段載入最快；每讀一塊就解壓一次（GPU 忙時），Cake 比較快。同一種做法只因解壓方式不同，就差到約 6.8 倍 [M1、M3-g、E3]。整段重算在 32K 時從來不是最好 [M1]。
5. **答案穩定**：在測過的條件下，不論重算變快，或 GPU 同時跑著像真實服務的背景工作，最快的做法都沒換；所以事先查一張表就夠 [A5、M3]。
6. **GPU 共用**〔模擬〕：GPU 同時在跑別的工作時，改用 MPS 讓送回和別的工作一起跑（先不限制別的工作），第一個字出現前的等待，比單純共用（各用一條 stream）縮短 30.7–62.9%，別的工作的處理量最多只少 6.5 個百分點。若再限制別的工作、替送回保留更多 GPU，回答會更快，但別的工作會更慢；要保留多少，看各自更在乎哪一邊 [S2、M4]。
7. **再加預測**〔模擬〕：在真實的 agent 服務紀錄 FreeInference（前 6 週）上，就算預測完全準確，在測過的每種 CPU 記憶體大小都省不到 15% [B3-X1、B3-T5]。在另一組公開紀錄 Mooncake 上，192 種組合裡有 36 種能省 15% 以上；這已扣掉「紀錄太短」造成的假象，也不算慢層寫不完的情況 [B9]。其中「先把資料搬回來」這一項，用「使用者開始打字」這個免費訊號，就能拿到完美預測約八成的好處 [C2-GPU]〔待決〕。
8. **其他機制**：漸進還原（先送最重要的部分）、近似重算、借用別的工作的算力，都沒過登記的門檻；借一張閒著的鄰卡多開一條搬運路徑過了，兩張卡時快 1.99 倍，但只量了 2 張卡 [G-A0、G-M12、G-M08、G-M06]。

## 摘要

多輪對話與 AI agent 的每一輪，都會帶著前面的整段對話送進模型。為了不重算前面的內容，服務系統會把算好的中間結果（KV cache）留著；GPU 記憶體不夠時，就把它移到 CPU 記憶體或更慢的儲存。使用者送出下一句話時，系統得先把這份 KV 搬回 GPU 或重新算出來，回答的第一個字才會出現；這段等待就是 TTFT。

搬回來的做法很多：整段載入、整段重算，或一邊重算前段、一邊載入後段（Cake）；KV 可以存原本的 16 位元，也可以壓成 4 位元（INT4）；GPU 同時在跑別的工作時，還能用 MPS 替「搬回」保留一部分 GPU。在這些之上，還可以再加預測（例如事先猜誰會回來），或其他更複雜的機制。哪一種組合、在什麼情況下最好，並不清楚。

我們在一張 NVIDIA H200 上，用兩個 7–8B 的模型量測這些選項；「值得做」的門檻在看到任何數字之前就登記好。結果有三點。

第一，資料放在哪裡，決定該怎麼搬。放在慢速儲存層（本文的 b32、b48 與 NFS 級）時，INT4 加 Cake 最快，比次好的做法快 11.0–40.7%。放在 CPU 記憶體時，要看 4 位元的資料怎麼解壓：同一種做法，只因解壓方式不同，就差到約 6.8 倍。在 32K token 的量測裡，整段重算從來不是最好的。這些排名在測過的條件下，GPU 變忙、重算變快都沒有改變，所以照一張固定的表選就夠。

第二，GPU 要和別的工作共用時，改用 MPS 讓搬回和別的工作一起跑，第一個字出現前的等待縮短 31–63%，別的工作的處理量最多只少 6.5 個百分點（模擬）。若再限制別的工作、替搬回保留更多 GPU，回答越快、別的工作越慢；要保留多少，由各自的需求取捨。

第三，在這張表之上再加預測，只在某些工作負載上划算（模擬）。在真實的 agent 服務紀錄（FreeInference）上，就算預測完全準確，省下的時間也不到 15%。在另一組公開紀錄（Mooncake）上，192 種組合裡有 36 種能省 15% 以上；其中「先把資料搬回來」這一項，用「使用者開始打字」這個免費訊號，就能拿到完美預測約八成的好處。其他機制裡，漸進還原、近似重算、借用別的工作的算力都沒過門檻；只有借一張閒著的鄰卡多開一條搬運路徑值得做，兩張卡時快 1.99 倍。

對設計者來說：先依資料所在的層與解壓方式查表，選定格式與搬法；要不要蓋預測器，應該先在自己的工作紀錄上量出「完美預測能省多少」，再決定。

## 1 引言：先畫地圖，再問固定的表之上還缺什麼

**停放的 KV 該怎麼送回，可以寫成一張表：只要知道 KV 停在哪一層、GPU 忙不忙、用哪個模型、INT4 用哪種解壓實作，就查得到答案。GPU 要和別的工作共用時，改用 MPS 能讓回答快很多，但替送回保留得越多，別的工作就越慢。在這張表之上，預測只在部分 trace 上值得加 [M1、M3、M4、B3-T5、B9]。**

聊天與 agent 讓同一段對話在幾秒到幾分鐘後又回來。GPU 記憶體要留給正在生成的請求，所以服務系統把等待中的對話的 KV 移到 CPU 記憶體或更慢的儲存（§11）。使用者回來時，系統要先把 KV 送回 GPU，才能開始算新訊息；這段等待使用者看得到，就在 TTFT 裡。

業界從幾個方向縮短這段等待：改送回的方式、把 KV 壓小、只讀重要的部分、多一條路或提前開始，還能調整 GPU 分給送回的比例（§11）。每個方向都有系統報告收益，但比較的對象各不相同，而且大多一次只看一個方向。設計者要的是另一件事：手上的條件該選哪個組合，再加什麼才值得。

本文回答三個問題。第一，不加預測時，送回方式（全部載入、全部重算、Cake）與格式（BF16、INT4、低秩）怎麼選，這個選擇會不會隨情況改變（§4、§5）。第二，GPU 要和別的工作共用時，要保留多少 GPU 給送回；回答因此快多少，別的工作因此慢多少（§6）。第三，在固定的做法之上，再加預測（寫入時、回來時）或更複雜的機制（漸進、近似重算、借算力、多一條路徑），還能省多少，能不能用免費的訊號代替預測（§7、§8）。第二題在第一題的表上加 GPU 資源這個條件。第三題建立在第一題的發現上：§5 顯示一張固定的表就夠，所以第三題問的是這張表之上還缺什麼。

**貢獻**：
1. **組合地圖與穩定性**：在兩個模型、六種存放層、GPU 閒與忙的每一種情況下，量出哪個組合最快、比第二名快多少，全部在 GPU 上量；CPU 層的答案取決於 INT4 的解壓實作；換了條件之後，最快的做法在測過的範圍內都沒換（§4、§5）。
2. **GPU 共用的取捨**：改用 MPS 讓送回和別的工作同時跑時，回答快了多少；若再限制別的工作、替送回保留更多 GPU，別的工作又慢了多少；以及登記時的判定（§6）。
3. **固定做法之上的增量**：在三份真實 trace 上，用完美預知（oracle）算出預測最多能省多少，並在 GPU 上檢查模擬；其他機制各自和事先登記的門檻比（§7、§8）。
4. **決策流程**：把三個答案依序整理成設計者可以照做的流程（§9）。

## 2 背景：KV 從哪裡回來、要等多久

**本節說明要選的東西：KV 有多大、停在哪、回來時有哪些送法（圖 2）。**

**KV cache 是什麼**。模型讀過的每個 token 都會留下一組中間結果，叫 KV；下一則訊息要接著這些結果算，才不用重讀整段對話。KV 隨對話變長：32K token 時，Llama-3.1-8B 的 KV 有 4.0 GiB，Qwen2.5-7B 有 1.75 GiB（BF16）[M1]。

**它為什麼離開 GPU**。使用者在打字或在看回答時，這段 KV 只是佔著 GPU 記憶體。主流的服務引擎都會把它移到 CPU 記憶體；CPU 記憶體滿了，再移到 SSD 或遠端儲存，或直接丟掉（§11）。本文的 SSD 級與 NFS 級是限速模擬；這兩組頻寬常數沿用先前在另一個平台（MI300X）上量到的值，H200 上沒有重量 [§0]。

**使用者回來時**。系統有三種送回方式。全部載入：把存的 KV 整段搬回。全部重算：在 GPU 上把整段對話重讀一次。Cake：GPU 從第一塊往後重算，同時從儲存層從最後一塊往前載入，兩邊相遇就完成（圖 2(a) 右上）。儲存層越慢，會合點越靠後，GPU 算的部分越多。

**TTFT**。從使用者送出下一則訊息，到看到回答第一個字的時間。它包含送回 KV 的時間，加上算新訊息的時間（prefill）；在忙的服務裡還有排隊。§4 的地圖只量送回這一段。

**還不知道的事**。送回方式、格式、GPU 分配、預測與其他機制可以疊在一起（圖 2(b)），但哪個組合在哪種條件下最好、再加東西值不值得，沒有一張共同的表（§11）。

## 3 方法：怎麼判斷「值得」

**送回的組合在 GPU 上直接量；GPU 共用的端到端與預測用 trace 模擬，再在 GPU 上檢查模擬（圖 3）。**

### 3.1 兩種量法與「值得做」的標準

- **GPU 微基準**〔實測〕：一次送回一段 32K 的 KV，量送回時間（不含新訊息的 prefill 與排隊）。每種做法重複 10 次（CPU、b32、NFS 級）或 30 次（b16、b48），取中位數 [M1]。§4、§5、§6 的微基準與 §8 的機制用這種量法。
- **trace 模擬**〔模擬〕：照真實 trace 的時間一次送一個請求，算回來請求的平均 TTFT；成本常數來自 GPU 微基準 [§0]。模擬是確定性的，每格跑一次。§6 的端到端與 §7 的預測用這種量法。

「值得做」的標準在看到任何數字之前就寫進登記檔：一個做法要快超過 5% 才算有改進（該實驗的量測雜訊比 5% 大時，就用雜訊當門檻），兩種做法差不到 5% 算平手；換格式時，答對率比 BF16 低不能超過 2 個百分點（看 95% CI 的下界）；預測最多能省的比例要 ≥15% 才算值得做、全部 <5% 算死路，中間算可能 [§0]。5% 與 15% 沿用研究計畫一開始就定好的停損規則 [§0]。

我們用自己的 harness（量載入、重算與 Cake 的程式），而不是 vLLM、LMCache 或 SGLang，因為要能分開控制載入、重算與會合點。harness 的重算比 vLLM 慢（sdpa 1.75／1.76 倍，fa3 1.30／1.32 倍）；模擬裡把重算加速到 vLLM 級，預測的判定不變 [E1、E2、B7]。

### 3.2 預測的底、oracle 與公式

**底**：預測模擬的起點是一套固定、不預測的做法，接近 §4 的表在「逐塊解壓」時的答案 [§0]。慢層用 INT4＋Cake；CPU 層用 Cake，而逐塊解壓時 INT4 在 CPU 層不比 BF16 快 [D2]，所以 CPU 層存 BF16。和 §4 不同的有兩點：沒有 MPS；Mooncake 的 36 格主結果裡，19 格在地圖外的 SSD 級，另外 17 格在 b32 [B9]。寫入時的預知另在 GPU 上量，對照的做法是「延後到 CPU 層滿了才決定」[A1'']。

**上界的意思**：oracle 是同一個策略，只多了某一個未來量的完美資訊，所以它界住的是「把這個量的預測器放進同一個策略」最多能省多少，不是所有策略的極限。它也不是嚴格的上界：NFS 級有 4 格打字提示預取比 oracle 預取還快 [C2]。

一塊的載入時間：位元組 $b$ 除以那一層的頻寬 $B$，INT4 再加解壓時間 $d$；那一層正在寫入時，讀取再乘量到的 $k_{\text{read}}$ [§0]。

$$\ell_{\text{BF16}}=\frac{b_{\text{BF16}}}{B_{\text{CPU}}},\qquad \ell_{\text{INT4}}=\frac{b_{\text{INT4}}}{B_{\text{層}}}+d \tag{1}$$

Cake：有存的前綴是第 0 到第 $L-1$ 塊；每一步讓落後的一邊前進一塊，兩邊在第 $m$ 塊相遇，送回時間取兩邊較晚的那一個。$f(i)$ 是在 GPU 上重算第 $i$ 塊的時間；H200 上量到第 79 塊（約 40K token），之後線性外插 [§0]。

$$T_{\text{restore}}=\max\Big(\sum_{i=0}^{m-1} f(i),\ \sum_{i=m}^{L-1}\ell(i)\Big) \tag{2}$$

模擬的 TTFT 是送回時間，加上重算沒存的塊與新訊息；策略 $\pi$ 的成績是所有回來請求 $\mathcal{R}$ 的平均。

$$\text{TTFT}_r=T_{\text{restore}}+\sum_{i=L}^{n_r-1} f(i),\qquad T(\pi)=\frac{1}{|\mathcal{R}|}\sum_{r\in\mathcal{R}}\text{TTFT}_r(\pi) \tag{3}$$

四種回來時的 oracle 從 trace 讀「下一個讀到這個 session 的請求」，每個只改一個決定，其他照 LRU [§0]：

- **預取**：慢層讀取線空著時，先把最早回來的 session 的後段以 INT4 搬進 CPU 層。
- **淘汰順序**：CPU 層滿時，先降級最晚回來的 session（Belady；或把距離乘上能空出的位元組），每格取較快的一個。
- **回合結束就丟、輪到淘汰時才丟**：不再回來的 session 在這兩個時間點直接丟掉。截尾 $H$ 時，離 trace 結尾不到 $H$ 秒的決定一律當「會回來」。
- **知道誰不回來**（另列）：替每個 session 選去處（CPU BF16、CPU INT4、慢層或丟掉）；對手是最好的固定規則，任一主格 ≥15% 就算值得做。

上界是 oracle 比最好的同動作對手 $\mathcal{S}_c$ 少花的比例；同一組設定要有兩種以上的 CPU 容量 ≥15%，才算值得做。Mooncake 沒有 session 欄位，我們用兩種規則重建，每格取較小的上界 [§0]。

$$h_c=\frac{T_{\text{rival}}-T_{\text{oracle}}}{T_{\text{rival}}},\qquad T_{\text{rival}}=\min_{\pi\in\mathcal{S}_c}T(\pi) \tag{4}$$

打字提示的提前量：這一輪新輸入的 token 數 $\Delta_r$ 扣掉 10 個模板 token，換成字元數（每 token $c_{\text{tok}}$ 個字元），除以桌機打字速度 51.56 WPM（Dhakal et al.），再以兩請求之間的空檔為上限（TPOT 取 50 ms）[§0]。

$$L_r=\min\Big(\frac{\max(\Delta_r-10,\,0)\cdot c_{\text{tok}}}{51.56\times 5/60},\ \text{think}_r\Big) \tag{5}$$

慢層的寫入負載 $\rho_w$＝寫入的忙碌時間 ÷ trace 長度；$\rho_w\ge 1$ 的格就是寫入飽和 [§0]。

## 4 哪個還原組合最好：慢層用 INT4＋Cake，CPU 層看解壓實作〔實測〕

**不加預測時，最快的組合隨層、GPU 忙閒、模型與 INT4 的解壓實作變；在 b32、b48、NFS 級每一格都是 INT4＋Cake [M1]（表 2、圖 1）。**

**圖 1 怎麼讀**（圖在一頁看懂之後）：每一列是一種「層 × GPU 忙閒」，每一欄是一種送回方式與格式；格子裡的數字是送回時間除以該列最快的時間，粗框是最快。**看到什麼**：在慢層，BF16 整段載入最慢，例如 Llama、NFS 級、GPU 閒時要 12.082 s，INT4＋Cake 只要 1.2412 s [M1]；在 CPU 層、GPU 忙時，最快的是 INT4 整段載入 [M1]。**為什麼**：INT4 每塊的位元組小 3.2 倍 [D1]，所以載入那一邊更快；Cake 的送回時間是「前段重算」與「後段載入」兩者中較晚的那一個（§3.2 公式 (2)），載入變快，會合點就往前移，兩邊一起縮短。CPU 層本身搬得很快，所以解壓的做法決定快慢：同樣是 Llama、CPU 層、GPU 忙的 INT4 整段載入，一次拆完要 0.0342 s，逐塊解壓要 0.2325 s [M3-g]。整段重算最慢，因為 32K 的 64 塊全部重算要 1.85–4.05 s [M1]。**代表什麼**：先看 KV 停在哪一層，再看解壓實作，就能查出該怎麼送回。

## 6 GPU 共用時怎麼分：改用 MPS 回答快很多，保留越多別的工作越慢〔模擬＋GPU 檢查〕

**§4 假設送回時 GPU 只做這件事；本節讓 GPU 同時跑別的工作。改用 MPS 讓兩者同時跑、先不限制別的工作時，回答比單純共用 stream 快 30.7–62.9%，別的工作的處理量只少 0–6.5 個百分點；若再限制別的工作、替送回保留更多 GPU，回答更快，但別的工作明顯變慢 [S2、M4]（表 4、圖 5）。**

這裡是模擬的設定：慢層用 §4 的 INT4，送回與別的工作先各用一條 stream，底另含打字提示預取（§7.4）[M4]。我們用 B 表示別的工作的處理量，是它獨自用 GPU 時的幾成；就算只是單純共用 stream，B 也只有 0.697–0.957，6 組裡只有 1 組達到登記要求的 0.95 [M4、S2]。

## 7 在固定規則之上，預測還值多少：要看 trace〔模擬；寫入時是實測〕

## 9 給設計者的決策流程

**三個答案依序串成一個流程：先用 §4 的表選送回方式與格式，再照 §6 決定保留多少 GPU，最後才照 §7、§8 決定要不要加東西（圖 9）。**〔判讀〕

![](figs/fig11_decision.png)

**圖 9　送回停放 KV 的決策流程：先查表選送回方式與格式，再分 GPU，最後才考慮預測與多一條路徑。**

**怎麼讀**：由左到右依序回答問題，每一欄的方框是在各種情況下的建議，底下兩框列出不值得做的與本文沒涵蓋的。**代表什麼**：照這個順序，大部分情況只要查表與分 GPU；只有在自己的 trace 上量到上界夠高時，才需要預測。

1. **選送回方式｜KV 停在 CPU 記憶體**：先看 INT4 的解壓實作。一次拆完 → INT4 全部載入；逐塊解壓 → Cake；不確定 → 一律 Cake（成本模型的測試格平均多 6.7%，但一次拆完時最多慢到 2.18 倍）[M1、M3-f]。
2. **選送回方式｜KV 停在 b32、b48 或 NFS 級**：INT4＋Cake [M1]。b16 上 Cake 與全部載入差不到 10.4%，選哪個都行；SSD 級沒量，照慢層用 Cake 是外推 [M1]。
3. **選格式｜寫入時能付 SVD 的成本、模型是 Llama**：低秩＋INT4 在 GPU 閒時更快；Qwen 不要用 [M1、M2]。
4. **分 GPU｜要和別的工作共用**：先決定別的工作最少要保有多少處理量，再在自己的 GPU 上試兩三個 MPS 等級；模擬的絕對值不可信 [S3、M4]。
5. **加預測｜**先在自己的 trace 上量 oracle 上界。低於 5% 就不蓋；5–15% 先試打字提示這類免費訊號，不蓋預測器；≥15% 時預取先用打字提示，淘汰順序目前沒有免費訊號 [B3-T5、B9、C2-GPU、B1-ORD]。
6. **加路徑｜有閒置的鄰卡**：多一條還原路徑值得試（只量 2 卡、鄰卡受的影響沒量）；漸進還原、近似重算、借鄰居的算力在我們的門檻下不值得 [G-M06、G-A0、G-M12、G-M08]。

## 10 限制

## 11 相關研究

**前作各自改進一個方向，比較的對象也各不相同；本文把這些選擇放在同一張 H200 上、同一套事先登記的門檻下，依「選組合 → 分 GPU → 加東西」的順序比較。**

**分層 KV 系統**。vLLM 的 offloading 與 tiering、LMCache、Mooncake 與 CachedAttention 都把 KV 移到 CPU 或儲存層，回來時再送回〔文件、ATC'24〕。它們提供機制與預設值，沒有回答哪個組合在哪種條件下最好。本文 §4 量的就是這些機制上方的選擇。

**算與載的還原**。Cake 讓 GPU 從前段重算、同時從後段載入〔內文〕；HCache 依離線 profile 決定每層用 hidden state 投影、傳 KV 或重算〔部分〕；CacheFlow 用 DP 規劃多個 session 的還原〔摘要；先前讀過內文〕；Cascade 用延遲預算決定搬多少、其餘重算〔內文〕；py-kvcache 與 *When the KV Cache Is Slower Than the GPU* 用離線量到的成本決定載或算〔內文〕。它們假設成本可以離線量好，或算與載互不干擾。本文把 Cake 放進格式、解壓實作與 GPU 分配的組合裡比較，並量到在測過的條件下表不翻轉。

**壓縮**。TensorRT-LLM 只在 host 或磁碟上把 KV 存成 NVFP4〔文件〕；KVServe 依頻寬與 SLO 挑壓縮組合〔內文〕；CacheGen 壓縮 KV 再串流〔內文〕；ShadowKV 與 xKV 用低秩分解〔部分〕。它們多半只看位元組或頻寬。本文把格式和送回方式一起比，量到 INT4 在慢層要配 Cake、在 CPU 層要看解壓實作，以及低秩的寫入成本。

**選擇性讀取（聚焦）**。ReadKV 與 Fathom 讓 decode 時的 query 決定每塊讀多細〔內文〕；Janus 用原生稀疏模型的索引預測要從 SSD 讀哪些塊〔內文〕；IMPRESS 依新請求挑塊〔部分〕。它們多在 decode，query 是精確的。本文量的是回來那一刻、用新問題決定先讀粗版再精修的漸進還原，結果沒過門檻。

**部分重算的重用**。CacheBlend 等工作重用已存的 KV、只補算一部分〔未讀內文〕。本文的近似（稀疏）重算屬於這一類，在 32K 回來請求上品質掉太多。

**預測型管理**。PBKV、SAGA、CacheScout、CacheWise、Continuum、KVFlow 預測下一步呼叫、回來時間或存活時間，報告大的收益〔摘要〕；*Ask the Tool* 用工具回報的進度當免費訊號〔摘要〕；SARIA 與 Gandalf 在寫入時決定准不准進 SSD，目標是寫入量與壽命〔摘要〕。從摘要看，它們的對照組不是分層儲存＋Cake。本文在固定、不預測的底上量預測的 oracle 上界，發現它依 trace 而定。

**工作負載特性與極限研究**。Liu 等人在 FreeInference 上比較 14 種淘汰策略，發現花俏的策略贏不了 LRU、但離 Belady 遠，miss 的成本只算重算〔內文〕；*Where Should the KV Cache Live?* 用合成 workload 說預取 oracle 也贏不了不預取〔內文〕；*KVCache Cache in the Wild* 描述 trace 的重用特性〔摘要〕。本文的 miss 是從慢層用 Cake 送回、指標是 TTFT，並經 GPU 縮小重播檢查。

**GPU 分享與 SM 分割**。Tutti 把 SSD I/O kernel 放進獨立的 green context〔部分〕；Bidaw 把 KV 轉換放到低優先權 stream〔內文〕；vLLM 用固定 12 個 SM 的 kernel 搬小塊 KV〔PR〕；NanoFlow、Bullet 等在同一張 GPU 上分 SM 給 prefill 與 decode〔部分〕。查過的 12 個 GPU 共用系統都沒有把 KV 還原放進 SM 分配。本文 §6 量到：改用 MPS 讓送回和別的工作同時跑，回答快很多；替送回保留得越多，別的工作越慢。

## 12 結論

使用者回來時，停放的 KV 該怎麼送回 GPU，在我們量的 H200 範圍內可以依三步決定。先選送回方式與格式：慢層（b32、b48、NFS 級）用 INT4＋Cake；CPU 記憶體上先看 INT4 的解壓實作，一次拆完就整段載入，否則用 Cake；全部重算從來不是最好，而且這張表在測過的條件下不翻轉，所以查表就夠 [M1、M3]。再分 GPU：要和別的工作共用時，改用 MPS 讓兩者同時跑，在模擬裡別的工作的處理量只少 0–6.5 個百分點；若再限制別的工作、替送回保留更多 GPU，回答會更快，但別的工作會更慢，確切的數字要在自己的 GPU 上量 [S2、S3、M4]。最後才考慮加東西：寫入時的預知不必做；回來時的預測在 FreeInference 前 6 週、測過的 CPU 容量上連完美預知都快不到 15%，在 Mooncake 上預取可用打字提示、淘汰順序還沒有免費訊號；其他機制裡只有借閒置鄰卡多一條還原路徑過了門檻 [A2、B3-T5、B9、C2-GPU、G-M06]。〔判讀〕有效的做法都在減少要搬的位元組、讓搬與算重疊，或多開一條搬的路（INT4、Cake、多一條路徑）；預測只在上界高的 trace 上值得，而且預取用打字提示就拿到大部分。

**未來工作**（每項對應 §10 的一條限制，都還沒有結果）
- **真實的慢層與 SSD 級的地圖**：在真的 NVMe SSD 與網路儲存上量送回時間，補上 SSD 級。
- **更長的 context 與實作**：把地圖延伸到 64K 與 128K；b16、b48 改用一次拆完的實作重量。
- **真實的負載與品質**：用像真實服務的背景重量 b16、b48、NFS 級的穩定性；為 Qwen 的 INT4＋Cake 找過 ε 的設定。
- **端到端服務**：在有 batching 與排隊的服務系統裡量回來請求的 TTFT，檢查照表選擇與 MPS 的效果。
- **預測**：用更多真實 trace 找出能分開 FreeInference 與 Mooncake、設計者量得到的特徵（例如兩者同容量下的命中率）；用有真實按鍵時間的 trace 驗證打字提示；在 §4 的表上逐格重量預測的增量；量聯合 oracle；為淘汰順序找一個免費訊號。
- **更大的模型與多卡**：在多卡上量多一條還原路徑的收益與對鄰卡的影響。
