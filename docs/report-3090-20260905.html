M4

停損點：oracle 到底留了多少空間

整個研究的 go/no-go

問題是「一個知道未來的完美策略，比最好的可部署策略好多少」。 小於 5% 就停止這個方向。做法是 trace 驅動的模擬，成本常數全部來自 M2， 而且模擬器必須先複現 M3 的實測行為才算可信（16K 差 8%、32K 差 3%）。

本週修掉的一個缺陷：oracle 少算了自己的空間 量到「多給 oracle 一個 512 GiB 的 SSD 階，它反而慢 3.3%」—— 最佳策略不可能因為多了一個可用資源而變差，這是結構性矛盾。 原因是目的地規則拿「整條尾巴」當丟棄的邊際成本，而那條尾巴是該請求所有缺塊共用的， 整條算給每一個 block 等於重複計價，門檻因而被壓得太低，把 25 萬個 block 寫上 SSD 再用 10.245 ms 讀回，而重算只要 3.5–4 ms。 修法是新增一條逐 block 計價的規則並取三者較佳。 結果：headroom 由 8.42% / 9.23% 升到 12.33% / 12.00%，容量單調性恢復。 已把「加大任一階容量，oracle 不得變慢」寫成自動不變量。

M5-2

未來效用預測器：訓練出來，接回模擬器

本週新做的部分

前面四個里程碑量的是「環境有多少空間」。這一步是真的把方法做出來： 重放 trace 產生特徵 → 兩個機制標記 → GBDT → isotonic 校準 → 依成本設門檻 → 接回模擬器當線上策略。 全程不碰 GPU（LightGBM 在 CPU 上跑），所以與其他量測不互相干擾。

三道自我檢查先過了才看數字：（一）把預測換成「上次存取時刻」（＝LRU）之後， 這支策略的迴圈逐位元重現 M4 模擬器的 LRU 結果——兩邊用的是同一把尺； （二）「下次存取落在視窗內」的比例（34.8% / 4.3%）必須等於 M4 實測的 GPU 命中率 （34.9% / 4.3%）——兩條獨立路徑對得上；（三）七組訓練重跑，模型檔 md5 完全相同。

風險

最大的問題：同一個機制會反噬

在兩個預測失效的工作負載上，同一支策略比 LRU 差好幾倍。 重算率完全一樣（都是強制未命中），差別全在「從哪一階拿回來」： GPU 命中率由 49.0% 掉到 14.1%，40.9% 的存取落到 SSD（10.245 ms，是 CPU 的 34 倍）。

設定預測排序CPU/SSD 改用 recency逐出鍵分桶後以 LRU 破平手
lc32ks（長上下文、事件多）−458%−96%—
lc128ks（長上下文、4 並行）−171%−29%—
長上下文 131K（會贏的那個）+15.40%−0.13%−9.46%
 三個「退路」都試過：把 CPU/SSD 階改用 recency 排序，可以把慘敗由 −458% 收斂到 −96%， 但同一個改動也把會贏那個設定的 +15.40% 吃成 −0.13%。 分桶破平手同樣兩邊都失去。這條軸沒有安全的固定預設值。
三個被自己的資料推翻的假設 為了找出「為什麼失效時會慘敗」，先後提了三個機制，都被量測否定： (a) 分數離散度不足——但會贏的那個設定離散度最小（std 0.042）； (b) key = t + τ̂ 退化成 MRU——但會贏的設定 std/壽命 也最小（0.08）； (c) SSD 階誤用——改成逐 block 計價後仍是 −320%。 最後量到的是 CPU 階的保留崩掉。三個假設都留在紀錄裡，沒有事後刪掉。
誠實性

抓到並修正的錯誤

每一個都是「數字看起來完全正常」的那種

這些不是失誤清單，是這個專案怎麼防止自己騙自己的證據。 共通點：沒有一個是靠讀程式碼看出來的，全部是靠「同一個量被兩條路徑算出來而對不上」， 或「這在物理／邏輯上不可能」抓到的。抓到之後都變成自動檢查。

錯誤後果怎麼抓到的現在的防線
Mooncake 的 hash_ids 是 512-token 的 block，被當成 16-token 工作集少算 32 倍、每個 block 的絕對位置少算 32 倍 → DROP 被算得太便宜 請求長度中位數被兩條路徑算過而對不上 載入函式裡寫「用 A 欄位驗算 B 欄位」的斷言
量 SSD 階時 CPU 階開太大，東西沒 cascade 到磁碟 「SSD 0.40 ms/block」其實是 CPU 階，比真值便宜 13.7 倍 修正後 SSD 竟然比 DROP 還貴，反常 工作集必須大於容量的守門
A 模型的記憶體預算配 B 模型的成本常數 兩邊不可通約，整批 oracle 數字作廢 剖面自我一致性檢查：容量 × 每 token 大小 > 整張卡 剖面綁成一組，成本模型的 model_key 對不上直接拒跑
oracle 的目的地規則重複計價（本週） headroom 被自己壓低 32%（8.42% vs 12.33%） 多給一階容量，oracle 反而變慢——結構性矛盾 check_capacity_monotone 自動不變量
「取樣以 block 為單位」被讀成「每 block 最多 C 個樣本」（本週） 正樣本率 0.3% vs 真值 34.8%，差 100 倍 與 M4 實測的 GPU 命中率對不上 改成逐存取均勻取樣；兩條路徑的數字寫進 RUNLOG
trace 結尾把「視窗還沒觀察完」標成負樣本（本週） 測試集正樣本率被壓到 1.3%，AUC 看起來 0.9998 正樣本率與別的設定對不上 只保留視窗完整可觀測的樣本
校準集只有單一類別（本週） isotonic 把輸出壓成常數：AUC 恰為 0.5、Spearman 是 nan、ECE 0.3334——三個指標都有數字 AUC 恰好等於 0.5000 偵測到單一類別就改用訓練期等距抽樣，全期單一類別則中止
write_csv 在 append 模式不檢查檔頭（本週） 加一個欄位就整排錯位，而檔案看起來完全正常 加欄位時主動想到 欄位集合不同就中止；順序不同則照既有檔頭重排

Zhao, H. (2008), KAIS 15:321–334 正面比較了「樣本加權」與「事後移門檻」兩種成本敏感做法， 結論是對 naive Bayes／邏輯迴歸／類神經網路兩者相近，對決策樹族差很多。 我們用的是 GBDT，正是樹族。論文 §5.3 目前把「加權訓練會贏」寫成推導出來的預期， 但這個問題在文獻裡已經被實證比較過，而且沒有一致的贏家—— 我們自己量到的方向（在高 κ 區加權反而更差）與這條線索一致。建議把主張縮減到門檻校準。
