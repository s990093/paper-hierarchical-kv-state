## 2. 討論中問到的（已回答）

- **為什麼 S5 沒贏？**
  - CPU 層載入一個 chunk 只要 1.76 ms，重算最便宜的 chunk 要 28.9 ms，差 16 倍，所以分界 b 只有 0–3 個 chunk。
  - Cake 在**讀取時**已經會依資料實際在哪一層決定會合點，寫入時先放好等於重複做同一件事。
- **改用 SSD 算 b 呢？** b 會變大（本地 SSD 約 20%，NFS 約 78%）。但這個版本（S5s）也沒贏：CPU 有空時，前段放 CPU 一定比放 SSD 再重算快。
- **是 context 太小嗎？** 不是。context 越長，後段重算越貴，前段被重算的比例反而略降（NFS：4K 88% → 32K 78%）。
- **Cake 原文怎麼說？**
  - 宣稱平均比只算、只載快 2.6 倍。這個數字同時對兩種基線平均，而且拿掉了超過 10 倍的極端值。
  - 原文目標是低頻寬的 SSD／遠端（0.5–4 GB/s），沒有評估從 CPU 載入。
  - 原文自己的 Table 6：GQA 的 Llama-3.1-8B 在 32 Gbps 時只有 0.98 倍。
- **不管裝置、只看頻寬，Cake 好多少？**（A0，32K，對「只算、只載兩者較快的」）

  | 頻寬 | Cake 加速 |
  |:--|:--|
  | 0.33 GiB/s | 1.38× |
  | 0.81 GiB/s | 1.93× |
  | 2.9 GiB/s | 1.50× |
  | 3.7 GiB/s | 1.39× |
  | 6.5 GiB/s | 1.24× |
  | 11.6 GiB/s | 1.05× |

  載入時間約等於重算時間（這台機器約 1 GiB/s）時最有效。
- **Cake 適合冷啟動嗎？** 適合「KV 在冷的（慢的）層」，例如很久沒回來、被降到 SSD 的 session，或從遠端拿別台機器算好的 KV。真正的冷啟動（哪裡都沒有 KV）只能整段重算，Cake 幫不上。
