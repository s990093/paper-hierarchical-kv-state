# 02 故事：從「為什麼要存 KV」到「第一階段要回答什麼」

> **一句話**：長 context 的 KV 太大，回來時搬不動就撞牆。Cake 讓「重算」和「搬運」同時進行，但它假設 KV 全部都已經存好了。我原本想在寫入時就決定怎麼存；老師問的是，這樣是否比更簡單的做法好。第一階段就是用實驗回答這個問題。

---

## 1. 為什麼要存 KV

LLM 讀輸入（prefill）時，會替每個 token 算出 KV，生成回答時要用到它。多輪對話或 agent 裡，使用者下一輪回來時，前面的內容都一樣。如果 KV 還在，就不用重算，第一個字很快就出來，也就是 TTFT 變短。這是 KV cache 能加速的原因。

## 2. 問題：KV 太大，撞牆

- context 越長，KV 越大。Llama-3.1-8B 每個 token 的 KV 是 128 KiB，32K token 就是 4 GiB〔計算〕。
- GPU 放不下所有使用者的 KV，只好搬到 CPU 記憶體或 SSD 存著。
- 使用者回來時要搬回 GPU。搬得慢，就會撞牆：
  - **容量牆**：快的層（GPU、CPU）放不下；
  - **I/O 牆**：從慢的層搬回來太慢。

## 3. 現有最好的還原方法：Cake

- 拿回 KV 有兩條路：重算（越長越慢），或從儲存搬回來（受限於頻寬）。
- Cake 讓兩條路同時跑：GPU 從前面往後重算，I/O 從後面往前搬，兩邊在中間會合。所以它比只算或只搬都快。
- 前段交給 GPU 算，是因為前面的 token 重算比較便宜。
- 會合點不是固定的，每次還原時依當下兩邊的速度調整。
- 但 Cake 有三個前提：
  1. KV 全部都已經存好（原文：「we precompute and store all requests' KV cache in advance」）；
  2. 只有一個儲存層；
  3. 全部用同一種精度。

  它完全不管寫入時要怎麼放。

## 4. 我的觀察和原本的想法

- Cake 的會合點其實告訴了我們每一段 KV 回來時會怎麼被用：
  - **後段**：一定是搬回來的；
  - **前段**：多半是重算的；
  - **中段**：看當時的情況。
- 既然用法不同，存法也應該不同。所以我原本想在寫入時就依位置決定：前段不存，中段放 SSD，後段放 CPU 或 GPU。
- 好處是省下寫入和空間，讓撞牆的長度往後推。

## 5. 老師的三個問題

用一個比喻說明：筆記有 12 頁，出門前可以影印一份放倉庫。回來時，小明（GPU）從第 1 頁開始重抄，快遞（I/O）從倉庫把第 12 頁往前送，兩人在中間碰頭。

1. **少印前幾頁，回來時有比較快嗎？** 沒有。影印是你出門後才做的，那時沒人在等。回來時小明一樣抄、快遞一樣送，時間一樣。
2. **小明正在忙的時候呢？** 他抄得很慢，本來應該叫快遞多送幾頁。但前幾頁沒有影印本，只能等小明慢慢抄，反而更久。
3. **有沒有更簡單的方法？** 有兩個：
   - **延後寫入**：先不印，等桌子放不下了再印；
   - **成本感知逐出**：先全部印，倉庫滿了再丟最好重抄的頁。

   這兩個方法也能省，而且不用在出門那一刻就猜未來。

## 6. 修正後的想法：不刪任何一段，只改放的地方

我把「前段不存」改成「前段也存，只是放在便宜的層」，理由有三個：
- **連續前綴命中不會斷。** vLLM、SGLang 的 prefix cache 是從第一塊開始一塊一塊比對，前面缺一塊，後面全部算沒命中。
- **GPU 忙時有退路。** 老師的第二個問題自然解決。
- **「前段便宜」只是相對的。** 長 context 的前 30K token 重算起來還是一次 30K 的 prefill，不是免費的。

修正後的方法（第一階段的「初階版」）：
- **寫入時依位置決定每段放哪一層**：後段放 CPU（快），前段放 SSD（便宜，當備份）。
- 每段只寫一次，不刪任何一段。
- 精度先全部用 BF16，降精度留到第二階段。

效果是：要搬的後段從比較快的地方來，會合點往前移，GPU 要算的變少，使用者等得少，GPU 也省下算力給別人。

## 7. 剩下真正的問題

「依位置放」這件事，成本感知逐出也做得到：後段留在快的層，前段被擠到慢的層。所以我的方法和其他做法最後只差一件事：**在寫入當下就決定，還是等到空間不夠才決定。**

| | 寫入當下決定（我的） | 晚點決定（延後寫入＋成本感知） |
|:--|:--|:--|
| 可能贏的情況 | 空間不夠那一刻不必一口氣大量寫入，不會擋到正在回來的人，尤其 SSD 寫得慢時（這台機器的 QLC 持續寫入只有 181 MiB/s，RUNLOG） | 使用者常常不回來，或 CPU 一直夠用，就一次 SSD 都不用寫 |

這只能實測，所以第一階段的關鍵比較是 **S4+ vs S5**（`03` §3）。

## 8. 第一階段做什麼

- 照老師的要求：一台機器、一個模型、BF16、還原方式固定用 Cake。
- 先確認純 Cake 跑得通，再比較 9 個寫入策略，看差別來自哪裡（`05`）。

結果怎麼解讀：
- 比最好的簡單策略好超過 15%：進第二階段。
- 5–15%：帶數字找老師。
- 低於 5%：簡單策略追平，照實寫成「什麼時候不值得做」。
