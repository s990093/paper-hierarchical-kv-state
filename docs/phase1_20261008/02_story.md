# 02 故事：從「為什麼要存 KV」到「第一階段要回答什麼」

> **一句話**：長 context 的 KV 太大，回來時搬不動就撞牆。Cake 讓「重算」和「搬運」同時進行，但它假設 KV 全部都已經存好了。我原本想在寫入時就決定怎麼存；老師問的是，這樣是否比更簡單的做法好。第一階段就是用實驗回答這個問題。

---

## 1. 情境，以及為什麼要存 KV

**情境：長 context 的多輪對話與 agent，使用者隔一段時間才回來。**

例如：
- 一個人把整份文件或整個程式庫放進 context，和模型來回問答好幾輪；
- 或一個 coding agent 每輪都帶著越來越長的歷史，中間去跑工具、等結果。

這類情境有三個特點：
- **context 很長，而且每輪都在後面追加**：前面的內容一直沿用；
- **使用者會離開一段時間**：去讀答案、想下一步，或等工具跑完，之後才回來，也可能就不回來了；
- **同一台機器同時服務很多這樣的 session**：GPU 放不下所有人的 KV。

**為什麼要存 KV**：LLM 讀輸入（prefill）時，會替每個 token 算出 KV，生成回答時要用到它。使用者下一輪回來時，前面的內容都一樣。如果 KV 還在，就不用重算，第一個字很快就出來，也就是 TTFT 變短。這是 KV cache 能加速的原因。

**第一階段怎麼模擬這個情境**：B 實驗用 8 個 session，每個 4 輪，每輪追加 8K，每個 session 有一定機率不再回來（`05` B）。這些參數目前是設計值。比較好的做法是從有時間戳的真實 trace 取：每輪追加多少、隔多久回來、多少比例不回來。候選 trace 是 Mooncake 的 conversation／toolagent 和 TraceLab（EVAL_FOUNDATIONS §10.4）。用哪一種、怎麼縮放，開跑前要寫死。

## 2. 問題：KV 太大，撞牆

- context 越長，KV 越大。Llama-3.1-8B 每個 token 的 KV 是 128 KiB，32K token 就是 4 GiB〔計算〕。
- GPU 放不下所有使用者的 KV，只好搬到 CPU 記憶體或 SSD 存著。
- 使用者回來時要搬回 GPU。搬得慢，就會撞牆：
  - **容量牆**：快的層（GPU、CPU）放不下；
  - **I/O 牆**：從慢的層搬回來太慢。

## 3. 現有最好的還原方法：Cake

- 拿回 KV 有兩條路：重算（越長越慢），或從儲存搬回來（受限於頻寬）。
- Cake 讓兩條路同時跑：GPU 從前面往後重算，I/O 從後面往前搬，兩邊在中間會合。所以它比只算或只搬都快。
- 前段交給 GPU 算，是因為前面的 token 重算比較便宜。
- 會合點不是固定的，每次還原時依當下兩邊的速度調整。
- 但 Cake 有三個前提：
  1. KV 全部都已經存好（原文：「we precompute and store all requests' KV cache in advance」）；
  2. 只有一個儲存層；
  3. 全部用同一種精度。

  它完全不管寫入時要怎麼放。

## 4. 我的觀察和原本的想法

**「用法」**指的是：使用者回來、Cake 還原時，每一段 KV 會怎麼被拿回 GPU。Cake 的兩條線一條從前面算、一條從後面搬，所以每一段的命運，在寫入時就大致看得出來：

| 位置 | 回來時怎麼被用（用法） | 所以該怎麼存（存法） |
|:--|:--|:--|
| **後段** | 一定是搬回來的：重算它最貴，載入線一開始就搬它 | 放在**最快**的層（CPU 或 GPU），搬得越快，使用者等得越少 |
| **中段** | 看當時的情況：GPU 閒就重算，GPU 忙就搬 | 放在中等的層（SSD），兩種情況都能應付 |
| **前段** | 多半是重算的：重算它最便宜，重算線一開始就算它 | 不太需要快速搬回來，所以原本的想法是**不存** |

**「存法也應該不同」**：Cake 和現有系統是每一段都用同一種方式存，例如全部放 SSD。但既然每一段回來時的用法不同，就應該依位置選不同的存法：快的層留給一定會被搬的段，慢的層（或不存）給多半會被重算的段。

**好處**：快的層容量有限，只放「一定會被搬」的段，同樣的記憶體就能撐更多 session、更長的 context，讓撞牆的長度往後推。

## 5. 老師的三個問題

用一個比喻說明：筆記有 12 頁，出門前可以影印一份放倉庫。回來時，小明（GPU）從第 1 頁開始重抄，快遞（I/O）從倉庫把第 12 頁往前送，兩人在中間碰頭。

1. **少印前幾頁，回來時有比較快嗎？** 沒有。影印是你出門後才做的，那時沒人在等。回來時小明一樣抄、快遞一樣送，時間一樣。
2. **小明正在忙的時候呢？** 他抄得很慢，本來應該叫快遞多送幾頁。但前幾頁沒有影印本，只能等小明慢慢抄，反而更久。
3. **有沒有更簡單的方法？** 有兩個：
   - **延後寫入**：先不印，等桌子放不下了再印；
   - **成本感知逐出**：先全部印，倉庫滿了再丟最好重抄的頁。

   這兩個方法也能省，而且不用在出門那一刻就猜未來。

## 6. 修正後的想法：不刪任何一段，只改放的地方

我把「前段不存」改成「前段也存，只是放在便宜的層」，理由有三個：
- **連續前綴命中不會斷。** vLLM、SGLang 的 prefix cache 是從第一塊開始一塊一塊比對，前面缺一塊，後面全部算沒命中。
- **GPU 忙時有退路。** 老師的第二個問題自然解決。
- **「前段便宜」只是相對的。** 長 context 的前 30K token 重算起來還是一次 30K 的 prefill，不是免費的。

修正後的方法：**每段都存，只在寫入時依位置決定每段的「狀態」**。
- 原本的狀態有六種：GPU 的 BF16、FP8、INT4，以及 CPU、SSD、不存。
- 第一階段把狀態縮小成兩種：精度固定 BF16，所以狀態就只剩「放在哪一層」；不刪任何一段，所以沒有「不存」；GPU 只放正在服務的請求，所以也不放在 GPU（`05` §1）。
- 剩下的兩種是 **CPU（快）** 和 **SSD（慢、便宜）**。照上面的「用法」決定：
  - 預期會被搬的後段 → CPU；
  - 預期會被重算的前段，以及中段 → SSD，當備份。
- 前段和中段都放 SSD，是因為第一階段沒有比 SSD 更便宜的層。如果之後加一層更慢的儲存（例如平台 B 的 NFS），規則就會自然變成「前段 → 最便宜的層，中段 → SSD，後段 → CPU」，和原本的三段一樣。
- 這就是 `03` 的 S5。它不是另外加的新策略，而是你的方法在第一階段只有兩種狀態時的樣子。

效果是：要搬的後段從比較快的地方來，會合點往前移，GPU 要算的變少，使用者等得少，GPU 也省下算力給別人。

## 7. 剩下真正的問題

「依位置放」這件事，成本感知逐出也做得到：後段留在快的層，前段被擠到慢的層。所以我的方法和其他做法最後只差一件事：**在寫入當下就決定，還是等到空間不夠才決定。**

| | 寫入當下決定（我的） | 晚點決定（延後寫入＋成本感知） |
|:--|:--|:--|
| 可能贏的情況 | 空間不夠那一刻不必一口氣大量寫入，不會擋到正在回來的人，尤其 SSD 寫得慢、或和別人共用時（例如 MI300X 上的 NFS 寫入只有 683 MiB/s，本地 SSD 和 7 個鄰居共用，RUNLOG_MI300X） | 使用者常常不回來，或 CPU 一直夠用，就一次 SSD 都不用寫 |

這只能實測，所以第一階段的關鍵比較是 **S4+ vs S5**（`03` §4）。老師的四個疑問在新設計下還剩哪些，整理在 `01` §3。

## 8. 第一階段做什麼

- 照老師的要求：一台機器、一個模型、BF16、還原方式固定用 Cake。
- 先確認純 Cake 跑得通，再比較 9 個寫入策略，看差別來自哪裡（`05`）。

結果怎麼解讀：
- 比最好的簡單策略好超過 15%：進第二階段。
- 5–15%：帶數字找老師。
- 低於 5%：簡單策略追平，照實寫成「什麼時候不值得做」。
