## 0. 一頁看懂

**問題**：使用者會回來的長對話，KV 要存到 CPU（快、小）或 SSD（慢、大）。讀回來時用 Cake：GPU 從前面重算，I/O 從後面載入，兩邊在中間會合。我的想法（S5）是：**寫入當下就依位置決定**。前段反正會被重算，就直接放 SSD；後段放 CPU。這樣能不能比「先全部放 CPU，滿了再搬」讓使用者等得更少？

**答案：在測過的範圍內不能。** 但有一個前提：harness 和模擬器**一次只服務一個請求，延後動作不佔用空閒時間**。在這個前提下，寫入時決定能做到的事，下面這些更簡單的做法都做得到：

| 更簡單的做法 | 證據 |
|:--|:--|
| **Cake 讀取時自己調整**：資料在哪一層，它就重算多少 | 第一階段：S5 和「滿了再依位置搬」（S4+）在所有設定都只差 ≤3% |
| **同一條規則，滿了才套用**（S4B） | 08：四個條件都成立時，S5L 比 S4B 只快 0.7%；換個 seed 就平手 |
| **寫穿**（S1、S2b） | 08：搬移卡在請求路徑上時，寫穿反而最快（chat 時快一倍以上） |
| **LRU／閒置時間** | 第一階段：容量緊時，LRU 類比依位置淘汰快 12–33% |
| **背景搬、預先清理** | 第 1 輪新加的對照組（S4W、S4C）。加進來之後存活的設定沒變（Llama 1、LongAlpaca 4） |
| **（第 1 輪 GPU 確認）** | 模擬裡唯一能上 GPU 的存活者（Llama、doc、CPU 11.6）在 GPU 上 **0／5 個 seed 通過**：S5L 和 S4B 差距在 ±2.4% 內。模擬預測的 +7.6% 沒有出現，因為模擬器對 S5L 偏樂觀約 5 個百分點 |

**為什麼**：位置這個資訊延後也拿得到。S4B 等 CPU 滿了才看位置，結果一樣。OS 的文獻也一樣：搬移免費時，「經過時就決定放哪層」只比「逐出時才往下搬」好 0.3–5%（Gill FAST'08）。

**還沒測、最可能讓結論翻轉的區域**：**沒有空閒、寫入積壓**的時候。
- 真實系統（vLLM、LMCache、SGLang、Dynamo）在 CPU 滿時預設是丟掉，或放棄這次卸載，不會等。
- 延後版平常追得上，是因為它有空檔。例如 Pensieve 就是在逐出時丟前段、回來重算。
- 但在寫入積壓、CPU 裡的 chunk 都被寫往 SSD 中的 I/O 鎖住時，延後版沒有東西可以淘汰，只能截斷，而該丟哪一段只能在寫入當下決定。
- OS 文獻也說：頻寬受限時，「經過時就決定放哪層」比「逐出時才搬」好很多（Gill FAST'08：3.42 vs 5.05 ms）。
- **這個區域現在的模型量不到**（一次一個請求），第 2 輪要先建出來。

**要證明的只有一件事**：找到一個**真實會發生**的設定，在那裡寫入時決定比**所有延後版**（滿了才做、背景做、預先清理、寫穿、讀取時做）快 ≥5%，GPU 實測，≥3 個 seed 都成立。在「一次一個請求」的模型裡**沒找到**：Llama 那個模擬存活者上 GPU 後 0／5 個 seed 通過（12 §5.4）。

**要找老師決定的**：
1. 第二輪要不要先建「有併發、寫入積壓、放不下就丟」的模型，再在裡面找延後版吃虧的地方（12 §8 第 1–3 點，最推薦）。
2. 還是把現有結果寫成負面結果或測量型論文：「讀取端會自適應時，寫入時放置什麼時候還重要？」
3. 還是換問題。

## 1. 方法

- **harness**：自己管 KV 的 Llama 前向（重用 HF 權重）。可以逐個 chunk（512 token）計時，讓 Cake 的「前段重算、後段載入」真的並行跑。
  - 正確性：重算的 KV 逐位元相同；載入後的 KV 逐位元比對，所有實驗 `kv_bad`＝0。
- **層**：CPU 是真實的 pinned memory，用限速器設頻寬（35.4 GiB/s 是單一 stream 實測，3.69 GiB/s 是 vLLM 實測）。SSD 用限速器模擬 NFS 或本地 SSD 的實測讀寫參數，加上讀寫干擾模型（share）。
- **策略**：S5 系列是「寫入時依位置」；S4 系列是「先寫 CPU、滿了才搬」；S1、S2b 是寫穿。完整定義見 `03_strategies.md` 與 08 §4。
- **工作負載**：
  - chat：每輪追加 8K，最多 4 輪。
  - doc：第 1 輪一次寫 32K，之後每輪只問短問題。
  - 8 個 session，一次服務一個。
- **判準**：寫入時決定要比對手快 ≥5% 才算有條件有效，≥15% 算強；只有 GPU 實測才算數。

## 2. 第一階段（07）

| 問題 | 結果 |
|:--|:--|
| A0：Cake 在這台機器上跑得通嗎？ | 27／28 格符合趨勢。**例外：4K × 100 Gbps，Cake 比只載慢 5.6%** |
| Q1：少寫能縮短等待嗎？ | 大多不能。寫入確實拖慢讀取（本地 SSD 讀取慢 2.2 倍），但寫 13 個和寫 64 個 chunk 拖慢的程度差不多 |
| Q2：GPU 忙時，沒存前段會變慢嗎？ | 會，慢 13–66%。支持「每個 chunk 都存」 |
| Q3：S5 vs S4+（只差寫入那一步） | **沒差別**，所有設定 ≤3% |
| Q4：S5 vs 最好的簡單策略 | **<5%，判定「簡單策略追平」**。容量 25% 時 S5 慢 29%（LRU 類贏） |
| Q5：空間何時是瓶頸 | 容量 ≤50% 時 |

**原因**：CPU 層載入一個 chunk 只要 1.76 ms，重算最便宜的 chunk 要 28.9 ms，差 16 倍。所以以 CPU 速度算出的分界 b 只有 0–3 個 chunk，寫入當下沒有東西可以決定。

**Cake 的好處和頻寬有關**（32K，對「只算」「只載」兩者較快的）：

| 頻寬 | 0.33 | 0.81 | 2.9 | 3.7 | 6.5 | 11.6 GiB/s |
|:--|:--|:--|:--|:--|:--|:--|
| 加速 | 1.38× | 1.93× | 1.50× | 1.39× | 1.24× | 1.05× |

載入時間約等於重算時間時最有效（這台機器約 1 GiB/s）。Cake 原文的目標是 0.5–4 GB/s 的儲存，沒有評估從 CPU 載入；原文 Table 6 的 GQA Llama-3.1-8B 在 32 Gbps 時也只有 0.98 倍。

## 3. 08 消融（09）：寫入時決定在什麼條件下不會被 Cake 抵消？

- **模擬器**：和 GPU harness 共用同一份策略程式碼與限速器，只是時間是虛擬的。
  - 重現第一階段 114 格，**全部在 ±10% 內**（中位 0.4%）。
  - 在 08 的新設定（doc、hold）上，44 格裡 43 格 ≤10%（中位 1.0%，最大 13.7%；41／44 偏樂觀）。
- **模擬掃描**〔模擬〕：
  - 單一因子（CPU 頻寬、搬移方式、工作負載、SSD、重算成本）都 <5%。
  - 390 格的組合裡，有 8 格同時贏過最好的不看位置策略與 S4B，全部是 doc。換 5 個 seed 之後，**沒有一組穩定**。
- **GPU 確認**：模擬裡最有希望的設定（doc＋hold＋CPU 3.69＋NFS）加上 chat＋hold，一共 16 組比較，**0 組通過**。

| 設定 | 結果 |
|:--|:--|
| doc，seed 0，50% | S5L 比最好的不看位置策略快 **18.9%**，但比 S4B 只快 **0.7%**。贏的是「前段不該占 CPU」這條規則，不是「寫入時」 |
| doc，seed 1，50% | 寫穿 S1 最好，S5L 慢 6.8% |
| chat＋hold | 寫穿 S1 比 S5 快一倍以上（1.56 vs 3.45 s） |

- **你列的四個條件已經一起測過了**：快的層 ≲4 GiB/s、空間緊、滿了再搬卡在請求路徑上、淘汰看閒置時間，就是 G1 的設定。結論：**四個條件必要，但不夠**。缺的第五個條件是「**這個決定延後做不到**」。

## 4. 破解第 1 輪（12）：往「寫入時才有、之後就沒有」的方向找

| 項目 | 結果 |
|:--|:--|
| **H0** 真實系統會不會因搬移擋住請求（讀原始碼） | 5 個實作預設都**不等**：CPU 滿了就丟或不存。往 SSD 都是寫穿，沒有「滿了才搬」。會等的只有非預設設定。**hold 只對應同步實作；比較真實的模型是「放不下就丟」** |
| **H1** 寫入時決定能不能少寫 SSD | 23 個設定只有 2 個（8.7%）。在 5% 帶內寫得最少的通常是延後的 S4。**殺掉** |
| **H2** 重算便宜的模型 | LongAlpaca-7B（MHA）在 CPU 3.69 GiB/s 時前段重算比例 0.59（Llama 0.31），Cake 加速 2.10 倍。Qwen3-30B-A3B 在 HF 實作下太慢，判定 **NOT_MEASURED**。用 vLLM 引擎時間戳觀察（沒過驗證）：它算一個 chunk 只比 Llama 慢 1.16–1.33 倍，chunk 比較小，所以 MoE 沒有幫助 |
| **H2 延伸**〔模擬〕和所有延後版比 | Llama 64 個設定存活 1 個，LongAlpaca 存活 4 個，全部是 doc。LongAlpaca 的 4 組不上 GPU：情境超過它的 32K 上限，hold 那組又處在 NFS 寫入過載；改看平均 TTFT 的話沒有一組存活。Llama 那組照計劃上 GPU：**0／5 個 seed 通過**，S5L 和最好的不看位置策略、S4B 都在 ±3.5% 內。模擬器對 S5L 系統性偏樂觀（5／5 個 seed 低估 1.8–8.8%，對照組平均高估約 1%），所以 5% 的模擬門檻挑不出可靠的存活者（12 §5.4） |
| **文獻**（3 個 agent，40 張卡） | 「寫入時決定」已經有人做（Krul、TierKV、Lachesis），但幾乎沒有一篇和延後版比過。OS 文獻：搬移免費時延後追得上。架構：只有 MHA 讓前段重算比例明顯變大；Cake 還原時不需要中間的 SSM 狀態 |

## 5. 整理：在什麼條件下有效、什麼條件下無效

**Cake（讀取時雙向還原）——已驗證**：
- 頻寬約 0.3–4 GiB/s（32K）時，比兩者較快的再快 1.4–1.9 倍。
- ≥7 GiB/s 時好處 <20%；≥11.6 GiB/s 時約 5%，短 context 甚至變慢。
- context 越長越有效。
- MHA 模型（KV 大 4 倍）：用公式算，3.69 GiB/s 時加速 2.10 倍（Llama 用同一個公式是 1.45 倍，A0 實測只有 1.39 倍，所以公式偏高）〔算術，GPU 實測 NOT_MEASURED〕。

**寫入時依位置放（S5）**：

| 條件 | 狀態 |
|:--|:--|
| 1. 快的層頻寬 ≲4 GiB/s，前段重算 ≥30% | 3.69 GiB/s 測過，成立，但不夠 |
| 2. 快的層空間緊（≤50%） | 成立時差距才出現 |
| 3. 滿了再搬卡在請求路徑上 | 寫穿就能解決；而且真實系統預設不會這樣等（H0） |
| 4. 淘汰看閒置時間 | S4+P、LRU 就做得到 |
| **5. 決定延後做不到** | **在「一次一個請求」的模型裡沒有任何設定滿足**（模擬存活者上 GPU 後 0／5）。候選是沒有空閒、寫入積壓、CPU 被鎖住時的截斷；這個區域模型量不到 |
| 6. 一次寫一大段（doc 型） | 所有存活的模擬設定都是 doc；chat 新寫的永遠是尾巴 |
| 7. 重算相對便宜（MHA） | 讓前段重算比例變大，但延後版一樣受益 |

## 7. 限制

- 只有一台機器（MI300X）。**主要結論只在 GQA 的 Llama-3.1-8B 上做過 GPU 實測**；LongAlpaca 只有重算成本的實測和模擬。
- SSD 層是限速器模擬，只用真實裝置（本地 SSD、NFS）的參數當錨點。
- **一次服務一個請求，沒有併發**；寫入、淘汰、背景清理都在同一個虛擬時刻。所以延後版天生不缺時間。這是反方審查認為最強的拒稿理由，所有「延後追得上」的結論都只在這個前提下成立。GPU 忙的情況只在 A1 測過。
- hold 和 free 都不是真實系統的預設行為（H0）。
- A0 有 1／28 格例外。
- 模擬器整體準（第 1 輪 GPU 確認 50 格裡 47 格誤差 ≤10%），但**對策略之間的相對差不夠準**（S5L 低估約 4.6%、對照組高估約 1%）。模擬只能挑候選，門檻要 ≥10% 或全部上 GPU。
- 文獻 agent 的部分 API 被限流；所有引用都要再核對原文才能進論文。
