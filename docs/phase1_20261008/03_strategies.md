# 03 策略與演算法

> **一句話**：每個策略只由三件事決定：**寫入時**怎麼放、**空間不夠時**丟或搬誰、**回來時**怎麼還原。9 個策略設計成每兩組只差一件事，所以差別從哪裡來可以直接看出來。

演算法用論文的寫法：先寫輸入、輸出，再寫編號的步驟。這些是說明用的，不是可以直接跑的程式；實作放在 `code/m7_*.py`（`06` §5）。

|:--|:--|:--|:--|:--|:--|:--|:--|
| R0 | 業界現狀（參考） | CPU、SSD 各寫一份（寫穿） | 刪掉最久沒用的 session 的 CPU 那份 | 刪掉最久沒用的 | **只載** | 2 | LMCache 預設 |
| S0 | **純 Cake** | 全部寫到 SSD | — | 刪掉最久沒用的 | Cake | 1 | Cake 原設定 |

- 各策略對應的論文與系統見 `04`。

## 2. 共用的演算法

**名詞**
- **chunk**：512 個 token 的 KV。Llama-3.1-8B 每個 chunk 是 64 MiB〔計算：512 × 128 KiB〕。
- **f(i)**：重算第 i 個 chunk 的時間（前面 1..i−1 的 KV 已經在 GPU 上）。由 C1 實測，越後面越大。
- **ℓ(層)**：從某一層搬一個 chunk 到 GPU 的時間。由 C2 實測；SSD 層由限速器決定（演算法 4）。

```
演算法 1　寫入分界 b：在寫入當下，估計 Cake 回來時會在哪裡會合
輸入：這個 session 目前的 chunk 數 n；重算時間 f(1..n)；目標層每個 chunk 的載入時間 ℓ
輸出：b，也就是預期回來時會被重算的前段 chunk 數
1: 對每個候選的會合點 m = 0, 1, …, n：
2:     重算線要花的時間 R(m) ← f(1) + f(2) + … + f(m)
3:     載入線要花的時間 D(m) ← (n − m) × ℓ
4:     這個會合點的還原時間 T(m) ← max(R(m), D(m))      （兩條線同時跑，等較慢的那條）
5: 回傳 使 T(m) 最小的 m
說明：只用寫入當下知道的常數，並假設回來時 GPU 是閒的。不看未來。
```

```
演算法 2　Cake 雙向還原（R0 以外的所有策略共用）
輸入：session s 的 n 個 chunk，以及每個 chunk 存在哪些層
輸出：GPU 上完整的 KV，以及第一個輸出 token
 1: 前指標 p ← 1；後指標 q ← n
 2: 同時啟動兩條線；任一條線要取 chunk 時，先鎖住兩個指標
 3:   重算線（GPU）：
 4:     當 p ≤ q：
 5:       取第 p 個 chunk，然後 p ← p + 1
 6:       用第 1..p−1 個 chunk 的 KV 重算它（這些 KV 已經依序算好）
 7:   載入線（I/O）：
 8:     當 q ≥ p：
 9:       如果第 q 個 chunk 沒有存在任何一層：載入線結束，剩下的留給重算線
10:       否則：取第 q 個 chunk，然後 q ← q − 1，從它所在最快的層搬到 GPU
11: 兩條線都結束時（p > q），所有 chunk 的 KV 都在 GPU 上
12: 計算新一輪的 256 個 token，輸出第一個 token（TTFT 量到這裡）
說明：會合點是動態決定的。GPU 忙時重算線變慢，載入線就會多搬幾個；
      但沒存的 chunk 不能搬，只能等重算線算到它。
```

```
演算法 3　只載還原（只有 R0 用；和 vLLM、LMCache 的語意一致）
輸入：同演算法 2
輸出：同演算法 2
1: i ← 1
2: 當 i ≤ n 而且第 i 個 chunk 有存：從它所在最快的層搬到 GPU，i ← i + 1
3: 從第 i 個到第 n 個 chunk：依序重算        （只認連續前綴，第一個缺的之後全部重算）
4: 計算新一輪的 256 個 token，輸出第一個 token
```

```
演算法 4　模擬的 SSD（CPU 記憶體＋限速器）
說明：「SSD 層」的資料其實放在 pinned CPU 記憶體，時間依照參數決定。
參數：讀取頻寬 B讀、寫入頻寬 B寫、每次 I/O 的固定開銷 c（都由 C2 實測）
狀態：t空閒，裝置下一次空閒的時間。讀和寫共用這個值，所以寫入會拖慢讀取
讀一個大小為 S 的 chunk：
1: 開始 ← max(現在, t空閒)
2: 完成 ← 開始 + c + S ÷ B讀；t空閒 ← 完成
3: 把資料從 pinned CPU 記憶體真實複製到 GPU（真實的 PCIe 搬運）
4: 等到 max(完成, 真實複製結束)，才把這個 chunk 交給 GPU 使用
寫一個大小為 S 的 chunk（在背景執行緒）：
5: 開始 ← max(現在, t空閒)
6: 完成 ← 開始 + c + S ÷ B寫；t空閒 ← 完成
7: 把資料從 GPU 真實複製到 pinned CPU 記憶體，然後等到「完成」
```

```
演算法 5　服務一輪（所有策略共用）
輸入：策略 P；session s
1: 如果 s 是回來的 session：照 P 的「回來時」還原（演算法 2 或 3）
2: 生成這一輪的回答
3: 寫入時：對這一輪新增的 chunk，照 P 的「寫入時」規則放
4: 當 CPU 用量 > CPU 容量：照 P 的「CPU 滿時」規則處理一次，重複到不超過為止
5: 當 SSD 用量 > SSD 容量：照 P 的「SSD 滿時」規則處理一次，重複到不超過為止
6: 釋放 GPU 上的 KV（GPU 只放正在服務的請求）
說明：每輪只處理新增的 chunk。已經存過的 chunk 不會因為 b 變了就重新搬，
      只會在空間不夠時被搬走或刪掉。這讓每輪的寫入量可以互相比較。
```

**策略裡用到的動作**
- **寫到（c, 層）**：CPU 層是真實的 GPU→CPU 複製；SSD 層走演算法 4，在背景執行。
- **刪掉（c, 層）**：只刪那一層的那一份。
- **降級（c）**：把 c 寫到 SSD，然後刪掉 CPU 那一份。也就是「被擠出來時才寫」。

## 3. 各策略的演算法

```
策略 R0　業界現狀（參考，不用 Cake）
寫入時：  1: 每個新 chunk 寫到 CPU，也寫到 SSD（寫穿）
CPU 滿時：2: 刪掉最久沒用的 session 在 CPU 的那一份（SSD 還有一份）
SSD 滿時：3: 刪掉最久沒用的 session 在 SSD 的那一份
回來時：  4: 只載還原（演算法 3）
```

```
策略 S0　純 Cake：全存單層
寫入時：  1: 每個新 chunk 寫到 SSD
SSD 滿時：2: 刪掉最久沒用的 session 在 SSD 的 chunk
回來時：  3: Cake 雙向還原（演算法 2）
```

```
策略 S1　寫穿＋LRU（只有回來時和 R0 不同）
寫入時：  1: 同 R0
CPU 滿時：2: 同 R0
SSD 滿時：3: 同 R0
回來時：  4: Cake 雙向還原
```

```
策略 S2a　先寫再丟
寫入時：  1: b ← 寫入分界（演算法 1，目標層＝SSD）
          2: 每個新 chunk 寫到 SSD
          3: 寫完之後，立刻刪掉其中位置 ≤ b 的 chunk
SSD 滿時：4: 同 S0
回來時：  5: Cake 雙向還原
```

```
策略 S2b　寫穿＋成本感知逐出
寫入時：  1: 同 R0（CPU、SSD 各寫一份）
CPU 滿時：2: 刪掉 CPU 裡最便宜的 chunk 的那一份（SSD 還有一份）
SSD 滿時：3: 刪掉 SSD 裡最便宜的 chunk
回來時：  4: Cake 雙向還原
```

```
策略 S3　一開始不寫
寫入時：  1: b ← 寫入分界（演算法 1，目標層＝SSD）
          2: 新 chunk 中，位置 > b 的寫到 SSD；位置 ≤ b 的不寫
SSD 滿時：3: 同 S0
回來時：  4: Cake 雙向還原（沒存的前段只能由重算線做）
```

```
策略 S4　延後寫入（write-back）＋LRU
寫入時：  1: 新 chunk 只寫到 CPU，不寫 SSD
CPU 滿時：2: 把最久沒用的 session 在 CPU 的 chunk 全部降級到 SSD（這時才寫）
SSD 滿時：3: 刪掉最久沒用的 session 在 SSD 的 chunk
回來時：  4: Cake 雙向還原
```

```
策略 S4+　延後寫入＋成本感知
寫入時：  1: 同 S4（只寫到 CPU）
CPU 滿時：2: 把 CPU 裡最便宜的 chunk 降級到 SSD（這時才寫）
SSD 滿時：3: 刪掉 SSD 裡最便宜的 chunk
回來時：  4: Cake 雙向還原
```

```
策略 S5　寫入時依位置放（本研究，初階）
寫入時：  1: b ← 寫入分界（演算法 1，目標層＝CPU）
          2: 新 chunk 中，位置 ≤ b 的寫到 SSD    （前段：平常重算，放便宜的層當備份）
          3: 新 chunk 中，位置 > b 的寫到 CPU    （後段：一定要搬，放快的層）
CPU 滿時：4: 同 S4+（把最便宜的 chunk 降級到 SSD）
SSD 滿時：5: 同 S4+（刪掉最便宜的 chunk）
回來時：  6: Cake 雙向還原
說明：CPU 比 SSD 快，所以以 CPU 為目標層算出的 b，會比 S2a、S3 的 b 小。
```

## 4. 每兩組之間只差一件事

| 比較 | 差的那件事 | 回答什麼 |
|:--|:--|:--|
| R0 vs S1 | 只載 vs Cake；寫入和逐出完全相同 | Cake 本身比業界現狀好多少 |
| S2a vs S3 | 最後留下的東西完全一樣，差在前段有沒有先寫過 | 寫入這個動作本身，有沒有讓人多等（老師 Q1） |
| S0 vs S3 | 前段有沒有備份 | GPU 忙時沒備份要付多少代價（老師 Q2） |
| S1 vs S4 | 寫穿 vs 延後寫入（都用 LRU） | 延後寫入本身值多少 |
| S1 vs S2b、S4 vs S4+ | LRU vs 成本感知（寫入時機相同） | 成本感知逐出本身值多少 |
| **S4+ vs S5** | **只差寫入時那一步**：空間不夠時兩者做法完全一樣 | **「寫入當下就決定」到底有沒有用。這是最關鍵的一組** |
| S2b vs S5 | 寫兩份再挑 vs 依位置只寫一份 | 少寫的那一份值不值得 |

## 5. 老師點名的做法，跟本研究差在哪

| | 什麼時候決定 | 依什麼決定 | 前段有沒有備份 | 每段寫幾次 |
|:--|:--|:--|:--|:--|
| 先寫再丟（S2a） | 寫入當下 | 位置 | 沒有 | 1（前段白寫） |
| 一開始不寫（S3） | 寫入當下 | 位置 | 沒有 | 前 0、後 1 |
| 延後寫入（S4） | 空間不夠時 | 最久沒用 | 有 | 0 或 1 |
| 成本感知逐出（S2b） | 空間不夠時 | 位置（重算成本） | 有，被丟之前都在 | 2 |
| 延後＋成本感知（S4+） | 空間不夠時 | 位置 | 有 | 0 或 1 |
| **本研究（S5）** | **寫入當下** | **位置** | **有** | **1** |

本研究只有「寫入當下就決定」這一點是其他做法沒有的。所以要量的就是：

- **可能贏**：延後寫入在空間不夠的那一刻，要一口氣寫一大批到 SSD。如果這批寫入擋到正在回來的人，或 SSD 寫得很慢，就會讓人多等。本研究平常就把前段寫掉了，不會在最擠的時候大量寫入。
- **可能輸**：使用者常常不回來，或 CPU 一直夠用。這時本研究的前段白寫了，延後寫入一次都不用寫。

## 6. 兩個要注意的地方

1. **R0 的命中規則不同。** R0 只認連續前綴，和 vLLM 一致。其他策略的 Cake 還原允許「後段有、前段沒有」。結果要分開說明，不能混在一起比。
2. **多輪對話時只處理新增的 chunk。** b 會隨著對話變長而改變，但已經存好的 chunk 不重新搬。如果要做「每輪重新放置」，那是第二版的設計，要另外當成一組來比。
