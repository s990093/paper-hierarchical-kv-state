## 2. I/O 怎麼模擬：CPU 層和 SSD 層都用限速器（但先實測）

這是 Cake 自己的方法（延遲注入），也是 RESEARCH_INTRO §13 原本的規劃。這裡再多做一步：**CPU 層也用限速器**，讓每個策略看到的速度完全一樣，不受鄰居影響。

**做法分三步：**
1. **先測速**（C0、C2）：在不同時段至少量 3 次，量 pinned 記憶體的 H2D、D2H，以及本地 SSD、NFS 的讀寫。報最慢、中位數、最快。
2. **再定模擬速度**：每一層的模擬頻寬，設得**比實測最慢的時候再慢一點**（例如取實測的最小值再打九折〔設計值〕）。這是因為限速器只能讓搬運「變慢」，不能讓它「變快」：完成時間＝max（真實搬完、模擬時間）。模擬速度設得比真實最慢還慢，才能保證每次都是模擬時間說了算，鄰居再怎麼搶也不影響結果。
3. **最後用錨點對照**（C7）：在幾個點上比較「模擬」和「真實搬運」差多少，寫進每張圖。演算法見 `03` 演算法 4。

| 參數 | 設定 | 為什麼 |
|:--|:--|:--|
| CPU 層頻寬 | C0 實測的 pinned H2D（讀）、D2H（寫），依上面第 2 步設定。既有量測 50.8／48.6 GB/s（`gpu_smoke.py`，會受鄰居影響） | 讓 CPU 層的速度對每個策略都一樣 |
| SSD 層讀取頻寬 | 主要兩點：C2 在這台機器上**實測**的本地 SSD、NFS 讀取頻寬。敏感度分析另加 Cake 用過的 7、25、32、56、100 Gbps | 實測點讓結果貼近這台機器；Cake 的點讓結果能和 Cake 對照。既有量測（O_DIRECT 循序、8 GiB × 3 次）：本地 SSD 讀 5,392 MiB/s、NFS 讀 289 MiB/s（RUNLOG_MI300X）。C2 要再量一次，因為鄰居會影響 |
| SSD 層寫入頻寬 | C2 實測的**持續**寫入頻寬 | 既有量測：本地 SSD 寫 1,886 MiB/s、NFS 寫 683 MiB/s（同上）。本地 SSD 的寫入比 3090 的 QLC（181 MiB/s）快很多，所以在這台機器上，「省下寫入」的價值可能比較小。這本身就是 Q1 要回答的 |
| 每次固定開銷 c | C2 用「不同大小的讀取時間」做迴歸，取截距 | Cake 原文沒講清楚有沒有這一項；CacheFlow 的 Fig. 2 顯示它不能忽略 |
| 在途 I/O 數 | 1（主要）；敏感度分析用 4 | 寫明 |
| 讀寫是否共用頻寬 | 共用：讀和寫共用同一個「裝置空閒時間」 | 用最簡單的模型表達「寫入會搶讀取」。B 實驗的寫入干擾靠這個模型，所以要和 A2 的真實裝置結果對照 |
| 單位 | 一律寫 GiB/s；從 Gbps 換算時註明用 10⁹ | Cake 的 Gbps 單位有歧義 |

**限速器看不到的事**（每張用限速器的圖都要註明）：
- 真實裝置的寫入懸崖（只能用參數近似）；
- page cache；
- 檔案系統、overlay、LVM 和軟體層的開銷：RUNLOG 發現 11 顯示，vLLM 的 SSD 層約 65% 的時間是軟體開銷；
- **鄰居**：8 張卡共用主機的 PCIe root complex 與本地磁碟。用了限速器之後，鄰居不會影響結果；但這也代表真實世界裡「被鄰居拖慢」的情況，不在模擬結果裡。

所以 C7 要在錨點上對照限速器和真實裝置，A2 的寫入干擾要用真實裝置量。

## 3. 實驗

### C　校準：先過這關，才做比較

**為什麼**：如果 harness 算錯、限速器不準，或雜訊比差距還大，之後所有比較都沒有意義。

| 代號 | 做什麼 | 產出 | 不過關時 |
|:--|:--|:--|:--|
| C0 | **I/O 路徑盤點與測速**（不同時段至少 3 次）：GPU 的 PCIe 世代與寬度（用 `rocm-smi`／`amd-smi`，指令以 Lab 上實際能用的為準）；pinned 與 pageable 記憶體的 H2D、D2H 頻寬（既有量測 50.8／48.6 GB/s，`gpu_smoke.py`，會受鄰居影響）；檔案讀寫有沒有經過 page cache；本地 SSD 與 NFS 的裸頻寬 | 一張路徑圖，每一段都附實測頻寬 | — |
| C1 | 逐 chunk 重算曲線 f(i) | 確認「越後面越貴」（Cake Fig. 4 的趨勢） | 曲線不隨位置上升 → 停下來回報，因為 Cake 的前提不成立 |
| C2 | 載入與寫入成本：CPU→GPU（真實）；本地 SSD、NFS 的讀寫（含持續寫入）；用不同大小做迴歸求固定開銷；不同時段至少 3 次 | 每一層的實測範圍（最慢、中位數、最快）→ 限速器的參數（§2 第 2 步） | — |
| C3 | 會合點校準：用 C1、C2 預測會合點，再和 harness 實測對照 | 預測 vs 實測 | 差超過 1 個 chunk → 先修 harness，不做比較 |
| C4 | **雜訊底線**：同一設定（S0、L=16K、GPU 閒、限速器）重跑 10 次，每次重開 process；另外在同一個 process 內連續跑 10 次；兩組分別在不同時段各做一次，看鄰居的影響 | 中位數、95% CI、變異係數 → 雜訊底線 δ | δ 太大（§6）→ 找老師討論。如果兩種跑法的變異差不多，大部分重複可以在同一個 process 內做（每組先暖機）；關鍵比較仍用重開 process 的 run |
| C5 | GPU 忙的模擬：在同一張卡上跑背景負載（小記憶體的 matmul 迴圈，用 duty cycle 調強度），找出兩個強度，讓 chunk 重算約慢 1.5 倍和 2 倍〔設計值〕 | 兩個強度，以及**實測**的變慢倍數 | — |
| C6 | 和真實系統對照：同一個 L，比較 vLLM＋`OffloadingConnector`（CPU 層、只載入）和 harness 的只載入 | 兩者差多少、差在哪 | 差距本身就是結果，不擋進度 |
| C7 | **限速器自檢與錨點**：(1) 設定頻寬 X，量到的有效頻寬要接近 X；(2) 在 L=8K、16K、32K，把「限速器設成實測參數」和「真的搬」放在一起比：CPU 層（真的 H2D）、本地 SSD、NFS 各一組 | 自檢誤差；限速器與真實裝置的差距 | 自檢誤差 > 5%〔設計值〕→ 先修限速器。和真實裝置的差距不擋進度，但要照實報告 |

**正確性檢查**（AMD 版）：

平台 B 上已經發現，同一個模型在不同設定下輸出不完全相同：GSM8K 60 題 × 3 設定，有 36/120 的輸出 sha1 不同（RUNLOG_MI300X 發現 13）。原因可能只是 ROCm 的注意力 kernel 在不同分塊下的浮點差異，還沒有定論。所以不能直接要求「生成的 token 完全一致」。做法改成三步：

1. **先做對照**：同一個設定（整段 prefill）跑兩次，看輸出是否逐 token 相同。這一步告訴我們平台本身是不是確定性的。
2. **檢查 KV（主要判準）**：
   - 載入的 chunk 是位元組複製，必須**逐位元組相同**；
   - 重算的 chunk，和「用同樣切法」重算的參考 KV 比較，報最大絕對誤差。
3. **檢查生成**：如果第 1 步顯示平台本身就不是位元相同，就不要求 32 個 token 完全一致，改報一致率，並和第 1 步的對照放在一起比。

### A0　純 Cake 跑通（老師說的「把最接近的 baseline 跑通」）

**為什麼**：之後所有策略都用 Cake 還原。如果 Cake 在這台機器上沒有好處，或我們的實作是錯的，後面的比較都站不住。

| 項目 | 設定 |
|:--|:--|
| 寫入 | S0：全部存在模擬的 SSD 層 |
| 還原方式 | 只算、只載、Cake 雙向，三種都跑 |
| 自變數 | L ∈ {4K, 8K, 16K, 32K}；讀取頻寬：Cake 的 7、25、32、56、100 Gbps，加上 C2 實測的本地 SSD、NFS |
| 重複 | 每格 ≥6 次 |
| 量什麼 | 三種還原的 TTFT；Cake 對只算、對只載的加速比；會合點 |
| 怎麼算跑通 | 硬體不同，**比趨勢，不比絕對值**（EVAL_FOUNDATIONS §9.2）：(1) 對只算的加速隨長度變大；(2) 對只載的加速隨頻寬變大而變小；(3) Cake 不比只算或只載慢 |
| 沒跑通時 | 停下來找老師 |

這一組也順便回答 H1 的一小部分：在 4K–32K 之間，Cake 的好處會不會隨長度變小。MI300X 的算力比 3090 高很多〔推論，規格層級〕，會合點可能落在不同位置，這也是要量的。

### A1　單一 session：寫入與還原（回答老師的 Q1、Q2、Q3）

**為什麼**：沒有容量壓力時，最容易看清楚「少寫」和「沒有備份」各自的效果。

| 項目 | 設定 |
|:--|:--|
| 流程 | prefill 長度 L 的歷史 → 依策略寫入 → 清掉 GPU 上的 KV → 還原，加上新的 256 token → 量 TTFT |
| 策略 | S0（純 Cake）、S2a、S3、S5；另加「全放 CPU」當上界參考 |
| 自變數 | L ∈ {4K, 8K, 16K, 32K}；GPU ∈ {閒, 忙 1, 忙 2}（C5）；SSD 層頻寬 ∈ {實測本地 SSD, 實測 NFS} |
| 重複 | 每格 ≥6 次 |
| 量什麼 | TTFT 和拆解（§5）；會合點；GPU 實際重算了幾個 chunk、花了多少 GPU 時間；寫入多少位元組、花多久；寫入有沒有擋住下一個請求 |

〔假設，待驗證〕
- GPU 閒時，S0、S2a、S3 的 TTFT 差距在雜訊內；
- GPU 忙時，S3 比 S0 慢；
- S5 比 S0 快，因為後段從 CPU 載入。

### A2　寫入會不會拖慢別人（回答 Q1 的另一半）

**為什麼**：A1 只看自己回來時。省下的寫入，也可能幫到「同一時間正在載入的別人」，而這只有在真實裝置上才看得到。

| 項目 | 設定 |
|:--|:--|
| 流程 | session X 從 SSD 還原的同時，背景有另一個 session 正在寫它的 KV |
| 自變數 | 背景寫入量：S0、S2a 的全量，S3 的部分量，不寫入；裝置：真實本地 SSD（`/var/tmp`）、真實 NFS（`/mlsteam/data/tiara`） |
| 量什麼 | X 的 TTFT 和讀取時間，比較有沒有背景寫入 |
| 為什麼分兩種裝置 | 本地 SSD 寫得快，NFS 寫得慢、讀更慢。如果「省下寫入」有價值，最可能出現在 NFS 上，或鄰居也在用磁碟的時候 |
| 為什麼用真實裝置 | 限速器看不到真實的讀寫干擾。同一組也用限速器跑一次，兩者的差距就是 B 實驗裡寫入干擾模型的誤差 |
| 注意 | 本地 SSD 是整台主機共用的。每次 run 前後都要看 `/proc/diskstats`（§5.2），有外來 I/O 的 run 作廢 |

### B　多 session、容量有限：簡單策略會不會追平（回答 Q4、Q5）

**為什麼**：延後寫入、成本感知逐出這些方法，只有在空間不夠時才會表現出差別。這是老師最在意的「是不是強 baseline 還做不到」。

| 項目 | 設定〔設計值，開跑前固定並記錄〕 |
|:--|:--|
| 情境 | 長 context 的多輪對話與 agent，使用者隔一段時間才回來（`02` §1） |
| 參數從哪來 | 先用下面的設計值跑通。正式版改成從有時間戳的真實 trace 取：每輪追加多少、隔多久回來、多少比例不回來。候選是 Mooncake 的 conversation／toolagent（hash 是 512-token block，載入時要驗算，CLAUDE.md 規則 6）和 TraceLab（EVAL_FOUNDATIONS §10.4）。用哪一種、怎麼縮放，開跑前寫死 |
| session | 8 個；每個 4 輪；每輪在後面追加 8K，歷史從 8K 長到 32K |
| 回來的順序 | 用固定的 seed 隨機產生；每個 session 在某一輪後有 25% 機率不再回來（讓延後寫入有機會「一次都不用寫」） |
| 服務方式 | 一次服務一個請求，照順序（不做 batching）。寫入在背景進行，會和下一個請求的載入互相干擾 |
| 工作集 | 最多約 32 GiB〔計算：8 × 4 GiB〕 |
| CPU 容量 | 工作集的 25%、50%、100%（8、16、32 GiB） |
| SSD 容量 | 不限；另加一組 50% |
| SSD 層頻寬 | 限速器，用實測的 NFS 參數（最慢，最容易看出寫入的影響）；關鍵比較另外用實測的本地 SSD 參數跑一次 |
| 策略 | R0（參考）、S0、S1、S2b、S3、S4、S4+、S5 |
| 重複 | 關鍵比較（S5 vs 最好的簡單策略，在 25%、50% 兩個容量）每格 6 次；其他格先跑 3 次，標為「探索」 |
| 量什麼 | 每次回來的 TTFT（中位數、平均、P90，附 CI）；各層命中分布（CPU、SSD、缺少）；總寫入位元組；GPU 重算時間 |

如果時間不夠，可以用舊的 M4 模擬器（commit `9deda4f` 的 `code/m4_oracle.py`），拿 C1、C2 的常數延伸容量掃描。但要先用 B 的真機結果驗證模擬器，結果也要標「模擬」。

## 4. 每個實驗回答什麼

## 5. 量測方法

### 5.1 時間拆解（要給老師看的那張圖）

還原時有兩條線同時跑：**重算線**（GPU 算前段）和**載入線**（從 CPU 或 SSD 搬後段）。每次還原記錄下面這些欄位；GPU 上的時間用 `torch.cuda.Event`（在 ROCm 上是 HIP event）計，I/O 用 CPU 時戳計。

| 欄位 | 意思 |
|:--|:--|
| `t_recompute`、`n_recompute` | 重算線花的時間，和重算了幾個 chunk |
| `t_load_cpu`、`t_load_ssd` | 載入線從 CPU、從 SSD 各花多少時間，各搬了幾個 chunk |
| `t_wait` | 兩條線會合之前，先做完的那一條空等了多久 |
| `t_new` | 算新的 256 token，加上第一個輸出 token |
| `TTFT` | 從請求到第一個 token |
| `t_write`、`bytes_write` | 寫入花多久、寫了多少；寫入有沒有擋住下一個請求 |

### 5.2 I/O 與爭用的檢查

限速器不碰磁碟。以下 page cache 和磁碟的檢查，只用在真實裝置的量測：C0、C2、C7 的錨點、A2。

- **page cache**：container 裡就算是 root，也不一定能 `drop_caches`。所以一律改用：
  - 每次還原前，對 KV 檔呼叫 `posix_fadvise(POSIX_FADV_DONTNEED)`；
  - 或用 `O_DIRECT` 讀，緩衝區要頁對齊，用 `mmap.mmap(-1, n)` 取得（RUNLOG 的技術註記；平台 B 的 disk_bw 也是用 O_DIRECT 量的）。
- **確認真的讀了磁碟**：比對還原前後 `/proc/self/io` 的 `read_bytes`。讀了 4 GiB 的 KV，`read_bytes` 卻接近 0，代表命中了 page cache，這筆量測作廢。NFS 有自己的客戶端快取，要另外確認。
- **磁碟爭用**：每次 run 前後讀 `/proc/diskstats`，看 sda 的總 I/O 量。container 看到的是整台主機的 sda，所以這裡也包含鄰居的 I/O。比我們自己的量多出很多，就是有外來 I/O，在 run 目錄留下 `CONTAMINATED_DISK`。
- **GPU 爭用**：卡是獨佔的，主要風險來自鄰居佔用 PCIe 和主機記憶體頻寬。需要 AMD 版的爭用檢查：舊 `gpu_guard.py` 的 AMD 後端在平台 B 上修過（RUNLOG_MI300X 發現 1、6），可以從 commit `9deda4f` 取回。C5 的背景負載是我們自己的 PID，要列進白名單，不能被當成外來 process。
- **被污染的 run**：時間欄位一律作廢重量（CLAUDE.md §3）。

### 5.3 統計

- 每個點至少 6 次；報中位數和無母數 95% CI（EVAL_FOUNDATIONS §10.6）。
- 樣本只有幾十個時，不報 P99，改報 P90 並附 CI。
- 同時報平均和中位數。Fancy-eviction 的成本感知逐出就是平均變好、中位數變差。
- 兩組的差距要同時滿足兩個條件才算數：**大於雜訊底線 δ**，而且**兩組的 CI 不重疊**。

## 6. 判準（開跑前寫死，不准事後改）

| 問題 | 判讀 |
|:--|:--|
| C4 雜訊 | δ（C4 中位數的 95% CI 半寬 ÷ 中位數）> 10%〔設計值〕，就分辨不出 5% 的差距 → 先找老師討論，例如換時段跑，或改用別台機器 |
| 正確性 | 載入的 chunk 不是逐位元組相同 → 停；重算 chunk 的 KV 誤差比第 1 步的對照大很多 → 停 |
| A0 | Cake 跑通的三個趨勢條件，任一個不成立 → 停下來找老師 |
| Q1 | S3 在 A1、A2、B 都沒有讓任何人的 TTFT 比 S2a 短超過 δ → 結論：**省下的寫入沒有縮短等待，只剩下空間的價值** |
| Q2 | 報 S3 相對 S0，在 GPU 忙 1、忙 2 時慢多少，附 CI |
| Q4 | 在 B 的 25%、50% 兩個容量，比較 S5 和**最好的簡單策略**（S0、S1、S2b、S4、S4+ 中 TTFT 中位數最低的那一個；R0 只當參考）：**< 5%** → 簡單策略追平，照實寫成「何時不值得做」，調整方向；**5–15%** → 把數字交給老師判斷；**> 15%，而且大於 δ** → 進第二階段。門檻和專案的 go/no-go 規則一致 |
| Q5 | 某個容量下所有策略的 TTFT 都在雜訊內 → 那個容量下空間不是瓶頸，「省空間」在那裡沒有用 |
| 好處從哪來 | 用 `03` §4 的成對比較，拆出多少來自分層、多少來自依位置放、多少來自寫入時決定 |

## 8. 這樣比公平嗎？和主流論文的做法對照

**資料集**：第一階段**不需要品質資料集**。精度固定 BF16，搬的是原始位元組，輸出不會因策略而改變，要比的只有時間。Cake 也是用合成的 prompt，原文的理由是只有 token 長度會影響時間（ICML p5；E03）。真正要從真實資料取的是**負載的結構**：每輪追加多少、隔多久回來、多少比例不回來。正式版從 Mooncake、TraceLab 等有時間戳的 trace 取（B 實驗「參數從哪來」）。品質資料集（RULER、LongBench、SCBench）到第二階段的精度才需要。

| 面向 | 主流論文怎麼做（出處） | 我們 | 評語 |
|:--|:--|:--|:--|
| 模型 | Llama-3.1-8B 很常見：Cake、Strata、LMCache；Tutti、KVDrive 用 Llama-3-8B（E03、E04） | Llama-3.1-8B BF16 | ✅ 主流 |
| 負載 | 長 context 的跨請求重用，多半是「少量長文件被多次查詢」，用抽樣構造；主實驗有真實時間戳的只有 Mooncake、Bidaw（E04 共同模式 4）。Cake 是單一請求、沒有到達過程（E03） | 先用設計值；正式版從真實 trace 取參數 | ✅ 和主流相同或更接近真實 |
| 長度 | Cake 4K–16K；LMCache 10K–20K；Mooncake 平均約 12K；Strata 平均最長約 55K；Tutti 3K–200K（E03、E04 共同模式 4） | 4K–32K（可加 64K） | ✅ 和 Cake、LMCache 同一範圍；比 Tutti、KVDrive 短 |
| 到達與併發 | 多數用 Poisson 掃請求率，有併發（Strata、LMCache 等，E04） | **一次服務一個請求，照順序** | ⚠️ **最大的差異**。比較簡單，但可能低估搶資源的情況。寫入在背景進行，算是補了一部分 |
| 程式 | 多數改 vLLM 或 SGLang；Cake 改了 vLLM v0.6.2 約 1,000 行（E03） | 自寫 harness，另用 vLLM 當對照（C6） | ⚠️ 兩週內的合理做法，但不是完整的 serving 系統，要先問老師 |
| 慢層 I/O | 常常是模擬的：Cake 用延遲注入，Bidaw 用注入延遲模擬 5 GB/s，Mooncake 模擬 24–400 Gbps；端到端真的讀 SSD 的不多（E04 共同模式 1） | 限速器模擬，再加真實裝置的錨點（C7） | ✅ 和主流相同，校準更嚴 |
| GPU 容量 | 會刻意限制，例如 Strata 在 ShareGPT 上把 GPU 限制在約 500K token，凸顯分層的效果（E04 Strata 卡） | GPU 只放正在服務的請求 | ✅ 有前例，結果要註明 |
| 對手 | 常常是作者自己重做（E04 共同模式 6）；Cake、Pensieve 沒有公開程式碼（E03） | 全部在同一個 harness 重做 | ✅ 公平：條件完全相同 |
| 指標 | TTFT、同 TTFT 下的吞吐、命中率；倍數的定義各篇不同（E04 共同模式 5） | TTFT 的中位數、平均、P90，加上時間拆解與寫入量 | ✅ 多報了寫入的代價 |
| 重複與統計 | E04 的 8 篇都沒寫重複次數或誤差棒；Cake 也沒有（E03、E04 共同模式 6） | 每格至少 6 次，附 95% CI，先量雜訊底線 | ✅ 比主流嚴 |
| 品質 | 無損的系統論文都不量品質：Cake、Strata、LMCache（E03、E04） | 不量，只做 KV 的正確性檢查 | ✅ 一致 |

**結論**〔判讀〕：
- **策略之間是公平的**：所有策略在同一個 harness、同一個模型、同一台機器、同一份負載上跑。
- **和主流的做法大致一致**，統計上更嚴。
- **最大的差距是真實度**：一次只服務一個請求，而且用的是 harness，不是完整的 serving 引擎。

這兩點要寫進結果的限制，也是第一階段之後要補強的方向：
1. 加入併發，例如同時 2–4 個請求、閉迴路；
2. 接到 vLLM 或 SGLang 上；
3. 換一個平台重量。
