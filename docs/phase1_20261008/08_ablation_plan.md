# 08 消融實驗：什麼條件下「寫入時就決定」不會被 Cake 抵消（開跑前寫死）

**日期**：2026-10-09（第一階段報告 `07_report.md` 之後）
**狀態**：設計，開跑前寫死。本檔沒有任何實驗結果。

## 0. 為什麼要做

第一階段的結論是 S5 ≈ S4+，而且容量緊時兩者都輸給 LRU。可能的解釋是：Cake 在**讀取時**就會依資料實際在哪一層決定會合點，
所以**寫入時**依位置先放好，只是在重複 Cake 本來就會做的事。

要回答的問題：**寫入時的決定，在什麼條件下是讀取時補不回來的？** 做法是從 B 主設定出發，一次只改一個因子。

寫入時的決定能做到、讀取時做不到的事只有三種：
1. **省快的層的空間**：預期會被重算的前段，一開始就不放進 CPU。
2. **省寫入**：預期會被重算的前段，乾脆不寫，或只寫一份。
3. **改變寫入時間**：在空間還夠時先把資料寫到慢的層，而不是等空間滿了、在壓力下才搬。

第 1、2 點在第一階段已經測過，效果很小。第 3 點因為 D9 的簡化（搬走時 CPU 空間立刻釋放）而**完全沒有被測到**。

## 1. 基準設定（與 B 主設定相同）

- SSD 層用 NFS 參數，干擾模型 share，workload seed 0，請求間隔 gap＝0。
- CPU 容量 25%、50%。只統計回來的請求（第 2 輪起）的 TTFT。

## 2. 因子（一次只改一個；先在模擬器上掃，再挑幾組上 GPU）

| # | 因子 | 水準（第一個是基準） | 為什麼 |

## 3. hold 的定義（對所有策略一視同仁）

- 一個 chunk 只要正在被寫往 SSD，就占著一格 CPU 空間，直到寫完。適用的情況：
  - 從 CPU 被搬走（降級）時；
  - 寫入時直接寫往 SSD（經過 CPU 的暫存區）時。
- 寫穿（S1）時，CPU 那份本來就在，不另外占空間。但如果在 SSD 那份還沒寫完前就要把它從 CPU 丟掉，一樣要等寫完。
- 下一個請求必須等「CPU 已用＋寫往 SSD 中的 chunk 數 ≤ 容量」才能開始，因為 GPU 上前一輪的 KV 必須先卸載出去。等待時間算在 TTFT 裡。

## 4. 新增的策略（寫入時決定的變體，全部在開跑前列出）

| 策略 | 寫入 | CPU 滿時 | 對照組（只差寫入那一步） |
|:--|:--|:--|:--|
| S4L | 全部寫 CPU | 最久沒用的 session，從它最前面的 chunk 開始搬到 SSD，一次一個 chunk | — |
| S5L | i < b_cpu → SSD，其餘 → CPU | 同 S4L | S4L |
| S5P | 同 S5 | 同 S4+P（V＝f(i)/T） | S4+P |
| S5c | 全部寫 CPU，**另外**把 i < b_ssd 的 chunk 先複製一份到 SSD（預先複製） | 同 S4+（前段先走）；已經有 SSD 副本的直接丟，不用再寫 | S4+ |

既有策略不變：R0、S0、S1、S2b、S3、S4、S4+、S4+P、S5、S5s。

## 5. 方法

1. **模擬器 `code/m7_sim.py`**：用和 GPU harness **同一份** BState（寫入／淘汰邏輯）和同一個限速器，只是時間是虛擬的；重算一個 chunk 的時間用 C1 的 f(i)。
2. **模擬器驗證（先做，沒過就不用模擬器下結論）**：拿第一階段 B 的 9,300 列實測，逐格（設定 × 策略 × 容量）比較回來請求的 TTFT 中位數。
   - **通過條件**：≥90% 的格誤差在 ±10% 內；而且實測「S5 vs 最好簡單策略」差距 >5% 的格，模擬器要給出同樣的方向。
3. **掃描**：F1–F7 各自掃（模擬，標〔模擬〕），再做組合。
4. **GPU 確認**：模擬裡最有希望的設定，最多挑 4 組上 GPU 實測。每組 3 次，若結果落在判準邊界（±3% 內），補到 6 次。

## 6. 判準（開跑前寫死）

- **比較對象**：寫入時決定的策略（S5、S5L、S5P、S5c、S5s），對上「寫入不看位置的最好策略」（S0、S1、S2b、S4、S4+、S4+P、S4L 裡最好的）。比的是回來請求 TTFT 的中位數。
- **在 GPU 上實測**才算數：≥5% 算「有條件有效」；≥15% 算「強」。模擬器的結果只能拿來挑設定，不能拿來下結論。
- **多重比較**：所有試過的設定與策略都列在報告裡（包括沒用的），報告寫明總共試了幾組。
- 如果所有設定都 <5%：結論是「在這個硬體與模型上，寫入時的位置決定被 Cake 的讀取時調整抵消」，並列出模擬器指出的可能例外條件，等之後驗證。

## 8. 修正紀錄（開跑後才加的，照實列出）

- **2026-10-09 06:51，看過第一次模擬掃描（run `20261009-064926-m7-sim-sweep`）之後**：模擬裡贏最多的是 S5L（對 S4L 最多 +69%），而且只在「淘汰看最久沒用」的那一組出現。
  這可能不是「**寫入時**決定」的功勞，而是「分界 b 以前的 chunk 放在 CPU 沒有價值」這個**規則**的功勞；這個規則也可以等空間滿了才套用。
  所以加一個對照組 **S4B**：全寫 CPU，滿了才先搬 i<b_cpu 的 chunk（用該 session 目前的歷史長度算 b），沒有了才照 S4L。
  **判準改成**：寫入時決定的策略，必須同時贏過 §6 的「最好的不看位置策略」**以及 S4B**，才算「寫入時決定」有效；只贏前者、不贏 S4B，只能說「b 這個規則有效」。
  這個修正只會讓結論更保守。
