## 判準

**H1（寫入量）**：
- 每個設定（第一階段 B 和 08 的 b2）取「TTFT ≤ 最好的 1.05 倍」的策略當候選。
- 寫入時決定的策略（S5、S5s、S5L、S5P、S5c）只有在下面兩件事同時成立時，才算有寫入量優勢：
  - 它在候選裡；
  - 它的 SSD 寫入量 ≤ 候選裡所有不看位置的策略（含延後版 S4、S4+、S4+P、S4L、S4B）最小值的 0.8 倍。
- 判定：這種設定占所有設定的比例 ≥20%，H1 存活；否則 H1 殺掉。

**H0（會不會擋住）**：每個系統要給出原始碼的檔名和行號，回答三件事：
1. CPU 滿了時，是直接丟掉、同步寫到下一層，還是非同步寫到下一層？
2. 新請求的 KV 要放進 GPU 或 CPU 時，會不會等前一個寫入完成？
3. 有沒有水位線，也就是在背景提早搬？

判定：
- 三個系統都不會等 → hold 只剩理論意義；08 的 hold 結果要降級成「如果實作是同步的才成立」。
- 有任何一個會等 → hold 有現實意義。

**H2（成本比）**：
- 每個模型用同一套 harness（`m7_model.py` 的自管 KV 前向），量 512 token 一個 chunk 的重算時間 f(i)，量到 32K，3 次取中位數。
- chunk 大小用 `config.json` 算，再用 harness 實際配置的 tensor 大小驗算。
- 頻寬網格：0.33／1／3.69／11.6／35.4 GiB/s。用 `write_boundary` 算 32K（64 個 chunk）時的 b／n。
- **通過**：快的層（3.69 或 35.4 GiB/s）時 b／n ≥30%。
- MoE 的 f(i) 如果是 HF transformers 的實作，可能比 vLLM 的 fused kernel 慢，會讓重算看起來比較貴。這點照實標註；能量 vLLM 的話一起量，當作對照。

**H2 延伸（只做通過的模型）〔模擬〕**：
- 用該模型的 f(i) 和 chunk 大小跑 `m7_sim.py`。設定和 08 的掃描相同：CPU 頻寬 × 搬移方式 × 工作負載 × SSD × 容量，seed 0–4。
- 寫入時決定的策略必須**同時**贏過下面四個對照組各 ≥5%，而且 ≥3 個 seed 都成立，才算存活：
  - 最好的不看位置策略（S0、S1、S2b、S4、S4+、S4+P、S4L）；
  - S4B（延後版）；
  - **S4W（背景版，新增）**：做法同 S4B，但每一輪結束後就在背景先搬，讓 CPU 空出至少 25% 的容量，不等到滿了才搬；
  - 讀取時版：Cake 本身，所有策略都已經用 Cake。
- 存活的設定在第 2 輪才上 GPU（10 §9）。**模擬結果只能挑設定，不能下結論。**

## 追加（2026-10-09 約 17:57 UTC，看過 HF 的 f(i) 之後寫，在 run `20261009-175737-r1-vllmf-llama31-8b` 之前）

1. **Qwen3-30B-A3B 的 f(i) 改用 vLLM 再量一次。**
   - 原因：HF 實作的重算時間，grouped_mm 每個 chunk 217 ms、eager 1404 ms，Llama-3.1-8B 是 28.9 ms。這就是上面預告的實作偏差。
   - 方法：`code/m7_vllm_f.py`，開 prefix caching，量「算第 i 個 chunk」減掉「全部命中時的固定開銷」。用 `num_cached_tokens` 驗證快取命中的 token 數。
   - **方法要先過關**：同一支程式量 Llama-3.1-8B，和 harness 的 C1 比。每個 chunk 的 vLLM／harness 比值，中位數在 0.85–1.15 之間，才算方法可信。過關了，Qwen3 的 κ 篩選和模擬才用 vLLM 的 f(i)。HF 的數字照樣列出，標「實作偏差」。
2. **篩選門檻不夠嚴，照實記錄，判準不改**：Lit-C 指出，Llama-3.1-8B 自己在 3.69 GiB/s 時 b/n 就是 0.312，已經過了「≥30%」的門檻。所以這個門檻沒有區分力。照原設計，通過的模型都進模擬，結論只看模擬裡「同時贏過所有延後版」的那一關。

## 追加 2（2026-10-09 約 17:59 UTC，看過 LongAlpaca 的模擬之後寫，在 run `20261009-180002-r1-sim2-*` 之前）

- **看到了什麼**：LongAlpaca 最穩的存活設定（CPU 35.4、hold、doc、NFS、25%）的贏家是 **S5c**：全部寫 CPU，另外在寫入時把前段先複製一份到 SSD。
- **為什麼要加對照組**：S5c 贏的原因可能是 OS 早就有的「**預先清理**」（eager cleaning：背景先把快被淘汰的頁寫出去，淘汰時就不用等），而不是「寫入時」決定。這個延後版的對照組還沒做。
- **新增 S4C（預先清理版）**：
  - 寫入同 S4+（全寫 CPU），淘汰同 S4+（最便宜的先）。
  - 每輪結束後，在背景確保 S4+ 淘汰順序最前面的 25% × CPU 容量個 chunk 都已經有 SSD 副本；沒有的就複製，不從 CPU 移走。
  - 它不看「寫入當下」，只看淘汰順序。
- **判準改成**：寫入時決定的策略，要同時贏過最好的不看位置策略、S4B、S4W、S4C 各 ≥5%，≥3 個 seed 都成立，才算存活。
- 這個改動只會讓結論更保守。Llama 和 LongAlpaca 都重跑；Qwen3 等 vLLM 的 f(i) 出來後再跑。

## 追加 3（2026-10-09 約 18:03 UTC，vLLM 量法 v1 沒過驗證之後寫，在 run `20261009-180348-r1-vllmf2-*` 之前）

- **結果**：vLLM 量法 v1（相減法）**沒過**驗證。同樣量 Llama-3.1-8B，vLLM／harness 比值中位 0.275（範圍 0.18–0.49），不在 0.85–1.15 之間。
  原因：vLLM 每個請求有一筆隨 prompt 長度增加的固定開銷，32K 時約 170 ms，相減扣不乾淨（run `20261009-175737-r1-vllmf-llama31-8b`）。
  照判準，**Qwen3 的 κ 和模擬不用 vLLM 的 f(i)**。
- **探索性補量（不進本輪判定）**：改用 vLLM 引擎內部的時間戳。
  - 「排進 GPU」到「產生第一個 token」的時間（`first_token_ts − scheduled_ts`），只包含模型計算，不含前端開銷。
  - 用 FLOPs 換算成 MI300X BF16 峰值的比例，檢查合不合理。
  - 如果它和 harness 也不一致，代表 **harness 本身可能比正式引擎慢、重算成本被高估**。這會影響所有 κ 的結論，所以只照實報告，要不要用 vLLM 的 f(i) 重做，交給老師決定。
