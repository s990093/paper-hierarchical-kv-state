# 第三階段前置探索：結果分析

> 這份 md 是報告 PDF（`/mlsteam/data/tiara/stage3/report/stage3_report.pdf`，由 `code/m16_report_pdf.py build` 產生）的文字版；圖表、事先寫死的判定、run_id 出處以 PDF 與 `experiment_log.md`、`results.csv` 為準。


## 摘要

**這一輪做什麼**：在 2× AMD MI300X 上，用租約最後約 2.5 天的 GPU 時間（實際時間軸見第 2 章），篩選第三階段的題目。大問題：KV 放不下 GPU 時，要依什麼決定它的待遇（降精度、無損壓縮、搬到 CPU／SSD、丟掉）。每個實驗的判定條件都在看到數字前寫死。

#### 主要發現

1. **壓縮可以疊，而且有加乘**：跨層低秩（K 在 RoPE 前、每 4 層一起）＋係數量化，在每個倍數都顯著好過任何單一方法。獨立樣本下約 8 倍接近無損、12 倍掉 1–3 個百分點、32 倍掉 7–8；單用 INT4 是 3.2 倍。128K 撐得住，多輪不傷。
2. **配比隨倍數變**：8–20 倍用低秩＋INT4，24–32 倍改用低秩＋K4V2，最後再乘無損約 1.1–1.2 倍。依重要性丟 token、合併 token、逐 token 跨層共用都不值得疊。
3. **還原時「最快的格式」會隨 GPU 忙碌翻轉**（端到端實測）：GPU 閒或連線慢時低秩組合最快（SSD 上把還原壓到約 1/3），GPU 很忙時低秩重建被拖慢，INT4 最快，低秩組合甚至比不壓縮慢。前人都假設計算和搬運互不干擾。
4. **token 重要性（使用者的問題①）**：拿來丟在同樣大小下全面輸給量化，多輪更糟；拿來挑「還原時搬哪些」需要更好的索引——便宜的 Quest 摘要不夠（C1b 停），但完整 K 的上界顯示有空間。
5. **agent（使用者的問題②）**：MI300X 192 GB 沒有容量壓力，這次不改場景（模擬）。
6. **AMD 的搬運路徑**：vLLM 在 ROCm 上 CPU 卸載慢，主因是逐塊 copy 的固定成本；GPU 直接讀的 zero-copy 快 18–45 倍；開卸載還會強制退回較慢的注意力後端，8K 提示開卸載幾乎都變慢、32K 才變快（vLLM 實測）。

#### 第三階段候選（詳見第 6 章）

1. 疊加 KV 壓縮的配比與分層搬運；2. 爭用感知的還原格式選擇；3. AMD 上的快速 KV 還原路徑；4. 用低秩 K 當選擇性還原的索引。

#### 最需要注意的限制

壓縮極限的數字在不同題組之間差到約 3 個百分點，嚴格的 ε 規則下 32K 只有 INT4 正式過關；每題 SVD 的壓縮要數十秒，事先校準的基底還沒正式證明不輸；決策圖的模擬低估 5–26%，以實測為準。


## 背景與問題

這一輪不是要做出一個方法，而是**幫第三階段選題目**。大問題沿用前兩階段：KV 放不下 GPU 時，要依什麼決定它的待遇——降精度、無損壓縮、搬到 CPU／SSD，還是丟掉（之後重算，或依重要性直接不要）。

#### 四幕故事

1. **依位置**（前兩階段）：依位置決定放哪一層、用多少位元，都贏不過「晚點再寫」和「隨機挑」；整份降到 INT4 答對率幾乎不掉。這條走到底了。
2. **依內容**（使用者的問題①：KV 量化、依 token 重要性決定）：重要性能不能省空間（丟 token 對上量化）、能不能省搬運（只還原需要的 block）；10/20 起擴大成「各種壓縮能不能疊起來用」。
3. **依場景**（使用者的問題②：要不要改 agent）：agent 暫停時 KV 閒著，但只有顯存不夠時才是問題。
4. **依現場狀況**（這次新加）：前人假設「拿回來要多久」是固定的；第二階段量到 GPU 忙時重算慢約一倍、搬運慢約一半。

#### 這一輪實際回答了什麼

- 問題①：依重要性**丟** token 在同樣位元組下全面輸給量化，而且多輪會壞；重要性比較像「還原時挑要搬哪些」的訊號，但目前便宜的挑法（Quest 摘要）不夠準。真正把位元組省下來又不掉分的，是**跨層低秩＋量化**的疊加（第 4.6–4.11 節）。

- 問題②：MI300X 192 GB 在 agent 工作負載下沒有容量壓力，這次不改場景（第 4.12 節，模擬）。

- 現場狀況：還原端的實測顯示「最快的壓縮格式」會隨 GPU 忙碌翻轉（第 4.9 節），這是第三階段最有新意的線索之一。


## 文獻與查新

文獻由 agent 讀全文或摘要整理（self-review，不是 cross-model）。對這一輪設計影響最大的幾點：

- **Intel KV Cache 四件套**只有 KV Shrink 有程式（只壓 BF16 高位元組的無損壓縮，不支援 AMD）；另外三個名字只出現在媒體報導。所以四件套只當「方向的分類」，實驗全部自己設計。

- **「κ 隨硬體變」已被做過**（Stony Brook FSL-26-02、EfficientAgent），而且前人（CacheFlow、InferCept、FSL-26-02）都假設計算和搬運互不干擾 → 專案原本的 κ 主張不再當主軸，改看「現場狀況」。

- **壓縮的組合**：兩兩組合已有約 25 篇；「同一個預算下聯合分配」有 RDKV、JoLT、KVTC；xKV（每 4 層聯合 SVD）在 Llama-3.1-8B 64K 壓 8 倍贏 KIVI-2。但**三種以上、長上下文、同位元組的系統性比較，加上搬運速度與 GPU 忙碌**查不到 → X1–X4 的設計來源。

- **卸載時壓縮**：依頻寬選格式已有人做（CacheGen、KVServe、AdaptCache）；沒人把「GPU 忙不忙」放進決策 → X3 的設計來源。

- **跨層共用與 token 合併**：第三方報告 MiniCache 在 Llama-3.1-8B 長上下文上崩、合併的好處小；我們的 K1 與 X1 都證實了。

- **業界主流**：引擎預設 BF16、生產常開 FP8；主流是先在架構上縮 KV（GQA、MLA、局部注意力），量化疊在上面。精度不是越低越好：2–3 bit 有懸崖，INT4 是我們量到的甜蜜點。


## 各實驗的解讀


### 4.1 K1　KV 結構

K1 只看 KV 本身的幾何，不是答對率，但它決定了後面哪些壓縮值得試：

- **K 在加位置資訊（RoPE）之前很低秩**（保留 1/4 維度誤差約 25%，95% 能量只要 36–40 維），而且用前 4K token 算的基底套到後面幾乎不變差；RoPE 之後就不低秩、也不能事先算基底。**V 本身不低秩**（95% 能量要 108–110 維）。所以低秩一定要在 RoPE 前做，V 要靠別的方法（量化）。

- **相鄰層同一 token 的 KV 完全不像**（cosine ≈ 0），MiniCache 式的逐 token 跨層共用沒有依據，照事先條件停。但「多層一起找共用方向」（xKV）不受影響——X1 之後證實它是最好的家族。

- **相鄰 token 看起來像，主要是共同的平均方向**；扣掉平均後真正很像的不到 1%，合併相似 token 沒什麼可省（X1 也證實合併會崩）。


### 4.2 I4　搬法

KV 散在很多小塊時，**搬法決定速度**：逐塊 copy 只有 1–3 GiB/s，和 vLLM 在 ROCm 上 CPU 層實測約 4.1 GiB/s 同一個量級；GPU kernel 直接讀 pinned host（zero-copy）約 53 GiB/s，快 18–45 倍；CPU 端先收集再一次 copy 約 20 GiB/s。這表示 vLLM 在 AMD 上 CPU 卸載慢，主因是每次 copy 的固定成本，而不是頻寬。

在這個單純搬運的測試裡，背景負載（busy2）幾乎不影響搬運速度，和第二階段「GPU 忙時 H2D 慢約一半」不同；兩者設定不同（第二階段是還原器的整段流程），這一輪沒有再追，列為限制。


### 4.3 I1／I2　多 session 還原

I1 的事先預測（模擬）說「多個 session 同時回來時，一起決定誰重算、誰載入」每一格都比各自最佳差。GPU 實測和模擬的平均 TTFT 比在 0.97–1.05 之間，遠在 1.10 的門檻內，所以模擬可信、這個方向照規則收掉：好處只來自第二階段的單請求規則（G5b）與排隊順序。

計算、搬運、生成同時跑時彼此只拖慢 ≤6%。GPU 忙時 H2D 和別的工作同時跑反而比單獨跑快（比值 0.84–0.94），原因沒有查，不解讀。


### 4.4 C1a　能不能猜中第 2 輪的 block

C1a 是選擇性還原的閘門：第 2 輪答案所在的 block，能不能事先猜中？

- 寫入時就算好的重要性分數只比隨機好 11–24 個百分點（recall@16）；第 1 輪的問題也差不多。

- 等第 2 輪問題來了，用便宜的 block 摘要（Quest）挑，好 35–45 個百分點；用完整 K 挑（上界）好 61–68 個百分點。

- 照事先條件，閘門通過（G2、G4 都不觸發），C1b 照計畫做。

對使用者問題①的意思：「哪些 token 重要」在寫入時只猜得到一部分，要等下一輪問題來了才準。所以重要性比較適合用在**還原時挑要搬哪些**，不適合**事先丟掉**。


### 4.5 S1　無損壓縮

BF16 KV 可以無損壓到 1/1.47（32K 自然文字）到 1/1.52（128K），比文獻在 NVIDIA 上報的 1.31–1.33 倍好；Intel KV Shrink「只壓 BF16 高位元組」的作法有 1.46 倍，幾乎一樣。

但在 CPU 上解壓只有每秒 0.5–2 GB，所以只在慢的下層划算：NFS 級省 32%、限速慢層省 21–25%，本地 SSD 沒好處，CPU 記憶體（50 GiB/s）大幅變慢。X4 另外量到，把無損壓縮疊在「低秩＋INT4」的係數上還能再小 1.10–1.20 倍。無損壓縮是疊加的最後一層，而不是獨立的題目。


### 4.6 X1　疊加篩選（TF）

X1 用 teacher forcing（把正確答案餵進去，看答案機率掉多少）一次篩 161 種組合，只是篩選，正式答對率看 X2、X4。重點：

- **疊加有加乘**：在壓 8 倍、16 倍時，最好的組合明顯好過最好的單一方法（事先條件 S1-b 不成立 → X2 照計畫跑）。答案機率幾乎不掉時，組合能到的大小約是單一方法的 1/3（Llama 0.32、Qwen 0.35）。

- **贏的家族**是跨層低秩（xKV 式，每 4 層一起做 SVD，K 先轉回 RoPE 前），再把係數量化。**只靠降秩**壓到 16 倍就崩，同樣大小改成「中等秩＋INT4」幾乎不掉——這是「疊加優於單一方法」最直接的證據。

- **丟 block（依重要性）**在每個大小都大輸量化（約壓 4 倍時答案機率掉 19–26）；**合併相似 token**崩掉；**每層各自低秩**比跨層差。

- 便宜的代理指標（KV 重建誤差）和真實影響的相關只有 0.5–0.6，不能拿來取代模型本身的量測。


### 4.7 X2＋X2b　生成答對率

X2 量真正的生成答對率。照事先寫死的 M1 規則判 **GO**（任一模型的組合在 ε 內能用的大小 ≤ 最好單一方法的 0.85 倍）：Qwen 的組合約 10–12 倍在 ε 內，最好的單一方法只有 3.2–4.3 倍。

- **統計力是最大的限制**：ε 規則要求「CI 下界 ≥ −2 個百分點」，96 題時 CI 半寬約 3–4 個百分點，連單用 INT4 都過不了。所以加了 X2b（每個模型再 192 題），合併 288 題後 CI 半寬約 2。

- 288 題時：Qwen `xl:k22:v34+INT4`（約 12 倍）+0.3 [−1.9, +2.5] 過 ε；Llama 8–10 倍約 −1.2～−1.4、21 倍 −2.2（顯著但小）。

- **但這個數字要和 X4 的獨立樣本一起看**：X4b 用另一批 192 題，相近配置（11.7 倍）是 −2.6。兩次都在彼此誤差內，合起來 10–12 倍的真實影響約 −1～−3 個百分點，**不是零損失**（見 4.11）。

- **128K**（Llama 只有 18 題、Qwen 48 題，只當方向）：「低秩＋INT4」約 11–13 倍仍撐住；只靠降秩在 128K 比 32K 掉更多 → 上下文越長，疊加的好處越明顯。


### 4.8 xKV 事先校準的基底

每題算一次 SVD 的 xKV 壓縮要數十秒（4.9 節的寫入成本），實際部署用不了。事先用校準題算好、所有請求共用的基底，能把壓縮降成一次矩陣乘法，而且每個請求要存、要搬的位元組更小。

- 38c（96 題）：兩個模型都分辨不了；加了 INT4 之後校準基底點估計不差（Llama 還更好），只降秩時校準基底較差。

- 38k（新的 192 題，**主判定只看這批**：「只比兩組 INT4」是看過 38c 才決定的，舊的 96 題不算獨立）：兩個模型仍**分辨不了**，四組差值 −1.5～+2.1 個百分點、平均約 0。

- 結論：看不出事先校準會系統性變差，但也還不能證明「不輸」；要證明需要更多題（或放寬 ε）。Llama 的校準版約 14.6 倍、對不壓縮 −0.3，在合併 288 題下過 ε。


### 4.9 X3　還原時間與決策圖

X3 問：壓縮組合在還原時是不是真的比較快？最快的組合會不會隨連線速度和 GPU 忙不忙而改變（使用者的 B）？

- **只在第二階段驗證過的格式（FP8、INT4…）之間挑**：不管連線快慢、GPU 閒忙，都是 INT4 一次拆最快（STOP-0 成立），B 在這種動作集合下沒有空間。

- **把疊加組合加進選項後**（v2，零件實測、組合模擬）：Qwen 的「低秩＋INT4」在慢的下層比單用 INT4 再快 61–69%；「依連線＋GPU 忙動態選」比「固定最好的一種」只好 6.5%（介於 5–15%，照規則問人；使用者選擇做端到端實測）。

- **端到端實測**（8 格、全部沒污染）：照事先條件 STOP-3 成立——模擬普遍低估 5–26%，模擬決策圖不能直接用。但實測本身顯示**最快的格式會隨 GPU 忙碌翻轉**：Qwen 在 CPU 記憶體層，GPU 閒時低秩最快（0.015 s，INT4 0.018、BF16 0.039），GPU 很忙時 INT4 最快（0.020），低秩＋INT4 反而 0.083、比不壓縮（0.060）還慢；在本地 SSD 上，低秩把還原從 0.224 s 壓到 0.065 s。4 組實測的「依情況選」對「固定一種」快 27.6%。

- **寫入成本**：xKV 每題的 SVD 要 4–31 秒（16K token，GPU 閒），GPU 忙時再慢約 3 倍；係數量化只要毫秒。這是每題 SVD 版本實用化的最大障礙（見 4.8）。

這是 B 在「疊加組合」下才出現的空間，也和研究地圖缺口 #1（干擾）是同一條線；但實測只有 4 組，要另做實驗確認。


### 4.10 C1b　選擇性還原

C1b 照設計卡判 **STOP**（兩個模型、兩種 query-aware 挑法都一樣）：只放回一半的 block，答對率就掉 8–12 個百分點；放回 1/4 掉 18–35。生成時發現需要再補搬能補回 1–14 個百分點，但補不回 ε。寫入時分數、第 1 輪問題、位置、隨機都更差。

值得記下的是上界：**用完整 K 來挑**（實際拿不到），Qwen 只放回 1/4 答對率就不掉（+0.5），Llama 放回一半只掉 1.6。所以「只搬需要的 block」本身有空間，失敗的是 Quest 用 512-token 區塊最大最小值做的摘要太粗。C1a 的召回比隨機好很多，但答案 block 只要漏一塊答案就錯。

可能的方向（未測）：用 RoPE 前的低秩 K（K1：32 維就留住大部分能量，基底可事先算）當更準又便宜的挑選索引，逼近完整 K 的上界——這會把疊加壓縮和選擇性還原接起來。


### 4.11 X4　推到極限：哪樣配、配比、極限

X4 回答使用者的兩個問題，而且 X4b 用的是**和 X2／X2b 都不重疊的新題目**，是獨立檢驗。

#### 哪樣配（五種方法裡值得疊的）

- **降秩之後一定要量化係數**：同樣倍數下比只降秩好非常多（生成：Qwen 16 倍 +25.4、Llama 12 倍 +7.8 個百分點，都顯著）。

- 係數用 **INT4 比 INT8 好**：寧可多留秩、少給位元。

- **無損壓縮值得疊**：INT4 係數再小 1.10–1.20 倍，只影響大小（速度要看下層，見 4.5、4.9）。

- **低於 4 bit**（INT2、K4V2）：20 倍以下沒好處，24–32 倍時才值得。

- **窗口每 4 層**比每 2 層好；**輕度丟 block** Qwen 不值得、Llama 時好時壞；**合併**技術上不能和低秩疊；**跨層逐 token 共用**沒有依據。

#### 配比隨倍數怎麼變

8–20 倍：跨層低秩（K:V 秩約 1:1.5、每 4 層）＋INT4 係數；24–32 倍：同樣的低秩＋K 用 INT4、V 用 INT2；最後再乘無損約 1.1–1.2 倍。

#### 極限（要更正 X2b 的樂觀說法）

- 獨立樣本下：**約 8 倍以內接近無損**（Qwen −0.7、過 MLPerf 99%；Llama −2.0），**12 倍掉約 1–3 個百分點**，16–24 倍掉約 3–5，32 倍掉 7–8。照嚴格的 ε 規則，32K 只有單用 INT4（3.2 倍）正式過關。

- 128K（48 題，只當方向）：Llama 約 15.5 倍 +2.8 撐住；Qwen 9–18 倍掉 1–2。

- **多輪**：疊加壓縮在第 2 輪幾乎不傷（Qwen +0.9～+1.3、Llama −1.1），丟一半 block 的對照掉 17–19 → 多輪對話時疊加遠好於丟 token。

- 256K 沒有資料：出題程式做不出 256K 的 T5 題（詞表不夠長）。


### 4.12 I3　agent 暫停（模擬）

I3 是模擬（成本常數用第二階段實測，排程與佇列是模型），沒有 GPU 驗證。它回答使用者的問題②：agent 暫停去查資料時，KV 要留、要搬、還是要丟？

- MI300X 有 192 GB，同時 32 個 agent 時容量仍是需求的 4–9 倍——**在這台機器上這個問題幾乎不會發生**，所以這次不改成 agent 場景，使用者「太急」的直覺是對的。

- 事前凍結的「依 κ 選」在一般硬體上贏不過 vLLM 內建的卸載；只有下層是 NFS 或 CPU 記憶體很小時才明顯贏（+27～38%），但那時現成的 Tokencake 也贏 → 重點是「硬體不尋常時別用 vLLM 預設」，不是 κ 本身。

- 最大的改善空間是讓系統知道 session 已經結束（NFS 下中位快 26%）——這是應用層和系統之間的介面問題。

過程中我一度說「換成和固定作法比，結論會翻」，照實重算後大部分不成立；這個更正也記在實驗紀錄。


### 4.13 vLLM：V0／F2／F1

vLLM 這組回答「在真實的 serving 系統裡，復用與卸載什麼時候划算」，三個實驗都沒有被干擾。

- **V0**：vLLM 0.28 在 MI300X 上，APC、CPU 卸載、ROCm 修補、SSD 分層都能跑；命中與不命中的輸出只在「前兩名機率完全相同」的位置分歧（數值平手），不是快取把 KV 弄錯。第一次執行時 job 對這種分歧太嚴而停下，修正後重跑（失敗 5）。

- **F2**（共用前綴、大量併發）：vLLM issue #44294 的「開卸載慢一倍」在 MI300X 上**沒有重現**——和同一個注意力後端比，開卸載打平或更快。真正的代價是開了 CPU 卸載後 vLLM 在 ROCm 上會**強制改用較慢的 TRITON 注意力**，高併發時慢約一倍。

- **F1**（重疊 × 容量 × 到達 × 設定）：APC 的收益只由重疊決定（50% 重疊少 20–62%、100% 少 76–93%），容量和到達率幾乎不影響；照事先條件字面判「成功」，但找到的「沒收益區域」只有重疊 0%，是當然結果。比較有用的是 **CPU 卸載的邊界**：8K 的提示開卸載幾乎都變慢（容量緊、負載高時平均 TTFT 慢一倍以上），32K 才變快（+3～15%）。

合起來：在 AMD 上，CPU 卸載值不值得，取決於提示長度、注意力後端的退回、以及搬運路徑（I4：逐塊 copy 只有 1–3 GiB/s）。這些都是候選 3「AMD 上的快速 KV 還原路徑」的直接證據：如果搬運與後端的成本降下來，8K 的卸載邊界就會往有利的方向移動。


## 綜合

#### 把五種壓縮放在一起看

KV 大小 ＝ token 數 × 層數 × 每個 token 的維度 × 每個數的位元 ÷ 無損倍數。這一輪把每一項都試過：

- **token 數**（依重要性丟、合併）：同位元組下全面輸給量化，多輪更糟（丟一半 block 第 2 輪掉 17–19 個百分點）。

- **層數**（逐 token 跨層共用）：相鄰層完全不像，沒有依據。

- **維度**（低秩）：單獨用、每層各自做都不好；**跨層一起做（xKV 式）＋K 在 RoPE 前**是唯一有效的形狀。

- **位元**（量化）：INT4 是單一方法的甜蜜點（3.2 倍、不掉分）。

- **無損**：再小 1.1–1.5 倍，只在慢的下層划算。

真正有加乘的是「維度 × 位元」兩項的疊加（再乘無損）：約 8 倍接近無損、12 倍掉 1–3 個百分點、32 倍掉 7–8。和單用 INT4 相比，同樣答對率下大約多省 2.5 倍位元組；和只降秩相比，高倍數時答對率高出 8–25 個百分點。

#### 省下的位元組換不換得到時間

- **寫入**：每題 SVD 要數十秒，不實用；事先校準的共用基底在答對率上看不出變差（但還不能證明不輸），是實用化的關鍵。

- **還原**：慢的下層（SSD、NFS）上，低秩組合把還原時間壓到 BF16 的 1/3 左右；CPU 記憶體層、GPU 閒時也比 INT4 快一點。

- **GPU 忙時**：低秩重建是一次矩陣乘，會和模型計算搶 GPU，忙時慢約 2.8 倍；實測在 CPU 層、GPU 很忙時「低秩＋INT4」比不壓縮還慢。→ **最佳格式隨 GPU 忙碌翻轉**，這正是前人假設「互不干擾」漏掉的地方。

#### 收掉的方向（負面結果，都有事先寫死的條件）

依位置決定（第一、二階段）、多 session 聯合決定（I1）、agent 的 κ 策略（I3，模擬）、逐 token 跨層共用（K1）、token 合併（X1／X2）、依重要性丟 block（X1／X2／X4d）、用 Quest 摘要做選擇性還原（C1b）、只在單一格式之間依連線選（X3 STOP-0）。


## 限制與誠實聲明

- **模擬 vs 實測**：I1 的預測、I3、X3 的決策圖是模擬（零件是實測）。I1 的模擬經 GPU 驗證可信；X3 的模擬經端到端實測發現低估 5–26%（STOP-3），所以第 4.9 節的實測數字才算數；I3 沒有 GPU 驗證。

- **統計力**：ε＝2 個百分點的判定要 CI 下界 ≥ −2，96 題時連 INT4 都過不了；加到 288 題後 CI 半寬約 2。不同題組之間點估計差到約 3 個百分點（X2b vs X4b），所以極限要看獨立樣本並列，不能挑好看的那次。

- **事後決定的限定**：xKV 校準加題時「只比兩組 INT4」是看過結果才定的，所以主判定只用新的 192 題。

- **任務與模型**：兩個 7–8B 的 GQA 模型、四種合成長文任務（T2–T5）、第 1 輪為主；128K 題數少（Llama 18 題），256K 沒有資料。

- **teacher forcing 只是篩選**：X1、X4a 的結論都以生成答對率（X2、X4b）為準。

- **審查**：文獻與程式都是 agent 寫、我核對（self-review），不是 cross-model review。

- **失敗與修正**（清單見下方，自動從實驗紀錄抽出）：都照「記錄、停下、修正、重跑」處理，沒有跳過；修正的都是程式或參數錯誤（例如冒煙的上下文太短、job 腳本的變數展開、警告被當成工作名），沒有改任何判定門檻。
