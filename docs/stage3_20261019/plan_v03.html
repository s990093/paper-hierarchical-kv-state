總問題

KV 太大、只能搬出 GPU 時，前兩階段的「依位置決定」已經證明沒用。影片說的四個難題裡，哪一個在我們的 MI300X 上真的是瓶頸，而且前人還沒解決，值得當第三階段的題目？

故事：KV 就是模型的「筆記」

問題（影片在講的）

對話越長、agent 越多，筆記越厚，GPU 放不下，只好收進倉庫（CPU、SSD）。使用者回來時要拿回來：重抄（GPU 重算）或送回（從倉庫搬）。Cake：小明從前面抄、快遞從後面送，中間碰頭。

你問的，對應到這次的實驗

這次是探索：你問的兩件事和 Intel 的四個方向，各做一個最小的實驗，結果出來再由你決定第三階段做哪個問題。

你問的對應的實驗跑完你會看到
① KV 量化＋依 token 重要性決定S2、C1a（接在第二階段 44e 的 13 種重要性挑法後面）同樣省一半／四分之三空間，「依重要性丟 token」和「量化」誰保住答對率；重要性分數能不能猜中下一輪要用的 token
② 場景要不要改成 agent這次不改；I3 先用 CPU 模擬 agent 呼叫工具暫停時 KV 該留、搬、還是丟這題還有沒有空間（已有 Cascade 做了四種選擇，全面改 agent 太早）
Intel KV Shrink（壓縮）S1（照 Intel 的作法只壓指數那一半）、S2無損壓縮在 MI300X 能省多少、多慢的連線才划算
Intel KV Cascade（聚焦）C1a → C1b只載入跟問題有關的 KV、其餘先不搬：省多少搬運、答對率掉多少
Intel KV Fuse（復用）V0 → F2 → F1（vLLM 前綴快取）重複的前綴什麼時候省時間、什麼時候反而變慢
Intel KV Infinity（按需載入＋預取）I4、I1、I2（I3 也有預取）搬資料用什麼方式最快；搬資料會不會拖慢 GPU 計算；預先搬回來值不值得

影片查證：Intel 四件套只有 KV Shrink 有真的程式（GitHub 上的 vLLM 外掛，只支援 Intel 硬體），另外三個只出現在媒體報導；「agent 六成時間在搬資料」找不到出處。

文獻讀完後最可能有新意的方向（不是定案，看結果再選）

κ＝重算成本 ÷ 搬運成本；「爭用」＝GPU 同時在忙別的事。

原本的主張「重算 vs 搬運的成本比 κ 跨硬體變動 32 倍」，已經有人用 6 張 NVIDIA GPU、1,764 組硬體做過（Stony Brook 技術報告 FSL-26-02，2026-08，非同儕審查）。但它和 CacheFlow、InferCept 都明寫假設計算和搬運互不干擾。我們第二階段已經量到相反的證據：

重算（每塊，Llama）+107%
FP8 反量化+140–280%
CPU 層整段還原（Llama 32K）+74%
H2D 搬運（Llama）+50%
H2D 搬運（Qwen）+46%
CPU 層整段還原（Qwen 32K）+27%
0%+100%+200%+300%

實測（第二階段，MI300X）。重算 ×2.07：busy_levels.json（run 20261008-130834-m7-c5、-130956-m7-c5b）；反量化 ×2.4–3.8：09 §6.1；還原與 H2D：08 §2.1（run 20261015-161226-m10-grid-fp8-llama、20261015-194150-m10-regrid-fp8-qwen），H2D 是 L2 §0.1 從同一份資料算的。「GPU 忙」＝背景 matmul duty 0.7。

所以第三階段要量的是：這些干擾會不會改變「該重算還是該搬」的決定，以及搬運的方式（copy engine 或 kernel）在 GPU 忙時誰比較好。這是前作留下的空白。
