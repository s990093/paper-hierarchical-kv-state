X4a：一組放更多層（每 8／7 層、全部層）

  • 每 8／7 層一組（當初為了時間縮掉的）：照規則兩個模型都判「較好」，但要細看。Qwen 12 對裡 4 對 CI 下界 >0（其中 32 倍 K4V2 那對 W7 的位元組還比較少，+0.96 [+0.14, +1.78]）、其他接近 0 → Qwen 一組放更多層一致較好。Llama 只有 32 倍 INT4 那對勝出，但那一對 W8 多用約 7% 位元組 → Llama 看不出差別。
  • 全部層一組（看過 K1b 之後加的）：Llama 判不了（24 倍兩對反而較差，有一對位元組有混淆）；Qwen 只有 32 倍 INT4 那對勝出（+1.76）。全部層時秩只能取 k3／k4，格點太粗。
  • 讀法：每組 4 → 7／8 層有小幅、一致（Qwen）的收益，和 K1b 的重建誤差、KVTC「串越多層越好」同方向；但不是越多越好。這只是 teacher forcing 的篩選，沒有做生成答對率。

X3 翻轉格子：最快的還原格式會不會隨 GPU 忙碌翻轉（兩種背景，各 144 個端到端量測、0 列污染）

  • 算力型背景（同卡 matmul）：FLIP_REPRODUCED（6 條裡 3 條翻轉，兩個模型都有）。CPU 層兩個模型都翻：閒時「低秩 k11＋INT4」最快，duty ≥0.7（Qwen ≥0.4）起 INT4 最快；duty 0.9 時 Llama 的「低秩 k22＋INT4」0.126 秒、INT4 0.037 秒、BF16 原樣 0.140 秒。依情況選比固定一種好 13.6%（Llama）／5.9%（Qwen）。Qwen 的 SSD 層也翻（忙時「只降秩」最快，好 5.7%）。慢的層（b16、Llama SSD）不翻：位元組主導，最省位元組的永遠最快。只比答對率相近的 INT4 對「低秩 k22＋INT4」，CPU 層一樣會翻。
  • 頻寬型背景（同卡反覆複製大陣列，約 3.9 TB/s）：NO_FLIP（0／6）。各格式只慢 5–30%，排序不變，「低秩 k11＋INT4」在 duty 0.9 時仍最快。
  • 讀法：低秩重建是矩陣乘法，只有搶運算單元的背景拖得動它；搶記憶體頻寬的背景（像小批次 decode）幾乎不影響。所以「最快格式翻轉」是真的（算力型背景 144 個端到端量測、0 列污染，不再只有 4 對），但只在同卡有算力型工作（prefill、大批次 decode）時發生。這是文獻查新（L7b）提醒的效度風險，量完之後範圍比原本講的窄。真實併發下哪一種情況比較常見，還沒量。

I3g：agent 工具暫停後回來那一輪（vLLM 端到端）

Llama、64 個 agent session（6 輪、工具暫停中位 30 秒）、HBM 人為壓到參考工作集的 0.25 倍；四個設定都 CLEAN、364／364 請求成功。

  • 判定：RANK SIM_RANK_CONFIRMED（實測 c < b < a < d，和模擬同序）、FLIP FLIP_CONFIRMED。回來那一輪 TTFT P95：a（只有 APC）2.40 秒、b（＋CPU）2.04、c（＋本地檔案層）1.66、d（＋NFS 檔案層）105 秒。
  • 排序對、絕對值不對：實測／模擬 0.55、0.68、1.72、7.85，都在 ±30% 之外。
  • 誤差範圍與重跑：事後的 session bootstrap 給 c／b＝0.82 [0.72, 1.00]（碰到 1）。10/23 再把 b、c 各跑兩次（兩張卡同時、交叉順序，跑之前寫好規則）：三對的 c／b＝0.82、0.81、0.86，C_BETTER_REPLICATED（三對都好 ≥5%）；同一設定各次的 P95：b 2.02–2.30 秒、c 1.66–1.85 秒。→ 本地檔案層好約 15–20% 是穩的。b 比 a 好（CI 不含 0）；d 是 b 的 52 倍 [46, 61]。
  • NFS 慢在哪：vLLM 的指標 lookup_async_delay 在 d 平均每個請求 41.3 秒，TTFT 平均 41.8 秒幾乎全在這裡（c 只有 0.15 秒）。更正（10/23）：我原本把它讀成「查下層有沒有這個 block」的時間、寫「代價在查找、不在頻寬」——讀 vLLM 原始碼後發現，這個指標也包含找到之後從下層搬回 CPU（promotion）的等待（下層命中時回 HIT_PENDING，請求一直延後到搬完）。10/23 的 CPU 微量測（跑之前寫好規則）：NFS 上單次存在檢查平均約 0.1 毫秒（命中 0.015、未命中 0.2），有背景寫入時也一樣；推回 64 只佔查找執行緒 3% 的時間 → NOT_EXPLAINED_BY_LOOKUP_LATENCY。所以 41 秒主要是從 NFS 讀回 CPU 的路在排隊（d 平均要讀 182 MB/s）；NFS 的讀取上限沒有量（要對共用的 NFS 打滿流量，沒做）。CPU→GPU 的搬運速度 c、d 一樣（約 4.4 GB/s）。連第一輪（不需要還原）的 P95 也到 54 秒，因為請求在排隊。
  • 讀法：模擬說的「多一層下層，本地有幫助、NFS 反而變差」在真的 vLLM 上成立。模擬用 NFS 的頻寬算成本，方向對，但沒有排隊，所以低估 7.9 倍：讀回 CPU 的需求接近 NFS 能給的量時，等待是排隊爆出來的，不是單次搬運的時間。實務：vLLM 的檔案層不要放 NFS。這是人為壓容量的情境，MI300X 192 GB 實際上不會這麼緊。
  • 換 Qwen（10/23，同一份工作負載、每一層能放的 token 數和 Llama 相同；四個設定都 CLEAN、364／364 請求成功；各只跑一次）：RANK_SAME_AS_LLAMA（c < b < a < d）、FLIP_CONFIRMED。回來那一輪 P95：a 1.99、b 1.61、c 1.14、d 26.4 秒。事後 session bootstrap：c／b＝0.70 [0.57, 0.75]（不碰 1）、d／b＝16 倍（Llama 52 倍）。Qwen 每個 token 的 KV 只有 Llama 的 0.44 倍，從 NFS 讀的平均速率是 84 MB/s（Llama 182），等待從 41 秒降到 5 秒、第一輪幾乎不排隊——和「NFS 讀回 CPU 的路在排隊、越接近上限越非線性」一致；但兩次是不同時間量的共用 NFS、NFS 上限沒量，只能說一致、不是證明。
