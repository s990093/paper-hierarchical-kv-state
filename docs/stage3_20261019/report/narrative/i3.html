I3 是模擬（成本常數用第二階段實測，排程與佇列是模型），沒有 GPU 驗證。它回答使用者的問題②：agent 暫停去查資料時，KV 要留、要搬、還是要丟？

  • MI300X 有 192 GB，同時 32 個 agent 時容量仍是需求的 4–9 倍——在這台機器上這個問題幾乎不會發生，所以這次不改成 agent 場景，使用者「太急」的直覺是對的。
  • 事前凍結的「依 κ 選」在一般硬體上贏不過 vLLM 內建的卸載；只有下層是 NFS 或 CPU 記憶體很小時才明顯贏（+27～38%），但那時現成的 Tokencake 也贏 → 重點是「硬體不尋常時別用 vLLM 預設」，不是 κ 本身。
  • 最大的改善空間是讓系統知道 session 已經結束（NFS 下中位快 26%）——這是應用層和系統之間的介面問題。

過程中我一度說「換成和固定作法比，結論會翻」，照實重算後大部分不成立；這個更正也記在實驗紀錄。
