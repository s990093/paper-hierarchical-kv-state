排名候選題目證據（這一輪）前人（10/22 查新）風險下一步
1爭用感知的還原格式選擇：還原時依 GPU 忙不忙、連線快慢，在 INT4、低秩組合、不壓縮之間選；搬運路徑（逐塊 copy／批次／zero-copy）當成同一個決策的一維X3 實測：最快格式隨 GPU 忙碌翻轉。10/22 的完整格子（4.14）：算力型背景下 FLIP_REPRODUCED（CPU 層兩個模型都翻；依情況選好 6–14%），頻寬型背景下 NO_FLIP（各格式只慢 5–30%、排序不變）→ 翻轉只在同卡有算力型工作時發生沒查到把「執行期 GPU 忙碌」當成選還原格式輸入的作品。最大威脅 KVServe（SIGCOMM'26：執行期依工作負載、頻寬、SLO 選壓縮組合，GPU 負載只當誤差吸收）；機制最像 HCache（EuroSys'25：用矩陣乘法從 hidden state 重建，離線定一次）。「前人都假設互不干擾」要更正：ShadowServe、KVCodec、Tutti 都寫了解壓會搶 GPU，只是用靜態隔離避開新意只在「動作集裡有矩陣乘法型重建（低秩）」時成立（只有逐元素解碼的格式不會翻轉，X3 STOP-0 也看到）；而且只在背景搶運算單元時成立（頻寬型背景實測不翻）；真實服務的背景是哪一種、多常見，還沒量；還沒有真實併發在真實併發（多請求 decode）下量各格式的還原時間與 TTFT；和 KVServe 式的「慢慢學」比負載快速變動時的差距
2長上下文下，疊加壓縮當「存到下層的格式」的量測研究：跨層低秩（RoPE 前）＋係數量化＋無損，配比隨目標倍數變，壓縮後放到 CPU／SSD／NFSX1／X2／X2b／X4：組合在每個倍數都顯著好過單一方法；約 8 倍接近無損、12 倍掉 1–3；128K 撐得住、多輪不傷；慢層還原快約 3 倍（實測）；K1b：同位元組下「全部層一組」重建誤差更低作法已被做掉：KVTC（ICLR 2026）全部層與 head 串起來做離線 PCA、去 RoPE、DP 分配位元（0 位元＝降秩）、DEFLATE、放 GPU 外儲存；xKV 已報跨層 SVD＋4／3 bit。跨層共用子空間的觀察：xKV、JoLT（相鄰層奇異向量平方 cosine 分組）、arXiv 2609.28029（head／layer 模態接近滿秩）。沒查到的只剩：≥32K–128K 的生成答對率（獨立樣本、CI）與壓縮格式在各下層的實測還原時間不能說「第一個疊三層」或「發現共用的是子空間」；審稿人一定要 KVTC 式基準；Llama 在 ε 內判不了；每題 SVD 太慢、共用基底還沒證明不輸在 32K 題組上加 KVTC 式基準（全部層、校準 PCA、去 RoPE、位元分配），和我們的配比地圖同位元組比；接上 vLLM 卸載路徑量端到端
3多輪選擇性還原的索引（原候選 4）：第 2 輪回來時只搬需要的 block，索引用 RoPE 前低秩 K（或疊加格式裡現成的低秩係數）C1b：Quest 摘要不夠準（STOP），但完整 K 的上界很好（Qwen 只放回 1/4 不掉）；K1：K 在 RoPE 前 32 維就留住大部分能量（能量≠召回）整體形狀（還原時一次選完、多輪第 2 輪、512-token block、索引位元組算進下層搬運、補載）沒查到；但「低秩 K 比 Quest 準」在 decode 情境已被做掉（LOCKS、SAKI、FIER／YAKV），而且共用基底的低秩打分前人結果偏負面（LOCKS：每頁各自 fit 才準；YAKV：同搬運量下低秩 K 輸 1–2 bit K）。ShadowKV 選 chunk 用的是 RoPE 後的平均（landmark），低秩 K 只用來重建（之前寫錯）還沒做任何實驗；C1b 的 Quest 用 512-token block（原版 16），STOP 有一部分可能來自 block 太大；索引預算只剩約 3%在 C1b 題組上比 block 召回：r＝16 INT4、疊加格式的 K 係數、1-bit K、Quest-16／512、完整 K 上界；最好的兩種再做 k＝25% 的答對率
4AMD 上的 KV 搬運路徑（降級，併進候選 1 的搬運維度）I4：逐塊 copy 1–3 GiB/s、zero-copy 約 53 GiB/s；vLLM ROCm CPU 層約 4.1 GiB/s；F2：開卸載強制退回 TRITON 注意力；F1：8K 開卸載幾乎都變慢技術已被做掉：vLLM #42212（已合併）＝OffloadingConnector 的 Triton 快路徑（本機 0.28 原始碼裡有，ROCm 上被關掉）；#52700（open）＝在 ROCm 用 mapped host memory 重開，等於這個候選的實作；#43018（已合併）＝ROCm 7.14 批次 memcpy 快 6–19 倍；SGLang HiCache 的 ROCm 路徑已合併。MI300X 上的交叉點與干擾量測沒查到F1 最差的格子（重疊 0%）根本沒有東西要從 CPU 載回 → 8K 的損失可能主要來自寫入與排程；我們退到 TRITON 部分是因為沒裝 AITER先用 F1 已有的 offload store／load 時間拆解 8K 的損失（只用 CPU）；在 MI300X 量 #52700 當給上游的 benchmark
