這一輪做什麼：在 2× AMD MI300X 上，用租約最後約 2.5 天的 GPU 時間（實際時間軸見第 2 章），篩選第三階段的題目。大問題：KV 放不下 GPU 時，要依什麼決定它的待遇（降精度、無損壓縮、搬到 CPU／SSD、丟掉）。每個實驗的判定條件都在看到數字前寫死。

主要發現

  1. 壓縮可以疊，而且有加乘：跨層低秩（K 在 RoPE 前、每 4 層一起）＋係數量化，在每個倍數都顯著好過任何單一方法。獨立樣本下約 8 倍接近無損、12 倍掉 1–3 個百分點、32 倍掉 7–8；單用 INT4 是 3.2 倍。128K 撐得住，多輪不傷。
  2. 配比隨倍數變：8–20 倍用低秩＋INT4，24–32 倍改用低秩＋K4V2，最後再乘無損約 1.1–1.2 倍。依重要性丟 token、合併 token、逐 token 跨層共用都不值得疊。
  3. 還原時「最快的格式」會隨 GPU 忙碌翻轉（端到端實測）：GPU 閒或連線慢時低秩組合最快（SSD 上把還原壓到約 1/3），GPU 很忙時低秩重建被拖慢，INT4 最快，低秩組合甚至比不壓縮慢。查新沒找到把「執行期 GPU 忙碌」當成選格式輸入的作品（前人知道解壓會搶 GPU，但用靜態隔離避開）。10/22 的完整格子：背景搶運算單元時翻轉在兩個模型重現，背景只搶記憶體頻寬時不翻轉。
  4. token 重要性（使用者的問題①）：拿來丟在同樣大小下全面輸給量化，多輪更糟；拿來挑「還原時搬哪些」需要更好的索引——便宜的 Quest 摘要不夠（C1b 停），但完整 K 的上界顯示有空間。
  5. agent（使用者的問題②）：MI300X 192 GB 沒有容量壓力，這次不改場景（模擬）。
  6. AMD 的搬運路徑：vLLM 在 ROCm 上 CPU 卸載慢，主因是逐塊 copy 的固定成本；GPU 直接讀的 zero-copy 快 18–45 倍；開卸載還會強制退回較慢的注意力後端，8K 提示開卸載幾乎都變慢、32K 才變快（vLLM 實測）。

最需要注意的限制

壓縮極限的數字在不同題組之間差到約 3 個百分點，嚴格的 ε 規則下 32K 只有 INT4 正式過關；每題 SVD 的壓縮要數十秒，事先校準的基底還沒正式證明不輸；決策圖的模擬低估 5–26%，以實測為準。
