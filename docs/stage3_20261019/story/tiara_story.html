一頁摘要

問題：長對話的 KV cache 放不下 GPU，要搬到 CPU、SSD，或丟掉、回來時重算。使用者回來時，還原時間直接加在第一個 token 的等待上。

最初的想法（8 月）：重算和搬運的成本比（κ）隨硬體變很多，所以在寫入 KV 時，用一個預測模型替每一塊選狀態：GPU 上的 BF16／FP8／INT4、CPU、SSD，或丟掉重算。

兩個半月後的答案：寫入時逐塊預測大部分不需要。

  1. 放哪一層可以延後（第一階段）：寫入時依位置決定，沒有贏過「先放 CPU、滿了再搬」的同一條規則。MI300X 上 36 組 GPU 比較都沒贏過 5%；H200 上重現。
  2. 精度不需要位置（第二階段）：前、中、後 25% 存低精度和隨機 25% 比，答對率差都在 0.33 個百分點內。前段「沒掉分」是因為沒被讀到，不是不敏感。有用的是格式（依模型 KV 的數值特性選）和比例（慢層全部壓）。
  3. 剩下真正要決定的在還原那一刻：用 Cake（前段重算、後段搬）還是全部搬回來；這要看當下的頻寬、GPU 負載和 context 長度。

第三階段因此轉到還原時，分成兩個子問題：

  • 3a 還原時能不能少搬一點（MI300X 實測，10/23 跑完）：跨層低秩＋INT4 疊起來，約 8 倍接近無損；GPU 忙時「最快的格式」會翻轉，這是唯一沒查到前作的方向。
  • 3b 猜使用者何時回來有沒有用（模擬為主，加上 vLLM 端到端）：用處窄；併發時尾延遲多半是排隊。vLLM 上實測的層級排序和模擬一致，但絕對值差到 0.55–7.9 倍。

接下來：路 1 把第一、二階段寫成量測論文（ICPE，全文 11/16），第三階段只放能支撐主張的部分；路 2 往「GPU 忙時的還原排程」和「讀取時看新問題決定每塊讀多清楚」走，約 6–8 週。

1　起點：原本的 Tiara（8 月底–10 月初）

1.1 最初的主張

Tiara 的一句話主張是：重算與搬運的成本比 κ 跨硬體變動很大（論文假設 32 倍），所以「一種 KV 放置策略適用所有硬體」不成立。放置應該寫成「品質約束下、動作成本不同的線上決策」，動作有六個：GPU-BF16、GPU-FP8、GPU-INT4、CPU、SSD、丟掉再重算。決策發生在寫入時，由一個學習式預測器替每一塊打分，沒把握時退回 LRU。

背後的觀察是：重算第 i 塊要先看過前面所有的 token，所以越後面的塊重算越貴；從儲存搬回來的時間則和位置無關。位置在寫入時就知道，所以「這塊回來時該重算還是搬」似乎可以在寫入時算好。

1.2 平台 A（RTX 3090）：上界不夠大

  • FP8 KV 在 Ampere 上可以用（儲存用，不需要 FP8 運算單元），KV 容量剛好兩倍。〔實測〕
  • Oracle 上界（知道未來的最佳放置）在只算 prefill 時有 11.5–12.6% 的空間；把 decode 算進去只剩 2.8–3.3%，低於 5% 的停損線（NO_GO）。原因是 decode 時整份 KV 必須在 GPU 上，放置只能優化 prefill。〔模擬，常數實測〕
  • 過程中抓到模擬器的 oracle 一直用位置 0 的價格重算（等於作弊），修掉之後所有 oracle 數字少了 8–9 個百分點。這是後來「每個判定事先寫死、每個數字追到 run_id」這套規矩的來源。

1.3 文獻與平台 B（MI300X）的初步量測（9 月）

  • 讀完 Strata、MTDS、Bidaw、Cake、AdaptCache 和約 60 篇相關工作：KV 的待遇其實是三個決定（幾個 bit、放哪一層、回來時重算還是搬），每篇論文都只深挖其中一格，其他格用最陽春的預設。
  • MI300X 上的初步量測（9/30 報告）：KV 改成 INT4、配 vLLM 原廠的 LRU，就拿到最佳放置 92–104% 的好處，留給聰明放置的空間只有 2–3.5%；CPU 層的有效頻寬只換模型就差 17 倍（搬運速度是軟體決定的）；Qwen2.5 在 FP8／INT4 下會壞。〔實測，初步〕

這些結果都指向同一件事：與其做更聰明的放置，不如先問「寫入時決定」本身有沒有用。10/8 把它定成核心問題，分兩個階段回答：先放置，再精度。

2　第一階段：放哪一層可以延後（10/8–10/12）

問題：寫入時就依位置決定 KV 放 CPU 還是 SSD（S5），會不會比「先全部放 CPU、滿了再搬」的同一條規則（延後版 S4+）好？兩者最後的擺法一樣，差別只在什麼時候搬。

作法（延後測試）：每一個寫入時規則，都要贏過它的每一個「延後雙胞胎」至少 5%：同一規則在 CPU 層滿時才套用、在背景套用、預先清理、直接寫穿。判準在看到結果前寫死。

結果〔實測，MI300X〕：

  • 36 組 GPU 比較，沒有一個寫入時規則同時贏過所有延後雙胞胎 5%。最強的寫入時規則比最好的「不看位置」策略快 18.9%，但只比自己的延後版快 0.7%。原因很簡單：位置永遠不變，搬的時候一樣看得到。
  • 延後只在「SSD 寫入持續塞車、而且佇列有上限」時會輸；模擬裡唯一存活的那一格需要一顆 SSD 配 8 張 GPU。用 10 個新 seed 事先登記重跑，216 格裡 0 格勝出。
  • 真正有用的是讀取端的 Cake：頻寬 0.3–4 GiB/s 時，比「只算」或「只搬」快 1.4–1.9 倍。
  • H200 上重跑〔實測〕：判定「重現」。寫入時決定一樣沒贏（主設定 S5 對 S4+ 合併組 −0.12%），Cake 在 28 格裡有 25 格勝過單一路徑 5% 以上。

結論：寫入簡單、讀取聰明。放置照 vLLM 預設那種「先放 CPU、再往 SSD 寫」就好；要做判斷，時機是 CPU 往 SSD 降級的那一刻。

3　第二階段：精度不需要位置（10/13–10/20）

問題：放置可以延後之後，最有理由在寫入時決定的是精度：一塊存成 FP8 就回不去 BF16；常見的 KV 量化器也依位置保護開頭的 sink 和最近的 token。那麼依位置決定哪些塊存成低精度，會不會比「全部低精度」或「同比例隨機放」好？這裡壓的只是存起來的 KV，模型計算全程是 BF16。

作法（讀取記帳）：固定位元組、codec、attention 路徑，只改低精度塊放在哪裡；每次還原逐塊記錄「重算／載入 BF16／載入低精度」。兩種讀法把「不敏感」和「沒被讀到」分開：全部載入量敏感度，Cake 實際還原量讀到什麼。兩個模型（Llama-3.1-8B、Qwen2.5-7B-1M）、每一階 600 題、兩輪。

判定〔實測，MI300X〕：位置沒有貢獻，主線停。前、中、後 25% INT4 對隨機 25%，答對率差都在 ±0.33 個百分點內。

3.1 三個發現

  1. 前段壓了沒掉分，是因為沒被讀到。慢層上，前段存的 16 塊低精度一塊都沒被讀到（都被 Cake 重算蓋掉），時間也沒省；但在快的 CPU 層幾乎全被讀到（14–16／16）。所以「前段沒人讀」只在慢層成立。
  2. 要變快，只能全部壓。全 INT4 還原 0.68 秒、全 BF16 1.38 秒，品質一樣（Llama、b32 慢層、GPU 閒）。限速的慢層上低精度快 22–57%；真實 CPU 層反而最多慢 2.2 倍（反量化在 GPU 上和重算搶資源）。
  3. Qwen 的全 FP8 掉 33 分，問題在格式。Qwen 的 Key 有少數維度一直在 400 左右（平均 415，上下只差約 2）；FP8 在 256–512 之間每格差 32，有用的小差異被捨入掉。同樣 8 bit 換成 INT8、或先扣掉固定值再存 FP8 就回來；只保護 sink 只補回 0.3 分。

3.2 另外量到、只報告的

  • 長 context：好的格式到 128K 仍和 BF16 分不出差（Llama 40.3% 對 41.7–42.2%）。大的位置效應只出現在壞掉的格式。
  • 直接丟 token：以 block 為單位丟 25% 至少掉 4.8 分；照第一輪問題挑的，第二輪換問題就壞。只有「知道問題」的逐 head 丟 25% 過門檻。
  • 容量：INT4 每 TiB 主機記憶體多放 3.2 倍對話。
  • 降級順序：很慢的下層上要「舊的先降」（0.63 秒）；「新的先降」慢很多（2.64 秒）。

3.3 H200 上重跑

終點相同（位置沒有貢獻），但中間路徑不同〔實測，H200〕：H200 的真實 CPU 層、GPU 忙時，低精度一律比 BF16 慢（1.12–1.69 倍），所以判定流程改走 Qwen 的 FP8 階。那裡前段（F25）品質比較好，只是因為前段沒被讀到（和發現 1 同一件事），而且速度慢 8–10%，所以位置還是沒贏。照 MI300X 的路走 INT4 時，前、中、後對隨機也都在 ±0.6 分內。另外，H200 有一個節點（Llama、CPU 層、GPU 忙）是靠雜訊門檻 δ*＝0.284 才過的；照規則不改判，但要寫在限制裡。

4　兩階段之後，原本的設計剩下什麼

原本的設計（寫入時逐塊決定）第一、二階段之後還要做的
放 CPU 還是 SSD不用寫入時決定；先放 CPU、滿了才降級，效果一樣（第一階段）照 vLLM 內建；降級順序用 LRU（舊的先降）
每塊用 BF16／FP8／INT4不用逐塊；格式依模型 KV 的數值特性選，比例依儲存層（慢層全部壓）降級到慢層時才壓（vLLM 內建搬原始 BF16，要補）
丟掉再重算慢層＋Cake 時前段本來就被重算，可以不存；但 GPU 忙時「一開始不存前段」比「全存」慢 13–66%，範圍要保守，看會合點就能定真的丟（不重算）會掉分，不建議
學習式預測器大部分拿掉剩下的決定是還原方式（Cake 或全搬）
κ 隨硬體變動前提還在從「寫入時逐塊預測」改成「還原時依當下頻寬、GPU 負載、長度決定」

還原方式的規則還要補：目前用一條簡單規則（G5b）估兩種做法各要多久、挑快的。32K 時平均只比每格最好慢 0.4%；但 64K／128K 平均慢 2.7%、最差 20%；H200 上 CPU 層、GPU 忙時 12 格裡 10 格挑錯（整體慢 11.5%）。所以規則要把長度和 GPU 負載算進去。還原的實作細節則是固定做法：融合 kernel 反量化、全部搬完再一次反量化、每塊 512 token。

實際該怎麼做：寫入照 vLLM 內建（先 CPU、再 SSD），只補兩件事：(1) 搬去慢層時才壓縮（INT4 快 22–57%、品質不掉，格式依模型選）；(2) 拿回來時選對方式（CPU 層全搬、慢層 Cake；vLLM 目前沒有 Cake）。

5　第三階段 3a：還原時能不能少搬一點（MI300X，10/19–10/23）

第二階段說「格式和比例」才重要，3a 就問：在同樣的品質門檻下能壓到多小、壓過的格式還原起來是不是真的比較快。每個實驗的判定都在看到數字前寫死。

5.1 壓縮可以疊

  • 跨層低秩（K 在 RoPE 之前、每 4 層一組）＋係數量化，在每個倍數都顯著好過任何單一方法：約 8 倍接近無損、12 倍掉 1–3 分、32 倍掉 7–8 分；單用 INT4 是 3.2 倍。128K 撐得住，多輪不傷。〔實測，生成答對率〕
  • 配比隨倍數變：8–20 倍用低秩＋INT4，24–32 倍改用低秩＋K4V2，最後再乘無損約 1.1–1.2 倍。
  • 依重要性丟 token、合併 token、逐 token 跨層共用，都不值得疊上去；同樣位元組下，丟不如壓。
  • 要照實說：壓縮極限在不同題組之間差到約 3 個百分點，嚴格的 ε 規則下 32K 只有 INT4 正式過關；每題 SVD 要 4–31 秒（GPU 忙時再慢約 3 倍），事先校準的共用基底還沒正式證明不輸。

5.2 只搬下一題需要的塊

便宜的 Quest 摘要挑得不夠準（判定 STOP）；但用完整 K 當上界時，Qwen 只放回 1/4 也不掉分。所以「下一題需要哪些塊」是可預測的，只是目前的便宜索引預測不到。

5.3 GPU 忙時，最快的格式會翻轉

  • 端到端實測：Qwen 在 CPU 記憶體層，GPU 閒時低秩最快（0.015 秒，INT4 0.018、BF16 0.039）；GPU 很忙時 INT4 最快（0.020），低秩＋INT4 反而 0.083，比不壓縮（0.060）還慢。在本地 SSD 上，低秩組合快 2.5–3.4 倍。原因是低秩重建是矩陣乘法，GPU 忙時慢約 2.8 倍。
  • 10/22 補完 144 格：背景搶運算單元（matmul）時兩個模型都翻（6 條裡 3 條），依情況選比固定最好的一種好 6–14%；背景只搶記憶體頻寬時不翻（0／6）。所以要說成「隨同卡的算力型工作翻轉」。
  • 模擬的決策圖低估 5–26%（STOP-3），以實測為準。

5.4 前人做到哪

疊加的作法已經被做掉：KVTC（ICLR 2026）把全部層與 head 串起來做離線 PCA、去 RoPE、分配位元、無損壓縮後放 GPU 外；xKV 已報告跨層 SVD＋4／3 bit。我們剩下的是 ≥32K 的生成答對率和各下層的實測還原時間。「依執行期 GPU 忙不忙選還原格式」沒查到前作；最接近的 KVServe（SIGCOMM'26）依工作負載與頻寬選壓縮，但 GPU 負載只當誤差吸收。AMD 搬運路徑（zero-copy 比逐塊 copy 快 18–45 倍）的作法已在 vLLM 上游（#42212、#52700），只剩量測價值。

6　第三階段 3b：猜使用者何時回來，有沒有用

6.1 模擬（成本用實測常數）

  • 在最有利的設定（對話 trace、本地 SSD、CPU 128／256 GiB、GPU 閒、Cake），知道未來的預取可以比最好的對稱策略快 45–49%（H200 常數）；但換成真實的 agent trace，空間只剩 0.22%（MI300X 常數）。〔模擬〕
  • 「知道誰不會回來」有價值的地方只在 CPU ≤ 256 GiB、慢層又慢時：48 格裡 11 格 ≥ 15%，最多 37.4%。〔模擬，H200 常數〕
  • 多個請求同時回來時，最慢那 1% 的延遲，中位數 98% 是在排隊。〔模擬，H200 常數〕
  • MI300X 的 agent 暫停模擬：事先寫死的「依 κ 選」在一般硬體上贏不過 vLLM 內建的卸載；只有下層是 NFS 或 CPU 記憶體很小時才贏（+27～38%），但那時現成的 Tokencake 也贏。最大的改善空間是讓系統知道 session 已經結束（NFS 下中位快 26%）。〔模擬〕

小結：用處很窄，只有 CPU 記憶體很小、倉庫又很慢的時候才有差；提早搬回來，靠使用者打字那幾秒就夠。

6.2 vLLM 端到端：agent 暫停後回來那一輪（MI300X）

為了檢查模擬的排序，在 vLLM 0.28 上實際重播 64 個 agent session（6 輪、工具暫停中位 30 秒），HBM 人為壓到工作集的 1/4，比四種設定：a 只有 APC、b 加 CPU 卸載、c 再加本地檔案層、d 檔案層放 NFS。〔實測〕

  • 排序和模擬一致（c 最好、d 最差），兩個模型都是；CPU 卸載好過只靠 APC。
  • 本地檔案層比只加 CPU 好 15–20%，Llama 重跑三對都成立。
  • 檔案層放 NFS 時，回來那一輪的 P95 從約 2 秒變 105 秒（Llama）、26 秒（Qwen）。等待主要在「從 NFS 讀回 CPU」排隊；單次存在檢查只要約 0.1 毫秒，不是瓶頸。
  • 絕對值和模擬差 0.55–7.9 倍：模擬的排序可以信，絕對值不能直接用。

7　KV 看起來隨機？換個粒度看

這兩個半月有一個反覆出現的現象：逐 token、逐位置看，KV 很像隨機。

  • 位置對品質沒有貢獻（前、中、後對隨機在 ±0.33 分內）。
  • 逐 block 的敏感度只有 block 0（sink＋任務說明）突出約 3.5 倍，答案所在的 block 不比別處敏感。
  • 同一個 token 在相鄰層的向量幾乎不相關（cosine ≈ 0）。
  • 寫入時的重要性分數拿去丟 token，第二輪換問題就壞。

但換個粒度就有結構：

  • 子空間跨層共用：同一段 token 在不同層的 K、V，主要的 token 子空間大部分重疊（去平均後 0.63–0.76，兩個模型、K 和 V 都是）。
  • 通道有固定偏移：Qwen 的 K 有少數維度一直約 415，這正是 FP8 壞掉的原因。
  • 能量集中：K 在 RoPE 之前 32 維就留住大部分能量。
  • 下一題要哪些塊可預測：完整 K 的上界顯示 Qwen 只放回 1/4 不掉分。

7.1 Tucker 可以用在「少搬一點」

把 KV 看成「token × 層 × head × 維度」的張量，Tucker 分解在 token 那一維做的，正是讓多層共用同一組 token 基底、每層只存小的係數。子空間跨層共用就是它能用的原因。同位元組下的比較〔實測〕：

  • 4 維 Tucker 的誤差和「全部層一組的跨層 SVD」幾乎一樣，多分解 head、維度兩維沒有額外好處；真正的收益來自「一組放更多層」。
  • Qwen 全部 28 層一組的重建誤差，是每 4 層一組（xKV）的 0.78–0.85 倍（K）、0.69 倍（V）；Llama 的 K 每 16 層一組最好（0.83 倍）。
  • 上 GPU（teacher forcing，答對率的代理）：每 7／8 層一組在 Qwen 一致較好；全部層一組好壞參半。

所以 Tucker 在這裡是決定「幾層共用一組基底、每一維留多少秩」的工具。它的重建是矩陣乘法，GPU 忙時會變慢，剛好接上 5.3 的翻轉：秩可以當成「搬運位元組」和「重建計算」之間的旋鈕〔推論，未驗證〕。要注意全部層一起做 PCA 的作法 KVTC 已經做了，Tucker 本身不能當新意。

7.2 可以挖的方向〔推論〕

  1. 依通道、子空間的統計選格式，不依位置。
  2. 跨層共用基底當儲存格式，秩依 GPU 負載調。
  3. 讀取時看新問題，決定每塊讀多清楚，用低秩 K 當索引。
  4. 反過來利用「隨機」：既然敏感度很平，系統可以不管位置，設計就簡單；這正是路 1 的論點。

9.2 路 2：繼續往下做（兩個候選，都是第三階段看到的）

  • GPU 忙的時候：GPU 被別的工作佔用時，要用 GPU 的技巧都會打折：重算慢約 2 倍、解壓慢 2.4–3.8 倍、低秩重建慢 2.8 倍，最好的格式甚至會翻過來；多個請求同時回來時，延遲大多在排隊。所以這些技巧要放進整個推論的排程裡看：誰先做、給還原多少 GPU。很多相關論文假設還原和計算互不干擾。
  • 讀取時看新問題，再決定每塊讀多清楚：不丟 token，改成「全部載入縮很小的版本，和問題相關的塊再補清楚版」，挑錯也只是比較糊，不會漏掉。

兩個都要約 6–8 週，11/16 來不及；便宜的篩選 11/3 前會知道有沒有希望。

9.3 預測的方向還在嗎

還在，但位置變了：從「寫入時逐塊預測」移到「還原時依當下頻寬、GPU 負載、長度決定」（G5b 要補長度和負載），以及「GPU 忙時的排程」。預測「使用者何時回來」目前看用處窄。所以貢獻比原本設想的小，但比較集中。

10　限制與待確認

  • 模型與長度：只有兩個 8B 級 GQA 模型；品質資料最長 128K；256K 只有速度和 18 題（INCOMPLETE）；512K 以上沒做。8B 模型在 128K 自己的答對率只有約 40%。
  • 還原器比 vLLM 慢：MI300X 上 harness 的重算比預設 vLLM 慢 1.7–2.0 倍（H200 換 FA3 後 1.30 倍）；重算變快時會合點會後移，只有模擬覆蓋。
  • 慢層是限速模擬：SSD、NFS 級的層用 pinned 記憶體加限速器；I3g 用的是真的本地磁碟和真的 NFS，但只是一份工作負載、HBM 人為壓小。
  • 3b 大多是模擬；vLLM 端到端只驗了層級排序，絕對值差 0.55–7.9 倍。
  • H200 的時間數字：同節點別人的負載看不到；有一個判定節點靠雜訊門檻才過。
  • 外部說法沒有重新查證：給老師的訊息裡「KV 壓到多低實務上有人用」那段（vLLM、AMD、MLPerf、DeepSeek）是 AI 查的，送出前要附來源連結。
  • 審查：所有判讀都是 self-review，沒有 cross-model review。
