第四幕　這次新加

依現場狀況

前三幕都默認「拿回來要多久」是固定的，前人論文也這樣假設。第二階段量到 GPU 忙時重算慢約一倍、搬運慢約一半；vLLM 在 ROCm 的 CPU 層只有 4.1 GiB/s（直接搬可到 49.9）。

待跑：I4、I1、I2、V0→F2→F1、X3

κ（重算時間 ÷ 搬運時間）在這裡只是背景。「κ 會隨硬體變」已經有人做過（Stony Brook FSL-26-02），不再當主軸。

新主軸：壓縮可以疊起來用嗎

你問「又量化、又壓縮、又丟不重要的，全部疊起來會不會更好」。每種方法省的是 KV 大小的不同一項：

但疊起來不一定相乘：誤差會累積；方法之間會互相干擾（丟掉不重要的之後剩下的都重要，量化誤差影響變大；低秩之後數值分布更不均，量化更難）；每多一層，還原就多一步計算，GPU 忙時更慢。

方向文獻已知（agent 讀全文）對我們的意思
低秩
L5a		單獨砍維度輸給同大小的量化（Qwen2.5-7B：30.5 vs KIVI-2 46.8）。先換到低秩座標再分配位元有用（SVDq，64K、3-bit：69.7 vs 直接量化 39.9）。K 要在 RoPE 之前做，V 本身不適合降秩。INT4 那個大小沒空間；有空間的是更小的大小
合併、跨層
L5b		Llama-3.1-8B 的相鄰層其實不像：MiniCache 只壓 1.3 倍，RULER 64K 從 91.9 掉到 45.0（xKV 自己重做的版本）。xKV 每 4 層一起降秩：Llama 64K 壓 8 倍得 88.5，KIVI-2 是 86.9。token 合併疊在丟 token 上只多 0.6–1.7 分。跨層要用「子空間」，不是逐 token；合併證據弱
疊加
L5d		預算緊時（每值少於 3–4 bit，或只留不到 25% 的 token）兩兩組合贏單一方法（RDKV：只量化 39.1、只丟 42.5、一起 47.4）。量化已近乎無損時，組合贏不了。三種以上、長上下文、同大小的系統性比較：查不到。我們的 INT4 已不掉分，所以疊加的空間在壓 4 倍以上
卸載時壓縮（B）
L5c		依連線速度選格式已有人做（CacheGen、KVServe、AdaptCache）。沒人把「GPU 忙不忙」放進決策。第二階段資料：只在 FP8、INT4 之間挑時，處處都是 INT4 最快（Llama 32K CPU 層：BF16 84 ms、FP8 46 ms、INT4 33 ms）。只挑格式時自適應沒好處；把疊加組合放進選項後才可能翻
X1　GPU 大量篩選

上百種組合（各家族自己的超參數、兩兩、三種以上、順序對照），在同樣大小下用 teacher forcing 量 KL 和答案機率。S2（丟 vs 量化）也在裡面。順便量便宜的代理指標準不準。

停：每個大小下最好的組合都 ≥ 最好單一方法的 0.95 → 不上 X2。

X2　生成答對率

每個大小（壓 4、8、16 倍）挑前緣 2–6 個組合，量真正的答對率（32K，加 128K 切片）。對照：BF16、INT4 KIVI、各家族最好的單一方法、常見部署格式。

停：兩個模型都 r＞0.95（組合能省的不到 5%）→ 疊加沒有加乘。

X3　還原時間與決策圖（B）

每個組合的解壓、重建在 GPU 閒到忙（duty 0–0.9）的時間，配上各層連線速度（CPU、本地 SSD、NFS），畫「什麼情況用哪個組合」。

停：每一格最快的組合都沒比 INT4 快 5% 以上 → NO-GO。

停止條件在看到任何數字前就寫進說明檔。K1 先在 CPU 上量 KV 本身的結構（低秩程度、相鄰層像不像、相鄰 token 像不像），不用 GPU。

對照組

主對照維持 BF16（引擎預設、前兩階段基準）。另加「常見部署」：Llama 用 vLLM 的 FP8；Qwen 的 K 最大約 422，超出這版 FP8 的上限 240（找針 2/20，int8 是 18/20），所以 Qwen 改用 int8，FP8 那列標「已知會壞」。

MLPerf 規則

KV 可以量化、不能丟；只快取一部分、其餘重算是合法的。門檻是參考實作的 99%／99.9%。我們的「掉 2 個百分點內」約等於 97%，比較寬：兩種都列，判定照開跑前寫死的那個。

為什麼停在 FP8

硬體原生、容量剛好翻倍、不會變慢、一般模型幾乎無損。FP4 只有 NVIDIA Blackwell 才有，ROCm 上用不了。
