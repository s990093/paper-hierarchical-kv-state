M1

容量懸崖

量測

論文 §2.5 宣稱「3090 上 64K 可置入、128K 超出」——那是算出來的。 這裡量真的懸崖在哪。做法不是逐步加大直到 OOM，而是讀 vLLM 啟動時印出的 GPU KV cache size，再雙向驗證：用讀到的 N 啟動一次（應該成功）， 再用 N×1.15 啟動一次（應該失敗）。沒有後兩步就只是抄 log，不算量測。

M2·A

平時成本：每個狀態佔多少

量測

計畫書把成本常數定義成 2×N 矩陣而非 1×N 向量——「閒置時持續付出的」 和「被需要時一次性付出的」性質完全不同。這是矩陣的第一列。

發現 7 · 論文動作空間的四個精度階，全部是同一個旗標的不同取值

vLLM 的 --kv-cache-dtype 除了 fp8，還提供 int8_per_token_head 與 int4_per_token_head。 也就是說六階動作空間裡「住在 GPU 上」的四階，換一個字串就換一階， 不需要任何額外實作。計畫書原本判定平台 A 只能量到 BF16 一階。

那多出來的位元組算得出來是什麼——不是量測誤差，是 per_token_head 量化的中繼資料。這對論文有直接影響： 動作空間的精度階梯不是 2×/4×，而是 2.00× / 1.94× / 3.77×。 fp8 是純格式轉換所以恰好 2×；int8/int4 走 per-token-head 量化， 固定多帶 2 KiB/token。把 FP8 與 INT8 當成同一階（都是 1 byte）會失準 3%； 式(1) 若只寫 bytes/elem，會系統性高估低精度階的收益。

M2·C

重算成本隨位置怎麼變

量測

送一個長度 P 的前綴讓它進 prefix cache，再送「同樣的 P + 新的 2048 個 token」。 第二次的 TTFT 就是「在位置 P 重算 2048 個 token」的成本。

計畫書對的地方

C_recompute 確實不是常數

同樣重算 2048 個 token，在位置 24,576 要 2.29 倍的時間。 把重算當成單一純量會在長 context 系統性低估它的成本。

發現 8 · 要修

但是線性，不是二次

「隨 block 的絕對位置成長（attention 二次項）」　→ 對固定大小的 block，重算成本隨其絕對位置線性成長

成長的來源確實是 attention 的二次項（整段 prefill 是 O(L²)）， 但對固定大小的 chunk，觀察量是 O(chunk × P)——對 P 線性。 實測線性擬合誤差 < 1.6%，五個點都在線上，找不到二次成分。 論文若寫「二次成長」，審稿人只要做這個實驗就會抓到。

這條曲線的意義：DROP 的「平時成本 = 0」是它唯一的優勢， 而它要付的代價隨位置線性上升——這正是論文「重算的價值取決於未來效用預測品質」 的量化基礎。越晚才被需要的 block，重算越貴。

M3

Tier 0 對照組

量測·爭用

KV 卸載只在有重用時才有價值。單發一個長請求，連接器把 block 存到 CPU 就沒有下文，lru 與 arc 會給出完全相同的數字——而計畫書正把 「兩者相同」列為「卸載沒真的發生」的警訊。所以工作負載是兩輪、共享前綴： cold 依序送 N=4 個不同的長前綴，warm 用同樣順序再送一次。 N × ctx 刻意跨過實測的 GPU KV 容量，逼出逐出。 cold 與 warm 的 TTFT 差，就是那一階卸載的價值。

發現 3

容量量測準確預測了行為轉折

兩個模型的 full_gpu 都在工作集跨過自己的實測容量時崩塌， 而且崩塌點都夾住那個容量值。Qwen 在工作集 131,072（容量 121,072，只大 8%） 給出 59.8%——轉折不是階梯而是斜坡，斜坡位置正好落在容量上。 兩個量測沒有共用假設：一個讀 vLLM 啟動時的 KV pool，一個量端到端 TTFT。 論文 §2.5 從算術主張變成可觀測現象。

發現 2

ARC 在最大 context 輸給 LRU，兩個模型方向一致

llama 62.6% vs 92.2%；qwen 82.7% vs 95.2%。與工作負載性質相符——每個 block 恰好被重訪一次， ARC 的頻率分量（T2/B2）拿不到有用訊號，而 ghost list 佔的空間反而排擠實際資料。 這通過了計畫書「兩者若相同代表卸載沒真的發生」的驗收。 但這是單一工作負載，不足以宣稱「ARC 普遍較差」—— 它只說明 production 預設的兩個策略在長上下文重用型負載上都不是強對手。

HYG

共用機器：污染是真的，而且只打在一條路上

量測

這台機器 /ssd7 底下有二十幾個使用者。把 serial（一次一個 server） 與 parallel（五個同時跑）逐格相比，80 個格子給出乾淨的因果證據。

full_gpu 全部格子 ±2% 不走 PCIe 搬 KV — 對照組
卸載 cold TTFT +3~10% 算力為主
卸載 warm TTFT −26~52% PCIe 搬運為主 — 被灌水
|Δ|>12% 的格子 12/80 其中 11 個是卸載的 warm

GPU 的 SM 是各卡獨占的，但 PCIe、host RAM 頻寬、/dev/shm 是全機共用。別人在 GPU 1–6 上跑，不會出現在 GPU 0 的 compute-apps 裡， 卻會實實在在拖慢搬運量測。所以 gpu_guard 擋得住別人插隊， 擋不住自己的其他 job——而卸載量的正是最容易被自己人污染的那條路。

三個會靜默給出錯誤結果的坑

1 · /dev/shm 被自己的洩漏檔塞爆。 vLLM 的 CPU 階是 /dev/shm 上的 mmap 檔，server 被 kill 時不會回收。 連跑幾輪後 221 GB 全滿（8 個孤兒檔共 231 GB），接著每個帶卸載的 baseline 都在啟動時死掉，而錯誤訊息完全不指向真因。

2 · CSV 欄位錯位。 write_csv 只在檔案不存在時寫 header，而欄位取自當下的 row dict。 實驗跑到一半加了兩欄 → 608 列全部往右錯位， 而 csv.DictReader 讀起來完全不報錯。 靠「這列有幾個值」分辨三個 schema 版本後全數救回（640 列，ttft_ms 非數字 0 列）。

3 · torch.cuda.is_available() 回傳 True 但 kernel 會爆。 vLLM 的預設 wheel 是 CUDA 13 編的，本機 driver 只到 12.4。天真的檢查會通過， 跑一個 matmul 才爆。驗收條件因此改成「跑成一個真的 kernel」。

M4

Oracle 上界

模擬

計畫書把這一步定為整個研究的停損點：一個「知道未來」的完美策略， 比最好的簡單策略好多少？>15% 繼續、5–15% 停下來問人、<5% 停止。 做法是 trace-driven 模擬——單階用 Bélády/MIN（可證明最優），多階用成本感知貪婪。 工作負載用 Zipf 偏斜而非 M3 的兩輪重放，因為後者每個前綴恰好被存取兩次， Bélády 與 LRU 幾乎沒差別，會系統性低估 headroom。

 重算比從 CPU 取回貴 10 倍（4.01 vs 0.40 ms/block）—— 這是論文 κ 論述在本平台的直接量測。⚠ CPU/SSD 兩列是在整機 HEAVY 下量的。

Oracle 的優勢來源也很一致：它把 GPU 命中從 ~19K 拉到 ~51K（α=0.4）， 而重算次數完全相同（16,128 vs 16,128）。也就是說 Oracle 贏在「該把誰留在 GPU」，不是贏在「少重算」。

🔴 這組 14–20% 還不能拿來做 go/no-go 判定

模擬器的 docstring 自己寫了兩個前提，缺一則數字不可用。第二個沒過。

前提 1（成本常數來自實測）　✓ 通過。讀不到 M2 的檔案就中止，不使用預設值。

前提 2（模擬器能複現已量到的行為）　🟡 只過了一半。 拿模擬的 warm 段成本比對實測的 warm TTFT： ctx=16,384 實測 9.00 vs 模擬 14.33（偏 59%）；ctx=32,768 實測 12.27 vs 模擬 18.64（偏 52%）。 方向 2/2 正確，量級高估約 1.5 倍。

而且 CPU 取回成本是在整機 HEAVY 下量的（6 個外來 process、97% 使用率）， 已實測這會讓卸載的 warm TTFT 灌水 26–52%。CPU 成本被高估 → Oracle「少去 CPU 拿東西」的優勢被放大 → headroom 很可能也是高估的。

可引用的是趨勢（headroom 隨偏斜下降），不是絕對數字。 在凌晨批次的乾淨資料出來之前，不得宣稱「Oracle 顯示有 headroom，可以繼續」。

順帶修掉一個會讓驗證失去意義的錯誤：第一版拿「模擬的兩輪總成本」 去比「實測的 warm 那一輪 TTFT」，是蘋果比橘子。 實測 9.00 vs 模擬 1.87 看起來像模擬器壞掉，其實是比錯東西。

Δ

推翻計畫書的地方

實驗計畫書是在沒有這台機器的情況下寫的。這一天量到的東西裡有八項與它不符， 其中兩項會讓論文變強，一項若寫進去會被審稿人抓到。

發現 1

Ampere 可以用 FP8 KV cache

「sm_86 不支援原生 FP8 → 平台 A 量不到 GPU-FP8 那一階，標 NOT_SUPPORTED」

錯在混淆了 FP8 運算（tensor core 原生 matmul，Ampere 確實沒有）與 FP8 儲存（KV 以 fp8 存、讀取時反量化，與 tensor core 無關）。 論文的動作空間是儲存狀態。六階裡有五階在平台 A 就量得到。

發現 2

vLLM 0.28.0 跑不了 Qwen2.5-1M 的 Dual Chunk Attention

V1 engine 沒有可用的 DCA 路徑（FlashAttentionImpl 不吃 layer_idx， v1/attention/ 下無對應 backend），--hf-overrides 設 null 或 {} 都繞不過。已建 no-DCA 變體，評測上限因此是 262,144 ——那本來就是它真正訓練的長度。這對品質歸因反而更乾淨。

發現 6

容量懸崖不是單一常數

同模型、同卡、同 utilization，KV pool 在 5.09 / 5.88 GiB 兩個值之間擺動 （raw token 全距 13.5%）。capacity.csv 的四個數字只在 max_model_len=8192 下成立。論文 §2.5 要補一句： 懸崖位置與部署設定耦合，不是純硬體常數。正確的報法是 KiB/token 而非原始 token 數——正規化後全距 0.00–0.04%。

發現 7

四個精度階全部可在單卡量到

見上。這讓論文的動作空間從「需要兩個平台才驗證得完」變成 「五階在一張消費卡上就量得到」。

發現 8

重算成本是線性成長，不是二次

見上。論文 §2.6 與計畫書 §3 的措辭都要改。

附帶

CachePolicy 的 out-of-tree 掛載點真的存在

官方支援、不需 fork vLLM（cache_policy_module_path）。 但那個介面只有 get/insert/remove/touch/evict/clear， 決定的是「CPU 階裡淘汰哪個 block」——六階動作空間裡的 DROP→重算 與 GPU 內降精度表達不了。 Fig. 2 若讓讀者以為整個 Tiara 都靠這個介面實現就是過度宣稱。 這反而有利：說明本文不只是一個 policy plugin。
