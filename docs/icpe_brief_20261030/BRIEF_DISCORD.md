## 訊息 1/11　摘要（故事版，可單獨貼）　附圖：`figs/brief_0_story.png`

```
**【1/11】摘要（可單獨貼）**

使用者和聊天機器人或 AI agent 對話時，常隔幾秒到幾分鐘才回來。這段期間，系統把這段對話已算好的中間結果（KV cache）移出 GPU；使用者回來時要先搬回，才看得到回答的第一個字，這段等待叫首字延遲（TTFT）。近年不少系統押注在「預測 KV 的未來」：誰會回來、何時回來、該放哪一層。我們一開始也這樣假設：事先預測、寫入時就放對，應該比「滿了再搬」好。我們事先登記判定門檻，再在一張 NVIDIA H200 上驗證：搬回的各種組合直接在 GPU 上量，預測的上限用三份真實使用紀錄模擬，並用縮小的 GPU 重播檢查模擬。

**量完，這個假設大半落空。** 寫入時就放對，量不到收益（16 組比較，0 組同時贏過兩個對手 5% 以上），因為要搬的時候，當初用來決定的資訊（位置）一樣看得到。預測誰會回來，則要看使用紀錄：在 agent 服務的紀錄（FreeInference）上，完美預測也省不到 15%（CPU 128 GiB 時只有 0.30%），因為固定規則（LRU）已經命中 99.29%，沒有東西可補。

**過程中，我們發現真正有用的在別處。** 把 KV 壓成 4 位元（INT4），回來時一邊重算前段、一邊載入後段（Cake），最慢那層的 32K 對話從 12.1 秒降到 1.24 秒（比次佳做法快 11.0–40.7%）；同樣是 INT4，解壓寫法不同差 6.8 倍。GPU 要共用時，MPS 讓回答快 30.7–62.9%，別的工作最多慢 6.5 個百分點（模擬）。預測也不是全無價值：在對話紀錄（Mooncake）上，完美預取最多省 50.5%，而「使用者一開始打字就搬」這個免費訊號就拿到 0.81。

**建議**：① KV 放在慢儲存時，用 INT4＋Cake；放在 CPU 記憶體時，看 INT4 怎麼解壓：一次拆完 → 整段搬回（把存的 KV 整段載回 GPU），逐塊解壓 → Cake。這張對照就是後面說的「查表」。② 要不要建預測器，先在自己的紀錄上算完美預測的上限再決定。
```

## 訊息 2/11　起點：因為…所以…我採用…　附圖：`figs/paper_overview_zh.png`（論文風格總覽圖）

```
**【2/11】起點：我們一開始為什麼這樣想、打算怎麼驗證**

**場景**：你和聊天機器人聊到一半，離開幾分鐘。伺服器要把 GPU 記憶體讓給別人，就把你這段對話已算好的中間結果（KV cache，下稱 KV）移到 CPU 記憶體或更慢的儲存。你回來講下一句話時，KV 要先搬回 GPU，才看得到第一個字。32K token 的 Llama 對話，KV 有 4.0 GiB，搬起來不輕鬆。

**假設一**：**因為**重算第 N 塊要先重讀前面所有塊，越後面越貴，而從儲存搬回來的時間不隨位置變；**所以**前面的塊重算較划算、後面的塊搬較划算；於是假設可以**寫入時就依位置放好**。
**假設二**：**因為**「誰會回來、何時回來」寫入時不知道，**所以**假設再加預測器去猜，猜準就能更早放對、更早搬好。近年有不少預測型系統報告大收益（我們只讀了摘要），所以值得驗證。

**怎麼驗證，我採用**
- 驗證假設一：**因為**要確定贏的是「寫入時」而不是規則本身，**所以我採用**「同一條規則，只換套用時間」的對照：寫入時套用 vs 先全放 CPU、滿了才套用。
- 驗證假設二：**因為**蓋預測器要花功夫，**所以我先量**「完美預測」（oracle）的上限：它和對手做一樣的事，只多知道未來的一件事；連它都省不到，就不必蓋。
- 門檻在看數字前先登記（下一則）。

**貢獻**
1. **組合地圖（查表）**：在兩個模型、各種 KV 存放層、GPU 閒或忙下，量出哪個格式＋送法最快、比第二名快多少。慢儲存用 INT4＋Cake；CPU 記憶體要看 INT4 的解壓實作（差 6.8 倍）；在測過的條件下，這張表不翻轉。
2. **GPU 共用的取捨**：MPS 讓回答快 30.7–62.9%；替搬回保留越多 GPU，別的工作越慢（模擬）。
3. **預測的價值有上限，而且取決於 trace**：寫入時預知量不到收益；回來時的預測，在 agent 紀錄上完美預測也省不到 15%，在對話紀錄上最多省 50.5%，原因是固定規則已命中多少；免費的打字訊號拿到預取的 0.81。重點不是「預測沒用」，而是「先量上限，再決定要不要蓋」。
4. **決策流程與方法**：先查表、再分 GPU、最後才考慮預測；門檻事先登記、模擬用 GPU 重播驗證。

**範圍**：一張 H200、Llama-3.1-8B 與 Qwen2.5-7B、32K；三份真實使用紀錄（Mooncake 對話、Mooncake 工具／agent、FreeInference）。
```

## 訊息 3/11　設計方法的兩個重點　附圖：`figs/brief_m_method.png`

```
**【3/11】設計方法的兩個重點（附圖 M）**

**重點一：判斷門檻，看到數字之前先登記**
**因為**這些門檻是研究的停損點，看過數字才定，容易往對專案有利的方向調；**所以我採用**「先登記、再量、機械式判定」：
1. 開跑前把「量什麼、對手是誰、什麼算贏」寫成登記檔，連「登記前已經看過的數字」也列出。
2. 照登記去量；登記後才改的做法，一律記成「偏離」並標出影響，以較保守的版本為準（例：FreeInference 是登記後、看結果前才加入，所以它的結論標為偏離；截尾是登記後才加的，比原登記保守）。
3. 判定字固定：值得做／可能／死路；沒過門檻的結果也照列。
**門檻**：時間快 ≥5% 才算有改進（雜訊更大時以雜訊為準）；換格式時答對率比 BF16 低不能超過 2 個百分點（95% 信賴區間下界）；預測的上限 ≥15% 值得做、<5% 算死路。5%／15% 沿用計畫初期的停損規則，原登記沒有寫為什麼是這兩個數字。

**重點二：「完美預測上限」怎麼設計出來的**
**因為**蓋預測器要花功夫，**所以**先問：就算預測完全準確，最多能省多少？**我採用**一條「梯子」：同一份紀錄、同一套送回方法，只換最後一個條件，跑四種（圖 M 下半）：
① 底：INT4＋Cake，不預測
② 最好的不預測對手
③ 免費訊號：打字提示
④ 完美預測（oracle）：和②做一樣的事，只多知道未來的一件事
**上限＝1 −（④ 的 TTFT ÷ ② 的 TTFT）**。④ 都比 ② 快不到 15%，就不值得蓋；<5% 算死路。
注意：它只界住「把這個量的預測器放進同一個策略」最多能省多少，不是所有策略的極限（有 4 格打字提示甚至比完美預取還快）。

**量法分三層**：① GPU 直接量搬回（32K，重複 10／30 次取中位數）→ 選格式與送法；② trace 模擬 → MPS 取捨與預測上限（成本常數取自①）；③ 縮小的 GPU 重播 12 個 run → 檢查②（實測÷模擬 0.911–0.987，排名相同）。共用叢集，每個量時間的 run 有 GPU 監看，出現外來程式就作廢重量。
```

```
**【4/11】第一個假設落空：寫入時就放對，沒有用**

**因為**假設一是整個方向的根（寫入時放不對，預測也沒有意義），**所以**先驗證它；**我採用**「同一條規則，只換套用時間」的對照（寫入時套用 vs 先全放 CPU、滿了才套用），並加上對寫入時最有利的條件（CPU 慢、容量緊、搬移擋住請求），共 16 組比較。

**結果** [實測：H200]
- TTFT 差 −0.37～+1.16%（重算用兩種實作都測了；門檻 5%）：量不到差別。
- 16 組比較，0 組同時贏過兩個對手各 5% 以上。
- 模擬挑出 2 個「可能贏」的設定，上 GPU 確認，也是 0/2。
- 依位置決定精度（FP8、INT4），品質也沒有穩定的差距。
- 早期在另一張卡（MI300X）也一樣：216 格 0 格通過（見 10/12 進度報告；不放進這篇投稿的證據）。
這些都有測試過，也測過其他條件，細節沒有放在這裡（之後會再人工確認程式與數字）。

**為什麼**
1. 當初用來決定的資訊（位置），等到要搬的時候一樣看得到。延後版最後的擺法和寫入時放對一樣，只差在時間點。
2. Cake 回來時從前段重算、從後段載入，所以前段多半不被讀；前段放哪層、存什麼精度，影響不大。[判讀]

**轉折**：**因為**寫入時不用聰明，**所以**我們把力氣放到回來的那一刻；**我採用** Cake（ICML 2025）當底：回來時 GPU 從前面重算、同時從後面載入，在中間會合。選它是因為重算成本依位置變，Cake 正好在讀取時依位置切分；而且量測顯示慢層每一格都是它最快（下一則）。
```

## 訊息 5/11　轉向：回來的那一刻怎麼送回，以及「查表」是什麼　附圖：`figs/brief_a_tier_time.png`、`figs/brief_n_lookup.png`

```
**【5/11】轉向：回來的那一刻怎麼送回（附圖 A、圖 N）**

**因為**KV 放在慢層時，使用者等的時間幾乎全花在把位元組搬回 GPU [判讀]，**所以**只有兩條路：讓搬的位元組變少，或讓 GPU 別閒著。**我採用**：
- 位元組變少 → INT4（KIVI：K 按通道、V 按 token，每 32 個一組，每塊小 3.2 倍）。
- GPU 別閒著 → Cake（上一則）。

**怎麼比**：格式（BF16／INT4）× 送法（整段搬回＝把存的 KV 整段載回 GPU；整段重算＝在 GPU 上把整段對話重讀一次；Cake）× KV 停的地方 × GPU 閒或忙 × 兩個模型。KV 停的地方：CPU 記憶體（真的 PCIe 搬運）；三個限速慢層 b16／b32／b48（頻寬限到讓 Cake 在 64 塊的第 16／32／48 塊會合，分別代表「多半在搬、一半一半、多半在算」，不綁特定裝置）；NFS 級（模擬網路檔案系統，0.331 GiB/s）。「GPU 忙」用合成的固定背景負載。

**圖 A：停得越遠等越久，INT4＋Cake 把等待壓下來** [實測]
- 怎麼讀：橫軸是 KV 停的地方，由近到遠（下面是頻寬）；灰柱＝BF16 整段搬回，藍柱＝INT4＋Cake；縱軸是秒，對數軸（每格差 10 倍）。橘虛線＝整段重算約 2.1 秒。
- 看到什麼：灰柱越遠越高，NFS 級要 12.1 秒；藍柱 1.24 秒（約 9.7 倍）。b32、b48、NFS 級在兩個模型、GPU 閒或忙的每一格，都是 INT4＋Cake 最快，比次佳快 11.0–40.7%。
- 為什麼：INT4 讓載入那邊變快；Cake 讓 GPU 同時重算前段，時間取兩邊較晚的那一邊。整段重算在 32K 時從來不是最快。

**「查表」是什麼**（附圖 N）：把「KV 停在哪、INT4 怎麼解壓」對到最快的做法。
- KV 在慢儲存（b32、b48、NFS 級）→ INT4＋Cake。
- KV 在 b16（中等慢）→ INT4＋Cake 或 INT4 整段搬回，差不到 10.4%，選哪個都行。
- KV 在 CPU 記憶體 → 看 INT4 怎麼解壓：一次拆完 → INT4 整段搬回（GPU 忙時比 Cake 快 23.1%（Llama）、54.2%（Qwen））；逐塊解壓 → Cake；不確定 → 一律 Cake。（為什麼，見下一則）
- 整段重算：32K 時每一格都不是最好。

**這張表穩嗎**：重算換成更快的版本、GPU 換成像真實服務的背景負載，最快的做法都沒換。但只測了部分層（重算變快測 CPU、b32、NFS；背景負載測 CPU、b32；SSD 級沒量）。
```

## 訊息 6/11　過程中的意外：INT4 的解壓寫法；為什麼選固定表、為什麼選 INT4　附圖：`figs/brief_b_dequant.png`

```
**【6/11】過程中的意外：INT4 的解壓寫法（附圖 B）**

**因為** KV 放在 CPU 記憶體時搬得很快，INT4 省下的搬運時間不多，解壓的成本就變得顯眼，**所以**我們把「INT4 怎麼解壓」當成獨立的變數，**我採用**兩種實作並列比較：逐塊解壓（每讀一塊轉一次）和一次拆完（整段讀完再轉）。

**圖 B：同樣是 INT4，解壓寫法差 6.8 倍** [實測]
- 怎麼讀：Llama、KV 放 CPU 記憶體、GPU 忙；橘柱＝逐塊解壓，藍柱＝一次拆完。
- 看到什麼：0.2325 秒 vs 0.0342 秒；逐塊解壓時，INT4 整段搬回（0.2325 秒）和 BF16 整段搬回（0.2383 秒）一樣慢。
- 為什麼：CPU 層本身搬得快，省下的搬運時間被逐塊解壓的零碎工作吃掉。[判讀]

**因為**現場量測或成本模型可能比固定表更準，**所以**我們也試了線上選擇器與成本模型。**結果**：在 CPU 層、GPU 忙時它們常選錯（30–100% 的次數選了整段搬回，在逐塊解壓下比 Cake 慢 1.52–3.52 倍；部分來自逐塊解壓的實作，換成一次拆完後 CPU 層最快的反而是整段搬回）。**所以我採用**固定查表，表裡分開兩種解壓實作；不確定實作時一律 Cake（24 個測試格平均只比最好的多 6.7%，但一次拆完時最多慢 2.18 倍）。

**因為**位元越少搬得越快、但品質會掉，**所以**我先定品質門檻再選格式，**我採用**「通過正式品質測驗的最小格式」。正式測驗＝事先登記的主任務（4 種任務，Llama 735 題、Qwen 627 題，各 4 種讀法）；海選只看 KL 與第一個 token。[實測] FP8（小 1.94 倍）在 Qwen 正式主任務崩壞（掉 32.2 個百分點）；INT4（小 3.2 倍）是 BF16 以外唯一在兩個模型都過關的格式；2 位元（小 5.33 倍）更快，但海選的 KL 約是 INT4 的 30 倍，沒有正式測驗，所以不採用。
```

## 訊息 7/11　GPU 要共用怎麼辦　附圖：`figs/brief_c_mps.png`

```
**【7/11】GPU 同時在忙別的事（附圖 C）**

**因為**真實服務裡，搬回會和別的請求搶同一張 GPU，**所以**要讓搬回和別的工作同時跑、又能調整各自分到多少；**我採用** MPS（NVIDIA 多行程服務：多個程式同時在同一張 GPU 上跑，並能限制別的程式最多用多少計算單元 SM），對照 stream 共用（兩邊各放一條工作佇列，由 GPU 輪流交錯）。

**怎麼做**：用 trace 模擬端到端（慢層用 INT4，底含打字提示預取）。搬回的程式不設限，別的工作掃四個等級：不設上限，或最多用 87%、75%、50% 的 SM（登記沒有寫為什麼選這幾個）。背景工作分兩種：chunked prefill、mixed（預填＋逐字生成）。B＝別的工作的處理量÷它獨自用 GPU 時。登記的判準：回答快 >15% 且 B≥0.95。再用縮小的 GPU 重播檢查模擬（15 個 run）。

**圖 C：替搬回保留越多 GPU，回答越快、別的工作越慢** [模擬]
- 怎麼讀：橫軸 B（1.0＝別的工作完全不受影響），縱軸＝回來請求的等待比 stream 共用縮短幾 %。每條線由右往左：stream → MPS 不設上限 → 限制別的工作在 87% → 75% →（只有 mixed 有）50%。右邊綠區是登記的目標。
- 看到什麼：只改 MPS，縮短 30.7–62.9%，B 最多少 6.5 個百分點（藍線 B 0.801→0.777，縮短 50.4%；綠線 agent 紀錄 B 完全沒降，0.937，縮短 62.9%）。限制到 75%，chunked prefill 背景下縮短到 77.8–79.5%，但 B 掉到 0.64–0.75。
- 為什麼：MPS 讓搬回拿到固定的一份 SM，不必和別的工作輪流；保留越多，別的工作越少。[判讀]

**沒有任何一點進綠區**：登記判定「不成立」（可判的 24 格 0 格達標），原因之一是連 stream 共用，B 也常低於 0.95（6 組裡只有 1 組 ≥0.95）。GPU 重播的 7 格方向和模擬全相同，但 GPU 上回答變快的幅度比模擬多 4.6–31.3 個百分點。所以只寫成取捨旋鈕：趨勢可信，確切數字要在自己的 GPU 上量。
```

## 訊息 8/11　回頭驗證假設二：預測的設計　附圖：無

```
**【8/11】回頭驗證假設二（上）：預測怎麼量**

**為什麼現在才問**：**因為**預測的價值要在「最好的不預測做法」之上量才有意義，**所以**先把底做好：慢層 INT4＋Cake，CPU 層存 BF16 用 Cake（接近前面的表在逐塊解壓下的答案；底裡沒有 MPS，這個方向沒量過）。**我採用**完美預測（oracle）量上限（做法見 3/11 重點二）。

**每個設計都有原因**
- **因為**一次只給一種未來資訊，才看得出價值落在哪種決定上，**所以**四種 oracle 各只改一個決定、其他照 LRU：預取（先搬回會回來的）、淘汰順序（CPU 滿時先降級最晚回來的）、回合結束就丟、輪到淘汰時才丟。
- **因為**要和「同樣動作」的對手比才公平，**所以**每種 oracle 只對同動作的最好不預測對手（例：淘汰順序對 LRU、LRU2、ARC、S3-FIFO 等取最好的）。
- **因為** Mooncake 紀錄只有一小時，快到結尾的對話看起來都不會再回來，「回合結束就丟」因此顯得很有用，**所以我採用截尾**：結尾前 1 小時內的決定一律當「會回來」。不截尾是 95/192 格 ≥15%，截尾後 36/192。
- **因為**慢層寫不完時，模擬會讓還沒寫完的資料就能讀（偏樂觀），**所以**主結果排除這些格。
- **因為** Mooncake 沒有對話欄位，**所以**用兩種規則重建對話，每格取較小的上限（偏保守）。
- **因為**模擬可能和真的 GPU 不同，**所以**用縮小的 GPU 重播檢查（3/11）：排序與正負號一致，但不含排隊；含排隊時預取上限會變小（見 9/11）。

**價值怎麼判**：同一組設定要有兩種以上的 CPU 容量 ≥15%，才算值得做；全部 <5% 算死路。
```
