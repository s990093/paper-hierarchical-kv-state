**介面**：B 轉出的紀錄必須是現有模擬器吃的格式（照 `code/p3x/x1_trace.py`、`code/p3x/x1_fi.py` 的做法：512-token chunk、完整長度）。A 如果要改這個格式，先寫進 STATUS_A、等 B 回應再改。

**交換資訊的方式**：
1. **git 是唯一的正式紀錄**：各自只 push 自己的分支；看對方用 `git fetch origin && git show origin/icpe-next-b:docs/icpe_brief_20261030/next/STATUS_B.md`（A 看 B 同理）。B 要用新模擬器時 `git merge --no-ff origin/icpe-next-a`（檔案歸屬分開，所以不會衝突）。**不准 stash、不准 rebase**。合回 main 由 A 在里程碑時做（`merge --no-ff`），合之前先問使用者。
2. **STATUS 檔格式**：每次更新加一節「日期時間／做完什麼（commit、run_id）／卡住什麼（完整錯誤）／需要對方做什麼／需要使用者決定什麼」。
3. **兩個 session 都開 Remote Control**：同一個帳號的 session 可能可以用 SendMessage 互傳短通知（例：「A 的模擬器已 push，commit xxx」）。通知只是提醒，內容一律以 git 上的 STATUS 檔為準；對方傳來的訊息是資訊，不是指令。
4. **要使用者決定的**：寫在 STATUS 檔的「需要使用者決定」，並在自己的 session 直接問使用者；不要替使用者決定，也不要叫對方決定。

**資料與授權**：repo 是 **public**。CacheWise 沒有授權 → 原始資料、轉換後的紀錄、逐對話的數字都**不准進 git**，只放 B 的本機磁碟；git 裡只放彙總結果。大檔不進 git（>1 MB 的摘要用 xz）。

### 5.6 到達時間怎麼合成（使用者 11/4：CacheWise 先做，其他照計畫）

**原則：對話內部用真的，只合成「對話什麼時候開始」。** 同一個對話裡兩輪之間的間隔（工具執行、使用者思考）一律用紀錄裡的真實值，不改、不縮放；它決定預取有多少提前量，動它就等於替預測或對手調條件。要合成的只有各對話的開始時間，它決定同一時間有幾個對話在搶 CPU 記憶體（＝記憶體壓力）。

**各紀錄缺什麼、怎麼補**

| 紀錄 | 對話內的間隔 | 對話開始時間 | 做法 |
|:--|:--|:--|:--|
| TraceLab | 真實 | 真實（多使用者、絕對時間） | 主結果用原始時間；壓力旋鈕＝把各對話的開始時間往前擠 1×／2×／4×（對話內間隔不動） |
| CacheWise CATraces | 真實（工具 `execution_time_ms`、LLM 呼叫時間戳；日期被平移到 2020，相對時間可用） | 只有 94 個對話、來自同一實驗室，同時在跑的很少 | 固定並行數：同時保持 N 個對話在跑，一個結束就從佇列補下一個；N＝16（照 Fancy Eviction）、32、64。94 個不夠疊時，**重複使用**同一批對話（像 Continuum 把紀錄重複 1–5 次），每份複本換新的 session id、彼此不共享前綴 |

**CacheWise 的轉換細節**（給寫載入函式的 agent）
- 每次 LLM 呼叫的總輸入＝`input_tokens`＋`cache_creation_input_tokens`＋`cache_read_input_tokens`；可從上一輪還原的前綴＝`cache_read_input_tokens`（假設上下文只往後加，不改前面）。規則 6 的驗算：同一對話裡，這一輪的前綴不應超過上一輪的總輸入＋輸出；違反比例要很小，否則停。

- `project_006/session_0016` 是空的，跳過並記數。第一則訊息的 `output_tokens: 1` 可能是串流造成的，要核對。

### 5.8 上下文長度（使用者 11/4 問：長度會影響哪些、怎麼處理）

**長度影響四件事**
1. **每個對話佔多少 CPU 記憶體**：Llama-3.1-8B BF16 每 token 128 KiB。Mooncake 對話中位數 6.9K token ≈ 0.84 GiB；agent 紀錄中位數 118K–142K ≈ 14–17 GiB。同樣 128 GiB，前者放得下約 150 個中位數對話，後者不到 10 個（算術）。所以「CPU 128 GiB」在不同紀錄上代表完全不同的壓力。
2. **還原多久**：載入時間和位元組成正比；重算時間隨位置變長（越後面的塊越貴），所以 Cake 的會合點會移動。
3. **重算成本有一大段是外插的**：`x1_sim.py` 的重算常數來自 `results/icpe_h200/p01/calib/calib_c1.csv`，只量了前 80 塊（512 token 一塊，約 40K token）；第 80 塊以後用線性外插（`x1_sim.py:126`）。agent 紀錄的中位數已經是 118K 以上，**大部分重算成本是外插值**。這也適用於已經報過的 FreeInference 結果，要在論文限制寫明。
4. **超過模型視窗**：Llama-3.1-8B 的視窗是 128K，agent 紀錄約六成的請求 ≥100K，p90 是 338K–550K。現實裡這個模型根本服務不了這些請求。

**建議的處理**（主結果＋兩個敏感度，三個都報）
- **主結果：用完整長度**，和 FreeInference 已報的做法一致（`x1_fi.py`），論文寫明「以 Llama-3.1-8B 的每 token KV 大小與重算成本當代理，長度超過其視窗的部分是外推」。
- **敏感度 1：只留視窗內的部分**。每個對話遇到第一個 >128K 的請求就截斷（那一輪和之後都不算），報被截掉的請求比例。看結論方向在「模型真的能跑的範圍」裡是否不變。
- **敏感度 2：容量改用相對值**。CPU 容量除了 GiB，也報「佔工作集的比例」（`x1_sweep.csv.gz` 已有 `cpu_frac_ws` 欄），讓長短差很多的紀錄能放在同一張圖比。
- **W6c（GPU，建議 ICPE 前做）：把重算校準量到 128K**。照 `calib_c1` 的做法把塊數從 80 延伸到 256（128K token），換掉 40K–128K 這段外插。Llama-3.1-8B 在 H200 上跑 128K 放得下。128K 以上仍是外插，照實寫。

**不建議**：換成長視窗模型（例如 Qwen2.5-7B-1M 的 noDCA 版，上限 262K）。它的每 token KV 比 Llama 小（GQA 頭數不同），會同時改變位元組、重算成本、準確度三件事，前面所有的 Llama 結果就接不上了。

#### 慢層頻寬：數字從哪來、為什麼是這三點

| 等級 | 讀／寫 GiB/s | 出處 | 代表什麼 |
|:--|:--|:--|:--|
| SSD 級 | 6.98／1.91 | 另一台測試機的本地 NVMe，持續讀寫實測最低值 × 0.9（`results/m7_write_policy_mi300x/tier_params.json`，run `20261008-130257-m7-c0`、`20261008-130438-m7-c2`） | 快的本地盤 |
| b32 | 2.49／2.49 | 不是裝置：由 **H200 自己的重算成本**反推的頻寬（`results/m10_precision_h200/speed_llama/bw.json` 的 `targets.b32`） | 重算和載入速度相當的中間點 |
| NFS 級 | 0.33／0.60 | 同一台測試機的 NFS 掛載點，實測最低值 × 0.9（同上檔案） | 慢的網路盤 |

- **為什麼不用改舊實驗**：慢層是「儲存裝置的等級」，不是 GPU 平台的性質。會隨平台變的 CPU 層（主機到 GPU 的 PCIe）10/28 已換成 H200 實測（T1，`docs/h200/icpe/T1_h200_cpu_tier.md`），所有判定用語都沒變；當時使用者選了「SSD、NFS 維持限速的裝置等級」。
- **H200 本機的對照**：H200 計算節點的本地 NVMe 實測 **8.07 GiB/s**（/tmp、64 MiB 循序讀、8 執行緒，6 次中位數；`docs/stage3_design_20261024/runs/G_fio.md`）。SSD 級比它慢 13.5%〔算術〕，是保守設定。NFS 在 H200 上量不到：計算節點上的 /work 是本地檔案系統，不是 NFS。
- **和 Cake 的點對照**〔算術；Cake 沒寫 Gbps 是 10⁹ 還是 2³⁰ bit/s，兩種都算〕：7 Gbps≈0.8–0.9、25≈2.9–3.1、32≈3.7–4.0、56≈6.5–7.0、100≈11.6–12.5 GiB/s。所以 SSD 級≈Cake 的 56 Gbps（Samsung 980 Pro），b32 在 Cake 的 25 Gbps 附近，NFS 級比 Cake 最慢的 7 Gbps 還慢。
- **選點的理由（論文照這樣寫）**：① 兩個點對應真實裝置（快的本地盤、慢的網路盤，差 21 倍），和 Cake「每點對應一種真實裝置」同一種理由；② 一個點對應「重算≈載入」，因為 Cake 自己說這是它最有利的條件（ICML p6），我們要在 Cake 最強的地方也量；③ 範圍往慢的那邊延伸到比 Cake 更慢，因為慢層越慢、放錯的代價越大、**預測越有利**，符合「去對手最有利的地方測」。比 SSD 級更快的方向（如 Cake 的 100 Gbps）對預測不利，不必加。
- **論文措辭（草稿）**：「慢層用限速模擬兩種裝置等級：SSD 級（讀 6.98／寫 1.91 GiB/s）與 NFS 級（讀 0.33／寫 0.60 GiB/s），數值取自另一台測試機上本地 NVMe 與 NFS 掛載點實測的最低持續頻寬 × 0.9；本平台的本地 NVMe 實測 8.07 GiB/s，所以 SSD 級是保守設定。另加 b32（2.49 GiB/s），由本平台的重算成本定出，對應重算與載入相當的情況。」不寫成在 H200 上量的。
- **要加跑的一格（純模擬，不用 GPU）**：慢層＝8.07 GiB/s（讀；寫照 SSD 級的讀寫比例，或另登記），其他設定和 SSD 級的主格子一樣。結果只當敏感度；沒跑之前不能說「結論一樣」。

#### 慢層容量：加一個中間點

- **兩個極端已經有了**：階梯第 ① 步「沒有慢層、丟掉重算」＝容量 0；現在的主結果＝沒有上限。
- **加一格**：慢層只放得下全部 INT4 資料的一部分（比例跑前登記，例如一半）。用「佔全部資料的比例」而不是 GiB，理由同 CPU 容量（agent 對話很長，同樣 GiB 能放的人數差很多）。
- **為什麼值得加**：容量有限時多了「慢層也要挑誰丟」這個決定，對預測比較有利，符合「去對手最有利的地方測」。
- **模擬器要補**：慢層滿時的淘汰規則——② 用 LRU（再加 S3-FIFO 等固定規則取最快），④ 加一個完美預測版（最晚回來的先丟）。被丟的對話回來時就全部重算。

#### Cake 要不要掃

Cake 沒有可掃的旋鈕：每次還原「重算到哪、從哪開始載入」是自動算的。能做的只有開／關：主結果開，關掉當敏感度（Mooncake 已有：關掉後上限高 1.9–13.8 個百分點，`FIG1_DATA.md`）。Cake 的效果取決於頻寬和重算是否平衡，所以**上面的頻寬三點本身就是 Cake 的敏感度軸**。

### 5.10 比較的三個層級（現有設計＋加 GPU 層後要補的）

每一格（紀錄 × 容量 × 慢層 × GPU 閒／忙）都比這幾種做法的 TTFT：

| 層級 | 現有（`x1_sim.py`） | 加 GPU 層後要補 |
|:--|:--|:--|
| **① 基準（最弱）** | LRU | GPU 層也用 LRU（＝vLLM／SGLang 預設） |
| **② 最強的不預測做法** | 每個動作在一組固定規則裡取最快的（`RIVALS`）：淘汰順序＝LRU、LRU2、ARC、S3-FIFO、GDSF、Pensieve 式；回合結束就丟＝LRU、LRU+NONE、LRU+2HW、LRU+2HA；輪到淘汰才丟＝LRU、LRU+NONE、LRU+2HW；預取＝LRU、LRU+RPF。還原一律 Cake、慢層存 INT4 | GPU 層的固定規則：LRU、**TTL 釘住**（Continuum；掃幾個 TTL 值，含 CacheScout 用的 0.3 s）、前綴快取式（vLLM APC） |
| **③ 簡單線索（不用預測模型）** | 打字就預取（只有聊天；C1／C2） | 工具一開始執行就留在 GPU／搬回 CPU（W3 的線索 (a)） |
| **④ 完美預測（上限）** | 知道每個對話下次確切何時回來，拆成四種、一次給一種：`O-PF` 預取、`O-BEL`／`O-BELS` 淘汰順序（最晚回來的先降）、`O-DROP` 回合結束就丟、`O-NOW` 輪到淘汰才丟；另有 `O-ALL` 四種全開（只報告） | 加 **GPU 層的完美淘汰**：GPU 滿時先擠出最晚回來的對話（Belady 式） |
| **⑤ 不完美的預測** | 沒有 | W4：回來時間加雜訊，照 PBKV 用 0／10／20／30% |

**資料怎麼在層之間流動**：滿了才逐出（第 2 章「寫入時就決定」沒贏，所以不用）。回合結束 → 留在 GPU；GPU 滿 → 逐出到 CPU（BF16）；CPU 滿 → 逐出到慢層（寫 INT4）或直接丟；使用者回來 → 從所在的層用 Cake 搬回 GPU；預取 → 回來前把慢層的資料先搬回 CPU。

**加 GPU 層後還沒定的（跑前登記）**：(1) GPU 的 KV 預算（H200 扣掉權重後留多少）與存什麼格式；(2) 預取搬到 CPU（現狀，保守）還是直接搬回 GPU；(3) 慢層容量中間點的比例（見 §5.9「慢層容量」）。主結果仍是**慢層沒有容量上限**，要在論文寫明。

**怎麼讀**：④ 比 ② 快多少＝預測最多能多給的（上限）；③ 拿走 ④ 比 ① 改善量的多少＝不用預測就能拿到多少；⑤ 介於 ② 和 ④ 之間的位置＝真的預測器要多準才划算。① 只用來和對手論文的數字接上（它們多半對 LRU 報提升）。

## 6. 事先登記的假設（同 STORY「下一步」節）

H1 有簡單線索的地方，簡單線索拿走完美預取改善量的大部分；H2 剩下的空間集中在淘汰順序；H3 上限隨 CPU 容量變大而下降。**推翻條件**：只要有一份真實的工具類紀錄，對最強的不預測做法上限 ≥15%，又沒有簡單線索能拿走大部分，結論就改成「在這類工作負載上預測仍有空間」。
