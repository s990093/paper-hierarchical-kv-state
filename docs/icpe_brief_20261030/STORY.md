# 一個完整的故事（主線版，2026-11-03）

> 為什麼重寫：先前的簡報把幾個結果並排講（寫入時放置、INT4＋Cake、解壓寫法、MPS、預測），章與章之間只有「接下來」，沒有一條往下推的線。這一版只有**一個問題**，每一章回答上一章留下的問題，再留一個問題給下一章。
> 標記：[實測]＝H200 GPU 上量的；[模擬]＝用紀錄模擬；[判讀]＝作者的解讀。數字出處見最後。這份文件沒有新實驗，也沒有改 `PAPER.md`。

## 主線一句話

想知道「預測」值不值得做，只問一件事：**就算預測得完美（像開了天眼，知道誰、什麼時候會回來），比「不預測的最好做法」還能再快多少？** 所以要先把不預測的做法做到最好，再量這個差距。我們量到：上限取決於紀錄，也取決於 CPU 記憶體多大。FreeInference（真實的 agent 服務紀錄）在 CPU 記憶體 128 GiB 以上，差距幾乎是零（最多 0.30%）；Mooncake 對話紀錄上看起來很大（預取最多 50.5%，CPU 記憶體加到 1,024 GiB 降到 14.6%），但只要偵測「使用者開始打字」就先把資料搬回來（一個不用任何預測模型的簡單線索），就已經拿到其中大部分。Mooncake 的工具（toolagent）紀錄在 CPU 128–256 GiB 時上限也高（預取 30.0／24.1%），但沒有打字這種線索，還沒驗證。所以在驗證過的兩份紀錄上，預測能多幫的有限；還沒解決的是「淘汰順序」（CPU 滿了先擠掉誰）和 toolagent。

**研究的骨架（四件事）**：目標＝量「預測」讓 KV 還原最多能多快；資料＝三份真實使用紀錄（Mooncake conversation、Mooncake toolagent、FreeInference），H200 一張卡、32K 上下文，掃描 CPU 記憶體容量（停放對話 KV 的 CPU 記憶體大小，16–1,024 GiB）；跟誰比＝最好的不預測做法：還原方式用別人已發表的 Cake（使用者回來時，邊重算前段、邊載入後段）加 INT4 壓縮；淘汰與預取則和 LRU、LRU2、ARC、S3-FIFO、GDSF、Pensieve 式、LRU+RPF 等固定規則比，每個動作取最快的那個。Cake 不是我們的貢獻，它的意義是讓這個對手夠強；指標＝首字延遲 TTFT，上限＝完美預測比它再快的比例。

## 故事

**第 1 章｜問題與賭注**
使用者和聊天機器人或 AI agent 對話，常隔一陣子才回來。這段期間，系統把這段對話已算好的中間結果（KV cache）移出 GPU；使用者回來時要先搬回，才看得到第一個字，這段等待叫首字延遲（TTFT）。近年一批針對 agent 工作流的研究把預測放進 KV 管理：PBKV、CacheScout、CacheWise 以預測為核心（猜誰會回來、何時回來、下一步呼叫什麼，再據此淘汰、預取或保留 KV），SAGA 的預測是它三個機制之一（另兩個是排程與公平）。它們報告了大收益，但對照組是 LRU 或 vLLM／SGLang 的前綴快取；我核對的 8 篇全文都沒出現 Cake 這個字（Cake 是後面「最好的不預測做法」的核心）。這是近期的一條研究線，不是已證實的主流做法（只核對了 8 篇全文的標題與關鍵字，沒有調查整個領域）。我們一開始也這樣想；要公平量預測的價值，得先有一個夠強的「不預測的做法」當對手。
→ **留下的問題**：預測的好處，最多有多大？

**第 2 章｜最直接的版本：寫入時就決定**
預測可以用在兩個時間點：①寫入時：對話剛結束、使用者還沒回來，就先決定這段 KV 放哪層、存什麼精度，等於事先替回來時做準備；②回來之前：猜誰會回來、何時回來，用來預取或決定淘汰順序。先試最直接的①。
**規則（具體）**：一段 32K 的對話切成 64 塊（每塊 512 個 token）。越後面的塊重算越貴（要先重讀前面所有塊），從儲存搬回的時間卻不隨位置變。所以：位置最前面的塊重算便宜，放慢層；後面的塊重算貴，放 CPU。它可能帶來三種好處：省 CPU 空間、省寫入量、空間還夠時先把資料寫到慢層。
**兩個版本，只差「何時搬」**：「寫入時套用」＝對話一結束，位置最前面的幾塊（例如 64 塊裡的前 4 塊，剛好是 Cake 回來時會用重算拿回來的那幾塊）就直接寫慢層，其餘寫 CPU；「CPU 滿了才套用」＝先全部寫 CPU，滿了才把位置最前面的塊降到慢層。兩版用同一條位置規則；CPU 一滿，兩版都是「位置最前面的先降」（程式裡兩者都用同一個「挑位置最前面的塊」的函式）。
**數據①放哪層**：回來請求的 TTFT 只差 −0.37～+1.16%（三種 CPU 容量＝能放下全部停放 KV 的 25／50／100%、每點重複 6 次、兩種重算實作；門檻 5%；圖 1）[實測]。
**數據②消融**：把最有利於寫入時決定的條件（頻寬、容量、負載型態、重算成本等 7 個）一個一個、再組合起來掃：單獨改任何一個都贏不到 5%；組合起來只有少數設定贏，而且大多要重算便宜 2–4 倍（GPU 做不到），換個隨機種子就不穩（這部分是早期用另一張卡常數做的探索掃描）。H200 上 GPU 確認：16 組比較 0 組贏；模擬挑出的 2 個設定也都沒撐住（各只有 2/5 個隨機種子贏）[實測]。
**數據③精度**（前／中／後段各 25% 的塊降精度，對「同比例、隨機挑」的對照比答對率）：Llama INT4 差 −0.47～+0.08 個百分點、6 個信賴區間都含 0；Qwen FP8 前／中／後段 +17.3～+18.8／−4.9～−4.4／−3.4～−1.9 個百分點（GPU 閒／忙），方向不一，沒有穩定的差距；前段「變好」是還原時大多不讀前段 [實測；判讀]。寫入准入（少寫慢層、保護 SSD 壽命）沒量。全部整理在表 1。
**直覺（為什麼）**（見示意圖 `figs/brief_s_write_time_schematic.png`）：把對話想成 64 格，第 1 格最舊。使用者回來時系統兩頭同時做：GPU 從第 1 格往後重算，同時從第 64 格往前從儲存載入，在中間碰頭（例：重算前 4 格）。所以前 4 格是重算出來的，不從儲存讀。兩版的差別只有這前 4 格放哪：「寫入時套用」一開始就放慢層，「CPU 滿了才套用」先放 CPU。但回來時用不到它們在儲存裡的副本，放哪都一樣；CPU 一緊，另一版也會把最前面的格子降到慢層，兩版的擺法就一樣了 [判讀；原稿 §7.1 的解釋，沒有單獨驗證，見注意事項 7]。
**所以**：寫入時的預知不用做。**為什麼（數據→直覺→結論）**：三項數據都沒差（①放哪層 −0.37～+1.16%、②16 組 0 組贏、③精度沒有穩定差距）；直覺是寫入時只能依位置決定放哪層、什麼精度，位置回來時系統看得到，位置最前面的塊又本來就由 Cake 重算，預知派不上用場 [判讀]。預測要有用，得提供「到時候還看不到的資訊」；位置到時候看得到，所以沒用。剩下的是「誰、什麼時候會回來」，那是到時候才知道的，才可能值得預測 [判讀]。→ 預測只剩「回來之前」（預取、決定淘汰順序）。**留下的問題**：回來之前的預測值多少？**為什麼先量完美預測的上限**：連完美的都省不了多少，真的預測器（只會更差）更不值得蓋；上限很大，才值得往下做 [判讀]。怎麼公平地量，見第 3 章。

**第 3 章｜比較對象決定答案**
預測值多少，取決於跟誰比：對手越弱，預測看起來越值錢。**為什麼這樣設計**（登記檔 `docs/h200/icpe/T4_hit_vs_ttft_bridge.md` 記的理由）：Liu 等人（*When Fancy Eviction Fails*）在同一份 FreeInference 上說 LRU 和 Belady 的命中率差很多，但他們的沒命中成本只算重算；我們另一組結果說完美預知最多只省 0.30%。這一關要回答兩者怎麼兜起來：差距是被「慢層＋Cake」吸收了，還是我們的設定裡本來就沒有差距。所以只換「沒命中時怎麼辦」，從最接近他們的算法（只重算）一步步加強；CPU 容量 128 GiB 是先前結果的最小一格，用來接上，8–64 GiB 是新加的 [登記檔對該篇的讀法，我沒有重讀原文]。**怎麼量**：在同一段 FreeInference（前 6 週）上，用同一個完美預知（知道每個對話下次什麼時候回來，CPU 滿了就先降級最晚才回來的那個），只換「沒命中時怎麼辦」，並把 CPU 容量從 8 掃到 128 GiB [模擬]：
① 沒有慢層，沒命中就丟掉、回來時重算：CPU 32 GiB 時，完美預知比 LRU 快 15.9%；
② 有慢層（SSD 級，讀 6.98 GiB/s），整段載回：只剩 3.4%；
③ 有慢層，再加 Cake（邊重算邊載入）：只剩 2.6%。
CPU 64 GiB 時是 11.8% → 0.5% → 0.4%。（GPU 閒；都是對 LRU。）可見這個設定下，大部分差距來自「有沒有慢層」（15.9 → 3.4），Cake 只再壓低 0.8 個百分點（64 GiB 時 0.1）。
**也模擬了不同頻寬**：把慢層換成更慢的 NFS 級（0.33 GiB/s），對 LRU 的差距反而變大（32 GiB：27.7%），但那大半是 LRU 太弱：對最強的不預測對手（S3-FIFO）只剩 11.6%。所以「對手越強、預測越不值錢」在 SSD 級很乾淨；換到更慢的慢層，要連「對手強不強」一起講。全程以首字延遲（TTFT）為準；命中率只用來解釋原因，不當結果。
→ 所以先把「不預測」做到最強：預測的價值＝完美預測比最好的不預測做法好多少，對手越弱數字越大，只有對最強的對手，剩下的才是預測真正能多給的。**留下的問題**：最好的不預測做法是什麼？

**第 4 章｜把「不預測」的做法做到最強（為了公平，不是主角）**
慢層時，使用者等的時間幾乎花在搬位元組，所以兩件事：搬得少（INT4，位元組小 3.2 倍）、讓 GPU 別閒著（沿用別人已發表的 Cake：一邊重算前段、一邊載入後段；最強的不預測做法建立在它上面，Cake 不是我們的貢獻）。最慢那層的 32K 對話從 12.1 秒降到 1.24 秒，比次佳做法快 11.0–40.7% [實測]。CPU 記憶體層搬得快，轉換成本就決定快慢：同樣的 INT4，一次拆完 0.0342 秒、逐塊解壓 0.2325 秒（差 6.8 倍）[實測]。這 6.8 倍是我們自己兩種實作的差（較早的實驗用的是逐塊版），不是新方法，也不是 GPU 之間的差：兩種都在同一張 H200、同一個組合（CPU 層、GPU 忙、INT4 全部載入）上量；較早（10/17）的 D2 用逐塊版，INT4 在 CPU 層沒變快，後來（10/26）換成一次拆完才快（日期取自 run id）。GPU 閒或忙，慢層上 INT4 都比 BF16 快（b16／b32／b48 × 閒／忙 12 格全贏，快 36.7–54.5%）；只有 CPU 層沒變快（Llama 忙 −39.4%、閒 +13.0%，未過門檻），所以才要看解壓寫法 [實測]。壓縮要看準確度（表 2）：INT4 在多鍵大海撈針（180 題）和 LongBench（6 項、300 題）上和 BF16 幾乎一樣（大海撈針 Llama 99.7→99.7、Qwen 98.1→97.2；LongBench Llama 40.8→41.0、Qwen 42.8→43.0）；事先登記的主任務（Llama 735 題、Qwen 627 題）差 −0.18～+0.30 個百分點，兩個模型都過關（門檻：信賴區間下界 ≥ −2 個百分點）。FP8 在 Qwen 崩壞（大海撈針 49.7、LongBench 6.6；主任務 −32.2 個百分點）。INT2 更快，但沒有這兩項測驗，只有 96 題海選，誤差約是 INT4 的 30 倍 [實測]。換成更快的重算、換成像真實服務的背景負載，最快的做法都沒換（只測了部分層）。
→ **留下的問題**：不預測的做法做好了，預測還剩多少？

**第 5 章｜在最強的不預測做法之上量上限**
把完美預測拆成四種（預取、淘汰順序、回合結束就丟、輪到淘汰時才丟），一次只給一種，各和「同動作下最好的不預測對手」比 [模擬]。
**對手是誰**（`code/p3x/x1_sim.py` 的 `RIVALS`；預取的對手見 PAPER §5.2）：全是固定規則（不是學出來的預測器），每個動作各一組，取其中 TTFT 最小的：預取＝LRU、LRU+RPF（預取最近用過的對話）；淘汰順序＝LRU、LRU2（看倒數第二次使用時間）、ARC、S3-FIFO（三個先進先出佇列）、GDSF、Pensieve 式（看重算成本與閒置時間）；回合結束就丟／輪到淘汰才丟＝LRU、LRU+NONE（直接丟）、LRU+2HW／2HA（只用過一次的就丟）。FreeInference 在 CPU 小、慢層慢（NFS 級）的淘汰順序格上，最強的是 S3-FIFO。我沒有跑真的預測器（如 PBKV、KVFlow），所以界住的是「完美預知比固定規則多省多少」。結果依紀錄、也依 CPU 記憶體容量而定（圖 2；SSD 級慢層、Cake 還原、模擬）。FreeInference（真實 agent 服務紀錄）：128 GiB 以上最多 0.30%，因為固定規則已命中 99.29%，沒東西可補；容量小時預取甚至是負的（SSD 級 16 GiB −4.4%：完美預取反而比最好的不預測做法慢），淘汰順序最多 1.7%（SSD 級；NFS 級最高 11.8%）。Mooncake conversation（對話）：預取 50.5%（128 GiB）→ 14.6%（1,024 GiB），淘汰順序 27.6% → 31.0%（256 GiB）→ 10.2%。Mooncake toolagent（工具／agent）：預取 30.0% → 2.5%，淘汰順序 17.0% → 1.6%，只有 128–256 GiB 時 ≥15%。不只看最大值：兩條 Mooncake 紀錄共 192 格，把紀錄截到一小時、排除寫入飽和的格之後，仍有 36 格 ≥15%（不截尾 95 格）。為什麼 FreeInference 和 Mooncake 差這麼多、Mooncake 又為什麼隨容量下降，還沒驗證：Mooncake 的命中率沒算，紀錄也只有一小時。GPU 忙（背景有別的工作）時預取上限更低（Mooncake conversation 128 GiB：閒 50.5% → 忙 38.4%；toolagent 30.0% → 20.8%），淘汰順序幾乎不變（27.6% → 25.3%），排序和結論都沒變；圖 2 每格取閒／忙較大者 [模擬]。**拿掉 Cake 會怎樣**：把 Cake 換成整段載入，Mooncake 的上限會高 1.9–13.8 個百分點（SSD 級、模擬；例：conversation 預取 128 GiB 50.5% → 59.2%、1,024 GiB 14.6% → 20.9%），排序與隨 CPU 容量下降的趨勢不變。所以上面的數字是「在 Cake 之上」的；換一個更弱的對手，預測看起來更值錢 [模擬]。
→ **留下的問題**：Mooncake 上那個大的上限，是真的嗎？還剩多少？**為什麼要問**：同樣是 CPU 128 GiB，FreeInference 只有 0.30%、Mooncake 卻是 50.5%，差上百倍，原因還沒驗證（命中率沒算）；而且這是模擬，完美預知現實拿不到。所以下一章用一個不用預測模型的簡單辦法在 GPU 上實測，看它拿走多少，剩下的才是預測的空間。

**第 6 章｜大的上限，還剩多少**
**為什麼選「打字就預取」**：它不是主流做法，是我們選的一把尺。① 聊天裡使用者送出前一定先打字，這幾秒系統本來就閒著，是現成的提前量（Mooncake 對話、NFS 級慢層上，這段時間能藏住 62.2–72.0% 的還原時間 [模擬]）；② 它不需要預測模型，只要客戶端送一個「開始打字」事件；③ 相關工作多半是預測型（PBKV、CacheScout、CacheWise），或用排程佇列、工具回報的進度當提前量（CachedAttention、Ask the Tool），我們沒查到用打字訊號預取 KV 的論文（只查了摘要與關鍵字，不代表沒有）。所以它是「不用預測，能拿到多少」的參考點，用來看預測器還剩多少空間，不是我們提出的方法；它只適用有人在打字的聊天，工具／agent 紀錄沒有。
先試最輕的辦法（如果它已經拿到大部分，複雜的預測器能多給的就更少）：不用預測模型，一偵測到使用者開始打字，就立刻預取（把他停放的資料先從慢層搬回 CPU）。能提前多久，用打字時間算：新輸入的字數 ÷ 桌機打字速度（51.56 WPM，每分鐘字數），最多到兩次請求之間的空檔；Mooncake 沒有按鍵紀錄，所以這個時間是合成的。在 H200 上重播 Mooncake 對話紀錄的 1/8（Llama、SSD 級；CPU 記憶體也縮成 1/8：16 GiB，相當於全尺寸的 128 GiB），回來請求的平均首字延遲：不預測（LRU）0.278 秒、打字提示預取 0.237 秒、完美預取 0.228 秒 [實測]。完美預取比 LRU 快 17.9%，打字提示快 14.5%，所以打字提示拿到完美預取改善量的 0.81（14.5 ÷ 17.9）；完美預取只比打字提示再快 4.0%，低於事先訂的 5% 門檻。這個重播不含排隊；含排隊時，完美預取比 LRU 快的幅度從 17.9／16.2% 掉到 8.1／4.7%。順便檢查模擬：不含排隊時，實測÷模擬＝0.911–0.987，策略排序全同 [B6；PAPER §3.3]。這些只有 Mooncake 對話紀錄；toolagent 沒有按鍵，也沒有 GPU 重播。
→ **留下的問題**：沒有這種簡單辦法的部分呢？

**第 7 章｜結論與還沒解決的**
**在驗證過的兩份紀錄上，預測能多幫的有限。** FreeInference 上連完美預測都幾乎省不到（0.30%）；Mooncake 對話紀錄上，「使用者一開始打字就先搬」這種不用預測模型的簡單線索，就拿到大部分。還沒解決的四件事：① 淘汰順序（CPU 滿了先擠掉誰）目前沒有這種簡單線索（Mooncake 上限 27.6%），那才是預測器可能有空間的地方；② Mooncake 的命中率沒算，「取決於固定規則已命中多少」還只是對 FreeInference 的解釋；③ 我們沒有蓋真的預測器，只量了完美預測的上限（可補：給完美預知加雜訊，PBKV 有類似的雜訊掃描可當前例）；④ Mooncake toolagent 在 CPU 128–256 GiB 時上限也高（預取 30.0／24.1%），但那裡沒有打字這條線索（有人改讀工具回報的進度，見 Ask the Tool），我們也沒有為它做 GPU 重播，預測在那裡值多少還不知道。

**旁支（不在主線）**：送回時 GPU 被別的工作佔用怎麼辦。MPS 讓回答快 30.7–62.9%、別的工作最多慢 6.5 個百分點（模擬），是取捨，登記的判定不成立。這是另一個問題，和「預測值多少」無關，建議放附錄或另一篇。

## 要注意的地方（避免說過頭）

1. **第 3 章的 15.9% → 2.6% 是 FreeInference、SSD 級、GPU 閒、對 LRU 的模擬**。換成更慢的 NFS 級，對 LRU 在 16–32 GiB 仍有 17.7–27.7%，但那大半是 LRU 太弱：對最強的不預測對手（S3-FIFO）只剩 5.6–11.8%。所以「對手越強、預測越不值錢」在 SSD 級很乾淨，在 NFS 級要連「對手強度」一起講。
2. **SSD／NFS 級是限速模擬**，頻寬常數來自另一個平台（MI300X）。
3. **「簡單的打字線索就拿到大部分」只對 Mooncake 對話紀錄的預取成立**；淘汰順序、toolagent 還沒有這種線索。
4. **打字提示的時間是合成的**，GPU 重播只有一種設定（對話紀錄、SSD 級、Llama、不含排隊）。
5. 「先量上限」這個做法本身不是我們獨有的（PBKV、CacheWise、Ask the Tool 都有類似對照，見 `PREDICTION_RELATED_FULLTEXT_CHECK.md`）；我們的差別在 Cake 分層還原之上、以 TTFT 量上限、拆成四種，並跨紀錄比較。
6. **「差距幾乎是零」只對 FreeInference 成立。** Mooncake 的 toolagent 也是 agent 類紀錄，在 CPU 128–256 GiB 時上限也高（預取 30.0／24.1%、淘汰順序 17.0／15.9%）又沒有 GPU 重播，所以結論要寫「在驗證過的兩份紀錄上」，不能寫成「agent 工作負載」。
7. **第 2 章的「為什麼」沒有被單獨驗證**：沒做過「拿掉 Cake 再測寫入時放置」的對照（拿掉 Cake 後寫入時放置才贏，才支持「它重複 Cake 做的事」）；目前只是解釋 [判讀]。
8. **第 2 章「組合起來只有少數設定贏、要重算便宜 2–4 倍」來自早期另一張卡常數的探索掃描**，不是 H200 的結果；H200 的是 16 組 0 組贏、2 個模擬存活設定各 2/5 個種子。
9. **對手只有固定規則**：沒有跑 PBKV、KVFlow 這類真的預測器；我們能說的只是「完美預知比固定規則多省多少」，它界住的是把那個預測量放進同一個策略的好處，不是所有策略的極限（PAPER.md 對上界的定義）。
10. **Mooncake 的上限隨 CPU 記憶體變大而下降**（conversation 預取 50.5% → 14.6%；toolagent 30.0% → 2.5%）。原因沒驗證，可能和紀錄只有一小時有關；所以「Mooncake 上限很高」要連容量一起講。
11. **GPU 縮小重播的容量要換算**：縮小 1/8 的 CPU 16／32 GiB 相當於全尺寸 128／256 GiB；縮小重播的好處也比模擬小（預取對 LRU：實測 17.9%、同設定模擬 24.2%）。
12. **「打字就預取」不是主流做法，也不是我們提出的方法**：它是「不用預測模型能拿到多少」的參考點（原稿記錄的理由：打字那幾秒就夠藏住慢層還原，見 `docs/stage3_design_20261024/02_observations.md` O12；沒查到同類的論文，只查了摘要與關鍵字）。限制：要客戶端送打字事件、只適用聊天、打字時間是合成的。
13. **圖 1 是小工作量、而且每次重複有離群**：它是 8 個對話各 4 輪的小工作量（不是紀錄重播）、只有 NFS 級慢層、Llama；「CPU 25／50／100%」是佔這個小工作量的比例，不能和圖 2 的 GiB 對起來。登記的統計量是全部回來請求的中位數；每次重複的中位數有離群：fa3、25%、寫入時套用的 6 次裡有 2 次比其他高約 14%（0.935 對 0.822 秒；還原時間 0.499 對 0.362 秒，慢層載入的塊數中位數 1.5 對 1.0），原因沒查。方向對寫入時套用不利，所以「沒有收益」不受影響，但平均值版的差距是 −1.23%（中位數版 −0.37%）。sdpa、50% 兩種做法各有 2 次重複高約 9%，兩邊都有，像整體漂移。
14. **表 2 的分數是「BF16 的分數＋量到的差」**（全部載入的讀法，`report_only.json` 的 `e0acc` 加 `E1 A` 的差），不是另外跑的絕對分數；32K、只有 Llama-3.1-8B 與 Qwen2.5-7B。INT4 的標準是事先登記的主任務答對率對 BF16 的 95% 信賴區間下界 ≥ −2 個百分點；Qwen 在多鍵大海撈針的 Cake＋GPU 忙讀法少 0.8 個百分點、區間 [−2.2, +0.3]，沒過（表上列的是全部載入的 97.2，沒反映這個）。LongBench 是 6 項長文問答的平均分數（沿用上游評分）。INT8、K4V2 沒有這兩項測驗，未列入；INT2 只有 96 題海選（沒做多重比較校正），不能寫成「4 位元以下一定守不住」。64K／128K 沒量。
15. **「前 4 塊」只是例子**：用 `results/icpe_h200/p01/calib/calib_c1.csv` 的每塊重算時間（80 塊、GPU 閒的中位數）與 H200 CPU 讀取速度 43.59 GiB/s，依程式的 `write_boundary`（讓「重算前 m 塊」與「載入其餘塊」同時做完的 m）對 64 塊算出 m＝4；A1''、A1' 實際用的 fa3／sdpa 檔沒有逐一核對，所以只當例子，不當結果。「CPU 一滿兩版都先降位置最前面的塊」是讀 `code/m7_write_policy.py` 的結果（兩者都用 `_cheapest`），不是另外量的。
16. **Cake 的角色**：最強的不預測做法建立在 Cake 上，Cake 不是我們的貢獻；它的意義是讓「不預測」的對手夠強。所有上限數字都是「在 Cake 之上」量的。拿掉 Cake（整段載入）時，Mooncake 的上限高 1.9–13.8 個百分點（SSD 級、模擬、趨勢不變；`FIG1_DATA.md` 末段）；FreeInference 的階梯上 Cake 只再壓低 0.8 個百分點，主要差在有沒有慢層。NFS 級的 Mooncake 格全是寫入飽和，沒算。寫入時放置的對照沒有「拿掉 Cake」版（注意事項 7），所以第 2 章的「為什麼」仍只是解釋。
17. **預測模擬的 CPU 層沒有用上「一次拆完」**：PAPER §3.2／§0 說預測模擬的起點做法接近 §4 的表在「逐塊解壓」時的答案，CPU 層存 BF16（逐塊解壓時 INT4 在 CPU 層不比 BF16 快）；一次拆完時 CPU 層的 INT4 全部載入最快（Llama 忙 0.034 對 BF16 0.238 秒），所以 CPU 層的對手還不是最強，「把不預測做到最強」只對慢層成立。換成一次拆完，上限的方向很可能更低，但沒有量（PAPER 限制表也寫「方向沒有量過」）。跨平台只有 stage-2 的零件比較（每塊反量化 原寫法→融合：MI300X Llama INT4 閒 0.496→0.148 ms，H200 0.596→0.106 ms），同一種寫法跨 GPU 差不多，差很多的是寫法；不在 ICPE 範圍。

## 下一步：擴大驗證（計畫，還沒有任何結果）

**為什麼要做**：結論目前只在兩份紀錄上驗證（FreeInference、Mooncake 對話）。既有預測型研究的提升，多半是在 agent 工具工作流上量的（SWE-bench、GAIA 等）；我們手上唯一的工具類紀錄是 Mooncake toolagent，它的上限高（預取 30.0／24.1%）卻沒驗證。所以缺的不是「紀錄的數量」，是「工具類工作負載」這一類，以及它的 GPU 重播。

**A 類：跑既有研究用過的工作負載**（2026-11-04 從各篇全文整理，可取得性都還沒確認）
- 已有現成軌跡、可能直接拿來用：Ask the Tool 用的 mini-SWE-agent 排行榜軌跡（約 3,000 條）、OpenHands 評測、Terminal-Bench；Continuum 收的 100 條 mini-swe-agent（SWE-Bench）與 100 條 BFCL v4 Web Search；CacheWise 的 CATraces（作者實驗室自收，是否公開未確認）。
- 只有題目、要自己跑 agent 才有軌跡：PBKV（HoVer、SWE-bench、FinanceBench）、CacheScout（GSM8K、MT-Bench、GAIA、SWE-bench）、SAGA（SWE-bench、WebArena）。
- 每份軌跡要有：每輪的 token 數、前綴共享、兩輪之間的間隔（工具執行時間）。缺任何一項就不能用。依 CLAUDE.md 第 6 條，載入時要寫一條「用 A 欄位驗算 B 欄位」的斷言。

**B 類：參數掃描（合成工作負載，模擬）**
「所有可能」掃不完，可行的版本是把決定上限的旋鈕掃一遍：兩輪之間的間隔分佈、每個對話的輪數、上下文長度、並行對話數、CPU 記憶體容量、慢層頻寬，畫出「上限 ≥15% 的區域」在哪。限制：合成工作負載只能回答「在什麼條件下預測有空間」，不能取代真實紀錄。

**事先寫下的假設**（不是結果，不能當結論寫）
- H1：有簡單線索（打字、工具回報的進度）的地方，簡單線索拿走完美預取改善量的大部分。
- H2：對最強的不預測做法，剩下的空間集中在淘汰順序，不在預取。
- H3：上限隨 CPU 記憶體容量變大而下降。
- **推翻條件**：只要有一份真實的工具類紀錄，對最強的不預測做法上限 ≥15%，而且沒有簡單線索能拿走大部分，結論就要改成「在這類工作負載上，預測仍有空間」。

**時程**：A 類裡要自己跑 agent 的部分，ICPE 截止（11/16）前做不完；B 類與現成軌跡在截止前做不做得完，還沒評估。

```
**【故事 1/4】完美預測，比最好的不預測還能快多少？**

**一句話**：就算預測得完美（像開了天眼，知道誰、什麼時候會回來），比「不預測的最好做法」還能讓使用者回來時的第一個字（首字延遲 TTFT）再快多少？FreeInference（真實 agent 服務紀錄）在 CPU 記憶體 128 GiB 以上幾乎是零（≤0.30%）；Mooncake 對話紀錄看起來很大（預取〔使用者還沒送出，就先把停放的資料搬回 CPU〕最多 50.5%，CPU 記憶體加到 1,024 GiB 降到 14.6%），但「使用者一開始打字就先把資料搬回來」這種不用預測模型的簡單線索，就拿走其中大部分。所以在驗證過的兩份紀錄上，預測能多幫的有限；沒解決的是淘汰順序（CPU 滿了先擠掉誰）和 Mooncake 的工具紀錄（toolagent），見 4/4。

**起點**：使用者隔一陣子回來，系統要先把停放的 KV 搬回 GPU，才看得到第一個字。近年一批針對 agent 工作流的研究把預測放進 KV 管理：PBKV、CacheScout、CacheWise 以預測為核心，猜誰會回來、何時回來，再據此淘汰、預取（SAGA 的預測是它三個機制之一）。它們報告了大收益，但對照組是 LRU（最久沒用的先擠掉）或 vLLM／SGLang 的前綴快取，我核對的 8 篇全文都沒出現 Cake。這是近期的一條研究線，不是已證實的主流做法。我一開始也這樣想；要公平量預測的價值，得先有一個夠強的「不預測的做法」當對手。

**怎麼量**：三份真實使用紀錄（FreeInference＝agent 服務；Mooncake conversation＝對話、toolagent＝工具），H200 一張卡、32K；CPU 記憶體（停放對話 KV 的地方）從 16 掃到 1,024 GiB。對手是最強的不預測做法，建立在別人已發表的 Cake（ICML 2025）上：使用者回來時，GPU 一邊重算最前面的幾塊、一邊從儲存載入後面的塊，兩邊在中間會合；我再加 INT4 壓縮，並和 LRU、ARC、S3-FIFO 這類固定淘汰規則比（完整對手名單在 3/4）。Cake 不是我們的貢獻，用它是讓對手夠強，預測的好處才不會被弱對手灌水。

**第一步：預測能用在兩個時間點（寫入時、回來之前）。先試最直接的：寫入時就決定**（示意圖、圖 1、表 1）
寫入時決定＝對話剛結束、使用者還沒回來，就先決定這段 KV 放哪層、存什麼精度，等於事先替回來時做準備。
**規則**：一段 32K 對話切成 64 塊（每塊 512 token）。越後面的塊重算越貴（要先重讀前面所有塊），從儲存搬回的時間卻不隨位置變；所以位置最前面的塊重算便宜，放慢層（比 CPU 慢的儲存，如 SSD；省 CPU 空間），後面的放 CPU。
**兩個版本，只差「何時搬」**：寫入時套用＝對話一結束，最前面的幾塊（例如 64 塊裡的前 4 塊）就直接寫慢層，其餘寫 CPU；CPU 滿了才套用＝先全寫 CPU，滿了才把位置最前面的塊降到慢層。兩版用同一條規則。
**數據**：①放哪層：回來請求的 TTFT 只差 −0.37～+1.16%（門檻 5%；三種 CPU 容量各重複 6 次）。②消融（7 個條件）：單獨改任何一個都贏不到 5%；H200 上 16 組比較 0 組贏。③精度：前／中／後段各 25% 的塊降精度，答對率和「隨機挑同比例的塊」比：Llama INT4 差 −0.47～+0.08 個百分點（6 個信賴區間都含 0），Qwen FP8 方向不一，沒有穩定的差距。
**直覺**（看示意圖）：把對話想成 64 格，第 1 格最舊。使用者回來時兩頭同時做：GPU 從第 1 格往後重算，同時從第 64 格往前從儲存載入，在中間碰頭（例：重算前 4 格）。所以前 4 格是重算出來的，不從儲存讀。兩版的差別只有這前 4 格放哪：寫入時套用一開始就放慢層，另一版先放 CPU。但回來時用不到它們在儲存裡的副本，放哪都一樣；CPU 一緊，另一版也會把最前面的格子降到慢層，兩版的擺法就一樣了（我們的解釋，沒單獨驗證）。
**所以**：寫入時的預知不用做。**為什麼**：三項數據都沒差（①放哪層 ≤1.16%、②16 組 0 組贏、③精度無穩定差距），直覺也對得上：寫入時只能依位置決定放哪層、什麼精度，位置回來時系統看得到，前 4 格又本來就要重算 [判讀]。預測要有用，得提供「到時候還看不到的資訊」；剩下的只有「誰、什麼時候會回來」，所以預測只剩「回來之前」（預取、先擠掉誰）。
**下一個問題**：這種預測值多少？先量完美預測的上限：連完美的都省不了多少，真的預測器（只會更差）更不值得蓋。怎麼公平地量，見 2/4。
```

```
**【故事 2/4】比較對象決定答案；先把「不預測」做到最強**

**怎麼公平地量**：預測值多少，取決於跟誰比：對手越弱，預測看起來越值錢。

**為什麼這樣設計**：有一篇研究（Liu 等人，*When Fancy Eviction Fails*）在同一份 FreeInference 上說，LRU 和完美淘汰（Belady）的命中率差很多，但他們算「沒命中」的成本只算重算；我們另一組結果卻說完美預知最多只省 0.30%。我想知道兩者怎麼兜起來：是被「慢層＋Cake」吸收了，還是我們的設定裡本來就沒差距？所以用同一份紀錄（前 6 週）、同一個完美預知（知道每個對話下次什麼時候回來），只換「沒命中時怎麼辦」，從最接近他們的算法開始，一步步加強，看差距怎麼縮（模擬）。

**結果（CPU 32 GiB）**：① 沒有慢層、丟掉重算：完美預知比 LRU 快 15.9%；② 有慢層（SSD 級，讀 6.98 GiB/s）整段載回：只剩 3.4%；③ 再加 Cake（邊重算邊載入）：只剩 2.6%。可見大部分差距來自「有沒有慢層」，Cake 只再壓低 0.8 個百分點。CPU 容量掃 8–128 GiB：128 GiB 是先前結果的最小一格，用來接上；8–64 GiB 是新加的，用來找出「命中率差距大」的容量。我也換了更慢的頻寬（NFS 級 0.33 GiB/s）：對 LRU 的差距反而變大（27.7%），但大半是 LRU 太弱，對最強的固定規則（S3-FIFO）只剩 11.6%。

**所以**：預測的價值＝完美預測比最好的不預測做法好多少；對手越弱，這個數字越大（15.9% → 2.6%），只有對最強的對手，剩下的才是預測真正能多給的。所以我先把「不預測」的做法做到最強，再來比。

**第二步：把「不預測」的做法做到最強**（為了公平，不是主角）。不預測時，使用者回來要把停放的資料從慢層搬回 GPU，等的時間幾乎花在搬位元組，所以做三件事：
①搬得少：壓成 INT4（4 位元，小 3.2 倍），慢層還原比 BF16 快 36.7–54.5%（12 格全贏，GPU 閒或忙都一樣）。
②別讓 GPU 閒著：沿用 Cake，邊重算前段、邊載入後段。最慢的 NFS 級慢層上（Llama、GPU 閒），32K 對話從 BF16 整段載入 12.1 秒降到 INT4＋Cake 1.24 秒；各慢層、GPU 閒忙都比次佳做法快 11.0–40.7%。
③INT4 搬回後要「解壓」轉回可用格式，寫法影響很大：CPU 記憶體層搬得快，轉換成本就決定快慢。同一張 H200、同一個組合，我自己的兩種寫法差 6.8 倍：整段讀完一次轉 0.0342 秒，每讀一塊轉一次 0.2325 秒。這不是新方法，也不是 GPU 之間的差；較早的實驗用的是逐塊版，那時 INT4 在 CPU 層沒變快，換成一次拆完才快。
**要注意**：預測模擬的 CPU 層還用逐塊版的常數（CPU 層存 BF16），所以 CPU 層的對手還不是最強；換成一次拆完，對手更強，上限很可能更低（沒有量）。

壓縮還要看準確度（表 2）：INT4 在多鍵大海撈針和 LongBench 上和 BF16 幾乎一樣（BF16→INT4，大海撈針 Llama 99.7→99.7、Qwen 98.1→97.2；LongBench 40.8→41.0、42.8→43.0），事先登記的主任務也過關；FP8 在 Qwen 崩壞（大海撈針 49.7、LongBench 6.6）；INT2 更快，但沒有這兩項測驗，只有海選（誤差約是 INT4 的 30 倍）。所以用 INT4。

**所以**：最強的不預測做法＝INT4 壓縮＋Cake（CPU 層另看解壓寫法）。下一步用它當對手，量完美預測還能多快（3/4）。
```

```
**【故事 3/4】在最強的不預測做法之上，量完美預測的上限**

**第三步：在最強的不預測做法之上量上限**：把完美預測拆成四種，一次只給一種（為了看出好處落在哪一種決定上），各和同動作下最好的不預測對手比（名單見下）；上限＝完美預測的 TTFT 比對手少的比例：
・預取＝使用者回來前先搬回 CPU
・淘汰順序＝CPU 滿了先擠掉誰
・回合結束就丟＝知道這個對話不會再回來，答完就丟，不佔 CPU 也不寫慢層
・輪到淘汰才丟＝同樣知道，但等 CPU 滿、輪到它才丟
**對手是誰**：全是固定規則（不是學出來的預測器），每個動作各一組，取其中 TTFT 最小的：預取＝LRU、LRU+RPF（預取最近用過的對話）；淘汰順序＝LRU、LRU2（看倒數第二次使用時間）、ARC、S3-FIFO（三個先進先出佇列）、GDSF、Pensieve 式（看重算成本與閒置時間）；回合結束就丟／輪到淘汰才丟＝LRU、LRU+NONE（直接丟）、LRU+2HW／2HA（只用過一次的就丟）。FreeInference 在 CPU 小、慢層慢（NFS 級）的淘汰順序格上，最強的是 S3-FIFO。我沒有跑真的預測器（如 PBKV、KVFlow），所以界住的是「完美預知比固定規則多省多少」。
結果見圖 2（橫軸是 CPU 記憶體容量，SSD 級慢層）：FreeInference 在 128 GiB 以上最多 0.30%，因為固定規則已命中 99.29%，沒東西可補；Mooncake conversation 預取 50.5%（128 GiB）→ 14.6%（1,024 GiB）；toolagent 30.0% → 2.5%，只有 128–256 GiB 時 ≥15%。不只看最大值（可能只是單一異常格）：Mooncake 兩條紀錄共 192 格，扣掉兩種假象（紀錄只有一小時，尾端對話看似不會回來；慢層寫不完的格）之後，仍有 36 格 ≥15%（不扣假象 95 格）。15% 是事先登記的「值得做」門檻，原稿沒記錄為何是 15%。為什麼差這麼多、為什麼隨容量下降，還沒驗證（Mooncake 命中率沒算）。GPU 忙時預取上限更低（conversation 128 GiB：閒 50.5% → 忙 38.4%），淘汰順序幾乎不變，結論不變；圖 2 取閒／忙較大者。拿掉 Cake（改整段載入），Mooncake 的上限會高 1.9–13.8 個百分點，排序與趨勢不變；所以這些數字是「在 Cake 之上」的。我全程以首字延遲為準，命中率只用來解釋原因。

**下一個問題**：Mooncake 那個大的上限（50.5%），是真的嗎？**為什麼要問**：同樣是 CPU 128 GiB，FreeInference 只有 0.30%，Mooncake 卻是 50.5%，差上百倍，我還解釋不了（命中率沒算）；而且這是模擬，完美預知也是現實拿不到的。所以我拿一個不用預測模型的簡單辦法（使用者一開始打字就先搬）到 GPU 上實測，看它能拿走多少：拿走越多，剩給預測的空間越小（4/4）。
```

```
**【故事 4/4】大的上限，還剩多少？結論**

**為什麼選「打字就預取」**：它不是主流做法，是我選的一把尺。聊天裡使用者送出前一定先打字，這幾秒系統本來就閒著，是現成的提前量；它不用預測模型，只要客戶端送一個「開始打字」事件。相關工作多半是預測型（PBKV、CacheScout、CacheWise），或用排程佇列、工具進度（CachedAttention、Ask the Tool）；我沒查到用打字訊號預取 KV 的論文（只查了摘要與關鍵字）。所以它是「不用預測，能拿到多少」的參考點，不是我提出的方法，也只適用有人打字的聊天。

**簡單的辦法（不用預測模型）**：我先試最輕的辦法：如果它已經拿到大部分，複雜的預測器能多給的就更少。一偵測到使用者開始打字，就立刻預取。能提前多久，用打字時間算：新輸入的字數 ÷ 桌機打字速度（51.56 WPM，每分鐘字數；取自 Dhakal 等人量的照抄速度，所以提前量偏短、對打字提示偏保守），最多算到兩次請求之間的空檔。Mooncake 沒有按鍵紀錄，所以這個時間是合成的。

**怎麼測**（為什麼上 GPU：前面的上限都是模擬，這裡同時檢查模擬準不準）：把 Mooncake 對話紀錄依對話抽 1/8（原稿沒記錄為何是 1/8），在 H200 上用真的搬運與重算重播（Llama-3.1-8B、慢層 SSD 級；CPU 記憶體也縮成 1/8：16 與 32 GiB，相當於全尺寸的 128 與 256 GiB），比三種做法下回來請求的平均首字延遲：① 不預測（LRU）② 打字提示預取 ③ 完美預取（知道每個對話確切何時回來）。

**結果（圖 3，縮小重播 CPU 16 GiB）**：LRU 0.278 秒 → 打字提示 0.237 秒 → 完美預取 0.228 秒。完美預取比 LRU 快 17.9%，打字提示快 14.5%，所以打字提示拿到完美預取改善量的 0.81（14.5 ÷ 17.9）；完美預取只比打字提示再快 4.0%，低於事先訂的 5% 門檻。CPU 32 GiB 同方向（0.79、3.8%）。順便檢查模擬：不含排隊時，實測÷模擬＝0.911–0.987，策略排序全同。**但這個重播不含排隊**：加上排隊後，完美預取比 LRU 快的幅度從 17.9／16.2% 掉到 8.1／4.7%，上限更小。

**結論**：在驗證過的兩份紀錄上，預測能多幫的有限。FreeInference 上連完美預測都只省 0.30%；Mooncake 對話紀錄上完美預取的上限雖高（50.5%），但「使用者一開始打字就先搬」這種簡單辦法，就拿到其中大部分。

**還沒解決**：① 淘汰順序目前沒有這種簡單辦法；它在 Mooncake 上的上限是 27.6%，那才是預測器可能有空間的地方，還沒驗證。② Mooncake 的 LRU 命中率沒算，所以「差距取決於固定規則命中多少」只在 FreeInference 驗證過（128 GiB 時 99.29%）。③ 我沒有蓋真的預測器，只量了「完美」的上限；可以補：把完美預知故意弄不準（例如回來時間估錯），看好處多快消失。④ Mooncake toolagent 在 128–256 GiB 時上限也高（預取 30.0／24.1%），但沒有打字這條線索，也沒有 GPU 重播，預測在那裡值多少還不知道。

**要小心的地方**：慢層是限速模擬（SSD 級 6.98、NFS 級 0.33 GiB/s，常數來自另一個平台）；GPU 重播只有一種設定（對話紀錄、SSD 級、Llama、不含排隊）；打字時間是合成的；對手只有固定規則，沒跑 PBKV 這類真的預測器。

**旁支**：送回時 GPU 被別的工作佔用怎麼辦（用 NVIDIA 的 GPU 共用機制 MPS，回答快 30.7–62.9%、背景最多慢 6.5 個百分點，模擬）是另一個問題，和主線無關，放附錄。
```
