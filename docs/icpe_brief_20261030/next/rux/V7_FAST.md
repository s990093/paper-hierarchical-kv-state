# x1fast v7：慢層上限的加速（icpe-rux 第 3 段，RUX3DPRO）

> 2026-11-07。程式在 `code/icpe/rux_x1fast/v7_fast/`（`patch_v7.py` 從 v6 產生 `src/main.rs`）。**不改語意**：輸出和 v6、和 Python 逐位元相同。
> 使用者 11/7 同意做「低風險的三個」（ANALYSIS §3d 候選 2、3、5）；候選 1（BEL 的 lazy heap）、4（第一次超過上限前共用）沒做。
> 逐列數字在 `V7_rows.csv`（每列有 run_id、ts、host）。

## 0. 問題／要證明什麼

- **問題**：v6 照抄 Python，開上限後 Bailian 的慢層 LRU2／PENS／BEL 每次丟 session 都全掃慢層（上萬個 session）；SemiAnalysis 因為關掉快速路徑，每個規則都慢約 1.8 倍。
- **要證明**：(1) 加速後輸出仍和 Python 逐位元相同；(2) 快多少。

## 1. 結論

- **逐位元相同**：3 份紀錄 × 4 組子集，在驗證模式與一般模式各跑一次，對 v6 那次的 Python 參考，CSV 177,072 格、npz 11,424 個陣列，**兩次都 0 個不同**；功能關閉 G1、xc_sa 0 個不同。
- **快多少**（單執行緒、同一個 job，v6 ÷ v7）：
  - Bailian：慢層 LRU2 **12.6×**、PENS **2.2×**；
  - Mooncake：LRU2 3.1×；
  - SemiAnalysis：7 種規則都快 **1.16–1.26×**；
  - 其他設定在 ±10% 內，是量測雜訊，負載 2.7–13。
- **多執行緒**（主子集 1,104 個 job、16 worker 的 sweep 牆鐘，v6 → v7）：Mooncake 17.0 → 17.0 s、Bailian 54.5 → **37.1 s**、SemiAnalysis 71.8 → **60.2 s**。
- 沒做的候選 1（BEL）：Bailian 的慢層 BEL 仍是最慢的設定，每個 job 約 1.25 s；第二慢是 PENS，0.68 s。

## 2. 改了什麼（`patch_v7.py`）

| 候選 | 做法 | 為什麼不改結果 | 驗證模式（`X1FAST_SC_CHECK=k`）多做的檢查 |
|:--|:--|:--|:--|
| 2 LRU2 有序集合 | 鍵＝(prev 或 −1, last, 進入順序, s) 的 `BTreeSet`，取第一個 | 鍵在 session 待在慢層期間不變：prev／last／nreq 只在這個 session 自己的回合結束改，那之前 `step` 已經把它移出慢層。同分時「進入順序」小的先，等於 Python `min` 取 `mem` 裡的第一個 | 每次選擇另外全掃比對；每 k 個請求檢查每個成員的鍵沒有變、集合大小等於成員數 |
| 3 PENS 成本快取 | 成本（不含除以距離）按 session 存，帶「同一組 session 的 epoch」；epoch 變了才重算 | 成本只取決於這個 session 的塊清單和那些塊的 ref_live；任何改 refcount 的動作開頭都會 bump 那一組的 epoch。v5 的「下次回來」快取用同一套機制 | 每次都重算並和快取比**位元** |
| 5 快速路徑＋補記 | 開上限時也走三個回合結束的快速路徑；被跳過的 `fix(b)` 只剩「在慢層、沒有慢層持有者 → 放進 `clean_q`」這個效果，由 `sc_note` 在原本的位置、照原本的順序補做 | 被跳過的塊，`fix_inner` 什麼都不改（前綴：遞增又遞減；條件式 fix：兩個條件都不成立），所以 `n_slow` 不變；`clean_q` 的內容和順序相同 | 斷言每個被跳過的塊，`fix_inner` 確實是空動作 |
