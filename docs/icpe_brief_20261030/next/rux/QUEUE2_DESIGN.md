# 二階排隊（事件驅動）的設計（icpe-rux，2026-11-07；PREREG 偏離 19）

## 0. 問題／要證明什麼
- 一階近似（偏離 11 B，`qpost`）：快取的決定在「沒有排隊、照紀錄順序」的模擬裡做，排隊事後才套上。
  - 漏掉的是二階效果：排隊改了服務順序和時刻，這些又會回頭改快取狀態。
  - 重負載的格重排很多，所以一階只報告（SEMANTICS_2to5 §2b）。
- 二階：GPU 照**實際的服務順序**處理請求，快取狀態也照這個順序演進。
- 要回答的：把排隊的回饋算進去之後，版本 C 的上限（不含排隊）在輕、中負載的格會不會變；和一階比差多少。
- 地位：**敏感度**。主結果仍是版本 C，標「不含排隊」。

## 2. 模型
| # | 項目 | 二階（qev） | 一階（qpost，偏離 11） |
|:--|:--|:--|:--|
| 1 | 伺服器 | 單一 GPU，FCFS，一次一個 | 同 |
| 2 | 到達 | session 的第一個請求在紀錄時刻到；之後＝max(紀錄時刻＋這個 session 上一個請求「開始比紀錄晚多少」, **上一個請求完成**)（closed-loop：拿到回覆才送下一個） | 偏離 11 B（`qpost=1`）：沒有「不早於上一個完成」；偏離 19 的對照 `qpost=2`：有，上一個完成＝開始＋沒排隊的 TTFT |
| 3 | 服務時間 | **開始時刻用當下的快取狀態算**：還原＋prefill（＝TTFT；解碼不算） | 沒排隊模擬的 TTFT |
| 4 | 快取狀態 | **照服務順序演進**：還原在開始時刻讀；回合結束的寫入和 TTL 起算在完成時刻。下一個請求在完成之後才開始，所以在同一步做 | 照紀錄順序，不受排隊影響 |
| 5 | ④ 的「下次回來」 | 還沒服務的請求裡，序號最小、用到這個塊的那個（④ 只知道紀錄的順序） | 紀錄順序 |
| 6 | 新近度（LRU2、FREQ、PENS、GDSF、預取 RPF 等） | 服務順序 | 紀錄順序 |
| 7 | 時間（TTL、預取時間窗、I/O 線） | 模擬時刻（開始／完成） | 紀錄時刻 |
| 8 | 回報 | TTFT＝等待＋服務 | 同 |

- 一個 job 只能有 1 個時間設定。服務順序取決於時間設定，所以 6 個時間設定各跑一次模擬，比一階慢約 6 倍。
- **為什麼要「不早於上一個完成」**（審查第 1 點）：
  - 原規則下，如果模擬的服務時間比紀錄的間隔長，下一個請求會在上一個還沒完成時就「到達」。agent 拿到回覆才送得出來，所以這不可能發生。
  - 多算進來的等待（SemiAnalysis N16 s1，CPU 16／111 GiB × 4 個 CPU 規則 × 3 個 GPU 規則；run `20261107-153232-icpe-rux-v9-early-arrival`）：
    - 輕負載：約 2.1–2.3% 的請求，占總等待 16–21%。
    - 重負載：占總等待 < 3%。
  - 偏離 11 B 的一階有同樣的問題，結果不改。偏離 19 另外用新規則重跑一階（`qpost=2`），所以「二階 vs 一階」只差回饋。
- 審查第 2 點（fork 可能比它的來源先服務）：SemiAnalysis 沒有 fork（kind 2 是 0 筆），不影響。
- 範圍照偏離 11 B 的 3-4：只用固定並行的紀錄 SemiAnalysis。
- BELS 的距離＝下次回來的序號 −（還沒服務的最小序號 − 1）。沒有重排時和 v8 相同。
- 方向：④ 只知道紀錄的順序，所以 ④ 略弱，上限略偏低（SEMANTICS §0 說不可以的方向）。重排越多偏差越大，重負載因此只報告。這一點要在論文寫明。

## 5. 分析（登記在偏離 19）
- **單位**：(變體, CPU 容量, 慢層, GPU 閒／忙, 元件)，cake，和偏離 11 B 同一套格。
- **負載**：二階裡那一格 (LRU, LRU) 的平均等待。輕 < 2 s、中 2–20 s、重 ≥ 20 s；重的只報告。
- **比較 1（主要）**：二階 vs 版本 C（不含排隊）。報各負載 × 元件的：
  - ≥15% 的格數；
  - 跨過 15% 的格數（升／降）；
  - 差的中位數。
- **比較 2**：二階 vs 一階。報同樣的統計，以及負載等級的交叉表（二階 × 一階）。
  - 主對照是一階 `qpost=2`（A 段，到達規則和二階相同），兩者只差回饋。
  - 另外並列偏離 11 B 的一階（`qpost=1`）。
- **一階 `qpost=2` 本身**：和偏離 11 B 同樣的報法，負載用它自己的 (LRU, LRU) 平均等待分。
- 判定元件同偏離 7：O-ORD、O-DROP、O-NOW、O-PF、O-GPU。O-ALL(report) 只報告。
- 每個變體之外，另做 12 個變體的加總表（同偏離 11 B 在 STATUS_RUX 的報法）。

## 6. 試跑時看到的（揭露）
驗證時 `smoke_v9.py` 每組印了平均等待和 mean TTFT（二階、一階 `qpost=1`、一階 `qpost=2`）。上限表在登記前沒有算；端到端試跑算出的上限表沒有讀。
- **第一版**（到達還沒加「不早於上一個完成」）：
  - 快速驗證 run `20261107-151915-icpe-rux-v9-smoke-quick`（6 組）。
  - 完整驗證 run `20261107-152246-icpe-rux-v9-smoke-full2`（204 組 × 輕／重）。
  - 看到的趨勢：
    - 重負載 (LRU, LRU) 的平均等待，二階 871 s、一階 2,646 s（N16 s1、CPU 16 GiB、nfs 忙）。
    - 輕負載二階和一階的 mean TTFT 差 −8%～+7%。
  - 解讀〔推論〕：一階的服務時間來自沒排隊的模擬，重負載時那裡的 I/O 線已經互相搶頻寬，事後再排一次隊，等於重複算了一次擁擠。
- **提早到達的量測**：run `20261107-153232-icpe-rux-v9-early-arrival`（§2），24 組 × 輕／重。
- **第二版**（加了「不早於上一個完成」、加 `qpost=2`）：
  - 快速驗證 run `20261107-153556-icpe-rux-v9b-smoke-quick`。
  - 完整驗證 run `20261107-153730-icpe-rux-v9b-smoke-full2`。
  - 看到的趨勢（6 組、CPU 16 GiB）：
    - 輕負載：二階和 `qpost=2` 的 mean TTFT 差 −9%～+9%。GPU 用 LRU 的 3 組二階比較快（例：LRU, LRU 3.12 s 對 3.43 s），GPU 用 BELP 的 3 組二階比較慢（例：O-BEL, BELP 2.90 s 對 2.71 s）。
    - 解讀〔推論〕：BELP 是 ④，它只知道紀錄的順序，服務順序一變就變弱（§2 的方向）。所以 O-GPU 的上限在二階可能變小。
    - 重負載：(LRU, LRU) 的平均等待，二階 865 s、`qpost=2` 2,630 s。
  - 中途停掉一次 run `20261107-153659-icpe-rux-v9b-smoke-full`：報告欄 `mean_wait_qpost1` 誤取了到達時刻（解包順序錯）。只影響報告欄，修正後重跑。
