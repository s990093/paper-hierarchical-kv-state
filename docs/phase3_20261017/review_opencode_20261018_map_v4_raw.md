**v4 審查結果（同家族、零前文審查，不算跨模型審查）**

1. **【必改】E3／E4 裡沒有任何對手能用 INT2，GO 幾乎由資料統計事先決定**
   - 問題：寫 SSD 時 `idle_s`＝0，所以 D-idle 等於 D-len（policies.py L266–268；06 L105）。19 個對手裡也沒有「CPU 放 BF16、SSD 放 INT2」。只有 O 能把單輪 session 壓成 INT2，每 block 比 INT4 省 40%。
   - 證據：Bailian coder 26,406 個 session 裡只有 6,693 個多輪；Mooncake 是 1,959／9,595（06 L299、L302）。所以這兩格幾乎一定過，NO-GO 實際到不了。上一輪第 1 條點名的「E3＋單輪多」沒有處理。
   - 改法：加兩個不用學的對手，照樣過護欄：C1-2（BF16 寫 SSD 時壓 INT2）、「session 第一輪就存 INT2」。同時註明 O 不看「從哪層讀」，所以在 E3／E4 不是上界。

2. **【必改】E6 的主指標漏掉預取讀取**
   - 證據：預取把 block 從 SSD 讀進 CPU（engine_block.py L481–517）；`serve` 只替「不在 CPU」的 block 記 `lo_bytes`（L559–565）。所以預取、包括浪費掉的預取，都不算進主指標。
   - 偏差：格式越小，同一段時間預取越多、漏算越多，偏向會壓縮的做法（含 O）。04 §4 寫「只和放置有關」，對 block 引擎不成立（06 L526–527 自己也承認）。
   - 改法：E6 改用 SSD 實際讀取量（還原＋預取），依請求到達時間截尾。

3. **【必改】長請求多的資料，「省多少」量到的不是預測的好處**
   - 證據：合成資料 15 格有 14 格最好的對手是 C0（報告 §6）。FreeInference 每個請求平均 385 個 block，約 197K token（06 L486），壓過的 block 一被讀就要重算，對手實際只剩 C0。
   - 量到的是什麼：「不會再被讀的 KV 從 BF16 壓到 INT2（每 block 省 81%）」加上完美的長度資訊，而且建立在「32K 以上沒量過」這個量測缺口上。
   - 模型範圍：Llama-3.1-8B 的上下文上限是 128K，04 §3.3 L67「BF16 任何長度都過關」沒有根據。
   - 改法：事先登記一個「寬鬆版」雙胞胎（O 和所有對手都用 O-loose 的品質規則）一起報告；GO 的格子要標出最好的對手是不是 C0；超過 128K 的請求要定規則（排除或標出）。

4. **【必改】analyze_map 不檢查切片齊不齊**
   - 證據：切片清單直接取 CSV 裡有的（L335–338）；「完整」只看格子（L355–361）。少了一整週，或只有 A1 的輸出就跑 `--mode full`（FreeInference 只有 4 週），都會被當成完整，可以判 GO 或 NO-GO，違反 §10「判定等 B」。
   - 改法：每種 mode 寫死應有的切片清單，不齊就丟錯。

5. **【必改】凍結閘門只查一個字串**
   - 證據：只檢查文件裡沒有「未凍結」（run_map L155–164）。04 §9 L156 說凍結時記格式表的 sha256，但 v4 沒填值。格式表、costs、`kgpu_kmin_all.csv`、`return_gaps.csv` 都不比對 sha256；k 也沒對 §9 的表（只有 H 有對，L139–152）。程式有未提交的修改只標 `+dirty`，照樣跑（L743–744）。
   - 改法：§9 寫入所有輸入檔的 sha256 與程式 commit；執行器斷言這些值，有 dirty 就拒絕。

6. **【建議】護欄只管對手、不管 O；主指標鼓勵重算**
   - 證據：護欄只套在非 oracle 的做法上（analyze L206–224、L358），O 的等待時間從來沒檢查。重算掉的 block 也不算讀取（engine.py L661–689 的 `lob`），對手可以用重算換到更少的位元組，O 卻不准重算，所以 O 不是這個指標的上界。
   - 改法：O 也要過同一個護欄（沒過就不能支持 GO）；主格同時列出最好的對手與 O 的重算 token。

7. **【建議】沒有絕對流量門檻**
   - 問題：435 GiB 時寫進 SSD 的幾乎都是 LRU 趕出去、不會再被讀的 session，比例很大但位元組可能很小（合成資料 E2@435 是 61.9%）。SSD 不忙的格子，「省頻寬」沒有意義。
   - 改法：事先登記 GO 格子的 SSD 需求下限，或在判定旁邊列出 GiB/h 的絕對值。

8. **【建議】對手用「存的長度」，不是「請求長度」**
   - 證據：C4、C4r、D-len 用 `ctx["tokens"]`（policies L87、L245、L268），但嚴格規則看的是請求的輸入長度（engine L302–315、L672–675），而 `req_tokens` 是當下就知道的資訊。O-reuse 卻用 max(tokens, req_tokens)（L147）。對手被不必要地削弱，「O-reuse 對 D-idle」的拆解也用了不同的基準。
   - 改法：對手的門檻改成 max(tokens, req_tokens)。

9. **【建議】GO／NO-GO 仍然不對稱**
   - 問題：GO 只要一格（兩份資料），NO-GO 卻要所有資料、15 格的同時 CI 上界都小於 5%，max-T 又讓 CI 變寬。加上第 1 條，結果實際上只有 GO 或「問使用者」。
   - 上一輪 21 條的處理：#2、#6、#8 只做了一半（見本條、第 1、5 條）；#1 換個形式又出現了（第 3 條）；其餘處理正確。
   - 改法：在 04 明講並接受這個不對稱，或把 NO-GO 改成用事先指定的格子子集。

10. **【小事】判定程式的兩個小問題**
    - 護欄用沒截尾的 `ttftq`（analyze L48、L157），主指標卻是截尾 H；ledger L242–246 已經有 `ttftq_H_*` 可用。
    - 最好的對手是 0 而 O 大於 0 時被記成「省 0%」（L231–232、L261），會被算進 NO-GO。應記成 NaN 並加旗標。

11. **【小事】不是主視角的列被丟掉**
    - 證據：`Index` 只留主視角的列（analyze L76）。A2 跑的 E6「GPU 忙」（run_map L489 `is_primary=False`）永遠進不了報告；A1 在三個記憶體點也沒跑 E6 的 GPU 忙，但 §5 把 GPU 忙閒列為主地圖的軸。
    - 改法：索引的 key 加上視角名稱。

12. **【小事】文件之間不一致**
    - H200：審查紀錄 L16、L29 寫 162 GiB，04 L116 寫 170 GiB。1,393,029 MB÷8 只有在 Slurm 的 MB＝MiB 時才是 170，要寫明單位。
    - 06 L20、L53–56 仍寫解壓用「只載入」欄；L175–177 仍寫讀取長度＝前綴長度。都和現在的程式不符。

13. **【小事】違反 CLAUDE.md 的地方**
    - §2 規定大檔放 /ssd7，程式都寫到 /ssd8（run_map L48–49；P 快取見 06 L211）。
    - §4.3：run_id 預設 "adhoc"（run_map L401、analyze L489），真實資料應該拒絕。
    - §1.3：CPU 忙係數 1.35／1.81 是從文件抄進程式的，costs json 仍寫 NOT_MEASURED（06 L633），應從量測檔讀並帶 run_id。

**能不能凍結：不能。**
必改的第 1–5 條會讓判定變成「事先就知道會 GO」或「判不準」：沒有能用 INT2 的對手、E6 漏算預取、長請求下只剩 C0、切片沒檢查、凍結閘門太鬆。
