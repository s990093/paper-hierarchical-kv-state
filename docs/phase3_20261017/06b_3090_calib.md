## 3. CPU 忙的時候，搬運慢多少

### 3.1 量法（`code/p3cal/cpu_busy_restore.py`、`cpu_stress.py`；寫在跑之前）

- **壓力**：`cpu_stress.py --threads N`：一個 process、N 個執行緒，各自配 256 MiB 的 src、dst（first-touch），不停 `np.copyto(dst, src)`。numpy 的連續陣列複製會放開 GIL，單獨跑時 N＝1 → 8 的總複製速度 6.3 → 25.9 GiB/s（`cpu_stress_standalone.csv`，run `20261018-002700-p3cal-stress-selftest`），確認執行緒真的同時在搬。每秒記一次複製速度（＝每秒複製完成的位元組；記憶體控制器上的流量約 2–3 倍，不換算）。
- **量測**：一個 GPU process（GPU 6，綁 node1 的 CPU）載入 Qwen2.5-7B 一次、prefill 32K、做好 64 個 BF16 block 的 pinned 副本（寫入同 `x7_restore.py`），然後跑 12 段：
  `N:place ＝ 0 8 16 32 48 48 32 16 8 0`（place＝same：壓力綁 GPU 所在節點 node1 的 48 個邏輯 CPU）＋`48:all`（不綁）＋`48:other`（綁 node0）。每段：開壓力 → 等 READY＋3 秒 → 量 →關壓力 → 休息 2 秒。
  - (a) 搬運：`m7_calib.py` c0 的迴圈逐字照抄（64 MiB／1 GiB × pinned／pageable × H2D／D2H，各 5 次；Llama 形狀 64 MiB block 進 KV strided 視圖 15 次），另加 `m10_speed calib-f` 的「Qwen block（28 MiB）進 `km.chunk_view`」20 次。
  - (b) 還原：`m7_restore_harness.Restorer`（沒改），E0（全 BF16）、`cpu_real`（不限速、真的 H2D），cake、load_only 各 5 次＋compute_only 1 次，段內順序洗牌；每段每個 mode 的第一次做 KV 逐位元檢查。
  - 每段記：`/proc/loadavg`（頭尾）、`/proc/stat` 算的兩個節點 CPU 使用率、壓力程式段內每秒複製速度的中位數。
- **倍數**：頻寬＝N＝0 的中位數 ÷ 這格的中位數；時間＝這格 ÷ N＝0。N＝0 的基準＝開頭、結尾兩段合併；same 的每個 N＝往上、往下兩段合併（各 5 次 → n＝10）。

### 3.3 怎麼讀這張表（照實寫：有一個沒控制住的變數）

1. **壓力的記憶體落在哪個節點沒有控制**。這台沒有 `numactl`，`cpu_stress.py` 只綁 CPU、靠 first-touch。事後查（run `20261018-023443-p3cal-stress-numa`，02:33–02:35）：node1 的 MemFree 只剩 0.5–1.3 GB（其餘 171 GB 是 page cache），`zone_reclaim_mode=0`，綁 node1 CPU 的壓力有一大半配到 node0（啟動後 5 秒時已配的匿名頁：N＝8 node1 佔 44.5%、N＝48 佔 23.2%）。cpubusy run 當時（00:50–01:02）的分佈、以及量測 process 自己的 pinned 緩衝在哪個節點：**NOT_MEASURED**。
2. 所以 same 的 pinned H2D 倍數**不隨 N 單調**（1.35、1.42、1.06、1.04），而壓力綁 node0 的 other 反而最慢（1.76）。〔判讀〕和「pinned 緩衝有一部分在 node0、DMA 要跨 UPI」的解釋一致，但沒有驗證。同一個 N 的往上、往下兩段也差 20–25%（例：N＝8 pinned H2D 5.95 vs 4.81 GiB/s，壓力複製速度 28.0 vs 15.2），**這是這台機器、這個時段的狀態，不能推廣成「CPU 忙 N 個執行緒 ⇒ 慢 X 倍」**。
3. **只載入還原的倍數比較穩**：same 1.35／1.45／1.53／1.54（隨 N 單調上升），all 1.43，other 1.81。它是 64 次 28 MiB 的 H2D 加上每塊的 Python 開銷，所以同時吃到搬運變慢和 CPU 排程變慢。給地圖的「CPU 忙」係數，〔判讀〕用這一欄的範圍 **1.35–1.81** 最貼近「CPU 層還原」這件事。
4. **同節點的邏輯 CPU 用滿（N≥32 same）時，重算也慢 3.1 倍**（compute_only 11.6 → 36 s；other 只慢 1.006 倍、all 1.09 倍）：GPU 發 kernel 的 Python 執行緒搶不到 CPU，不是記憶體頻寬。這讓 Cake 的重算線變慢、會合點從 3 掉到 1–1.5，Cake 還原慢 1.6–2.0 倍，新一輪 256 token 也慢（TTFT 2.3–2.6 倍）。〔判讀〕地圖若把「CPU 忙」只當成「搬運係數」，會漏掉這個效應；它只在壓力和推論 process 搶同一組 CPU 時出現。
5. **pageable 路徑對 CPU 忙非常敏感**（2.4–14.7 倍），因為它要 CPU 先複製到暫存區。harness、X7 和 vLLM 的 CPU offload 都用 pinned，所以地圖不用它；列出來只是給「外層系統用 pageable」時參考。
6. 只有一個 launch；每格 n＝10 或 5。
