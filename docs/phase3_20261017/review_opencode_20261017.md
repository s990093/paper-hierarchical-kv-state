## 2. §8 GO/NO-GO

- **聚合單位沒定義，這是最大的漏洞。** 主設定下，每個 trace 還有 5 容量 × 4 頻寬 × 2 GPU 狀態＝40 格。「各時間段 headroom 的中位數」是逐格算，還是在區域內合併？
  - 如果逐格：GO 等於在 80–120 格裡挑最大值，這是多重比較問題。
  - 如果合併：怎麼合併沒有寫。
- **GO 和 NO-GO 不對稱。** GO 是「至少一個 trace、至少一個區域」，NO-GO 卻是「全部都 <5%」。NFS 0.331 GiB/s 在主網格裡；D4 在 NFS、CPU 2–5% 用總 TTFT 已經得到 12.5–17.5%。換成只算回來請求後〔判讀〕幾乎一定 ≥15%，所以 GO 等於事先決定了，而且落在論文已經讓步的角落。
- **10% 穩健條款在 3 段時沒有作用。** 3 段的中位數 ≥15%，就代表已經有 2 段 ≥15%，條款自動成立。
  - 分段重複測的是時間上穩不穩定。系統性的模擬偏差會讓每一段往同一方向偏，分段擋不住。
  - 5–6 個百分點的誤差是在 m7（單請求、placement）上量的，不能直接套到新的預取和併發模組。
- **NO-GO 那一側沒有保護。** <5% 本身就落在 5–6 pp 的誤差帶裡。B7 也顯示 oracle 實作錯誤曾經低估 headroom（8.4% → 12.3%），所以假 NO-GO 一樣可能。
- **中位數不是好的判定指標：**
  - 回來請求的 TTFT 是雙峰分布（CPU 命中約 100 ms，慢層數秒），中位數會在 0 和很大之間跳。
  - Belady 類 oracle 最佳化的是總和或命中數，不是中位數，所以在中位數上不保證是上界。
  - 只算回來請求，預取搶頻寬拖慢第一輪請求時不會被扣分，這是可以被操弄的地方。
  - TTFT 包不包含新回合的 prefill 和排隊時間，沒有定義。相對值也沒有絕對 ms 的下限。
- **把時間段當重複不成立。** 59 分鐘切成 ≥3 段，跨段 session（重用距離 p90 為 519 秒）會造成設限，快取狀態也互相依賴。只有 3 段時，bootstrap 只有 10 種可能的中位數，CI 沒有意義。
- **長度映射會影響判定，但 §8 沒處理。**
  - §4 說映射是合成變換，要分開列；§8 卻沒說映射後的格子算不算「真實 trace」。
  - b\* 對應的 16／32／48 頻寬是在 32K 長度上校準的（main.tex §3.4），對中位數 6.3K 的原始長度沒有意義〔判讀〕。等於頻寬軸暗中要求做映射。
- **容量用工作集百分比，掩蓋了絕對大小。** 11.2 TiB 的 2–10% 是 0.22–1.1 TiB，才是單機實際會有的 DRAM；25% 和 50% 不現實〔算術／判讀〕。
- **負載沒有預先定。** conversation 約 3.4 req/s，toolagent 約 6.7 req/s；第一階段的併發模擬只跑 0.05–0.4 sessions/s（main.tex §4.6）。GPU 過載時，排隊會把小的服務時間差放大成大的 TTFT 差，造成假 GO。
- **少了 D4 §2.3 原有的歸因規則。** 原本要求 headroom 必須來自可預測的資訊，不是來自知道確切時間；這次的判準把它拿掉了。

## 3. 對手與 oracle（§3）

- **oracle 不是上界。**
  - Belady 只在大小相同、成本相同、單層、沒有預取時最佳。
  - 這裡 session 大小不一，成本隨層、位置和 Cake 會合點非線性變化；預取和需求讀取共用頻寬（寫入干擾 3.31×）。
  - 三個貪婪元件組合起來不等於整體最佳（B9：元件不能相加）。
  - 「提前量＝還原時間」在多個預取同時進行時不可行。
  - 結果是可能高估（忽略爭用），也可能低估（貪婪）。§5.1 不變量 2 被違反時怎麼處理，沒有寫。
- **機制不對稱。** 必須寫明所有非 oracle 策略都能用同樣的機制（部分預取、丟掉、INT4、不寫慢層），只差在資訊。目前沒有「LRU＋部分預取」，所以部分預取帶來的位置收益會被算到 oracle 頭上。D4 §4.6 已經示範過：差別來自規則，不是時機。
- **缺少的對手：**
  - LRU＋不寫慢層：D4 §4.3 的判定就是被這一個翻掉的。
  - GDSF／LHD 類非學習的成本與大小感知策略：§6.2 介面 (ii) 用了 LHD 形式，基準裡卻沒有。
  - LRU-K／2Q。
  - Continuum 需要工具名，沒有工具名的 trace 跑不了，所以各 trace 的對手集合要事先定。
- **WA 查表本身就是擬合。** 在哪一段擬合沒有寫，含測試段就是洩漏；也碰到 CLAUDE.md §8「oracle 之前不調參」。ARC、S3-FIFO、Bidaw 的參數要寫死成預設值。

## 4. 模擬器（§5）

- **新模組的誤差沒有驗證。** 新加的 session 級丟掉、預取、INT4 慢層、併發（m8_conc_sim 沒有 GPU 驗證，main.tex §3.3），誤差都未知。
- **歷史上模擬出來的正面結果都是假的。** 模擬 survivor 預測 7.6%，上 GPU 後歸零；併發分析的 5/192 個贏家全部是建模錯誤（main.tex §4.3、§4.6）。
- **主設定依賴推算值。** 主設定用的是 stage 44 尚未量測的兩層還原〔推算〕。用推算值決定 go/no-go 碰到 CLAUDE.md 規則 1 的精神；實測出來後如果判定翻轉，哪一個算數要事先寫。
- **偏差方向〔判讀〕：** 理想化的預取（沒有 PCIe 和讀寫爭用）會系統性偏向 oracle。
- **用模擬判 NO-GO 可以接受，判 GO 不夠。** 前提是 oracle 夠緊。GO 之後直接進入一到兩週的訓練。oracle 的排程是離線已知的，所以 P3-4 之前應該先在 GPU 上重播 GO 格的 oracle 對 LRU。
- §8 沒有包含 harness 比 vLLM 慢 1.7–2× 的敏感度。

## 5. Loss 比較（§6）

- **介面混淆。** Cox 和 LambdaRank 只能用介面 (i)，BCE 和 AFT 可以用 (ii)，「最好的 loss」可能只是「能用 (ii)」的那個。應該做 loss × 介面全因子；Cox 可以用 Breslow baseline hazard 轉成 S(t) 進 (ii)。
- **標籤時點和決策時點不一致。** 標籤在回合結束，決策在降級當下；需要的是在「已閒置時間」條件下的剩餘時間（landmark）。存活模型天生支援這個，BCE 和點迴歸不支援，所以比到的是條件化能力，不是 loss 本身。
- **D1、D2、D3 需要的量不同**（順序、H 秒內的機率、分位數），單一個「最好的 loss」不成立，要分開報。
- **調參要對等。** H、Elkan 門檻、q、退路門檻的調參預算要相同，並且在時間切分的驗證段上調。退路觸發率一定要報，否則 loss 之間的差可能只是退回 LRU 的頻率不同。
- **統計檢定力不夠。** 預測器大概只拿到 headroom 的 22–66%（D4 引 LPC），loss 之間的差距很可能低於 5–6 pp 的模擬誤差。要預先定 ROPE，並在 7 loss × 2 模型族 × 介面 × trace 上做 Holm 校正。
- **特徵可能學到截尾的假訊號〔判讀〕。** 在 59 分鐘的 trace 裡，「時段」「整體到達率」和右設限是共線的。
- **看結果才定 loss 清單。** §8 寫明 Q1a–Q1c 的結果「會決定 P3-4 的 loss 清單」，這正是看結果才加對手的問題（main.tex「Post-hoc rivals」）。Q1c 結果和 loss 清單的對應要現在先寫死。
