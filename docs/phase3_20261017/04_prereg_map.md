## 1. 問題（一句話）

**預測每段 KV「之後會不會、多快再被用到」（舊論文說的「未來效用」），用來決定它的狀態，能比現在的做法省多少頻寬？**

- **狀態**只有三種：CPU（BF16）、CPU（INT4）、SSD（INT4）。**都會寫、不丟**（第一階段已經否決「丟掉」：猜錯時回來的人要等整段重算）。
- 預測只有一種：每個 session 多久之後會回來。用在三個決定上：先搬誰去 SSD、什麼時候先搬回 CPU、搬去時存成什麼精度。

## 2. 比哪些做法

| 代號 | 做法 | 要預測嗎 |
|:--|:--|:--|
| B0 | **論文的做法**：LRU，CPU 滿了才搬去 SSD，搬的時候壓成 INT4，回來才讀（Cake 還原） | 不用 |
| B1 | B0，但降級順序改成看使用次數（LRU-2；X1、X2 量到它是最強的簡單規則） | 不用 |
| B2 | B0＋請求進佇列就開始讀（CachedAttention 的做法） | 不用 |
| B3 | B0＋使用者開始打字就開始讀（X3；**需要客戶端回報**，另外列） | 不用（要提示） |
| O | **完美預測**：知道每個 session 何時回來，三個決定都做到最好；預取受 SSD 讀頻寬限制，和真正的讀取搶頻寬 | 完美 |
| O-順序／O-預取／O-精度 | 一次只開一種決定，看好處來自哪裡（只報告） | 完美 |

「最好的簡單做法」＝每一格裡 B0、B1、B2 中最好的那個（B3 另外比，因為它要客戶端配合）。

## 3. 量什麼

| 指標 | 意思 | 角色 |
|:--|:--|:--|
| **使用者回來時要從 SSD 讀的量** | 回來那一刻還要從倉庫搬多少（位元組） | **主指標** |
| SSD 讀寫的尖峰頻寬 | 每 1 秒窗口的讀＋寫，取 p99；**預取也算進去**，猜錯的預取是浪費 | 主指標（I/O 等效往後） |
| SSD 總寫入量、總讀取量 | 省了多少 | 報告 |
| 回來請求的等待時間（平均、p99） | 順便看 | 報告 |

**省多少**＝(最好的簡單做法 − 完美預測) ÷ 最好的簡單做法，兩個主指標各算一次。

## 5. 怎麼決定下一步（看真實機器，不挑最好看的格子）

**真實機器的點**（每張 GPU 分到的記憶體）：3090 約 63 GB → 看 64 GiB 那一格；H200 170 GB → 看 128 和 256 GiB 兩格；MI300X 約 435 GiB → 看 512 GiB 那一格。共用 SSD 的張數四種都看。

- **GO（開始訓練預測器、比較 loss）**：至少一台真實機器上，至少一份真實資料的「省多少」CI 下界 ≥15%（以 session 為單位 bootstrap），而且另一份真實資料在同一台機器上也 ≥5%。兩個主指標任一個成立即可。
- **NO-GO（寫成論文的 Step 3）**：所有真實機器、所有真實資料都 <5%。
- **其他：停下來問使用者。**
- 半合成（×2、×4）、合成資料、B3 只報告，不能單獨讓判定變 GO。

## 6. 用什麼跑、限制

- 模擬器沿用 X1 的（已驗證：預測換成「上次使用時間」時逐位元等於 LRU），加上頻寬記帳與 B1–B3。一次服務一個請求。排隊（X4）與 GPU 驗證留到 GO 之後：先在 3090 上一張卡一個設定，再到 H200 確認。
- 已知的模擬誤差：策略之間的差距有約 5–6 個百分點（第一階段量的），所以 GO 的門檻用 CI 下界 15%。
- 只用 CPU，不訓練任何模型（CLAUDE.md §8）。
