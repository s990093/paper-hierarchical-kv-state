> **狀態**：草稿 v2，2026-10-18 寫，取代 v1（v1 在 commit `d467ba9`）。還沒凍結、還沒跑任何地圖的格子。凍結＝使用者同意＋opencode 零前文審查改完＋commit，之後才跑**完整地圖**。凍結前只准做工具、驗證、量常數、合成資料上的方法開發（§7）。
> **為什麼改**：使用者 10/18：「我們只決定壓縮成什麼程度。搬去 CPU 還是 SSD，交給外層的系統（例如 vLLM）。外層的做法不要假設成一種，把常見的全部跑過，再加上 GPU 忙、CPU 忙這些情況，最後再說預測在哪些場景有用。」

## 1. 問題

**每個 session 的 KV 要存成什麼格式（壓縮程度），由「它之後會不會、多快被讀」的預測決定。搬到哪一層由外層系統決定。在各種常見的外層做法、機器忙閒、記憶體大小下，完美預測比固定的壓縮做法省多少頻寬？品質與等待時間會怎樣？**

- **不丟**：每段都存（第一階段否決了「丟掉」）。
- **只能往下壓**：寫進 CPU 時選一次格式；被外層搬去 SSD 時可以再壓更小，但不能變回原版（第二階段的理由：壓了就回不去）。
- **格式**：BF16、8-bit（Llama 用 FP8；Qwen 用 INT8，因為 Qwen 的 FP8 掉 32.8 分）、INT4（KIVI）、INT2（KIVI）。每種格式的大小、解壓時間、品質，照第二階段的實測（§5）。

## 2. 外層做法（場景，不是假設；預設參數照各系統的程式碼，見 X6）

| 代號 | 做法 | 代表 |
|:--|:--|:--|
| E1 | 只有 CPU 層，滿了趕最久沒用的；沒命中就重算 | vLLM 0.28 CPU offload |
| E2 | CPU＋SSD，CPU 滿了把最久沒用的搬去 SSD（使用者說的 case b） | LMCache |
| E3 | 一寫就同時寫一份到 SSD | SGLang write-through |
| E4 | 被用到第 2 次才寫 SSD | SGLang selective、Dynamo KVBM |
| E5 | 閒置超過 T 就搬去 SSD，T＝5 分、30 分、1 小時（使用者說的 case a） | Mooncake soft pin（預設 30 分） |
| E6 | E2＋請求一進佇列就開始從 SSD 讀 | SGLang HiCache、LMCache |

## 3. 比哪些壓縮做法

| 代號 | 做法 | 要預測嗎 |
|:--|:--|:--|
| C0 | 全部 BF16（不壓） | 不用 |
| C1 | **論文的做法**：CPU 放 BF16，搬去 SSD 時壓 INT4 | 不用 |
| C2 | 全部 INT4 | 不用 |
| C3 | 全部 8-bit | 不用 |
| C4 | 依長度：短的 BF16、長的 INT4（長度寫入時就知道） | 不用 |
| **O** | **完美預測**：知道每個 session 何時被讀、從哪一層讀、那時 GPU 忙不忙。之後會被讀的，選「品質過關、又最省的」格式；不會再被讀的，壓到最小（INT2） | 完美 |

「品質過關」照第二階段的判準：配對答對率差的 95% CI 下界高於 −2 分。INT2 的生成品質還在 MI300X 跑（stage 43），還沒有結果前，INT2 只能給「不會再被讀」的 session 用。

## 4. 量什麼

| 指標 | 角色 |
|:--|:--|
| **SSD 寫入＋讀取的總量**（位元組） | **主指標** |
| SSD 的尖峰頻寬（每 1 秒窗口的 p99，預取也算） | 主指標（I/O 會不會撞牆） |
| 被讀到的 KV 用了哪些格式；用了「品質沒過關」的格式的讀取次數 | 品質帳（O 一定是 0；別的做法照實報） |
| 回來請求的等待時間（平均、p99） | 報告 |

**省多少**＝(最好的固定做法 − O) ÷ 最好的固定做法。「最好的固定做法」＝每格裡 C0–C4 中，品質帳為 0、而且主指標最小的那個。

## 6. 怎麼決定下一步

**真實機器的點**（每張 GPU 的記憶體）：3090 約 63 GB → 64 GiB；H200 170 GB → 128 與 256 GiB；MI300X 約 435 GiB → 512 GiB。外層做法、共用 SSD 張數、GPU 忙閒都看。

- **GO（用真實資料訓練預測器、比 loss）**：至少一個真實機器的點、至少一種外層做法下，至少一份真實資料的「省多少」CI 下界 ≥15%（以 session 為單位 bootstrap），而且同一點、同一做法下另一份真實資料也 ≥5%。兩個主指標任一個成立即可。
- **NO-GO（寫成論文的 Step 3）**：所有真實機器點、所有外層做法、所有真實資料都 <5%。
- **其他：停下來問使用者。**
- 半合成、合成、敏感度只報告，不能單獨讓判定變 GO。
- 報告時列出**整張地圖**，並標出「在哪些外層做法、哪些機器上有用」：這就是使用者要的「最後再說預測在哪些場景有用」。

## 8. 限制（先講）

- 模擬器一次服務一個請求；排隊只在 E6 的「進佇列就讀」裡粗略模擬。GO 之後才上 GPU（3090 一張卡一個設定，再到 H200 確認）。
- 品質只有 32K 的實測；更長的 session 用 INT4 以下的格式時，品質標「未驗證」。
- 模擬器在策略之間的差距有約 5–6 個百分點的誤差（第一階段量的），所以 GO 用 CI 下界 15%。
