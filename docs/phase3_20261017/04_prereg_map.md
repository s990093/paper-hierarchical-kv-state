## 1. 問題

**每個 session 的 KV 要存成什麼格式，由「它之後會不會被讀、會讀多長」的預測決定。搬到哪一層由外層系統決定。在各種常見的外層做法、記憶體大小下，完美預測比「不用學的最好做法」省多少 SSD 頻寬？而且不能讓等待時間變差。**

- **不丟**：每段都存（第一階段否決了丟掉）。「不會再被讀就壓成 INT2」是合法動作裡最省的一個，不是丟。
- **只能往下壓**：寫進 CPU 時選一次格式；被外層搬去 SSD 時可以再壓更小，但不能變回原版（第二階段的理由：壓了就回不去）。
- **格式**：BF16、8-bit（Llama 用 FP8；Qwen 用 INT8，因為 Qwen 的 FP8 掉 32.8 分）、INT4（KIVI）、INT2（KIVI）。大小、解壓時間、品質照第二階段的實測（`05_format_table.md`）。
- **「何時讀」只影響等待時間**：主指標是位元組，位元組只看「會不會被讀、讀多長」。O 不用「何時讀、從哪層讀、GPU 忙不忙」來選格式。
- **和第一階段 X1、X5 的差別**：X1 的動作有「丟」；這裡不准丟，只能選格式。新的是「只決定格式」這個動作空間，加上外層做法的地圖。

## 2. 外層做法（場景，不是假設；預設參數照各系統的程式碼，見 X6）

| 代號 | 做法 | 代表 |
|:--|:--|:--|
| E1 | 只有 CPU 層，滿了趕最久沒用的；沒命中就重算 | vLLM 0.28 CPU offload |
| E2 | CPU＋SSD，CPU 滿了把最久沒用的搬去 SSD（使用者說的 case b） | SGLang `write_back` 選項、Mooncake `offload_on_evict`（預設關）。LMCache 的預設其實是寫穿，算 E3（X6） |
| E3 | 一寫就同時寫一份到 SSD | SGLang write-through（預設）、vLLM tiering、LMCache in-process |
| E4 | 被用到第 2 次才寫 SSD | SGLang selective、Dynamo KVBM |
| E5 | 閒置超過 T 就搬去 SSD，T＝5 分、30 分、1 小時（使用者說的 case a） | Mooncake soft pin（預設 30 分） |
| E6 | E2＋請求一進佇列就開始從 SSD 讀 | SGLang HiCache、LMCache |

## 3. 比哪些做法

### 3.1 不用學的做法（對手）

| 代號 | 寫進 CPU 時 | 搬去 SSD 時 | 參數（每格取對 O 最不利的那個） |
|:--|:--|:--|:--|
| C0 | BF16 | 不變 | — |
| C1（論文的做法） | BF16 | INT4 | — |
| C1-8 | BF16 | 8-bit | — |
| C2 | INT4 | 不變 | — |
| C3 | 8-bit | 不變 | — |
| C6 | 8-bit | INT4 | — |
| C4 | 長度 ≤ 門檻 → BF16，否則 INT4 | 不變 | 門檻 8K、16K、32K |
| C4r | 長度 ≤ 門檻 → INT4，否則 BF16 | 不變 | 門檻 8K、16K、32K |
| D-len（延後決定） | BF16 | 那時的長度 ≤ 門檻 → INT4，否則不變 | 門檻 8K、16K、32K |
| D-idle（延後決定） | BF16 | 那時已閒置 > τ → INT2；否則照 D-len（門檻 32K） | τ＝5 分、30 分、1 小時、4 小時 |

- D-len、D-idle 是「延後決定」的雙胞胎：只用搬去 SSD 那一刻已經知道的事。第一階段的結論就是「延後決定」，所以預測要贏，必須贏過它們。
- 「每格取對 O 最不利的」＝在完整樣本上選位元組最少、而且通過等待時間護欄（§4）的參數，之後 bootstrap 時固定。這是讓對手變強，所以是保守的，不算替我們的方法調參。

### 3.2 完美預測（參考線）

| 代號 | 知道什麼 | 怎麼選 |
|:--|:--|:--|
| **O** | 之後會不會被讀、最長讀到多長 | 寫進 CPU 時、搬去 SSD 時各決定一次：之後還會被讀 → 在之後最長的讀取長度下「品質過關」、位元組最少的格式；之後不會再被讀 → INT2 |
| O-len | 只知道之後最長讀到多長 | 每段都當成會被讀 |
| O-reuse | 只知道之後會不會被讀 | 會被讀的，用「現在的長度」選格式（像不用學的規則一樣）；之後可能長到沒驗證的長度，代價記在重算 |
| O-loose（只報告） | 同 O | 假設 32K 過關的格式在任何長度都過關 |

**拆解（只報告）**：兩種順序都報：O − O-len（知道「會不會再被讀」值多少）、O − O-reuse（知道「會讀多長」值多少）；O-len 對 C4r、O-reuse 對 D-idle（各自最像的、不用學的版本）。

### 3.3 讀取時的品質規則（所有做法都一樣，O 也是）

- 「品質過關」：第二階段的**生成**品質判準（配對答對率差的 95% CI 下界 > −2 分），只在 32K 量過。長度 ≤ 32,768 token 的讀取，用量過的結果；**更長的讀取一律算「沒驗證」**；只有 teacher forcing 的格式（INT2-KIVI 等）一律沒驗證；BF16 在任何長度都過關。
- **讀到「在這個長度沒驗證過」的格式 → 從那一段開始重算，不用它**。所以品質一律安全；猜錯的代價是重算，記在重算量與等待時間。
- 品質帳（用了沒驗證格式的讀取次數）因此一定是 0，留著當檢查。另外記「意外重算」：次數、block 數、token 數。

## 4. 量什麼

| 指標 | 角色 |
|:--|:--|
| **SSD 位元組＝寫入 ＋ 只載入的讀取量** | **唯一的主指標**。「只載入的讀取量」＝回來的請求要用的、存在 SSD 上的 block 全部讀進來的量，只和放置有關，不隨 GPU 忙閒、SSD 共用、Cake 會合點變 |
| 回來請求的等待時間（平均、p99） | **護欄**：主視角下（§6）不能比 C0 慢超過 5%。沒過護欄的做法不能當「最好的對手」 |
| Cake 實際的 SSD 讀取量 | 報告（會隨會合點變） |
| SSD 需求量的 1 秒 p99（不受頻寬限制）、SSD 滿載的時間比例（≥95% 頻寬的 1 秒窗口） | 報告（I/O 會不會撞牆）。窗口範圍＝資料片段的開頭到結尾，每個做法都一樣；兩邊都是 0 時記「無定義」 |
| 意外重算、重算 token、被讀到的 KV 用了哪些格式 | 報告 |

**省多少**＝(最好的對手 − O) ÷ 最好的對手。「最好的對手」＝§3.1 所有做法（含參數）裡，通過等待時間護欄、位元組最少的那個；在完整樣本上選定，bootstrap 時固定。

- **NO-GO（寫成論文的 Step 3）**：所有進判定的真實資料、所有主格，同時 CI 上界都 <5%。
- **其他：停下來問使用者。**
- 半合成、合成、敏感度、O-loose、拆解只報告，不能讓判定變 GO。
- 報告時列出**整張地圖**，標出「在哪些外層做法、哪些記憶體大小下有用」：這就是使用者要的「最後再說預測在哪些場景有用」。

## 8. 限制（先講）

- 模擬器一次服務一個請求；排隊只在 E6 粗略模擬（一張 GPU 先來先服務）。GO 之後才上 GPU（3090 一張卡一個設定，再到 H200 確認），並用小段資料和真實的 vLLM＋LMCache 對一次位元組。
- 重播是開迴路（照資料的到達時間）；閉迴路不在這輪。
- 品質只有 32K 的實測；更長的讀取一律算沒驗證，所以會重算（§3.3）。64K、128K 的品質（MI300X 44a–c）出來後，可以另報一版，但判定照凍結時的格式表。
- bootstrap 是在一次模擬的結果上，以 session 重抽歸屬給它的位元組；session 之間透過 LRU 的互相影響固定不動。
- session 引擎是整個 session 一起趕，真實系統是 block 層級、尾端先趕；只用 block 引擎的 E2 當敏感度。
- E6 的 k 張 GPU 各自算 SSD 尖峰，沒有把共用同一顆 SSD 的流量加總（尖峰只報告）。
- 模擬器在策略之間的差距有約 5–6 個百分點的誤差（第一階段量的，是等待時間的誤差，不是位元組），所以 GO 用 CI 下界 15%。
