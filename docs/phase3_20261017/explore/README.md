## 2. 九個方向與判準

### X1　oracle 拆解：猜對「誰回來」到底值多少，值在哪一種決定上？〔模擬，CPU〕
- **問題**：延後設計（BF16 進 CPU、滿了降級、降級時 INT4、Cake 還原）下，把 oracle 拆成四個元件，一次只開一個：O-降級順序（Belady）、O-丟掉（不回來的直接丟）、O-預取（回來前搬回 CPU，受慢層讀頻寬限制、和需求讀取共用頻寬）、O-不寫慢層（不回來的不寫）。每個元件都對上「機制相同、只差資訊」的最好非 oracle 對手（LRU、LRU＋不寫慢層、LRU＋2-hit、ARC、S3-FIFO、LRU-K、GDSF 類成本÷大小、Pensieve 式、依近期的預取）。
- **格子**：Mooncake conversation、toolagent（原始長度；session 用前綴鏈重建，重建規則和驗算要寫）；CPU 128／256／512／1024 GiB；慢層＝本地 SSD 限速 6.98 GiB/s、b\*＝32 的 1.47 GiB/s、NFS 0.331 GiB/s；GPU 閒／忙（2.07×）；還原＝Cake／只載入；負載＝trace 原始時間（一次服務一個請求，和第一階段相同），併發另見 X4。
- **判準**：
  - **有看頭**：某個元件在至少一個真實 trace、至少 2 種 CPU 大小（同一個慢層與 GPU 狀態下）讓回來請求的平均 TTFT 比最好的對稱對手快 ≥15%。
  - **死路**：四個元件在所有格子都 <5%。
  - 其他＝**可能**。
  - 另外報告（不改判定）：Cake 對只載入的 headroom 比值（≤0.5 的格子占多數＝「Cake 縮小預測的價值」）；oracle 是否真的不慢於所有對手（違反要列出）。

### X2　回來時間猜得到嗎？LRU 以外有沒有訊號〔無參數統計，CPU〕
- **問題**：「贏家由回來順序決定」（D3）不代表順序可預測。看真實 trace 的回來間隔：Kaplan–Meier 曲線、依「已閒置多久」的 life-table hazard（hazard 隨閒置時間單調下降時，LRU 本來就接近最好）、依輪數／上一次間隔／上一輪輸出長度分箱的條件分布。
- **比的分數**（全部無參數）：S0＝LRU（閒置越久越晚回來）；S1＝上一次間隔；S2＝輪數；S3＝上一輪輸出長度（Bidaw）；S4＝上一次間隔減掉已閒置時間。在「同時閒置的 session」快照上算 Harrell C-index（處理右設限）。
- **資料**：有 session 與真實時間戳的 trace（Mooncake 重建、Bailian 若可用、WildChat 若可用；CacheWise 只報告）。
- **判準**：
  - **有看頭**：在至少一個 ≥1,000 session 的真實 trace 上，某個 S1–S4 的 C-index 比 S0 高 ≥0.05。
  - **死路**：所有 trace 上都沒有一個比 S0 高 ≥0.02。
  - 其他＝**可能**。hazard 形狀只報告。

### X3　回來前幾秒的現成提示：不用長期預測就能預取嗎？〔算術＋模擬，CPU〕
- **問題**：使用者開始打字、agent 發出工具呼叫（工具時長大致可知）、請求進入佇列（CachedAttention 的做法）都是「回來之前」就看得到的訊號，不需要猜幾分鐘後的事。這些訊號給的提前量夠不夠把慢層還原藏起來？
- **算法**：需要的提前量＝該 session 從慢層還原的時間（依層、依長度、BF16／INT4，用 MI300X 常數）；拿得到的提前量＝(a) 打字時間（新一輪使用者輸入的 token 數 ÷ 打字速度，速度取自 HCI 文獻並附出處；貼上的內容不是打字，所以這是上界）、(b) 使用者思考時間（上一輪回應結束到下一輪請求，任何預取的上界）、(c) 工具呼叫時長（有資料的話）。報「可藏起來的比例」，並比整份預取與只預取 Cake 會合點之後的後段。
- **判準**：
  - **有看頭**：在至少一個真實 trace、至少一個 Cake 帶內的慢層（0.33–4 GiB/s）上，用 (a) 或 (c) 能藏起中位數回來 session ≥50% 的慢層還原時間。
  - **死路**：所有層、所有訊號都 <20%。
  - 其他＝**可能**。(b) 只當上界報告。

### X4　很多人同時回來時，尾端延遲有沒有預測能解的問題？〔模擬，CPU〕
- **問題**：第一階段說單卡有足夠的閒置時間給延後版（ρ_KV 最大 0.99）。但預取需要閒置時間，突發的回來會讓還原互相搶 I/O 和 GPU。用 trace 原始到達時間（Mooncake 約 3.4／6.7 req/s〔審查估算，自己重算〕）和 `m8_conc_sim` 的併發模型，比「看得到未來的閒置時預取」和「回來才還原（Cake）」以及「依近期的閒置時預取」。
- **判準**：
  - **有看頭**：在 GPU 利用率 ≤80% 的至少一個設定，oracle 預取讓回來請求的 p99 TTFT 比最好的對稱對手低 ≥20%。
  - **死路**：所有設定都 <5%。
  - 其他＝**可能**。GPU 利用率 >80% 的格子只報告（那是過載，不是預測問題）。
- **注意**：CLAUDE.md §8 禁止在平台 A 下多租戶結論；這是 MI300X 常數的模擬，標〔模擬〕，不寫成 3090 的結論。

### X5　精度×容量：每個 session 該留 BF16、在 CPU 壓成 INT4、搬去慢層、還是丟？〔模擬，CPU〕
- **問題**：第二階段量到：INT4 在慢層省時間、在真實 CPU 層反而慢（反量化搶 GPU），但 INT4 讓容量變 3.2 倍（main.tex §5.1、§6.3）。所以「CPU 裡放 INT4」是用還原速度換容量。這個取捨會不會隨 session 的回來時間而不同，讓預測變得有用？
- **比較**：oracle（知道回來時間，四選一）vs 固定規則：R1＝論文設計（CPU 放 BF16，降級時 INT4 進慢層）；R2＝CPU 全放 INT4；R3＝CPU 先 BF16，滿了在 CPU 裡壓成 INT4，再滿才進慢層；R4＝R3 但依近期決定誰先壓。每個 block 的還原與反量化成本用第二階段的實測（`results/m10_*_mi300x/` 的 summary 與 breakdown，標 run_id）。
- **判準**：
  - **有看頭**：在至少一個真實 trace、至少一種 CPU 大小，oracle 比最好的固定規則快 ≥15%（回來請求平均 TTFT）。
  - **死路**：所有格子都 <5%。
  - 其他＝**可能**。

### X6　真實系統怎麼做、在哪裡出事〔讀程式碼＋文件＋issue，不用 GPU〕

  - 其他＝**可能**。

### X7　換到 3090：成本常數變了，會不會出現 MI300X 上沒有的情況？〔GPU 實測，一張卡〕
- **問題**：3090 的重算比 MI300X 慢很多、PCIe 是 4.0，所以會合點、Cake 有用的頻寬帶都會移動。第一階段在 MI300X 上 CPU 層的會合點只在 block 0–3（main.tex §4.1），所以「讀取時決定」在 CPU 層幾乎沒事做。在 3090 上呢？
- **要量**（照 CLAUDE.md §4.1 記錄、`gpu_guard` 防污染）：用 `code/m7_restore_harness.py`／`m7_model.py`，Qwen2.5-7B-1M 與 Llama-3.1-8B（放得下的長度）在 3090 上的 f(i)、pinned H2D／D2H 頻寬、GPU 忙（背景 matmul 0.7 duty）時重算變慢幾倍、INT4／FP8 每個 block 的反量化時間；再用 Cake 的兩條線模型算 CPU 層與 b\* 層的會合點，和 MI300X 並列。
- **判準**：
  - **有看頭**：3090 上真實 CPU 層的會合點 ≥8 個 block（或 Cake 有用的頻寬帶涵蓋 3090 的 CPU 層頻寬），也就是出現 MI300X 上沒有的「讀取時決定很重要」的區域。
  - **死路**：3090 的會合點和頻寬帶都落在 MI300X 已經涵蓋的範圍內。
  - 其他＝**可能**。
- 量到的常數另外寫成 `results/p3_explore/x7/constants_3090.json`，給 X1、X4、X5 之後加跑用。

### X8　agent 工作負載與長 context：問題會不會變大？〔模擬＋算術，CPU〕
- **問題**：agent 的工具呼叫讓 session 在幾秒到幾分鐘後一定回來（Continuum 用工具時長設 TTL 把 KV 釘在 GPU）。長 context（64K–128K）讓放錯層的代價變大、能同時放的 session 變少。這兩種情況下，猜對回來時間的價值會不會比 Mooncake 大很多？
- **比較**：GPU 釘住（TTL）／CPU／慢層／丟，四種去處的 oracle vs 固定規則（LRU、固定 TTL、Continuum 式「工具時長的歷史中位數」要事先固定，不能用測試段估）。資料：CacheWise（只報告，94 個 session）、有工具時長的公開資料（找得到的話）、Mooncake toolagent。長 context 用第一階段 f(i) 的線性外插（標〔外插〕），並列出 128K 冒煙的那一次量測只能當參考（RUNLOG_MI300X 12.2）。
- **判準**：
  - **有看頭**：至少一個 ≥1,000 session 的工作負載上，oracle 比最好的固定規則快 ≥15%。
  - **死路**：所有工作負載都 <5%。
  - 其他＝**可能**。
