## 0. 一句話

**「猜對誰會回來」值錢的地方很窄。** 它只出現在 CPU 只裝得下最近約 1 分鐘歷史、一次服務一個請求的設定裡。在那裡，最大的一塊是**預取**，而預取的大部分好處，用「使用者開始打字」這種回來前幾秒的提示就拿得到，不需要預測。真正需要學的只剩「降級順序」裡 LRU-2 拿不到的那一部分，可是 X2 用簡單訊號猜不到它，學不學得到也還沒測。換成併發（X4）、真實的 agent trace（FreeInference）、或容量放大到 1 TiB，空間就消失了。

## 3. 跨方向發現的有效性問題（會影響任何後續判定）

1. **trace 太短會製造假的「不回來」**（X9 T3）：1 小時窗下 WildChat 14.6%、FreeInference 47.5% 的「最後一輪」其實之後有回來。所有用到「不回來」的 oracle 都要做截尾檢查。
2. **Mooncake 的兩份 trace 幾乎是同一份**（X5 發現，X1、X4、X8 驗算）：conversation 的 12,031 個請求有 10,938 個（90.9%）在 toolagent 一模一樣。只能算一份證據；而且它沒有 session id，用前綴重建，寬鬆規則會把整份併成 17／27 棵大樹。
3. **一次一個請求的模型 vs 併發模型結論相反**：X1 的預取空間 40% 以上，X4 加上排隊後 p99 只剩 3.75%（但 X4 的平均值有 10.6%）。下一輪要用同一個模擬器同時有兩者。
4. **真實系統先丟尾端、只認最長前綴**（X6）：X1、X5 的模擬器是整段 session 搬，沒有「頭不在、尾在」。
5. **oracle 不是上界**：X1 有 175 列 oracle 比某個對手慢（幾乎都在 NFS），X4 有 102／411。貪婪 oracle 只能當參考線。
6. **成本常數**：X1–X9 都用 MI300X 常數；harness 重算比 vLLM 慢 1.7–2×（只有 X4 做了 f×0.5 的敏感度）。3090 的常數（X7）讓 CPU 層變得像 MI300X 的本地 SSD（7 GiB/s 對 6.98），所以用 3090 常數重跑 X1、X5 時，結論可能不同，例如「CPU 裡放 INT4 是拿速度換容量」在 3090 上不成立。

## 4. 我的建議：下一步怎麼走

**預測器的訓練（你想做的部分）現在還不能開始**：
- 只有「降級順序」需要學，它的空間只在很窄的設定裡；
- 而那個設定在併發與真實 agent trace 上都還沒確認存在；
- CLAUDE.md §8 也規定要先過 oracle 判定。

建議先跑一輪**收斂實驗**，事先登記、判準先寫死，並先請 opencode 做零前文審查：
1. **統一的模擬器**：X1 的四個 oracle 元件＋X4 的併發與排隊（加 chunked prefill，避免 head-of-line）＋block 層級的尾端淘汰（X6）＋截尾檢查（X9）。工作負載用 Mooncake strict、Bailian coder、FreeInference，常數用 MI300X 與 3090。
2. **提示式預取**：在同一個模擬器裡，用 X3 的打字／工具提示做預取，量它拿到 O-PF 的多少。
3. **停損點**：降級順序對 LRU-2 的空間，在 (1) 的設定下若仍 ≥15%（session-cluster bootstrap CI 下界，多個 trace），才進入預測器與 loss 的比較（P3-4，照 `02_predictor_inventory.md` §5 的消融設計）；否則照實寫成論文的 Step 3：「延後設計下，預取用短期提示就夠，降級用 LRU-2 就夠，預測不值得做」。

**論文角度**：不論停損點結果如何，現在已經有一條站得住的故事延伸：
- 「延後」把決定移到資訊最多的時候；
- 而回來前幾秒的提示，正是最靠近讀取的資訊；
- 這和 Step 1、Step 2 的主線一致。
