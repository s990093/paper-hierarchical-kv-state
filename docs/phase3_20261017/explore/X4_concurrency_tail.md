## 1. 問題與要證明什麼

**問題**：第一階段說「單卡有足夠的閒置時間給延後版」（main.tex §4.5，ρ_KV 最大 0.99）。但預取也要閒置時間；很多人同時回來時，還原會互相搶慢層讀頻寬和 GPU。這時候「先知道誰會回來、在閒置時先搬回 CPU」能不能把尾端延遲壓下來？如果能，第三階段就有一個「值得預測」的問題。

**要證明的**：在 GPU 不過載（利用率 ≤80%）的負載下，**看得到未來的閒置時預取**（OP）比「機制相同、只差資訊」的最好對手（回來才還原 NP、佇列預取 QP、依近期 RP、依上次間隔 GP）讓回來請求的 p99 TTFT 低 ≥20%（有看頭）；或所有格都 <5%（死路）。

**白話名詞**：
- **佇列預取（QP）**：請求已經到了、在 GPU 前面排隊，這段時間先把它在慢層的 KV 搬回 CPU。資訊是確定的（佇列看得到），不用預測。CachedAttention 的做法。
- **閒置時預取（IP）**：GPU 沒事做、也沒人排隊的時候，猜誰快回來，先搬。要猜。
- **頭端阻塞**：一張 GPU 一次做一個 prefill，前面有一個很長的 prefill（Mooncake 最長 247 個 block，以 MI300X harness 的 f(i) 約 34 s），後面到的全部要等。
- **unit**：抽樣單位（§2.7）。

### 2.2 策略（對手機制對稱，只差資訊）

所有策略共用同一套 LRU、升回、降級、Cake。差別只在**預取**：

| 名稱 | 佇列預取（QP） | 閒置時預取（IP） | 資訊 |
|:--|:--|:--|:--|
| **NP** | 無 | 無 | 回來才還原（Cake 原樣） |
| **QP** | 有 | 無 | 請求在 GPU 佇列裡等的時候，用慢層讀通道把它在慢層的 block 先搬回 CPU（CachedAttention 式；零提前量、看得到的資訊） |
| **RP** | 有 | 依近期：最近被存取的慢層 block 先 | 只看過去 |
| **GP** | 有 | 依「同一 session 上一次的間隔」：預測下次＝上次到達＋上次間隔；沒有上一次間隔的不預測；已過期的不預取 | 只看過去（無參數規則，X2 的 S1） |
| **OP** | 有 | 看得到未來：真實下次存取時間最早的慢層 block 先 | **oracle** |
| OPn | 無 | 同 OP | oracle（只報告：看 QP 的貢獻） |

**預取機制（全部一樣）**：
- QP：服務中的請求還原完、慢層讀通道空下來之後，依佇列順序、每個請求由後往前，把慢層 block 讀回 CPU；輪到那個請求開始服務就停止送新的讀。
- IP：**只在 GPU 閒、佇列空的時候**做；一次送一個 block 的讀（不可中斷），下一個請求到達就停止送新的讀（停止規則是因果的，所有策略一樣）；還沒讀完的那一個 block 會讓到達請求的需求讀取排在它後面（預取的代價）。
- CPU 沒空間時：淘汰 LRU 那一個，**但只有在它的預測下次使用晚於候選 block 時**才換（RP 用最後存取時間、GP 用上一次間隔、OP 用真實時間；QP 不淘汰佇列中請求要用的 block）。不成立就停止這個空檔的預取。
- 預取進來的 block 放在 LRU 的最新端。慢層讀通道是同一條（需求讀取、QP、IP 共用；寫入干擾照 k_read）。

### 2.4 指標與判定（照 explore/README §2 X4 的字面）

- **回來請求**：前綴裡含有更早某個請求最後一個完整 block（block ≥1；同 D4 的 parent 定義）的請求。
- **TTFT**＝到達 → 新 prefill 結束（含排隊、還原、新 prefill）。
- **主指標**：回來請求 TTFT 的 **p99**；同時報平均、p90、中位數、只算還原的部分、排隊的部分、全部請求的總和。
- **GPU 利用率**＝GPU 服務時間總和 ÷（最後一個請求結束 − 第一個到達）。一格的利用率＝NP 在該格 3 個 seed 的平均。
- **headroom**（每格每 seed）＝(p99_最好對手 − p99_OP) ÷ p99_最好對手；最好對手＝NP、QP、RP、GP 中 p99 最小的。
- **一格通過 20%**：3 個 seed 裡至少 2 個 headroom ≥20%，而且 seed 中位數 ≥20%。**5%** 同理。
- **能進判定的格**：GPU 利用率 ≤80%，**而且**該子集 session 數 ≥1,000（explore/README §1 的門檻；p 小時 session 不夠的格只報告）。
- **判定**：
  - **有看頭**：至少一格能進判定的格通過 20%。
  - **死路**：所有能進判定的格，headroom 的 seed 中位數都 <5%。
  - 其他＝**可能**。
- 只報告、不改判定：利用率 >80% 的格；ρ_KV ≥1（降級寫入持續超過慢層寫入頻寬）的格另外標出；平均 TTFT 的同樣判定；OP 是否不慢於所有對手（違反要列）；OPn vs QP；f×0.5。

## 7. 如果要繼續

**我的建議：X4 照登記判死路，不再加軸。** 可以寫成一句負面結果：「在 FIFO 單 GPU、Mooncake 原始到達（抽樣到利用率 ≤80%）下，完美知道誰會回來的閒置時預取，對回來請求的 p99 只差 ≤3.75%；尾端是排隊造成的，佇列預取（不用預測）已經拿到預取的大部分好處。」

**如果要追**（最值得的一點，〔判讀〕）：預測的價值被頭端阻塞蓋住了。把排程換成不會頭端阻塞的（chunked prefill＋短的先、或 processor sharing），排隊就不再主導尾端，還原（OP 能砍 31–81%）才會露出來。

| 步驟 | 成本 | 會殺掉它的結果 |
|:--|:--|:--|
| 1. 在 `x4_sim` 加一個 chunked-prefill 排程（每步固定 token 預算、輪流服務），其他不動，重跑能進判定的 137 格 | 半天 | 換排程後排隊仍占 p99 的 >80%，或 OP 對 QP 仍 <5% |
| 2. 同時報 QP 和 OP：如果 QP 已經拿到大部分，問題就是「排程＋佇列預取」，不是預測 | 0 | OP 對 QP <5% |
| 3. FreeInference 全部 16 週、f(i) 不外插（只用 ≤40K token 的請求，或用 64K／128K 的實測 f） | 1 天 CPU | 長 context 的實測 f 和外插差很多 |
| 4. 任何正面結果都要上 GPU（P3-6），先事先登記 | 數天 | GPU 上 <10% |
