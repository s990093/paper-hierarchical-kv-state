### 1.2 今天新抓到的四個問題

**(1) P\* 是 vLLM 分層軟體的產物，不是硬體的。**
`qwen-awq`（主設定）的 SSD 階取回 96K 上下文花 62,328.9 ms，約 84 MiB/s【算術，由 `main.tex` 附錄數字換算】，只有同一顆 NVMe 裸讀的約 4–5%。

⚠️ `main.tex` 附錄第 1504 行寫的「NVMe 上 85% 不是 I/O」，用的是 Llama-BF16 那次 NVMe 量測，而 RUNLOG 發現 11 把那次標成「待查，不作為結論依據」（lookup 延遲累計 733 s）。所以這個論點改用 Qwen-AWQ 的常數支撐；SATA 上 Llama-BF16 的軟體開銷比較小（有效頻寬是裸讀的 1/1.29）。`qwen-awq` 那次量測是否也受同一問題影響，要查它的 guard 記錄。

用實測常數算三種讀回方式（`research_20260924/restore_modes.py`，【算術】）：

| 路徑 | 128K 前綴：只能前綴命中的最佳解 | Cake 式雙向重疊 | 雙向重疊時「前段被重算」的比例 |
|---|---|---|---|
| vLLM fs 階（實測 10.245 ms/block） | 83.9 s | 40.5 s（快 2.07×） | 51.7% |
| 同一顆碟的裸讀（0.42 ms/block） | 3.4 s | 3.1 s（快 1.09×） | 8.5% |

→ 換掉軟體路徑，「丟掉重算」這一階幾乎沒有存在的必要。**這跟 MI300X 實驗 #2 是同一類現象（軟體路徑主導傳輸成本），但機制不同**：3090 的 SSD 階是分層機制的查表、cascade 排程與 promotion；MI300X 的 CPU 階是每筆描述符的固定成本。兩個平台、兩種機制、同一個結論。

**(2) 「前面丟、後面存」在現在的引擎上做不到。**
- vLLM 的命中是一個 token 數，只能是一段從頭開始的前綴；官方文件寫明請求結束時 block 以反向順序放回，**刻意讓尾巴先被逐出**【網路，[vLLM prefix caching](https://docs.vllm.ai/en/stable/design/prefix_caching/)】。
- SGLang 的 radix cache 以 LRU「recursively evicts leaf nodes」【原文，[SGLang 論文](https://arxiv.org/pdf/2312.07104)】——也是從尾巴丟。
- MTDS 的「部分載入」定義為「載入命中的前綴、重算其餘未命中的 token」【原文，mtds2026 p.6】。
- 重算成本隨位置線性變貴，所以尾巴是最貴的。**前綴語意逼系統「前面載、後面算、從尾巴丟」——三個都是最貴的方向。**
- 可以推導（附錄 A）：若一段上下文都在同一階（例如 SSD）、而且計算與傳輸不重疊，那在前綴語意下最佳解只剩「整段載」或「整段算」兩種，交叉在長度約 2P\*；中間任何切點都比兩端差。Cake 的雙向重疊要成立，就得打破這個抽象。這變成故事 4。

**(3) SSD 寫入頻寬的絕對值用錯時間基準。**
`code/m4_sweep.py:274`：`ssd_write_mibps = 寫入量 ÷ trace_duration_s`，分母是 Mooncake trace 的真實時長（Kimi 整個叢集服務它的時間）。但即使是 oracle，單卡把 toolagent 串行跑完也要 21,038 s，是 trace 時長 3,537 s 的約 6 倍【A，RUNLOG 的 `21,037,931 ms` 與 `÷ 3,537 s`】。所以 `main.tex` §7.5「`tier_fs` 需要 4,666–4,892 MiB/s，超出 SATA QLC 26 倍」這種**單機可行性結論要重算**；「oracle 的寫入量是 `tier_fs` 的 1/4–1/7」是同一分母的比例，不受影響。遠端最新程式碼仍是這個寫法。

**(4) 9/19 三個關鍵實驗的數字目前不可追溯，而且 MI300X 的 CSV 全都不在 git 裡。**
`git ls-tree origin/main` 裡 MI300X 的 CSV 是 **0 個**：9/21 的 commit 寫「原始 CSV 留在 results/ 目錄但不進 git」，結果連 `connector_transfer_mi300x.csv`（30 列）、`cost_constants_mi300x.csv` 這種小摘要也沒進去。所以 MI300X 的每個數字目前只能追溯到那台機器上的檔案；`CLAUDE.md` §2 規定 < 1 MB 的摘要要進 git。

另外，`EXPERIMENTS_20260919.md` 寫明腳本在當時 session 的 scratchpad（`joint_s1`、`swapbench`、`confirm`、`uncertainty`），**未寫入 `results/`**。依 `CLAUDE.md` §4「沒有 run_id 的數字視同不存在」，91.8%／103.9%、12.9–16.3 µs、20.6% CI 這幾個數字在重跑並入庫前，**不能寫進論文，也不該當成定論告訴老師**（可以說「初步結果，正在依記錄協定重跑」）。

### Q2　「大家都沒統一標準，所以才只能跟 LRU、ARC 比，數據也比較亂」

**你的觀察是對的，但不能拿來當「只比 LRU」的理由**——老師已經明說 vLLM 是底座不是對手。查證後的具體證據與做法：

**結論：當「一階地圖」站得住，但自變數要從「硬體」擴成「硬體 × 軟體路徑 × 模型 × ctx × 負載」。** 完整表在 `research_20260924/kappa_map.md`（18 篇、每個規格附 URL、算術另標）。

**(a) 只看硬體，方向跟你的直覺相反**（參考模型 Llama-3.1-8B、MFU 0.5、PCIe 取 80%，【算術】）

| 卡 | κ_cpu | κ_ssd（SATA 0.55 GB/s） | κ_ssd（Gen4 NVMe 7 GB/s） | 讓 SSD 打平重算所需的碟頻寬 |
|---|---|---|---|---|
| RTX 3090 | 88 | 1.9 | 24 | 0.29 GB/s |
| A10（MTDS 用的） | 50 | 1.1 | 13.7 | 0.51 GB/s |
| A100 | 20 | 0.43 | 5.5 | 1.3 GB/s |
| H100 SXM | 12.7 | 0.14 | 1.7 | 4.0 GB/s |
| MI300X | 9.6 | 0.10 | 1.3 | 5.3 GB/s |
| B200 | 5.6 | 0.06 | 0.76 | 9.2 GB/s |

- **邊緣卡的 κ 最大**：算力弱，重算最貴；連 SATA 碟都比重算快（κ_ssd ≥ 1）。所以「邊緣上長請求重算比較好」**不是硬體給的**。
- **伺服器卡由碟的等級決定**：H100 要 4 GB/s 以上的碟、B200 要 9 GB/s 以上，才贏得過重算。你說的「server 跟 NVMe 跟 SSD 又差這麼多」，在這張表上成立。

**(b) 18 篇放上去的結果**：11 篇跟各自的硬體區間一致（包括 Strata、Cake；Cake 的表 3 能用公式在 12–20% 內重現）；3 篇不一致，都要加別的因子：MTDS（容量＋軟體）、Tutti（軟體路徑約 13×）、Bidaw（GPU 負載的機會成本）；4 篇動作不同、無法比。

**(c) 實測和規格差很多**：κ_cpu 在 3090 實測 6.81、規格 88.1（差 12.9×）；MI300X 實測 1.12、規格 9.6。兩平台實測只差約 6 倍。同一張 MI300X 上跨模型的 κ_cpu 就差 9.5 倍（1.08–10.25），主要來自描述符粒度。

**(d) 所以選 SOTA 的鍵不是 GPU 型號，而是五元組**（κ_hw, 軟體路徑倍數 X, 模型, ctx 分布, 負載）。問題是：除了 Tutti、Bottlenecks、LMCache、Strata 和我們兩個平台，**其他論文都沒揭露軟體路徑的有效頻寬**——這本身就是「大家沒統一標準」最具體的證據。見故事 6。

### Q4　資料集：「數據集根本不夠」「prefix hit 是 full 還是 partial？」「ShareGPT？Bidaw 的 trace？AdaptCache 的 LongBench 6 個？」

完整清單與計算在 `research_20260924/workloads_eval.md`（每個 trace 都上網查證、用公開檔自己算過）。

**(a) prefix hit 是 full 還是 partial？——文獻慣例是 partial，但沒有人寫清楚。**
同一份 Mooncake `toolagent` trace（無限容量），依定義可以是：

| 定義 | 命中率 |
|---|---|
| 請求「完整」命中（整個 prompt 都在快取） | **1.1%** |
| block 級（命中的前綴 block ÷ 總 block） | 55.3% |
| token 加權的連續前綴（Marconi 的定義） | 57.1% |
| 逐請求的命中比例取平均 | 66.9% |
| 請求「任一」命中（至少一個 block） | **100%** |

- 完整命中幾乎是 0，因為最後一個 block 通常含這一輪新打的字；任一命中幾乎是 100%，因為第一個 block 多半是共用的系統提示。「請求命中率」不說清楚是哪一種，數字可以在 1% 到 100% 之間任選。

- **報命中率一定要寫的四件事**：粒度與 block 大小；token 加權還是請求級；只算 GPU 還是任一層；有沒有排除暖機、容量是否有限。

### Q5　「多使用者看起來才能把數據衝高，之後也這樣做？」

**多使用者是必要條件，但報出來的倍數幾乎由「選哪個工作點」決定。**
- **為什麼必要**：單請求 benchmark 沒有跨請求的逐出，分層的價值是 0；MI300X 上壓力 1× 時 headroom 一律 0%【B】。
- **為什麼倍數會被放大**：文獻裡最大的倍數（LMCache 14×、Mooncake 525%、EvicPress 3.6×）都出現在 baseline 已經接近飽和的工作點——「同 TTFT 下的吞吐」這類指標在膝點附近會非線性放大。
- **Cake §5.7（逐字核對屬實）**：1 個 16K 的 prefix-caching 請求，加 22 個 32–448 token 的短請求（spiked distribution），完成時間 1.5 s → 1.19 s，吞吐 +26%。但它自稱「an example」，只跑一次；23 個請求裡只有 1 個有 prefix cache，所以量的是「一個重用請求加上別人的算力競爭」，不是多使用者重用。
- **反例**：3090 上 131K × 4 並行的 oracle headroom 是 0%【A】；MI300X 真實 trace 壓力 6–86× 時 headroom 反而只有 7–21%，壓力越高越低（重用太少）【B】；SAECache 在 Chatbot-Arena 反而慢 12–34%。
- **真實的並發其實不高**：TraceLab（43 位開發者、8 個月）同一個 5 分鐘內的活躍 session 中位數 1、p90 為 4。
- → **誠實的做法**：報整條負載曲線與膝點位置，不只報峰值比值；固定對照組；同時報 prefill-only 與端到端。另外，多使用者真正改變的是 κ 的有效值（GPU 被別人用時，重算的機會成本上升；Bidaw 的結論就要靠這一項才解釋得通）。

### Q6　「我在 MI300X 跑，但是是模擬機、SSD 有點慢，會影響嗎？」

- **不是模擬機**：K8s 容器、SR-IOV 1VF、實體整張 MI300X（SPX、304 CU、192 GiB），`rocm-smi`／`amd-smi`／`torch` 三條路徑互相對上。9/19 已經跟老師更正過「虛擬機」這個說法，**之後對外不要再用**。
- **慢的不是本地碟**：本地 overlay 底下是 Broadcom MegaRAID volume（不是 NVMe），64 GiB 測試循序讀 5,728 MiB/s；慢的是 **NFS**（循序讀 363 MB/s、隨機 128K 讀 118 MiB/s）與 **vLLM 的 SSD 路徑**（有效 1.3–3.2 GB/s）。
- **真正會影響的**：(i) 主機 PCIe、磁碟、NFS 與 7 個鄰居共用，量傳輸時要同時記錄鄰居狀態、重複取分佈；(ii) SSD 階放在容器的 `/var/tmp`，是暫態儲存，要寫進 threats to validity；(iii) 論文與 RUNLOG 裡寫的「本地 NVMe」要改成「本地 overlay（Broadcom MegaRAID volume）」。

### Q7　「怎麼判斷誰是 SOTA？看比較多篇？選 ICML 那種？跟我做的類似也算？」

三個直覺各對一部分（查新 §4）：
- **看篇數**：被當 baseline 的次數是好指標，但有兩個偏差：地板會贏（vLLM、LRU）；新論文會輸（Strata、Bidaw 太新，0 次）。要看「同一問題設定下、最近 12–18 個月、同儕審查過的論文拿誰比」。
- **看 venue**：只能當過濾器。Cake 是 ICML，但整條 I/O 路徑是模擬的；Pensieve、HCache 在 EuroSys。系統題目要看評測是不是在真實機制上。
- **跟我做的類似**：只有「問題設定等價」才算。把問題寫成五元組，至少前兩項要相同：(1) 決策變數；(2) 決策時點與可用資訊；(3) 目標與約束；(4) 負載型態；(5) 硬體型態。例：Cake 是「重算 vs 載回」格的 SOTA，但**不是**「寫不寫 SSD」格的 SOTA，因為第 2 項不同（Cake 假設 KV 早就全部存好）。
- **一套可以照做的判準**：① 問題設定等價；② 被後續同設定、同儕審查的論文拿來當 baseline，而且沒被打敗；③ 有開源、被併進 vLLM／SGLang／Dynamo／llm-d（審稿人會預期你比）；④ 頂會當過濾器；⑤ 引用數只當平手參考。
- **Semantic Scholar（2026-09-24 查詢，引用數／influential）**：Cake 38/6、Strata 32/4、AdaptCache 5/0、Bidaw 2/0、MTDS 1/0；對照 Pensieve 88/8、CachedAttention 252/21、LMCache 147/25、Mooncake 274/25、CacheBlend 268/40。**Pensieve 是本題最容易被忽略、卻最接近 Tiara 的一篇**——你對它的印象是對的（它依「重算成本 ÷ 閒置時間」優先逐出前段）。

### Q8　「也需要參考 DeepSeek 推理那塊的 KV 設計？」

**要，而且它對三個決策各給了一個生產端的答案**（κ 地圖 §5，全部附原始連結）：

| 決策 | DeepSeek 怎麼做 | 對 Tiara 代表什麼 |
|---|---|---|
| ① 幾個 bit | KV 精度**依成分靜態決定**：V3.2 的 sparse 路徑存 FP8（每層每 token 656 B），RoPE 的 64 維刻意留 BF16「for accuracy」；V4.1 的滑動視窗 KV 用 FP8、壓縮注意力 KV 用 FP4 | 生產端選的是「結構化、靜態、依成分」的精度，**不是**逐 block 動態選 bit → 支持故事 1「bit 是全域／結構化的開關」；是六態動作空間的反例 |
| ② 放哪一層 | 分散式碟（3FS，NVMe＋RDMA）服務 **56.3%** 的輸入 token（24 小時內 608B 中的 342B 命中 on-disk KV cache）；128K prompt 的首 token 延遲從 13 s 降到 500 ms；外部 KV 儲存在系統圖上標為「Optional」 | **SSD 階在生產中存在而且划算**——但那是 MLA（KV 只有 Llama-8B 的約一半）＋專用儲存網路的組合，κ_ssd ≥ 5，不能外推到 GQA 模型配單顆本地碟（MI300X 上 Llama-8B 實測 κ_ssd = 0.53） |
| ③ 重算還是載回 | 命中就載、沒命中才算；**沒有**逐 block 的重算判斷。命中條件：2024 年是「從第 0 個 token 起的相同前綴」、64 token 一單位；現行文件（V4 的滑動視窗之後）改成「只能完整命中某個已持久化的 prefix unit」 | MLA 讓 κ 放大 8.6 倍，所以「載回永遠贏」。**真正的問題變成命中粒度**——跟故事 4 的「命中＝前綴」是同一類抽象問題 |

另外兩點：
- **DSA（V3.2 的稀疏注意力）把「重算成本隨位置線性上升」的斜率壓平約 5 倍**（主注意力每個 query 只讀 top-2048）。所以 P\* 這種位置判準在 MLA＋DSA 模型上幾乎沒有意義，只適用於 GQA/MHA、κ ≈ 1 的平台。

### Q9　「可以先做理論模型」

**可以，而且有現成的最小路線**（OS 工具箱 §6，全部是提案、每一步都有可證偽的輸出）：
1. trace 前處理加單位斷言（Mooncake 的 `hash_ids` 是 512-token block，`CLAUDE.md` 規則 6）。
2. 用 Little's Law 驗模擬器的一致性。
3. **算 MRC**（LRU 與 OPT、成本加權版），在 C 與 3.77C 讀間隙 → 預測 BF16 headroom 與 INT4 殘餘 headroom，再跟 20.66%／2.02% 比對。
4. **下包絡（KV 五分鐘法則）**：以實測常數畫每個位置區段的下包絡、列出被支配的狀態；把描述符合併到 4 MiB 做 what-if。
5. **oracle 夾擠**：全 BF16 與全 INT4 各做一次 min-cost flow 精確解 + 多層 LP 鬆弛下界 → 報「真 headroom ∈ [下界, 上界]」。
6. 預測器重評：改用 good decision ratio 與 Kendall τ（不要再用 AUC）；實作「GBDT ⊕ tier_fs」切換。
7. Amdahl 對帳：每個主結果同時報 prefill 口徑與端到端口徑。

### Q10　「幫我查 OS 可以用的技巧或演算法，像是 Little's Law」

對 Tiara 最有用的前 8 項（OS 工具箱 §5，約 50 條、128 個 URL 的精選）：

| # | 工具 | 用在哪 | 風險 |
|---|---|---|---|
| 1 | Stack distance／MRC＋Wilson 1999 壓縮快取 | 事先預測「量化取代放置」；解釋 3090 的 +0.004% | 原理是教科書，新意要放在 KV 的量化證據 |
| 2 | 離線上下界：FOO、weighted caching min-cost flow、Gill OPT-UB/LB | 把貪婪 oracle 夾住；全 BF16／全 INT4 可精確求解 | 低，最便宜最有說服力 |
| 3 | 多態 ski rental／下包絡 | 統一三個決策、給跨硬體可重推的門檻、預測被支配的狀態 | 中 |
| 4 | Little's Law | 描述符固定成本的正確框架；還能反查資料一致性 | 高（Strata、vLLM 已用），當工具不當貢獻 |
| 5 | Amdahl | 一行字講清楚端到端天花板 | 不是貢獻，但審稿人一定接受 |
| 6 | Learning-augmented caching（Wei、Chłędowski、LARU…）＋LRB 的 good decision ratio | 解釋預測器為何輸、給便宜的修法 | LARU 已用於 LLM |
| 7 | 五分鐘法則 | 最好講的故事句 | MatKV 已帶進 KV（兩態、美元單位） |
| 8 | GreedyDual／GDSF／LHD／DTR | 解釋「剩餘價值 ÷ 位元組」、提供強 baseline | 這條路已擁擠 |

另外兩個跟你筆記直接相關的：
- **Little's Law 在我們資料上的實例**：X = C·S / (t0 + S/B)。MI300X 上 ≥32 KiB 的各列一致指向 t0 ≈ 13 µs，符合「與大小無關的固定成本」。這跟 Strata §3.1 是同一條式子，你筆記說「Strata 用 Little's Law 講故事」，我們可以用它**解釋自己的量測**，但不能當貢獻。
- **Delayed hits**（Atre et al. SIGCOMM'20；Strata 也處理）：同一段 KV 正在載入時又有人要它。這會影響模擬器的計時是否正確——Belady 的次序在有 delayed hit 時不是延遲最優。這是模擬器的已知缺口，要列進 threats。

### Q11　「token level 大家都沒做」「AdaptCache 可以用 token level」

要講精確：
- **token／page 級的「這一步要讀誰」很多**：Quest、ShadowKV、ArkVale、InfiniGen、DeepSeek 的 DSA。
- **放置系統多半以整段為單位**：EvicPress 明確寫「context-level, instead of chunk-level … or token-level」（p6）——可以引來劃界。
- **但位置級的放置已經有人做了一部分**：Pensieve 以 chunk 為單位逐出前段；AsymCache 用位置線性成本逐出；HCache 在 layer 維度決定哪些層不存。
- → 我們能主張的 token 級，是故事 4 的「區段命中＋寫入時跳過前段＋append-only 時會合點單調」這整套論證。查新判定為窄新，而且要先改引擎。

### Q12　「看起來趨勢要往 query 訊號去看；大部分都是普通統計、模型小、context 小、損失代價也還好，如果大一點可以改變格局？」

- **query 訊號**：對跨請求放置已被我們自己推翻（7 模型 AUC 0.480–0.500，故事 7）。對單請求內挑 token 仍然有效。
- **「大一點會改變格局」**：有一個支持的點——Seed-OSS-36B（階間差距最大、重算最貴）上學習式策略輸得最少（−9.7%，Llama-8B 是 −33.2%）。但目前只有這一個大模型點；而且 INT4 在 Seed-OSS 的撈針上也是 100%，所以「大模型」不一定讓放置更有價值，要看能不能降精度。

### Q13　「我的指標 perplexity、ROUGE、F1；老師的指標 TTFT、throughput」

- 品質當**約束**、速度當**目標**：在品質 ≥ 1−ε 的前提下比 TTFT／吞吐。
- 但現在品質不只是約束，而是**關鍵路徑**：放置策略只在「品質不允許降精度」時才有價值（故事 1、3）。你的指標在這裡是主角。
- CPU／SSD 的搬移是無損的（位元組層級），品質只跟精度階和丟 token 有關；但端到端輸出不保證位元相同（MI300X 上 36/120 輸出不同、答案差 8/120，原因是分塊邊界）。

### 故事 1：「INT4 一開，放置的空間就沒了」（量化與放置是替代品）

**一句話**：KV 放置的最佳化空間是 bit-width 的函數——全 BF16 時，最佳放置比最好的 baseline 少花 21% 的 prefill 時間；只把 KV 改成 INT4，這個空間就掉到 2–3.5%。

**起：大家以為量化與放置是正交、互補的。**
AdaptCache、EvicPress 的前提是「壓縮和逐出／放置要聯合最佳化」；KV Survey 說壓縮跟其他行為各做各的是「a missed opportunity for co-design」；9/14 的新論文 *Where Should the KV Cache Live?*（arXiv 2609.16215）直接寫「placement is orthogonal and complementary … we hold those fixed to isolate placement」。

**承：我們量到的是替代。**
- MI300X、Mooncake 真實 trace（前 4,000 請求、原始順序，prefill 口徑）：全 BF16 的 oracle headroom 20.66%／20.91%。
- 只改 `--kv-cache-dtype int4_per_token_head`、配 vLLM 原廠 LRU：拿到 oracle headroom 的 **91.8%／103.9%**，之後剩 **2.02%／3.52%**。
- 兩個 oracle 幾乎一樣（差 −0.08%）：oracle 靠「少重算」到達的地方，INT4 靠「多裝 3.77 倍」也到得了。【B，EXPERIMENTS #1，⚠️腳本待入庫】
- 3090 上另一個角度：逐 block 降成 INT8 在 LRU 排序下完全留不住（降級 780,108 次，總時間 +0.004%）。【A】

**轉：為什麼。**
headroom 來自「重用距離落在 GPU 容量之外、但在 CPU/SSD 之內」的存取。容量乘上 3.77，這批存取大多直接落進 GPU，剩下的主要是第一次出現、誰都躲不掉的 compulsory miss。

這可以寫成一條定律（OS 工具箱的「壓縮等效容量律」，由 Mattson 1970 的 stack inclusion 與 Wilson 1999 的壓縮快取分析推得，屬我們的推導）：

> 實體容量 C 裡，若壓縮比 r 的 block 常駐量為 U_c，則等效容量 C_eff = C + (1 − 1/r)·U_c；任何放置策略相對 LRU 還剩的空間 ≤ MR_LRU(C_eff) − MR_OPT(C_eff)。

它同時解釋兩個平台：
- 3090 逐 block 降級：被降的是最冷的，U_c ≈ 一個 block → C_eff ≈ C → +0.004%。
- MI300X 全域 INT4：U_c = 全部 → C_eff = 3.77C，落在 MRC 平坦區 → 剩 2–3.5%。
- 品質預算 q 時，等效倍數 m(q) = 1 / (1 − q·(1 − 1/3.77))。

**一句話版**：「量化值多少，取決於它把你推到 MRC 的哪裡；推到平坦區，放置就沒事可做。」這就是你筆記裡想要的「先做理論模型」：只要一條 trace 的 MRC，就能在跑模擬之前預測 BF16 與 INT4 各剩多少 headroom（§2 Q9）。

**合：所以我們提出。**
「幾個 bit」不該是逐 block 的放置動作，而是每個（模型, 任務族）一個、由品質約束決定的全域開關。放置策略只在「品質不允許降精度」的殘差區間才值得做。

**老師的三準則**：① ✅ 沒人量過「oracle headroom 隨 bit-width 的變化」，而且它推翻了領域的正交假設；② 🟡「量化 vs 放置」的取捨在多數情況下不存在；③ ✅ bit 從逐 block 動作變成全域開關，問題變簡單。

**新穎性威脅**（查新判定：窄化後存活）
- EvicPress：證明 joint 比 single 好 2.19×，但沒有 oracle 上界，不知道離最佳解多遠。
- AdaptCache：2-bit 下 adaptive 把 DRAM hit rate 從 38% 拉到 81%。但它混了逐條目的壓縮率、不是同品質比較、比的是 hit rate 不是延遲 headroom。
- 2609.16215：已經說過「放置策略沒那麼重要」，但它歸因於容量比與 batch-1，沒有 bit-width、沒有 Belady oracle。
- FlexGen：吞吐導向、極高壓力下，壓縮讓卸載更快，是**互補**。所以要找出「替代 → 互補」的轉折點。
- ⚠️ 寫法紅線：只能寫「headroom 隨 bit-width 崩潰」，**不能**寫「我們發現放置不重要」（那句已經有人講了）。
- ⚠️ 護城河要修正：9/20 的查新寫「沒有一篇有 Belady 上界」，但 Bidaw（FAST'26）§3.3.2 已經有 Belady **hit-rate** 上界。還空著的是：「以延遲為單位、多層、位置相依成本下的最佳 headroom，作為 bit-width 的函數」。
- ⚠️ 我們的 oracle 是**貪婪解**，所以 2.02% 只是真實 headroom 的下界。全 BF16 或全 INT4 時 block 等大，單層可以用 min-cost flow **精確**求解，要用它把真實值夾住。
- ⚠️ 要核對：實驗 #1 的 INT4 臂把 CPU/SSD 搬運「÷3.77」，這是實測，還是按位元組比例縮放？如果每筆描述符的固定成本主導（故事 2），INT4 只縮小每筆大小、不減少筆數，按比例縮放會**高估** INT4。

**還缺什麼**
1. 依記錄協定重跑並入庫（腳本進 `code/`、CSV 進 `results/`、附 run_id），並先核對上面兩個 ⚠️。
2. 壓力掃描，找出替代轉成互補的壓力點。
3. 在 3090 重做：用 INT8，因為 INT4 在 Qwen-AWQ 撈針是 0%。
4. 品質預算 q 的掃描：S1「先選 bit、再最佳化放置」vs S2「每個 block 聯合決定」。這要等故事 3 把 ε 量準。
5. 用 MRC 預測 headroom，跟模擬結果比。

### 故事 2：「頻寬是程式決定的，不是硬體」（實作決定傳輸成本）

**一句話**：在 vLLM 的卸載路徑上，KV 搬運速度由每筆描述符約 13 µs 的固定成本決定，所以同一張卡、同一條 PCIe，換個模型就差 17 倍；用「傳輸 ≈ 硬體頻寬」推出的放置結論都要重算。

**起：大家以為傳輸時間 ≈ 位元組 ÷ 鏈路頻寬。**
我們論文的 κ 表是這樣算的（「32 倍」就是從這裡來）；Bottlenecks（MLSys'26）雖然量到 sustained 只有峰值的 23%，但把它當成硬體給定，建議改用 NVLink-C2C。

**承：我們量到的是程式。**
- MI300X，同一條 PCIe Gen5、同一版 vLLM：CPU 階有效頻寬跨模型 2.27–38.28 GB/s（17.1×），組內變異 < 4.2%。【B，vLLM connector 計數器，30 次量測】
- microbenchmark：每筆描述符固定成本 12.9–16.3 µs，與 payload 大小無關，而且重現了三個端到端值（2.4 vs 2.27、4.7 vs 4.47、38.9 vs 38.28 GB/s）。【B，⚠️腳本待入庫】
- 根因在原始碼：vLLM 在 ROCm 上停用 Triton 快速路徑，改走 `hipMemcpyBatchAsync`，而且因 ROCm 7.2.1 的 bug 只能用 `numAttrs=0`。【B】
- 3090（CUDA）上是另一種機制、同一個結論：主設定的 SSD 階有效頻寬約只有裸讀的 1/18，CPU 階約只有 PCIe 的 1/7【A，κ 地圖 §4.3】。換成裸讀頻寬重算，P\* 從 37,717 變成 0。【算術】
- 外部佐證：同一台 H100 上，LMCache 與 vLLM 原生 CPU 載入差 4.5 倍（LMCache 論文 p13 表 5）；Tutti 的結論要成立，端到端 SSD 路徑須比硬體慢約 13 倍以上（κ 地圖 §4.3 的反推）。

**轉：為什麼。**
Little's Law：X = C·S / L。每筆的 L 固定在約 13 µs，X 就由每筆大小 S 決定，而 S 由模型的 KV 佈局決定（每層 32 KiB vs 整塊 1.5 MiB）。Strata §3.1 用同一條定律論證要放大 S——你筆記裡「Strata 用 Little's Law」那一條，在我們的資料上有了一個實例。

**合：所以我們提出。**
1. 描述符合併（依曲線，4 MiB 可到 48.5 GB/s，約 10.8×）。
2. 放置研究的成本常數必須在實際的實作路徑上量，並標明實作。
3. 修掉之後重算 κ、P\*，看哪些放置結論翻轉：κ_ssd 0.72 會不會變成 > 2？MI300X 上學習式策略的負面結果會不會反轉？

**老師的三準則**：① ✅ 跨模型 17× 加上機制；② ✅ 描述符合併讓「小 page（命中率好）vs 大傳輸（頻寬好）」的取捨消失（Strata 用 page-first layout 做過同一件事，我們是在 vLLM／ROCm 的 DMA 路徑上）；③ 🟡。

**新穎性威脅**（查新判定：一半被搶）
- Bottlenecks：achieved-vs-peak 23%，還點名 transfer granularity 是原因之一。
- SGLang PR #37701：AMD 上 `block_quota` 從 2 調到 8，24 → 55 GB/s。但機制是 kernel occupancy，不是描述符。
- SGLang PR #40278：TMA kernel，同期工作（9/19）。
- LMCache PR #5067：128 KB 門檻。
- → 只能寫到「DMA 路徑＋固定成本的數值＋跨模型 17×＋ROCm 根因＋修法＋對放置結論的影響」，**不能**寫「首次發現卸載沒吃滿頻寬」。
- ⚠️ 符號撞名：Bottlenecks 用 κ_crit，建議我們換符號。

**還缺什麼**
1. microbenchmark 入庫，並回原始 log 核對兩個數字（OS 工具箱用 `t0 = S·(1/X − 1/B)` 驗算）：1.5 MiB 那一列推回來約 13.0 µs，不是表上的 16.3 µs；≤16 KiB 的列隱含每筆只有約 2.7–2.8 µs，而且 16 KiB 比 32 KiB 還快，表示小描述符可能走不同路徑。INT4 的每層頁約 8.5 KiB，正好落在這個區間。

4. 修完重跑 M4／M5。

### 故事 6：「什麼時候才值得做聰明的放置？」（事前判準）

**一句話**：KV 分層值不值得做聰明策略，跑之前就能用五個常數加一條 MRC 算出來；文獻互相矛盾的結論，是各自站在這張圖的不同位置。

**起：大家以為每篇論文的結論都能互相比較、搬到別的硬體上用。**

**承：我們看到結論互相矛盾，而且會翻轉。**
- Strata 說長上下文重算「increasingly costly … an unattractive alternative」【原文 p5】；MTDS 量到命中很長時載入「non-linear slow-then-fast」，反而不載入比較好【原文 p6】。
- 把 18 篇的評測平台放上同一條 κ 軸（κ 地圖）：11 篇的結論跟它的硬體區間一致；3 篇不一致，而且都要加上別的因子才解釋得通——MTDS 要加容量與軟體、Tutti 要加軟體路徑（約 13×）、Bidaw 要加 GPU 負載的機會成本；另外 4 篇動作不同、無法比。
- 而且只看硬體時方向跟直覺相反：邊緣卡的 κ 最大（3090 約 88、A10 約 50），伺服器卡最小（H100 約 13、B200 約 6）。「邊緣重算、伺服器載回」這個直覺，硬體本身不支持。【算術，Llama-8B、MFU 0.5】
- 3090 上（ctx 16K、vLLM 路徑）SSD 被 DROP 支配【A】；MI300X 上用 M2 分塊法量，4 個模型有 3 個「SSD 永遠比重算便宜」，但換成 M3 校準的成本模型，多數模型的 P\* 落在 7K–14K【B，κ 地圖 §4.5】——連「同一平台的結論」都取決於量法。
- 同一份學習式策略：3090 拿到 82%，MI300X 輸 10–47%。【A】【B】
- 「最佳 baseline」是誰，會隨成本常數的抽樣翻轉（27%）。【B，⚠️待入庫】

**轉：為什麼。**
OS 工具箱給了兩條可以直接用的式子（我們的推導）：
- **Amdahl 上限**：端到端改善 ≤ prefill 佔比 × prefill 改善。MI300X 上 20.66% × 0.18–0.22 ≈ 3.7–4.5%，跟實測端到端 3.76–4.41% 對得上【算術】。
- **KV 的五分鐘法則（多態 rent-or-buy 的下包絡）**：每個狀態寫成「GPU 租金 h + 要用時的喚醒成本 a」，喚醒成本裡要含 `描述符筆數 × 每筆固定成本`。不在下包絡上的狀態永遠不該用（例如 κ_ssd < 1 的區段就不該寫 SSD）；P\* 只是 SSD 與 DROP 兩態的特例。修掉描述符問題後重算下包絡，就能**不實作**先預測哪些結論會翻轉。

放置的價值由四個可以事先量的東西決定：
1. **prefill 佔比**：Amdahl 上限，端到端 ≈ prefill-only × prefill 佔比（MI300X 是 18–22%）。
2. **能不能降精度**：ε(模型, 任務)，見故事 3。
3. **實作路徑的有效傳輸成本**：不是硬體頻寬，見故事 2。
4. **壓力與重用距離分布**：MRC。

**合：所以我們提出。**
一個「五個常數＋一條 MRC」的判準，事先算出 headroom 上限、哪類機制會贏；用兩個平台、7 個以上模型驗證；再把各篇論文的評測設定放上這張圖，解釋它們為什麼得出不同結論。**這就是你筆記裡「用 κ 把大家的設備列出來、再選對應的 SOTA」的正確版本**：變數要換成「實作路徑的 κ＋能不能降精度＋prefill 佔比」，不是規格表上的硬體 κ。

**老師的三準則**：① ✅；② ❌；③ ✅ 把「該選哪個系統」變成「量五個常數、查表」。

**新穎性威脅**：Bottlenecks 的 κ_crit 已經是一種判準；py-kvcache（arXiv 2609.11744）有硬體相依的 break-even 與准入；MatKV 有「ten-day rule」。差異在於：我們多了 bit-width 與 prefill 佔比、用 oracle 上界、跨平台驗證。

### 故事 3：「品質決定放置有沒有意義」（ε 是模型 × 任務）

**一句話**：KV 能不能降精度要看模型和任務，不看平均分數；而放置策略只在不能降精度的地方才有價值。

**起：大家以為量化的品質損失可以用平均分數代表**（GSM8K、LongBench 平均、NIAH）。

**承：我們量到平均分數會騙人。**
- GSM8K 五種精度差距 ±5pp，n=120、CI ±7–10pp，與 0 無法區分；同一批設定在撈針上可以掉 100pp。【A】【B】
- Qwen2.5-7B-1M 在 FP8／INT4 下是**退化生成**（重複字元、空字串），在 3K 就發生；Llama-8B、UltraLong-8B、Qwen3-MoE、Seed-OSS 在 129K 五種精度都是 100%。【B】
- RULER 多鍵 UUID 在 INT8 下掉一半。【A】
- FP8 E4M3 只有 3 bit 尾數，動態縮放也救不了。【B】

**轉：為什麼。**
精確取回某個位置的值，對 KV 雜訊很敏感；答案是整體統計量的任務（例如摘要）可以把雜訊平均掉；不同模型族對 outlier channel 的敏感度差很多。

**合：所以我們提出。**
一套「對量化敏感」的 ε 協定：按（模型 × 任務族）報保留率、大 n、附 CI、以最差任務為準。它決定故事 1 的全域開關能不能開，也就決定放置策略還剩多少價值。

**這條最適合你**：你筆記裡的 perplexity、ROUGE、F1，正是這條要用的指標。它不是配角，而是「放置研究到底有沒有價值」的關鍵路徑（9/19 的實驗 #1 也得到同一個結論：「新的關鍵路徑不是更好的 predictor，是把 ε 量準」）。

**老師的三準則**：① ✅；②③ ❌ → 論文裡的必要章節；除非做成 benchmark，否則不單獨成篇。

**新穎性威脅**：Yandex YAKV（context-intensive 任務）、KVTuner（逐層敏感度）、KVServe（97% 品質門檻）、KIVI／KVQuant（outlier channel）。

### 故事 4：「命中不該只是一段前綴」（區段命中＋前段不存）

**一句話**：把命中從「前綴」改成「區段」，前段就可以不存、要用時跟後段的載入並行重算。

**起：大家以為命中就是一段從頭開始的前綴，而且逐出從尾巴開始。**
vLLM 用一個 token 數表示命中，請求結束時 block 反向放回、讓尾巴先走【網路】；SGLang radix tree「recursively evicts leaf nodes」【原文】。

**承：我們看到三個「最貴的方向」。**
重算成本隨位置線性變貴（兩平台、7 個以上模型，R² ≥ 0.947）。所以前綴語意逼系統「前面載、後面算、從尾巴丟」。推導：同一階、不重疊時最佳解只剩整段載或整段算（交叉約 2P\*）。Cake 式雙向重疊在 3090 的 vLLM 路徑上比前綴最佳解快 1.5–2.3×，而且 43–72% 的前段是被重算的，這段根本不必存。【算術】

**轉：為什麼。**
因果依賴只要求「前綴的 token 相同」（hash 鏈已經保證），不要求「前綴的 KV 存在」。

**合：所以我們提出。**
命中改成區段集合；讀取用雙向重疊；寫入時跳過前段（多輪只往後追加時，會合點只會往後移，那段永遠用不到）；逐出從前段開始。

**老師的三準則**：① 🟡；② ✅ 「存得少」與「還原快」不再衝突；③ ✅ 換掉抽象層。

**新穎性威脅**（查新判定：部分已知、窄新）
- HCache：在 layer 維度做了「會被重算的層不必存」。
- CacheFlow（arXiv 2604.25080）：最佳切點 ℓ = L·T_io/(T_comp+T_io)，就是 1/(1+κ)。
- Pensieve（EuroSys'25）：依「重算成本 ÷ 閒置時間」優先逐出前段——你對 Pensieve 的印象是對的。
- AsymCache：位置線性成本的逐出。
- **五個反論**：會合點在讀取時會動（Cake 原文）；前段常被共享（系統提示）；要改引擎；P\* 與重疊切點不同；平台與量法相依（3090 換成裸頻寬後前段只剩 7–10%；MI300X 的 P\* 依量法從 < 0 到 14K）。
- **DeepSeek 的生產端也在同一個抽象上卡住**：現行 API 文件寫「只能完整命中某個已持久化的 prefix unit」，無法命中的部分只能重算（κ 地圖 §5.2）。這可以當「命中抽象是真問題」的佐證。

**還缺什麼**：在模擬器加「區段語意＋雙向重疊」模式，用「實作路徑修好後」的常數重估量級。量級小就放棄；量級大才做引擎原型（Cake 沒有開源）。

### 故事 5：「SSD 卡的是寫，不是讀」（寫入預算）

**已有人做**：HILOS（ASPLOS'26，耐久度）、HBF 特性化（arXiv 2608.11668，寫入准入條件 ρ > AC/S）、Dynamo KVBM（freq ≥ 2，「to extend SSD lifespan」）、SGLang HiCache selective write-through、vLLM `store_threshold`。

**剩下的**：把「每位元組省下的時間 S」寫成位置相依的 S(p) = max(0, 重算(p) − 取回)，再加上消費級 SSD 的實測價值（3090 的 QLC 持續寫入只有短測的 37%）。**併入故事 4 當一節。** 另外，INT4 讓寫入量也少 3.77 倍——又是一個「量化取代放置」的例子。

## 附錄 A：為什麼前綴語意下只剩「整段載」或「整段算」（推導）

設一段上下文有 N 個 block 都在同一階（例如 SSD），載入每個 block 的成本是常數 L，重算第 k 個 block 的成本是 R(k) = R₀ + a·k（遞增，兩平台實測皆為線性）。前綴語意下，系統只能「載入前 g 個、重算其餘」，總成本（計算與傳輸不重疊時）

C(g) = g·L + Σ_{k=g}^{N−1} R(k)，所以 C(g+1) − C(g) = L − R(g)。

因為 R 遞增：g 小於交叉點 k\* 時 R(g) < L，C 隨 g 上升；g 大於 k\* 時 C 隨 g 下降。所以 C(g) 在 k\* 有**最大值**，最小值只可能在兩端：g = 0（整段算）或 g = N（整段載）。整段載比較便宜的條件是 N·L < Σ R(k)，也就是 N ≳ 2k\* + 1，換成 token 約等於 2P\*。

**反過來的分工**（Cake：前面算、後面載，兩者並行）完成時間是 max(Σ_{k<m} R(k), (N−m)·L)，可以比兩端都好；在線性區間，被重算的前段比例約為 1/(1+κ)（CacheFlow 已經寫出同一個切點公式）。

**「前段永遠不必寫」的單調性論證**：會合點 m\*(N) 由遞增的 Σ R 與遞減的 (N−m)·L 的交點決定；N 變大（多輪只往後追加）時，遞減那條往上移，交點只會往右，所以 m\*(N) 對 N 單調不減。成立的前提：讀取時的算力與 I/O 速度不變（Cake 原文說會合點會隨資源移動）、重用是「往後追加」而不是「只重用前面一小段」、引擎支援非前綴命中。
