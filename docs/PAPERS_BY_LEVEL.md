# 論文內容說明：按 L0–L5 分層

> 這份是給自己讀的，用來搞清楚報告裡提到的每一篇論文到底在做什麼。
>
> **每篇的格式**：一句話 → 想解決什麼 → 怎麼做 → 實驗 → 成果 → 短板 → 跟我們的關係。
>
> **讀到多深**（每篇標題後面都會註明）：
> - **全文**：9/23 讀過全文。出處是 `docs/PAPER_GUIDE.md` 和 9/19 三票驗證過的 `SOTA_MATRIX_20260919.md`。
> - **部分**：讀過相關段落，或經多個查證 agent 交叉讀過。出處是 `docs/research_20260924/`、`docs/research_20260927/`。
> - **摘要**：只讀了摘要，或只有單一 agent 擷取過。細節引用前要回原文確認。
>
> 文中所有數字都是**原論文在它自己的硬體上**量的，不是我們的量測。

```
L5  誰在用、用多久？    ← 使用方式與契約
L4  怎麼找到筆記？      ← 命中規則
L3  怎麼搬筆記？        ← 傳輸
L2  筆記放哪裡？        ← 放置
L1  筆記寫多細？        ← 精度／格式
L0  要存的是什麼筆記？  ← 物件種類
```

很多論文橫跨好幾層。下面把每篇放在它**主要貢獻**所在的那一層，並標出它也碰到哪些層。

## 先懂幾個名詞

| 名詞 | 白話 |
|---|---|
| KV cache | 模型讀過文字後留下的筆記。一般模型是每個 token、每一層各存一組 K 和 V |
| prefill | 第一次讀整段輸入。輸入越長越慢，決定第一個字多久出來（TTFT） |
| decode | 一個字一個字往後產生。每一步都要讀全部 KV |
| 重算（recompute） | 筆記丟了，就把原文再讀一次。越後面的 token 越貴，因為要看的前文更長 |
| 卸載（offload） | 把 KV 從 GPU 搬到 CPU 記憶體或 SSD |
| prefix caching | 兩個請求的開頭一模一樣時，直接重用前一個請求的 KV |
| LRU／ARC | 空間不夠時丟誰。LRU 丟最久沒用的；ARC 同時看「最近用過」和「用過幾次」 |
| MHA／GQA／MLA | 注意力的三種結構。GQA 的 KV 比 MHA 小很多；MLA（DeepSeek）更小 |
| P/D 分離 | prefill 和 decode 放在不同機器上做，KV 要經網路傳過去 |
| oracle | 事先知道未來所有請求的理想策略，用來算「最多能好多少」 |

## L0：要存的是什麼筆記

> 一般 Transformer 只要存 KV。新出現的 hybrid 模型除了 KV，還有一份會被覆寫的「狀態」要存；另外，不同模型之間也可能互相借用 KV。

### Marconi（MLSys'25，Princeton／AWS）〔全文〕
**一句話**：為「Attention ＋ SSM 混合模型」設計的 prefix cache。決定存不存、丟不丟時，同時看重用機率、能省多少計算、佔多少記憶體。

- **想解決什麼**：混合模型（例如 Jamba）的 SSM 層是就地更新狀態，不能像 KV 那樣退回前面某個位置。所以只有完全相同的前綴才能命中，快取裡塞滿又大又少用的項目。
- **怎麼做**：
  - **准入**：依命中情境分類，預測一個項目未來被重用的機率，機率低就不存。
  - **逐出**：除了最近使用時間，也看「命中一次能省多少計算 ÷ 佔多少記憶體」。
- **實驗**：自建 7B 混合模型、Jamba-1.5-Mini；LMSys、ShareGPT、SWE-Bench；8 × A100-40GB。
- **成果**：token 命中率最多高 34.4 倍，TTFT 少 71.1%。
- **短板**：只在 GPU 內，沒有 CPU／SSD 階；到達間隔是人工設定的；用在純 Transformer 上會退化成一般的 prefix cache。
- **跟我們的關係**：hybrid 模型快取的第一篇，但沒有分層。

### Sparse Prefix Caching（arXiv 2605.05219，2026-04）〔部分；三票驗證〕
**一句話**：hybrid 模型的狀態不必每個位置都存，只在幾個位置存 checkpoint；位置怎麼挑，用動態規劃求最佳解。

- **怎麼做**：
  - 命中時，從最深的 checkpoint 恢復，再精確重算剩下的部分，輸出無損。
  - 給定「請求重疊深度的分布」，用 O(NM) 的動態規劃決定 checkpoint 放哪。
  - 命中成本分三項：checkpoint 從 CPU 載入、recurrent 層重播、attention 層載入 KV。
- **實驗**：只在 Qwen-3.5-0.8B 的一組層上計時；一張 RTX 2080 Super。
- **短板**：checkpoint 只放 CPU 記憶體；最佳化目標只算重算量，沒算載入成本；全文沒有 SSD，也沒有精度。

### DASC（arXiv 2608.30386，2026-08）〔部分；三票驗證〕
**一句話**：hybrid 模型（Qwen3-Next 的 Gated DeltaNet、Kimi-Linear 的 KDA）的 state checkpoint 太佔 GPU 記憶體，所以壓縮它，只保留重要的部分。

- **想解決什麼**：state 會被就地覆寫，SGLang 只好每隔固定 token 數存一份完整 checkpoint，跟 KV 並存；沒存到的只能重跑 prefill。
- **怎麼做**：依架構的衰減粒度挑選要保留的 state 單元。
- **實驗**：Hopper GPU、TP8、SGLang、LRU；短 prompt 高併發。
- **成果**：KDA 上 TTFT 降 42.6%〔擷取〕。
- **短板**：全部在 GPU 內，全文搜 offload、CPU、SSD、DRAM 都是 0 次。
- **跟我們的關係**：說明 state checkpoint 是「單份很大、只在邊界有效」的新物件。依 HF config 換算〔算術〕，一份約 43–77 MB，相當於數千 token 的 KV。

### Tail-Replay（arXiv 2608.30310，NeurIPS'26 workshop）〔部分；三票驗證〕
**一句話**：不存 hybrid 模型的 state，命中時用一小段重播把它近似重建回來。

- **成果**：
  - 重播比例 5% 時，品質保留 full prefill 的 92.8–98.9%（LongBench）、93.1–99.9%（RULER）。
  - 直接把 state 歸零則崩掉：RULER 從 0.81–0.97 掉到 0.22–0.42。
- **短板**：
  - 每個設定只跑一次，RULER 只測到 16K。
  - 機制細節的 claim 在驗證中被否決，要回原文確認。
  - SGLang 有一份 RFC（#40865）論證：在某種交錯架構上，這種重播「省下 0」。
- **跟我們的關係**：多了一個「有損重建」的動作，而且品質損失也是模型 × 任務相依。

### LRAgent（ICML'26 poster，arXiv 2602.01053）〔部分；三票驗證〕
**一句話**：同一個底座模型掛不同 LoRA 的多個 agent，能不能共用彼此的 KV？

- **成果**：
  - 完整共用、完全不重算時，準確率最多掉 5.28 分。
  - 只共用 base 部分時，最多掉 0.67 分。
  - 作者也指出：準確率低的方法會讓 agent 多走幾步，context 變更長。
- **實驗**：LLaMA-3.1-8B、Ministral-8B；HotpotQA、ScienceQA；context 只有 1.0–1.5K token。
- **短板**：沒有長 context；評估全部在 GPU 記憶體內，沒有分層。
- **跟我們的關係**：「借別人的 KV」是一個帶品質代價的新動作。vLLM 預設會把 LoRA 名稱放進 hash，所以跨 LoRA 的命中預設是 0。

### DroidSpeak（NSDI'26，arXiv 2411.02820）〔部分；三票驗證，2-1〕
**一句話**：同一架構、不同 fine-tune 的模型之間借用 KV，只重算少數敏感的層。

- **成果**：prefill 延遲降 1.7–3.1 倍。「品質損失可忽略」的定義是：profiling 時掉分 ≤ 5%。
- **短板**：每一組模型對都要離線 profiling；資料路徑是 GPU 對 GPU，走 InfiniBand。

## L1：筆記寫多細（精度與格式）

> 用 BF16、FP8、INT8、INT4 存 KV。越省空間，品質損失越大，而損失多少跟模型、任務都有關。

### KIVI（ICML'24，Rice 等）〔全文〕
**一句話**：KV 可以壓到 2 bit。關鍵是 K 沿通道方向分組、V 沿 token 方向分組量化，因為兩者的離群值分布不同。

- **成果**：峰值記憶體少 2.6 倍，batch 可大 4 倍，吞吐量高 2.35–3.47 倍，品質幾乎不變。
- **短板**：只在 GPU 裡；最新的 token 要保留全精度。

### KVTuner（ICML'25，華為諾亞方舟）〔全文〕
**一句話**：每一層對量化的敏感度不同，所以離線逐層決定 K、V 各用幾 bit。

- **成果**：Llama-3.1-8B 平均 3.25 bit 就近乎無損；對量化敏感的 Qwen2.5-7B 要 4.0 bit。
- **短板**：每個模型都要離線搜一次；評測偏重數學題。
- **跟我們的關係**：跟我們看到的「Qwen2.5 比較怕量化」方向一致。

### QuantSpec（ICML'25，arXiv 2502.10424）〔摘要＋擷取〕
**一句話**：把 INT8 KV 拆成「高 4 bit」和「低 4 bit」兩半：只用高 4 bit 當草稿快速生成，再用兩半合起來的 INT8 驗證。

- **成果**：128K context 下草稿接受率 94.31%，端到端快 2.49 倍〔擷取〕。
- **短板**：全部在 GPU 內，沒有卸載；只測 Llama-2 系；batch 1。
- **跟我們的關係**：「拆成上下兩半、放在不同層」這個想法的最接近前作。

### VeriCache（arXiv 2605.17613，2026-05，UChicago 等）〔部分；三票驗證〕
**一句話**：壓縮過的 KV 放 GPU 當草稿，完整的 KV 放 CPU 用來驗證。greedy 解碼下輸出跟用完整 KV 一模一樣。

- **怎麼做**：建在 vLLM＋LMCache 上；壓縮方法可以替換（丟 token 或量化）；每次驗證都從 CPU 重載完整 KV。
- **短板**：同一份資料存兩份；全文沒有 SSD，也沒有 AMD。
- **跟我們的關係**：直接挑戰「每個 block 只有一種精度、一個位置」的假設。審稿人可能會問：為什麼不同時留 INT4 和 BF16？

### SpeCache（arXiv 2503.16163）〔摘要＋擷取〕
**一句話**：GPU 只留 1–2 bit 的低精度副本，完整的 16-bit KV 放 CPU；每一步用低精度副本判斷要哪些，再把那些從 CPU 抓回來。

- **成果**：LongBench 上跟 16-bit 只差 1–2%，GPU 上只佔約 10% 的 KV 大小〔擷取〕。
- **短板**：單一請求，沒有跨請求重用，沒有 SSD。

### Lynx（arXiv 2607.01831，原投 SIGCOMM'26）〔摘要〕
**一句話**：P/D 分離時，KV 經網路傳輸可以拆成兩條流：先傳高位元（Anchor），decode 立刻開始；低位元（Residual）到了再驗證。

- **成果**：TTFT 接近 INT4，準確度接近 BF16；比 INT8 最多快 1.43 倍。
- **短板**：只做網路傳輸；頻寬是人為限制在 10–50 Gbps 的，頻寬越高收益越小〔擷取〕。

### Rethinking KV Cache Compression（MLSys'25，arXiv 2503.24000）〔摘要＋擷取〕
**一句話**：把各種 KV 壓縮法放進真正的服務框架裡量，發現很多收益不見了。

- **發現**〔擷取〕：
  - 在有 PagedAttention 的框架裡，4-bit KV 的 decode 吞吐只有 FP16 的 0.88–1.02 倍。
  - 壓縮會讓輸出偏長，端到端反而可能變慢。
  - 平均分數不掉，但很多個別樣本從答對變答錯。
- **跟我們的關係**：「INT4 取代放置」目前只在 prefill 上成立，端到端要另外量；品質要看個別失敗，不能只看平均。

## L2：筆記放哪裡（放置）

> 決定每段 KV 放 GPU、CPU、SSD，還是丟掉重算。論文最多的一層，原本的 Tiara 也在這裡。

### Strata（OSDI'26，Stanford／NVIDIA 等）＝ SGLang HiCache 的研究版〔全文〕
**一句話**：把「KV 從 CPU 搬回 GPU」做得又快又不卡，並讓排程器知道搬運要花時間。已在生產環境部署。

- **想解決什麼**：長 context 時，系統卡在搬 KV 而不是計算。原因有三：
  1. KV 在 GPU 上被切成很多小 page，搬運變成大量小傳輸；
  2. 載入 KV 會卡住 prefill；
  3. delayed hit：同一段 KV 正在載入時又被請求，排程器卻不知道。
- **怎麼做**：
  - GPU 協助搬運，並讓 GPU 端和主機端用不同的資料版面，以便整批傳輸。
  - 排程器同時看「要載入的」和「要計算的」，把載入時間藏起來。
  - 寫入策略預設是「被存取超過 2 次才寫到下層」。
  - **逐出每一層都用 LRU。**
- **實驗**：Llama-3.1-8B/70B、Qwen2.5-14B-1M、DeepSeek-V3；全部用 Poisson 到達；H200、H20＋NVMe、GH200。
- **成果**：吞吐量比 vLLM＋LMCache 最多高 5 倍。
- **短板**：
  - 放哪、丟誰都用 LRU，貢獻在機制不在策略。
  - 不把重算當選項，原文認為長 context 重算是「an unattractive alternative」。
  - 沒有量化；SSD 只出現在一個子實驗。
- **跟我們的關係**：最強的機制底座。它用 Little's Law 說明「每次搬運的量要放大」，我們量到的「每筆固定成本」可以用同一條式子解釋。

### Cake（ICML'25，密西根大學）〔全文〕
**一句話**：GPU 從前面往後重算，I/O 從後面往前載入，兩邊在中間會合。

- **為什麼這樣分**：越後面的 token 重算越貴，所以後面交給 I/O、前面交給 GPU 最划算。
- **實驗**：LLaMA 3.1-8B/70B 等；合成 prompt（4K–16K）；2 × A100、1 × H100。
- **成果**：TTFT 平均比純重算或純載入降 2.6 倍。
- **短板**：
  - I/O 頻寬是算出來的，沒有真實儲存裝置。
  - 假設 KV 都已經存好。
  - 沒有成本模型、沒有 fallback（作者列為未來工作）。
  - 有設定比單純載入還慢（0.80 倍）。
- **跟我們的關係**：它證明了「重算成本隨位置增加」。它是讀取時算切點的演算法，**不做預測**。

### Pensieve（EuroSys'25，arXiv 2312.05516）〔部分〕
**一句話**：多輪對話的 KV 快取。空間不夠時，優先丟「閒置比較久」和「比較便宜重算」的，而且從對話的**開頭**丟起。

- **怎麼做**：以 chunk 為單位逐出到下一層或直接丟掉；丟掉的前段要用時再重算。
- **短板**：只有 GPU／CPU，沒有 SSD，也沒有精度；沒有開源。
- **跟我們的關係**：最早把「位置越前面越便宜重算」用在逐出上，是跟原本 Tiara 最接近的一篇。

### Bidaw（FAST'26，清華）〔全文〕
**一句話**：多輪聊天的 KV 存在「記憶體＋SSD」兩層，讓計算端和儲存端互相知道對方的狀態。

- **怎麼做**：
  1. 依 KV 在記憶體還是 SSD 分開排程。
  2. 用「上一輪回答多長」預測使用者多久後回來：回答越長，KV 越早趕到 SSD。
  3. 不存 KV，改存可以換算回 KV 的中間 tensor，因為它「每 MB 能省下的計算」比較多。
- **實驗**：OPT、Qwen1；合作廠商的真實聊天 trace（一百萬輪以上，平均 22 輪）；1 × A800、SATA SSD RAID。
- **成果**：延遲最多降 3.58 倍，接近「全部放記憶體」的上限。
- **短板**：
  - 第 2 招要靠真實時間戳，用 Poisson 補的時間就失效（原文自承）。
  - 第 3 招只對 MHA 有利，現在的 GQA 模型用不上。
  - 對話很短，問題平均 36 token。
- **跟我們的關係**：它有 Belady 命中率上界，證明多輪對話確實有改善空間；trace 公開。它也是「在 vLLM 上重做閉源對手」的先例。

### MTDS（Complex & Intelligent Systems'26，中國電信）〔全文〕
**一句話**：在 24 GB 小卡的邊緣伺服器上做 GPU→DRAM→SSD 三層；每個請求先判斷「載入快還是重算快」，再決定全載、部分載或不載。

- **怎麼做**：
  - 用歷史延遲預測載入時間與重算時間。
  - 被越多佇列請求共用的 KV 越優先卸載。
  - DRAM 用會自動調整的門檻逐出。
- **實驗**：GPT-2 1.5B 到 Qwen-3 14B；ShareGPT＋Poisson；4 × A10。
- **成果**：TTFT 降超過 25%。
- **短板**：整段一起決定，不依位置切開；只看得到已進佇列的請求；沒有精度；模型偏小。
- **跟我們的關係**：結論跟 Strata 相反（命中很長時不載反而快），可以用「各自的傳輸速度不同」解釋。

### AdaptCache（SOSP'25 BigMem workshop）〔全文〕
**一句話**：對每段 KV 決定用哪種壓縮、壓多少、放 DRAM 還是 SSD，目標是讓更多命中發生在 DRAM。

- **怎麼做**：效用 ＝ 預估的未來命中頻率 ×（α × 品質 − 大小 ÷ 頻寬），用 greedy 求解。未來命中頻率用過去的命中頻率估。
- **實驗**：只有 Llama-3.1-8B；LongBench 6 個資料集；1 × A100、SSD 1 GB/s。
- **成果**：同等品質下延遲省 1.43–2.4 倍。
- **短板**：
  - workshop 初步結果，只有一個模型。
  - 品質曲線每個資料集只抽 10 筆，問題由 GPT-4o 產生。
  - 品質是效用裡的一個權重，不是硬性約束。
  - 沒有列出實際用了哪些壓縮法。
- **跟我們的關係**：「壓縮和放置一起決定」的代表。它有考慮品質，只是品質評估很薄。

### EvicPress（arXiv 2512.14946，同一團隊）〔全文〕
**一句話**：AdaptCache 的完整版。同時決定每段 KV 壓多少、放哪一層；對壓縮敏感的少壓一點、放高一點。

- **實驗**：5 個模型；LongBench 555 段上下文，問題由 GPT-5 產生；1 × H100、SSD。
- **成果**：同等品質下 TTFT 最多快 2.19 倍。
- **短板**：假設各層頻寬已知且穩定；DRAM 夠大或各層頻寬相近時，優勢就消失（原文自承）；沒有 oracle 上界。

### LMCache（arXiv 2510.09665，UChicago／Tensormesh）〔全文〕
**一句話**：業界最常用的開源 KV 快取層，把 vLLM／SGLang 的 KV 存到 CPU、磁碟、遠端，讓不同請求、甚至不同引擎共用。

- **成果**：搭配 vLLM，吞吐量最多高 15 倍。
- **短板**：
  - 它提供機制和 API，放置策略不是它的貢獻。
  - 真實 trace 只用了長度分布，還把數天壓縮成 1 小時。
  - 大倍數出現在對手已經接近飽和的工作點。
  - 相依套件是 NVIDIA 專屬，在 AMD 上很可能跑不起來。

### Mooncake（FAST'25 Best Paper，月之暗面 Kimi）〔全文〕
**一句話**：Kimi 的生產架構。prefill 和 decode 分開用不同機器，再把整個叢集閒置的 CPU 記憶體和 SSD 池化成一個大的 KV 倉庫。

- **成果**：真實負載下讓 Kimi 多處理 75% 的請求。
- **短板**：需要多節點＋RDMA；用 dummy model，沒有量品質。
- **跟我們的關係**：我們用的真實 trace 就是 Mooncake 公開的。注意它的一個 hash block 是 512 token。

### py-kvcache（arXiv 2609.11744，VU Amsterdam／IBM，2026-09）〔部分〕
**一句話**：在 vLLM 加 NVMe SSD 上量出「存 SSD 比重算划算」的損益平衡長度；短於這個長度的前綴，就不存也不載。

- **原文重點**：外部 KV 快取應該被當成「依每套硬體設定而定的准入決策」；損益平衡點會隨 GPU、模型、SSD 移動。
- **短板**：以整段前綴長度判斷，不看 block 位置；決定發生在讀取時；沒有精度。
- **跟我們的關係**：跟我們「先量常數、再決定」的想法最接近，必須引用並劃清界線。

### vLLM OffloadingConnector／NVIDIA Dynamo KVBM〔部分〕
**一句話**：生產環境內建的分層規則。

- vLLM 的 CPU 階提供 LRU 和 ARC，並有「出現夠多次才寫入」的門檻（`store_threshold`）。
- Dynamo KVBM 預設「至少用過兩次才寫 SSD」，目的是延長 SSD 壽命。
- **跟我們的關係**：這是我們在 AMD 上真正能跑的對手。

### HCache（EuroSys'25，清華）〔全文〕
**一句話**：不存 KV，改存每層的 hidden state（MHA 下約 KV 的一半大），要用時做一次矩陣乘法轉回 KV。

- **成果**：TTFT 比 KV 卸載快最多 1.93 倍。
- **短板**：只適用 MHA。GQA 模型的 KV 本來就比 hidden state 小，所以用不上。

### CacheFlow（arXiv 2604.25080，UIUC）〔部分〕
**一句話**：把 Cake 的「前段算、後段載」寫成公式：最佳切點 ＝ L × T_io ÷ (T_comp + T_io)。

- **跟我們的關係**：這個切點等於 1/(1+κ)，和我們成本比 κ 的形式相同，必須引用。

### AsymCache（arXiv 2606.02964）〔部分〕
**一句話**：用「重算成本隨位置線性增加」做逐出，並拿 Pensieve 當 baseline。

## L3：怎麼搬筆記（傳輸）

> 把 KV 從 CPU／SSD 搬回 GPU，或在機器之間傳。大多數論文假設「傳輸時間 ≈ 資料量 ÷ 頻寬」。

### vLLM 官方部落格：KV Offloading Connector（2026-01-08，IBM Research）〔抽查原文〕
**一句話**：vLLM 0.12.0 把 KV 的記憶體佈局改成「每個 block 包含所有層、連續存放」，每次搬運的單位因此放大了 2 × 層數倍，卸載速度提升約一個數量級。

- **數字**（H100）：
  - Llama-3.1-8B 的搬運單位從 32 KB 變成 2 MB，TTFT 最多降 4 倍、吞吐最多高 5 倍。
  - 微基準：DMA 只在大 block 時才快。
- **沒有的**：每筆固定成本的模型；AMD 的數字；hybrid 模型「尚未最佳化」；SSD 階是下一步。
- **跟我們的關係**：這是「搬運速度由軟體決定」**最接近的前作**，必須正面引用。我們在 MI300X 上（同版 v0.28）看到多數模型仍是一層一小塊，原因待查。

### vLLM issue #55434（2026-09-05，GB200）〔抽查原文〕
**一句話**：在 NVIDIA GB200 上做 P/D 分離時，KV 傳輸的瓶頸是「提交描述符」，不是網路頻寬。

- **數字**：
  - 每次傳約 4.9 GB 要發 91k–120k 個描述符。
  - 每個描述符的成本依傳輸方式差 20 倍：cuda_ipc 4.067 µs、InfiniBand 0.204 µs。
  - 名義上較快的 NVLink 路徑，端到端反而比 InfiniBand 慢。
- **關鍵觀察**：prompt 從 10.3k 變 41.1k token，描述符數量不變。描述符變多是因為 prefix 重用讓 block 散落各處，不是因為 context 變長。
- **注意**：這是單一回報者的量測，沒有 maintainer 回覆。
- **跟我們的關係**：在另一條路徑、另一家硬體上，獨立印證了我們在 MI300X 上看到的「每筆固定成本」。也是「命中越高、搬得越慢」這個推論的來源。

### Bottlenecks（MLSys'26，arXiv 2601.19910）〔全文〕
**一句話**：KV 卸載到 CPU 後，prefill 會從算力瓶頸變成 PCIe 瓶頸；作者推導出一個臨界比值 κ_crit 判斷什麼時候發生。

- **成果**：
  - κ_crit 介於 1–76，真實負載的比值遠超過這個範圍。
  - 99% 的延遲花在傳輸。
  - 實際只用到峰值頻寬的約 23%。
- **短板**：只測 prefill；把頻寬當成硬體給定，建議換更快的硬體。
- **跟我們的關係**：它的 κ_crit 和我們的 κ 代數上是同一個量（符號撞名，要改）；它量到「只用到 23%」，但沒追到軟體原因。

### Tutti（arXiv 2605.03375，廈門大學）〔全文〕
**一句話**：從 SSD 讀 KV 回 GPU 時，連發 I/O 指令都讓 GPU 自己來，不經過 CPU。

- **想解決什麼**：零碎的小 block 會變成海量小 I/O，CPU 成了瓶頸。
- **成果**：比開了 GDS 的 LMCache，TTFT 降 78.3%。
- **短板**：只解決「怎麼搬」；需要 NVMe 和特殊的 GPU 檔案系統。
- **跟我們的關係**：也是「軟體路徑決定搬運速度」的證據。我們的 MI300X 沒有 NVMe，跑不了。

### llm-d 網路部落格（2026-06-23）〔擷取〕
**一句話**：比較 KV 傳輸的三種後端（UCCL、UCX、Mooncake），發現軟體開銷只在快的網路上看得到。

- **數字**：400G InfiniBand 上 UCCL／UCX 約 49.5 GB/s、Mooncake 約 42 GB/s；100G RoCE 上三者都約 12 GB/s，被網路本身限制住。
- **另外**：vLLM 的 P/D 只把重算當「傳輸失敗時的 fallback」，沒有依成本選擇。

### AMD ROCm Infinity Context（AMD 部落格，2026-07-22）〔擷取〕
**一句話**：AMD 在 GPU 記憶體和 CPU 記憶體之下，再加一層經 RDMA 連接的網路儲存，KV 可以直接讀進 GPU。

- **短板**：全文沒有任何量測數字；MI300X 列為支援，但 2026 秋季才有 tech preview。

## L4：怎麼找到筆記（命中規則）

> vLLM 和 SGLang 只認「從第一個 token 開始完全相同」的前綴。中間只要有一個 token 不同，後面就全部作廢。

### CacheBlend（EuroSys'25 Best Paper，UChicago）〔全文〕
**一句話**：RAG 時把好幾段文件各自預先算好的 KV 直接拼起來，只挑一小部分 token 重算，補上段落之間的交互。

- **成果**：TTFT 降 2.2–3.3 倍，品質不掉。
- **短板**：選擇性重算是有損的；只針對 RAG 的多段拼接。
- **跟我們的關係**：「中段內容也能重用」這條研究線的起點。

### MEPIC（arXiv 2512.16822，Huawei）〔部分；三票驗證，2-1〕
**一句話**：CacheBlend 這類方法對每個請求各自修補 KV，結果同一段內容的 KV 在不同請求之間不一樣，不能共用同一份記憶體。MEPIC 讓它們可以共用。

- **原文重點**：各自修補後「cannot be page-aligned or shared in the paged KV cache」。
- **短板**：只測一個模型（Mistral-7B）、在 Ascend 910B 上；請求平均只有 1.4–2.2K token。
- **跟我們的關係**：如果要做「中段命中」，修補的結果不能寫進共享的記憶體頁。

### vLLM issue #39321 與 SGLang PR #23315（2026-04）〔抽查原文〕
**一句話**：reasoning 模型的「思考內容」會被 prefix cache 存起來；但使用者下一輪把思考刪掉以後，這些 KV（連答案也算）就永遠不會再命中。

- **vLLM issue**：
  - 以 QwQ-32B、每輪約 5,000 個思考 token 估算，每條「死掉的 KV 鏈」約 1.3 GB（作者紙上估算）。
  - 答案的 KV 明明在快取裡，卻因為前面卡著思考內容，只能重算。
- **SGLang PR**：已合併，加了 `--strip-thinking-cache`，預設關閉。答案的 KV 也一起丟，理由是刪掉思考後位置編碼會錯位。
- **我們讀程式碼確認的**：vLLM v0.28 開啟 CPU 卸載時，預設會把 decode 產生的 KV 也搬到 CPU／SSD。所以死掉的思考 KV 也會被搬（還沒實際量）。
- **跟我們的關係**：token 是「思考」還是「答案」，寫入當下就知道，可以直接決定存不存。

## L5：誰在用、用多久（使用方式與契約）

> 大多數論文把負載當成固定前提，但使用方式和服務規則會回頭影響快取。

### Anthropic prompt caching 文件（2026-09 擷取）〔擷取〕
**一句話**：商業 API 的快取是「保證至少存 5 分鐘（或 1 小時）」的契約，按次計價，不是單純的 LRU。

- **重點**：
  - KV 只放記憶體、不落地；組織之間隔離。
  - 寫入 5 分鐘快取收 1.25 倍價格，命中收 0.1 倍。
  - 保證命中與未命中的輸出完全相同。
- **跟我們的關係**：在「輸出必須相同」的契約下，有損的精度只能是全域開關，不能只對快取的部分降精度。

### Keepalive Economics（arXiv 2607.19214，單一作者、5 頁）〔抽查原文〕
**一句話**：agent 等工具或等人核准的那幾分鐘，快取就過期了。客戶端可以每隔一段時間「戳一下」讓它保持新鮮；作者算出最省錢的間隔。

- **數字**：
  - Anthropic 的快取 300 秒還在、360 秒消失。
  - 最省的戳法是每 4 分鐘一次，不是常見的 30 秒。
- **論點**：如果所有客戶端都這樣做，LRU 就排不出誰真的重要。
- **跟我們的關係**：可以純模擬，看人為刷新會怎樣影響 LRU 和放置策略。

### Auditing Prompt Caching（ICML'25，Gu／Liang 等，arXiv 2502.07776）〔抽查原文〕
**一句話**：從回應快慢可以看出某個 prompt 是否被別人快取過，構成隱私風險。7 家 API（包括 OpenAI）的快取是跨使用者共享的。

- **跟我們的關係**：「只對每個使用者各自快取」會少命中多少，沒人量過；多層快取的命中延遲不同，還可能洩漏資料放在哪一層。

### GreenCache（arXiv 2505.23970）〔摘要＋擷取〕
**一句話**：把 SSD 的製造碳排算進去後，KV 快取不一定省碳：在低碳電網上，快取反而增加碳排。所以依電網碳強度每小時調整 SSD 快取的大小。

- **成果**：法國電網平均減碳約 15%，最高 25%。
- **短板**：只調 SSD 容量一個維度；context 只有 8K；沒有精度。

### Towards More Economical Context-Augmented LLM Generation（UChicago，arXiv 2503.14647）〔摘要＋擷取〕
**一句話**：用 AWS 的價格算，把長 context 的 KV 存起來重用，比每次重算便宜。

- **重點**：節省上限取決於「被重用的 context 在 prefill 裡佔多少」。
- **跟我們的關係**：我們「事前判準」裡的 prefill 佔比那一項，這篇已經有類似的式子，必須引用。

### SparseSpec（arXiv 2512.01278，Stoica／Han 等）〔摘要＋擷取〕
**一句話**：reasoning 模型輸出很長，瓶頸從計算變成讀 KV。它用稀疏 attention 當草稿做投機解碼，並把 KV 依請求卸載到 CPU 來撐大 batch。

- **成果**：吞吐量最多高 2.13 倍。
- **跟我們的關係**：reasoning 時代的 KV 大多是 decode 自己產生的，分層壓力來自「請求內持續長大」，而不是跨請求重用。

## 不屬於跨請求分層、但常被拿來比的

### Quest（ICML'24，MIT）〔全文〕
**一句話**：每個 KV page 記下 key 的最小值和最大值，用當下的 query 估出每個 page 最多能拿到多少注意力，只讀前幾名。

- **短板**：只省讀取量，不省容量（KV 全部還在 GPU）。

### ShadowKV（ICML'25，字節／CMU）〔全文〕
**一句話**：key 壓縮後留在 GPU，value 搬到 CPU；每一步用壓縮的 key 挑出重要的，再把對應的 value 抓回來。

- **短板**：在需要大量抽取資訊的任務上會挑錯（Yandex 的發現）；只有 GPU／CPU 兩層；單一請求。

### InfiniGen（OSDI'24）〔全文〕
**一句話**：在算第 i 層時，先用低成本預演第 i+1 層的注意力，猜出重要的 KV，只把那些從 CPU 預取上來。

- **短板**：要修改模型權重；準確度只在短任務上量。

> **這三篇的共同點**：都是「單一請求內，這一步要讀哪些 KV」，用當下的 query 決定。它們不處理「跨請求，哪段 KV 該放哪一層」。所以報告裡才說：在放置系統裡，沒看到有人在 token 層級預測「存、載，還是重算」。

## 附錄：diffusion LLM（dLLM）的 KV 問題〔摘要〕

> dLLM（例如 LLaDA）一次猜一整段、反覆修改，注意力是雙向的。後面的字一改，前面的 KV 也跟著變，所以每一份快取都只是近似值。

| 論文 | 一句話 |
|---|---|
| Fast-dLLM（NVIDIA，2025） | 利用相鄰去噪步之間 KV 很相似這一點，做區塊級的近似 KV 快取 |
| dKV-Cache（2025） | 延遲一步才把已解碼的 token 存進快取 |
| BiCache（arXiv 2606.07571） | 直接套用一般 LLM 的前綴快取，準確率會掉到接近 0。只有淺層的前綴 KV 可以重用；吞吐提升 36–98% |
| GroupKV（arXiv 2609.17573） | dLLM 長 context 的分層卸載：用「組」為單位挑選與預取，並修正過期的 KV。可服務長度最多長 48 倍 |
| Fixed State, Long Reach（arXiv 2609.11998） | dLLM 改用 Mamba 這類固定大小的狀態當快取；256K 時延遲降 4.3 倍、記憶體少 11 倍 |

**判斷**：這是另一個世界，我們現有的 harness 幾乎都要重寫。暫時只放在 future work。
