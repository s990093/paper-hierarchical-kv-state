## 2. F1 帶出來、會影響之前結論的事

1. **harness 的重算比預設 vLLM 慢約 1.7–2 倍。**
   - 第一階段的 C6 說「harness 和 vLLM 同一個量級，不是稻草人」。但 C6 的 vLLM 開了 connector，跑在慢的 attention 上。
   - 影響：f(i) 偏大，所以 κ＝ℓ／f 偏小、b 偏小。Cake 有效頻寬帶的**絕對數字**要重量。
   - **更麻煩的是**：真實的重算速度約是 harness 的 f×0.5–0.6，正好落在 09 標為「還沒排除的例外」的區域。
     - 09 的模擬裡，free 時 f×0.5 是 0／48 格通過，最大領先 3.3%；f×0.25 有 1 個設定存活。
     - hold 時另有 2 個設定存活〔模擬，F5 從 `sim_sweep_gain.csv`、`sim_probe.csv` 重算〕。
     - 這些只比了兩個對手，也沒上 GPU。
   - 所以「寫入時決定正式結束」要加一個但書：**在真實速度的重算下還沒用完整的對手集合測過**。
   - 已在 07 §7 和 FULL_REPORT §7 加上更正。（第一版寫「結構性結論仍成立」，是錯的，F5 指出後改正。）
2. **在 vLLM 0.28＋ROCm 上，比較「卸載 vs 重算」時，兩邊要釘死同一個 attention 實作**，不然量到的是 kernel 的差，不是放置策略的差。D2 的時間比較就有這個問題。
3. **D2 的「doc C＝1 回來的請求快 2 倍」是假象**：命中率在 50% 上下，中位數就在約 0.1 s 和約 2.2 s 之間跳。
4. **從 CPU 載入可能輸給重算**：在快的 attention 上，chat 回來的請求從 CPU 載入約 16K token 要 1.678 s，重算只要 1.460 s。原因是每次複製都有固定開銷。
5. **NFS 層的長時間等待重現了**：回來的請求最久等了 89.3 s 等資料，而不是重算。
