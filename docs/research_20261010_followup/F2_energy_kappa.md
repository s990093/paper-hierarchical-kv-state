### 2.1 要回答的問題

- 還原一個 32K context（64 個 chunk，每個 512 token、64 MiB）時，有三類做法：
  - **只重算**（R）：64 個 chunk 全部讓 GPU 重算。
  - **只載入**（L）：64 個 chunk 全部從儲存層搬回來，GPU 等。
  - **Cake**（C）：GPU 從前面重算、I/O 從後面載入，兩邊在中間會合（harness 的動態版）。另外量**固定切點**版 S(m)：前 m 個重算、後 64−m 個載入，兩條線同時跑。S(0)＝只載入，S(64)＝只重算。
- **時間最佳**＝還原時間（中位數）最短的做法；**能量最佳**＝GPU 能量（中位數）最少的做法。
- 問題：在每一層，能量最佳和時間最佳是不是同一個？如果不同，選能量最佳能省多少能量、要多花多少時間？

### 2.3 指標與「帳怎麼算」

- **量法**：GPU 能量計數器（`amdsmi_get_energy_count` 的累加值 × 解析度）在每次還原前後各讀一次（前後都先 `torch.cuda.synchronize()`）。

- **次要帳（照實報告，不改判定）**：

## 0. 一句話結論＋判定

**一句話**：在 MI300X 上，GPU 重算時約 726 W，等資料時約 169 W（相差 4.3 倍）。所以在 CPU 層和本地 SSD 層，**最省 GPU 電的是「只載入」**，比時間最佳的 Cake 少用 62–70% 的 GPU 能量，但還原要慢 4–43%。在 NFS 層，能量最佳和時間最佳一樣，都是 Cake。

**判定（照 §2 事先寫的規則）：有看頭**。主要帳 A 有 4 層「不同且省 ≥10%、各次範圍不重疊」；次要帳 B、C、D 也都一樣是有看頭。
**我的判讀：有看頭，但很窄**。
- 結論幾乎可以從 P_b／P_wait＝4.3 直接算出來：Cake 在快的層只多快一點，卻要用 726 W 去重算。
- 換成錢，GPU 租金遠大於電費。以每度電 0.10 美元〔假設〕算，GPU 租金要低於每小時 0.14–1.35 美元，選「省電」才划算〔算術〕。所以只有在「電是瓶頸」或「GPU 本來就閒著」時，這個差別才重要。
- 「載入比重算省能量」在伺服器層級已經有人量過（HotCarbon 2026，H200）。新的是「部分重算的切點」：時間最佳的切點在快的層很耗電。
- 補充的 LongAlpaca-7B（KV 大 4 倍）方向一樣（帳 A 省 29–53%），但要慢 14–144%；主機功率假設設高時，CPU 3.69 與本地 SSD 層會翻回接近 Cake（§4.8）。

## 1. 問題

**問題是什麼**
- 使用者回來時，要把 32K context 的 KV（64 個 chunk）放回 GPU。可以讓 GPU 重算，也可以從儲存層搬回來，或兩邊一起做（Cake）。
- 到目前為止，專案都用「時間」比較這三種做法。
- 但重算時 GPU 全速在算，很耗電；搬資料時 GPU 大多在等，耗電少。所以「最省時間」和「最省電」可能是不同的選擇。

**要證明什麼**
- 先量出 MI300X 上兩個功率：GPU 重算時的功率 P_b，和 GPU 等資料時的功率 P_wait。
- 再把整段還原的 GPU 能量量出來，在 5 個層上比較：只重算、只載入、Cake，以及固定切點。
- 看「能量最佳」和「時間最佳」是不是同一個做法。如果不是，選能量最佳能省多少電、要多等多久。

**白話名詞**
- **chunk**：512 個 token 的 KV，64 MiB。
- **層（tier）**：KV 放的地方。這裡用「限速器」模擬：資料都在主機記憶體，但故意照某個頻寬慢慢搬，搬的空檔 GPU 就在等。
- **κ（時間）**：重算一個 chunk 的時間 ÷ 搬一個 chunk 的時間。κ_E 是同樣的比，但用焦耳算。
- **Cake**：GPU 從頭往後重算，I/O 從尾往前搬，兩邊在中間碰頭。碰頭的位置叫「切點」或「會合點」。
- **能量計數器**：GPU 自己累加的耗電量（焦耳），用 `amdsmi_get_energy_count` 讀。只算 GPU 卡本身，不算 CPU、記憶體、SSD。

## 6. 如果要繼續

〔判讀〕照「多快能判生死」排：

1. **把它變成一條規則，而不是一個現象**（約半天，不用 GPU）：
   - 「能量感知的 Cake」：在時間和能量之間加一個權重 λ，切點選 argmin（時間 ＋ λ × 能量）。§4.3 的 Pareto 表已經給了每層的前緣，可以直接算出「λ 多大時切點從 Cake 跳到只載入」。
   - 殺法：如果所有合理的 λ（例如用 §4.7 的電價／租金比換算）都落在「選時間最佳」那一側，這條線就只剩「功率上限機房」一個用途。
2. **在真實系統上確認**（約半天 GPU）：harness 的載入路徑是「pinned → strided 視圖」，會跑 GPU 的複製 kernel（CPU 35.4 層只載入時 GPU 使用率 43%）。vLLM 的 CPU 卸載路徑走的是別的 kernel。要在 vLLM 0.28 上量「CPU 卸載開／關」時，回來請求的 GPU 能量。這也可以和 F1（開卸載反而變慢）一起看。
3. **多人同時用**：單一請求時 GPU 等待是真的閒著。多人同時用時，等待的時間會被別的請求填滿，這時要用帳 B（扣閒置）。帳 B 下每一層都是只載入最省（§4.5），所以結論只會更偏向「少重算」。但時間的代價會變成別人的排隊時間，要用 D1 的模擬器算。
4. **功率上限軸**（D8 選做）：`amd-smi set` 調功率上限會改變 P_b 和 f(i)。這會改機器設定，本次規則禁止，沒有做（NOT_MEASURED）。
5. **整機能量**：這個 container 讀不到 RAPL。要在有 RAPL／IPMI 的機器上量主機那一塊，才能把帳 C 的 0／50／150 W 換成實測。

**寫進論文的方式**〔判讀〕：適合放在「κ 會隨目標改變」那一段（D8 的故事）。用一張 Pareto 圖：快的層 Cake 用很多電換一點點時間；慢的層兩者一致。不適合當成獨立的系統貢獻。
