# 02 逐出（替換）到底在選什麼？學習式方法怎麼處理寫入？

> **一句話**：「KV 逐出」其實是兩個不同的問題：
> - **跨請求**的快取替換：無損，丟掉的可以重算或搬回；
> - **單一請求內**的 token 逐出：有損，丟掉就再也看不到。
>
> recency、frequency、reuse distance 屬於前者，importance、attention score 屬於後者。本研究屬於前者，要看的是「會不會再被用」和「拿回來要花多少」，不是注意力分數。學習式方法幾乎都只做逐出，沒有在寫入時決定放哪一層。

---

## 1. 「KV 逐出」是兩個不同的問題

你貼的那段說明，把兩個問題混在一起了：

| | **跨請求的快取替換**（本研究這一類） | **單一請求內的 token 逐出**（有損） |
|:--|:--|:--|
| 什麼時候發生 | 使用者離開後，GPU／CPU 要放別人的 KV | prompt 或生成很長時，同一個請求的 KV 太大〔複核修正：原只寫「生成很長時」；SnapKV、PyramidKV、KVP、LookaheadKV 都是 prefill 後就壓 prompt 的 KV（E07、E06）〕 |
| 選的是什麼 | 哪個 session（或哪一段前綴）離開快的層 | 哪些 token 的 KV 永遠丟掉 |
| 丟掉之後 | 可以搬回來或重算，**答案不變** | 再也看不到，**答案可能變** |
| 「存取」是什麼 | 使用者回來時用到這段前綴 | 每一步解碼，注意力都會讀**全部**的 KV |
| 適合的訊號 | recency、frequency、reuse distance、回來的時間、拿回來的代價 | importance、attention score |
| 代表 | LRU（LMCache、Mooncake）、Pensieve、LARU、LPC | H2O、SnapKV、KVP、TRIM-KV |
| OS 的類比 | 很像：RAM 滿了踢哪個 page | 不太像：OS 的頁不會「丟了就算了」 |

**你貼的例子「KV100 很久沒被用到，之後可能又被注意力用到」**：
- 在**完整注意力**下，每一步解碼都會讀全部的 KV，沒有「很久沒被用到」這回事。
- 只有在**稀疏注意力**下，每一步只讀一部分（Quest、ShadowKV、InfiniGen），或是**檢索式**的取用（ReKV），才會出現「某些 KV 很久沒被讀」的情況（`03_paper_map.md` C 組）。

**最後那句「被踢出去後，重新搬回來的成本是多少，比 LRU 更接近你的研究問題」**：方向對，但要分清楚兩件事：
- 「搬回來的成本」是**代價**，和 attention score 無關。
- 本研究在意的代價是「重算 vs 搬運」，而且依位置不同：越後面重算越貴，搬運則看放在哪一層。這是成本感知（cost-aware）的替換，例如 Pensieve、AsymCache、Fancy-eviction 的 RandomCompute。

---

## 2. 選誰離開：三種訊號

| 訊號 | 回答的問題 | 例子 | 本研究用不用 |
|:--|:--|:--|:--|
| **機率**：會不會再被用、多久之後 | 留著值不值得 | recency（LRU）、frequency（LFU）、reuse distance、Belady；學習式預測（LARU、LPC）；啟發式預測（Bidaw 用上一輪回答長度估重用距離下界，再用 Belady 影子快取估命中潛力）〔複核修正：原把 Bidaw 列為學習式；Bidaw 沒有訓練模型（E04 Bidaw 卡「分層實作」，[B] p.8–9）〕 | **用**：第三階段的預測器就是預測這個 |
| **代價**：被踢掉後拿回來要多少 | 踢錯了會有多痛 | 重算成本隨位置增加（Pensieve、AsymCache）；從哪一層搬回來 | **用**：第一階段的核心（依位置、依層） |
| **品質**：丟掉會不會讓答案變差 | 能不能永遠丟掉 | importance、attention score（H2O、SnapKV、KVP） | 第一階段**不用**（無損）；第二階段的精度才相關 |

OS 的經典做法（FIFO、LRU、LFU、CLOCK、ARC、LRU-K）只看**機率**，而且假設每一頁的代價都一樣〔教科書〕。KV 的特別之處在於**代價不一樣**，所以要「機率 × 代價」一起看。經典的 GreedyDual-Size 就是這樣做的（RESEARCH_INTRO 表 12 [41]）〔判讀〕。

## 3. 替換的原理有哪幾種？（LRU、模型、前綴，原理不同）

| 原理 | 怎麼選 | 例子 | 備註 |
|:--|:--|:--|:--|
| **新舊、次數** | 最久沒用、最少用 | FIFO、LRU、LFU、CLOCK、ARC、LRU-K；KV 系統的預設多是 LRU | Fancy-eviction 測了 14 種（含 LRU 本身〔複核補充〕）：LRU 很穩，頻率派明顯落後（E05） |
| **成本感知** | 機率 × 代價，代價小的先走 | Pensieve（重算成本 ÷ 閒置時間）、AsymCache、Fancy-eviction 的 RandomCompute | 第一階段的 S2b、S4+ |
| **結構限制（前綴）** | 標準前綴快取裡，後面的塊要前面的在才有用，所以只能從樹葉（尾端）開始丟 | SGLang 的前綴樹（E01）；LARU 的候選限於樹葉（E06） | 這是**限制**，不是打分方式。也是標準前綴快取裡「前段不存，後段就算不上命中」的原因。〔複核修正：原未限定「標準前綴快取」。卡片中有三個放寬的例子：Pensieve 從對話**開頭**逐出、用支援非連續 KV 的 kernel，被丟的再重算（E03）；AsymCache 的 MSA kernel 允許前綴＋後綴的不連續命中（E05）；Fancy-eviction 允許「洞」之後的 block 仍算命中（E05）〕 |
| **學習式預測重用** | 用模型預測會不會、何時再被用 | LARU（GBDT）、LPC（對話會不會繼續）、SAECache（依 token 類型分佇列） | 無損，跨請求 |
| **注意力重要度** | 對答案多重要 | H2O、SnapKV、KVP、ForesightKV、LookaheadKV、TRIM-KV | 有損，單一請求內 |

所以「LRU 可能不夠，用模型；或看前綴關係」，其實是三件不同的事：
- 用模型，是想把**機率**猜得更準（LARU、LPC）；
- 看前綴，是**結構限制**；
- 看注意力，是**品質**（有損）。

## 4. 學習式（模型預測）方法怎麼處理寫入？

依評測卡 E06（7 篇）與 E05 的 LRB、HALP：

| 方法 | 它決定什麼 | 何時決定 | 有沒有處理寫入 |
|:--|:--|:--|:--|
| LARU、LPC、SAECache | GPU 前綴快取裡誰被逐出（單層） | 逐出時 | **沒有**。它們都是單層的 GPU 快取，KV 算出來就在 GPU，沒有「寫到下一層」這件事 |
| LRB、HALP（CDN） | 誰被逐出 | 逐出時 | 沒有 |
| ForesightKV | 單一請求內哪些 token 丟掉 | 解碼中每 L＝256 步一次 | 沒有（有損） |
| KVP | 單一請求內哪些 token 丟掉（排出保留順序） | prefill 後一次 | 算是寫入時決定，但決定的是「丟不丟」（有損），不是放哪一層〔複核修正：原與 ForesightKV 同列、寫「每一步」。卡片：KVP「只在 prefill 後壓一次，decode 零額外 FLOPs」（E06，[KVP] p17）；ForesightKV 是每 L 步壓一次（E06，[FKV] p6）〕 |
| LookaheadKV | 依預測的回應注意力，決定 prompt 裡哪些留下 | prefill 時 | 算是寫入時決定，但決定的是「丟不丟」（有損），不是放哪一層 |
| TRIM-KV | token 產生時給一個保留分數，之後只衰減 | 寫入時給分 | 最接近「寫入時決定」的資料結構，但決定的是丟不丟（有損）（E06 卡〔判讀〕） |

**結論**〔判讀，限於評測卡涵蓋的範圍〕：
- 學習式方法幾乎都在**逐出時**決定，而且多半是單層。
- 寫入時就決定的（KVP、LookaheadKV、TRIM-KV）都是有損的「丟不丟」，不是無損的「放哪一層」。〔複核修正：補上 KVP〕
- 所以「寫入時、依位置（加上預測），無損地決定放哪一層」在學習式這一側也是空的。

另外要注意：L2 的學習式方法（LARU、LPC、SAECache）的 label 來自 trace 本身的未來存取，不用跑 LLM；例外是 SAECache 的「首輪會不會變多輪」分類器讀的是服務中 LLM 的 hidden state，等於也綁 LLM。L1 的 label 來自目標 LLM 的未來注意力（KVP、ForesightKV、LookaheadKV），或對原模型輸出分布的蒸餾（TRIM-KV），所以每個模型各訓一次（E06 共同模式 3）。〔複核修正：原漏了 SAECache 這個例外，也把 TRIM-KV 一併說成「來自注意力」〕

這和本研究的設計方向一致〔判讀〕：RESEARCH_INTRO 表 13 的預測器輸入都是負載訊號（session 輪數、內容類型、上一輪回答長度、工具類型、過去的間隔、佇列長度、batch 大小），不讀 KV 的數值；`../phase1_20261008/02` §9 也寫第三階段的預測器「只預測負載」。〔未查證→已改寫：原文用引號寫成 RESEARCH_INTRO 表 13「預測器只預測負載、不碰 KV 內容」，但表 13 沒有這句話；「只預測負載」出自 phase1 `02` §9〕
