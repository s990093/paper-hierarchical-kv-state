# C_GLMHybridRecovery Validating Hybrid-State Cache Recovery for GLM-5.3-Flash with vLLM and LMCache

- **出處**：Frank Li（UNSW Sydney）。arXiv 2609.15030v1，2026-09-14，cs.DC。venue：未查證（單一作者的案例研究）。<https://arxiv.org/abs/2609.15030>。讀了 p.1–3（全文 8 頁，PDF 實體頁）。
- **寫入時做了什麼決定**：**混合模型的狀態檢查點寫在哪些位置**——固定間隔 C＝1,792 token；經 LMCache 存到外部 CPU cache〔原文 p.2 表 1、圖 1〕。原文的貢獻不是新的放置規則，而是**讀取端的修正**：查表時只找「嚴格短於 prompt 的 prefix」，讓還原的狀態位置 B 和排程器記的已算 token 數 p 對齊〔原文 p.2 §2.2、p.3 圖 2〕。
- **用什麼資訊做決定？寫完之後還在不在？（N1）**
  - 原文：「把 token 數減一，不能重建較早的遞迴狀態」〔原文 p.1〕。也就是說，狀態只存在於當初寫下的位置；寫完之後沒辦法再得到別的位置的狀態（N1）。
  - 觀察到的錯誤：prompt 3,584 token、間隔 1,792，傳輸端還原了代表 3,584 token 的狀態，排程器卻只記 3,583，多算一個 token，第 11 個輸出 token 開始不同〔原文 p.1、p.3 圖 2〕。
- **有沒有和延後版、寫穿版、背景版比較？**
  - 只有「從 CPU 重載」對「修改過的重算對照組」。修正後 36/36 次生成（每次 64 token）與重算一致（修正前 34/36）〔原文 p.1〕。
  - 序列效能測試：CPU 重載讓 TTFT 少 46–64%，整個請求時間少 1.9–7.0%〔原文 p.1〕。
  - 沒有延後版、寫穿版、背景版。原文明說不證明一般性的確定性、品質等價、併發服務的好處，或超出 GPU 記憶體的容量〔原文 p.1〕。
- **硬體**：之後補記的是 4 張 NVIDIA RTX PRO 6000 Blackwell Server Edition；原文說這不能回推早期各輪用的裝置〔原文 p.1〕。TP＝4、單機〔原文 p.2 表 1〕。
- **軟體**：vLLM 0.1.dev20051+g487ecf187、LMCache 0.5.4、PyTorch 2.13.0+cu130；功能修補動了 LMCache 與 vLLM 共 11 個檔案〔原文 p.2 表 1、§2.3〕。
- **模型架構、模態**：GLM-5.3-Flash（45 層，sparse attention＋linear attention 的混合），用 RedHatAI 的 NVFP4 量化版；FP8 KV 設定；文字〔原文 p.1–2〕。
- **和本研究的關係**
  - **H7 的可行性證據（CUDA 上）**：vLLM＋LMCache 可以把混合模型的狀態檢查點存到 CPU 再載回，但需要一大包修補，而且檢查點位置是固定間隔〔原文 p.2〕。這是「寫入時固定規則」的現況，不是依位置或依重疊分布決定。
  - **正確性風險**：狀態位置和排程位置錯一格就會靜默改變輸出〔原文 p.1、p.3〕。任何 H7 的實作都要有逐位元比對（像本專案的 `kv_bad`），不能只看命中計數〔判讀〕。
  - 證據強度低：單一模型、單一設定、單一作者〔原文 p.1 自述〕。
- **證據等級**：〔原文 p.X〕；對 H7 的意義〔判讀〕。
