## 0. 要回答什麼

08 的結論（FP8 這一階不需要位置策略）只在 32K 量過（08 §5）。長度拉長可能從三個方向改變結果：

1. **BF16 自己變難多少？**（題目一樣、haystack 變長；「lost in the middle」）
2. **低精度的傷害會不會隨長度變大？** 每個 K 的量化誤差都讓 attention 分數多一點雜訊，key 越多、錯的 key 越容易排到前面〔推論〕。
3. **位置在長文裡會不會開始有用？**（同樣 25% 低精度，放前／中／後 vs 隨機）
4. 速度：同樣的儲存層，長度變長後低精度省多少、會合點移到哪裡、反量化占多少。

## 1. 和主線、大掃描的關係

- 主線（07）、大掃描（09）照跑、照判；這裡的結果不能拿來改它們的判定或挑它們要報的數字。
- 這是**探索**：題數小（§3.3），而且格子很多。只能說「看到什麼趨勢」，要寫成結論必須另外登記複賽（新 seed）。
- 32K 那一點在這個實驗裡**用同一支程式、同樣的設定重跑**（不只借 09 的海選），三個長度才能直接比。題目 seed 和 09 海選相同（40000 起），所以 32K 的 teacher-forcing 數字應該和 09 海選同題同格逐位元相同，這是一個檢查（§4.3）。

## 2. 長度

| 名稱 | block 數 | context token | 位置帶（前／中／後，含頭尾） |
|:--|--:|--:|:--|
| 32K | 64 | 32,768 | 1–16／24–39／48–63（和主線相同） |
| 64K | 128 | 65,536 | 1–32／48–79／96–127 |
| 128K | 252 | 129,024 | 1–63／94–156／189–251 |

- 128K 只用 252 個 block：Llama-3.1 最多 131,072 個位置，context＋問題＋答案不能超過（實測產生的題目最長 129,115，§4.1）。這和 RULER 把整段序列算進「128K」的慣例相同。
- 位置帶照比例縮放（`m10_tasks.bands`）：每一帶都是 1/4 的 block。64 個 block 時和主線逐字相同（§4.1）。
- 題目參數和主線相同（`CANDIDATE_PARAMS.json`），**不重調難度**：問題就是「同樣的題目、文章變長，BF16 和低精度各掉多少」。BF16 的答對率照實報。

## 3. 量什麼

### 3.1 格式、放法、佔比

- **格式**：09 §2.1 的 13 種全部（FP8 e4m3 主線粒度、FP8 e5m2、FP8 扣 K 平均、INT8、INT4 每 token、INT4 KIVI、INT4＋Hadamard、MXFP4、NVFP4、INT2 KIVI、INT2＋Hadamard、K8V4、K4V2）＋ BF16（E0，基準）。
- **放法**：F、M、B、R0、R1、ERR、ATT、AXE、ORC（09 §2.3 去掉 R2–R4）；另外每個格式都有 ALL（block 1 以後全部低精度＝主線 E1s）。
- **佔比**：10%、25%、50%、75%、90%。
- block 0 一律 BF16（和主線、09 相同）。

### 3.2 每題記什麼

- **teacher forcing**（09 §3 相同）：對 E0 的 KL、標準答案 log 機率、逐位置 top-1 一致率、第一個 token 對不對。
- **真的生成、計分**（10/16 新加，09 的海選沒有）：greedy、主線的生成長度（T5 120、其他 64 token）、主線的計分（`m10_tasks.score`）。生成的格子：
  - E0（BF16）；
  - 每個格式的 ALL；
  - 主線的三個格式（FP8 主線粒度、INT8、INT4 KIVI）另外生成 F／M／B／R0 在 25%。
- **讀法**：A（全部從儲存載入：量敏感度）；B_idle／B_busy（b32 頻寬，會合點用 `m10_sweep_sim` 推算，參考線來自 §3.4 同一個長度的速度格子；32K 用主線 FP8 格子）。生成只用讀法 A。
- 每列有 `n_blocks` 欄。逐列 CSV 放 `/mlsteam/data/tiara/longctx_m10/`（大，不進 git）。

### 3.3 題目數（試跑後照規則決定，事先寫死）

- 任務 T2–T5，第 1 輪；兩個模型。
- 試跑：每個（模型, 長度）每任務 1 題。
- 正式：n ∈ {12, 9, 6, 3}（每任務每長度），三個長度兩個模型合計的牆鐘時間 ≤ 14 小時，取最大的。
- 3 都超過 → 依序：拿掉讀法 B → 佔比只留 25%、50%、90% → 拿掉 ERR、AXE。仍超過就照實記，用最小設定跑。
- 同一個 seed 在三個長度是同一組內容（鍵、值、問題相同），只有 haystack 長度和位置不同，所以可以跨長度配對。

### 3.4 速度（真的量，`m10_speed grid`）

- 長度 64K（65,536）、128K（129,024），兩個模型；格式：主線 FP8 粒度、INT4 KIVI（主線第 2 階的格式）。
- 主線的 8 個配置（E0、E1、E1s、E1sr、F25、M25、B25、R25；混合配置照比例取 block），頻寬 b16／b32／b48（主線的 `bw.json`，**沒有**為長 context 重新校正）＋ 真實 CPU 層，GPU 閒／忙，2 launch × 5 rep（主線是 3 × 10），參考線 E0、E1（給 §3.2 的讀法 B 推算用）。
- gpu_guard 照常：任何一份不是 CLEAN，那一格的時間不能用、要重量（CLAUDE.md §3）。

## 4. 已經做的檢查（寫這頁之前，CPU）

1. **32K 題目不變**：改 `m10_tasks`（位置帶照比例）前後，32 題（兩個模型、四個任務、seed 10000 與 40000 起）的完整題目 JSON 雜湊逐一相同。
2. **長題目產生得出來、自測過**：64K、128K × 兩個模型 × 四個任務 × 3 題，`_check_item` 全部通過（答案位置在指定的帶、同 seed 兩次相同、標準答案自己計分＝1）；128K 最長 129,115 token。
3. **放法在 252 個 block**：每個放法、每個佔比剛好 k 個、不含 block 0；25% 時 F＝1–63、M＝95–157、B＝189–251。
4. GPU 上的冒煙（§6 的 39a）：還沒跑。

## 5. 怎麼報（事先寫死；探索，不做判定）

- **主圖**：每個模型一張「長度 × 答對率」：E0、主線三種格式的 ALL；每點附「以題為單位」的 bootstrap 95% CI。
- **傷害隨長度**：每個格式，ALL 對 E0 的差（生成的答對率、teacher forcing 的 KL 與第一個 token）在 32K／64K／128K，以 seed 配對算「128K 的傷害 − 32K 的傷害」與 CI。CI 不含 0 才說「隨長度變大」，而且標「探索」。
- **位置**：每個長度，主線三種格式的 F／M／B 對 R0（25%）的生成答對率差與 KL 差（配對 CI）。題數小，只報方向與 CI，不寫成結論。
- **讀法 B**：每個長度讀到多少低精度 block、品質差多少（「沒被讀到 vs 不敏感」在長文是不是一樣）。
- **速度**：E1 對 E0 快多少（每格），和 32K 主線的表並排。
- 所有數字附 run_id；沒跑到的寫 NOT_MEASURED。

## 6. 佇列位置

- 使用者 10/16：「都在之前 32K 實驗後」。所以 90（速度）→ 91（試跑＋決定題數）→ 92（正式）排在**所有** 32K 工作之後（主線、大掃描海選與複賽、只報告的 45／55／60／70／75／88）。
- **例外：39a 冒煙**（約 15–20 分鐘，128K 一題、少數格式，加一次 128K 的小速度格子），排在 39 冒煙之後、大掃描之前。理由：程式第一次跑 128K，現在抓 bug 比 10/18 才發現好。冒煙的數字不進結果；失敗只寫 NEEDS_HUMAN、把 90–92 擱置，不擋其他工作。
- 時程（估計）：32K 工作約 10/18 晚上跑完 → 90 約 6 小時 → 91 約 1 小時 → 92 ≤ 14 小時。10/20 的報告可能只有部分長 context 結果。

## 7. 限制（先講）

- Llama 的 128K 剛好在它支援的上限附近；Qwen2.5-1M 本來就是長文模型（這裡用 HF 路徑，不用 DCA）。
- 頻寬沿用 32K 校正的 `bw.json`，所以長 context 的會合點不在 16／32／48；這是「同樣的儲存、文章變長」的情境，不是重新校正的實驗。
- 題目沒有重調難度；BF16 在 128K 可能很低，這本身就是結果之一，但會讓「低精度掉多少」的空間變小（地板效應），報告要並列 E0。
- teacher forcing 只看標準答案的機率；生成的格子有限（§3.2）。
