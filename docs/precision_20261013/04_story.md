# 04　故事：改成「精度」這條線，論文怎麼寫

> 回到 [README](README.md)。實驗計劃見 [03](03_plan_3090.md)；前作機制見 [02](02_papers.md)。
> **這一頁沒有任何新數字。** 故事裡要填數字的地方都寫〔待量〕，等 [03](03_plan_3090.md) 跑完才填。

**一句話**：故事從「寫入時決定放哪一層沒有用」接下去。精度看起來是唯一「丟了就回不來」、需要提早決定的東西。但在 Cake 式還原下，一個 block 的精度只有在**被讀到**時才影響品質，而會不會被讀到要到讀取時才知道。這週的實驗決定故事停在「格式比位置重要」（故事 A），還是走到「依讀取機率／敏感度配精度」（故事 B 或 C）。

---

## 1. 故事主幹（不管結果如何都成立的部分）

照 Cake 的敘事順序（情境 → 牆 → 現有做法 → 空白 → 我們的問題 → 怎麼驗）：

1. **情境**：長對話的使用者會離開再回來。回來時，之前的 KV 要嘛存在 CPU 或 SSD、要從那裡搬回來，要嘛要重算。還原時間直接變成等待時間（TTFT）。
2. **讀取端已經會自己調整**：
   - Cake：GPU 從前面重算，I/O 從後面載入，在中間會合；會合點隨 GPU 忙碌程度與頻寬自己移動。
   - CacheGen：每個 chunk 事先編好幾種壓縮等級；傳送時依實測頻寬逐 chunk 挑等級，太慢就改傳文字讓接收端重算。
3. **我們第一階段的結果（負面）**：「寫入時依位置決定放哪一層」在所有測過的條件下，都被「滿了再搬」的延後版追平。原因是位置在之後一樣看得到；真正有用的資訊（GPU 忙不忙、頻寬）寫入時反而拿不到。
4. **那精度呢？** 精度和放置不一樣：存成 FP8 就回不去 BF16。這看起來是唯一「真的要提早決定」的東西，所以值得單獨問。
5. **這週的關鍵觀察（待驗）**：在 Cake 下，block 存成什麼精度，**只有在它被載入時**才會影響品質；被重算的 block 一律是精確的 BF16。會不會被載入，由會合點決定，而會合點是讀取時才知道的。所以「依位置決定精度」其實混了兩件事：
   - **敏感度**：這一段壞一點，答案會不會錯；
   - **讀取機率**：這一段的低精度備份到底會不會被讀到。
6. **怎麼驗**：同樣的位元組、codec、attention，只換 FP8 的位置（前／後／隨機）；品質分「強制全載入」和「Cake 實際還原」兩種讀法；GPU 閒／忙；看第 2 輪（[03 §2](03_plan_3090.md#2-規則預測判準事先登記)）。

**這個主幹的好處**：第一階段的負面結果不用丟掉，它變成故事的第一個發現（放置可以延後），精度是第二個發現。兩者合起來回答同一個問題：**提早決定，到底有沒有不可取代的價值？**

## 2. 「寫入時決定」還要不要？

老師說「先不用把寫入時決定留成一定要有的設計，最後有沒有必要，讓實驗決定」。目前的判斷：

- **這週所有配置都只描述「最後的版面」**（哪些 block 是 FP8），不規定什麼時候決定。
- **延後一樣到得了同一個版面**：先存 BF16 到 CPU，降級到慢層時才量化。CPU 層本來就存 BF16，所以 SSD 一個位元組都不多寫〔算術，D6 §4.4〕。
- **延後要付的只有兩件事**（D6 §4.4）：CPU 暫時多佔一些空間；降級完成前就回來的使用者，拿到的是 BF16（反而品質更好，只是載入慢一點）。
- **只有一種情況寫入時決定比較划算**：沒有 CPU 層、直接寫 SSD，而且 SSD 寫入頻寬是瓶頸。這是第一階段 D1 的區域，在單卡、實測參數下沒有持續發生〔模擬，D1、F6〕。

**所以故事裡的設計點（如果有）會是「降級時或讀取時決定精度」**，和 10/12 提的「寫入簡單、讀取聰明」一致。這一點這週不量，等結果出來再決定要不要量。

## 3. 三種結果，三個故事

對應 [03 圖 2](03_plan_3090.md#24-判準開跑前寫死) 的出口。**哪一個成立，由實驗決定，不由我們偏好決定。**

### 故事 A：停損（K1、K2 或 K3）——「精度是 codec 的問題，不是位置的問題」

**觸發**：FP8 和 INT4 兩階都「均勻就夠」（K1、K1s，或 FP8 階換 codec 就夠的 K3）；或在「均勻不夠」的那一階，位置不比隨機好（K2）。目前的舊證據和文獻最支持這個結果（[01 §3](01_advisor_feedback.md#3-我們自己發現老師沒提但會影響計劃的一件事)、[02 §4.2、§5.2](02_papers.md#5-vllm-的-fp8怎樣才算正確校準)）。

**暫定標題**：
- 中：讀取端自適應時，提早決定 KV 的放置與精度都不重要
- 英：*Decide Late, Read Smart: Write-Time KV Placement and Precision Under Adaptive Restore*

**摘要骨架**（數字都〔待量〕）：
> 長對話的 KV 要在使用者回來時還原。近年的系統在寫入當下就決定 KV 放哪一層、存成什麼精度，常用的依據是 token 的位置。讀取端也已經會自適應：Cake 讓重算和載入在中間會合。我們問：讀取端自適應時，提早決定還有沒有不可取代的價值？
> 放置方面，寫入時依位置放置在所有測過的條件下都被延後版追平〔第一階段〕。精度方面，我們把「位置敏感度」和「讀取機率」分開量：在 Cake 還原下，前段的低精度備份在 GPU 閒時有〔待量〕% 沒被讀到；控制 attention sink 之後，強制全載入時前段和後段的敏感度差〔待量〕；同樣位元組下，依位置配精度比隨機配〔待量〕。而〔正確校準的全 FP8／只保護 sink 的 FP8／K 去偏移的 FP8／全 INT8〕在〔待量〕題上就符合品質要求。
> 結論：在我們測過的範圍內（兩個 GQA 模型、FP8 與 INT4 兩個工作點、≤32K），KV 精度是 codec 和比例的問題，不是位置的問題；放置和精度都可以延後到降級或讀取時再決定。

**貢獻**：
1. **量測方法**：逐 block 記錄「重算／載入 BF16／載入 FP8」的還原器；用「強制全載入」和「Cake 實際還原」兩種讀法，把敏感度和讀取機率分開。這是我們找到的前作都沒做的事（[02 §4](02_papers.md#4-最接近的做法新穎性威脅)）。
2. **發現 1（放置）**：寫入時依位置放置沒有不可取代的價值（第一階段，GPU 上 36 組比較）。
3. **發現 2（精度）**：在 Cake 下，「前段量化沒掉品質」〔是／不是〕因為沒被讀到；位置規則〔沒有〕勝過同比例隨機；〔全 FP8／只保護 sink／換 codec〕就夠。如果是換 codec 才夠，機制是「K 的固定偏移 × FP8 只有 3 位尾數」〔待驗〕。
4. **方法上的提醒**：未校準的 FP8、沒被讀到的備份、沒控制的 sink、比雜訊還小的判勝門檻，這四個陷阱都會讓「位置策略有用」的假象出現。我們自己踩過第一、二、四個。

**這個故事站不站得住**：
- 優點：每一步都有事先登記、有反方對照；負面結果有清楚的機制解釋。
- 弱點：「沒用」的論文要靠方法和範圍說服人。單模型、單長度（32K）、限速模擬的層，會被問「換個設定會不會不同」。至少要補 Llama 的兩個端點，最好再一個長度。
- 適合的地方：ICPE（效能工程，重視量測方法）的研究論文或 workshop／Emerging Research。

### 故事 B：位置有貢獻——「依讀取機率配精度」

**觸發**：K1–K3 都不成立，位置規則對隨機有穩定差距，而且和強規則（S25）差不多好。

**核心論點**：在 Cake 下，最該省的是「很少被讀到」的 block。讀取機率主要由位置決定（從後面往前載入），所以位置是一個**便宜、寫入時就拿得到**的訊號，效果接近要算 attention 的強規則。

**要補的證據**（這週做不完）：
- 讀取機率要從真實的 GPU 忙碌分布和頻寬分布來，不能只用兩個狀態；
- 第二個模型、第二個長度；
- 和 PatchKV（依 attention 風險逐 block 混精度）正面比較；
- 放進真實系統（vLLM 的 connector）的可行性。

**適合的地方**：CCGrid 12/1（Track 4：LLM 系統）。時間緊，但比 ICPE 11/16 實際。

### 故事 C：有用的是敏感度，不是位置

**觸發**：有穩定差距，但強規則（看內容）明顯勝過位置規則。

**核心論點**：位置只是敏感度的一個很弱的代理。這和 ZipCache、MuKV 的觀察一致：attention 的位置偏差要用內容訊號修正（[02 §3](02_papers.md#3-位置敏感度文獻真正支持什麼)）。

**問題**：新穎性威脅最大。PatchKV 已經在「重算集＋載入集」的結構下，依 attention 風險逐 block 混精度；Cocktail、DiffKV、SemKV 都在 GPU 內依內容選精度，而且 SemKV 的指標大多寫入時就算得出來（[02 §4](02_papers.md#4-最接近的做法新穎性威脅)）。要站得住，必須說清楚我們多了什麼：例如把 Cake 的讀取機率和敏感度合在一起，或證明在讀取時（而不是存的時候）決定比較好。

## 4. 一頁對照：我們和最接近的做法差在哪

（細節與出處見 [02](02_papers.md)；這裡只放結構。）

| 做法 | 精度怎麼決定 | 什麼時候決定 | 和重算／載入的關係 | 量了品質嗎 |
|:--|:--|:--|:--|:--|
| Cake | 不決定；均勻量化當成正交技術 | — | 雙向會合，會合點自然形成 | **沒有**（只報速度） |
| SparKV | 逐層非均勻，不隨位置變 | 串流前 | 拿「Cake＋載入段量化」當 baseline；說位置是**成本**的差勁代理 | 有，但沒量品質對位置 |
| CacheGen | 依頻寬逐 chunk 挑等級 | 讀取（傳送）時；寫入時存多個版本 | 逐 chunk 可改傳文字重算，依序處理 | 有 |
| PatchKV | 依 attention 風險逐 block | 卸載時凍結 | 全部量化存起來；恢復時重算集不讀，只有載入集讀回 | 有（比均勻 INT8 快 5.6%） |
| HA-RAG | 依存取熱度逐 chunk | 離線 | 多層放置，沒有重算 | 有逐格式品質；混精度沒和均勻 INT8 並排 |
| KIVI／KVQuant／QEvict／PM-KVQ | 位置規則（最近的、sink） | GPU 內 | 沒有 | 有，但都在 2–4 bit |
| Cocktail／DiffKV／SemKV | 內容（query 相似度、attention、內部指標） | GPU 內 | 沒有 | 有；SemKV：在 Mistral 上隨機明顯比內容指標差 |
| **這週的實驗** | 位置 vs 隨機 vs 均勻（同位元組、sink 控制） | 不規定（只看最後版面） | **逐 block 記錄實際讀到什麼** | 有，分兩種讀法、兩輪 |

## 6. 這週結束時，故事要能回答的三句話

1. **位置資訊到底多幫了什麼？** F25、M25、B25 對 R25，在同樣位元組下，品質與延遲各差多少〔待量〕。
2. **前段量化沒掉品質，是不敏感，還是沒被讀到？** 讀法 A vs 讀法 B，加上 F25 的 FP8 被讀到幾個〔待量〕。
3. **全 FP8 夠不夠？不夠的話，是 sink、格式，還是位置的問題？** K1、K1s、K3〔待量〕。
