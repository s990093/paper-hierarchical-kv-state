## 1. 原文（2026-10-13，回覆 10/12 進度報告）

> 6 組裡沒有一組能同時贏過簡單策略和延後版，這個結果其實很有用。你願意把原本的方法停下來，而且用時間線說明差別來自哪裡，我覺得這輪有進步。研究本來就會遇到想法被推翻，能把原因弄清楚，後面才不會繼續花時間在同一個地方。
>
> 轉去看精度，我覺得沒有歪掉。不過下一個問題要更明確：在品質要求和資源限制相同的時候，依位置決定精度，為什麼會比全 FP8 或簡單的混精度策略更好？現在先不用把「寫入時決定」留成一定要有的設計，最後有沒有必要，讓實驗決定。
>
> 例如前段量化後品質沒掉，我想確認，是那一段真的比較不敏感，還是 FP8 備份根本沒被讀到，已經被重算成 BF16 了？如果是後者，重算的時間要一起算。GPU 忙起來改成多載入，或量化讓搬運變快、會合點改變，品質還守得住嗎？至少也看一次下一輪重用，不能只看第一次還原。
>
> 另外，StreamingLLM 的 attention sink 是最前面少數 token，不能直接推成整個前半段都比較重要。MuKV 也有用內容訊號修正 attention 的位置偏差。所以你要壓前段還是後段，先寫成清楚的規則，再去驗它，不要先把文獻觀察當成答案。Cake 本身已經測過搭配 KV 量化，CacheGen 也會依 chunk 調整壓縮或重算，這幾個最接近的做法要讀到機制。
>
> 這週先維持同一台機器、同一個模型、32K 以內。完整 BF16 和正確校準的全 FP8 先當兩個端點，再挑一個比例，例如 25% 的 block 用 FP8，比較前段、後段和隨機位置。這幾組的實際 bytes、codec 和 attention 計算方式要相同；品質測試把需要的資訊放在前、中、後，不要只用容易滿分的單題撈針。有穩定差距，再加一個敏感度感知的強規則對照，不用一開始把所有設定掃完。
>
> 量測也先整理一下：SSD／NFS 是限速模擬，就保留這個範圍；還原器比正常 vLLM 慢的原因，以及 6.2% 波動和 5% 判勝的差異，要釐清。0.03 毫秒是反量化微基準，整體還要算編碼、搬移和等待。下次帶品質對延遲的比較圖，以及真正用到哪些低精度 KV、重算了哪些的分解，我們比較容易判斷有沒有新的效果。
>
> CVPR 的可能可以留著，但目前還是文字系統問題。若之後要往視覺走，要先找到現有方法處理不好的視覺證據或時間關係，不能只是換個 VLM 就算。先不要同時開第二條線。ICPE、CCGrid 可以考慮，也一樣要有站得住的研究結果；你列的日期都是摘要截止，ICPE 全文是 11/16，CCGrid 全文是 12/1，都是 AoE。
>
> 不用先逼自己這個月一定生出一篇 paper。先看這週能不能回答「位置資訊到底多幫了什麼」；如果全 FP8 已符合品質要求，速度也不輸，就把位置策略停下來。你前面搭的量測和還原流程還是用得上，我們用這些結果一起收斂下一步。

## 3. 我們自己發現、老師沒提但會影響計劃的一件事

**舊紀錄顯示，Qwen2.5-7B-1M 的 FP8 失敗，主要不是校準造成的。**

- 3090（8/31，Qwen AWQ 權重，32K 撈針 20 題）：BF16 20/20、FP8（靜態、未校準）1/20、INT8（每 token 每 head 動態）19/20、INT4 0/20〔實測 20260831-181930-m5-needle；D6 §4.5 重算〕。
- MI300X（9/16，BF16 權重，要求 131,072 token；實際 prompt 長度記在已遺失的 CSV 裡，同設定的 Llama 是 129,024；撈針 20 題）：BF16 20/20、FP8 2/20、**FP8 每 token 每 head 動態縮放 0/20**、INT8 18/20、INT4 0/20〔實測 20260916-065920-m5-b-qwen7b-needle，F4 稽核轉錄〕。
  - 注意：動態縮放的 FP8 走的是另一個 attention kernel（TRITON_ATTN，F3 §4.4），和靜態 FP8（ROCM_ATTN）比會混到 kernel 差異〔判讀〕。
  - 但動態 FP8 和 INT8 都走 TRITON_ATTN：0/20 對 18/20 這組比較**沒有 kernel 混淆**，支持「格式」的解釋〔判讀，獨立複核建議補上〕。
  - 3090 那次用的是 AWQ 量化權重，和 KV 精度混在一起〔判讀〕。這週改用 BF16 權重。
- 8/31 的分析（commit `c4d24f7`，用高斯合成資料）：FP8 e4m3 只有 3 個尾數位元，相對誤差約 2.6%，**改縮放方式幾乎沒幫助**（靜態 2.64% vs 動態 2.56%）；INT8 每 token 每 head 只有 0.65%〔算術，`code/quant_error.py`，高斯資料，不是真實 KV〕。
- Llama-3.1-8B 則相反：MI300X 上撈針 64K／129K 五種精度都 20/20〔實測，D6 §4.5〕。

**對計劃的影響**：
1. 「正確校準的全 FP8」要先定義清楚。正確校準能修好的是「溢位和落入次正規區」，修不好「尾數只有 3 位」（[03 §1](03_plan_3090.md#1-固定的條件開跑前寫死)、[cards/P04](cards/P04_vllm_fp8_calibration.md)）。
2. 如果 FP8 在 Qwen 上仍然不過品質，第一個要問的是「**換成同樣 8 bit 的 INT8 就過了嗎？**」。如果是，問題在 codec，不在位置，位置策略一樣要停（停損 K3，[03 §2.4](03_plan_3090.md#24-判準開跑前寫死)）。這一條已加進計劃。
3. **但這些舊結果本身的設計有問題**：題目太簡單（撈針碰天花板）、題數太少、情境不同（vLLM 原生 FP8 從第一次 prefill 就讀 FP8）、有混雜（AWQ 權重、換 kernel）。所以不能用它們選模型。改成兩個模型都跑端點，再照事先寫好的表選主模型（[03 §1.1](03_plan_3090.md#11-模型兩個模型都跑端點再照規則選主模型)、[05 §3](05_QA.md#3-llama-全部-2020是不是實驗設計有問題)）。
