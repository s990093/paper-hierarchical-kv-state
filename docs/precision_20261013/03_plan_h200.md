## 0. 這週只回答一個問題

**問題**：在同樣的品質要求、同樣的資源（存的位元組、頻寬、GPU 可用度）下，依位置決定哪些 block 用 FP8，會不會比「全 FP8」或「同比例隨機放」更好？

把「位置可能有用」拆成三個機制，每個都要能單獨量到：

| 機制 | 白話 | 怎麼量 |
|:--|:--|:--|
| **敏感度** | 這一段壞一點，答案會不會錯 | 強制全部從儲存載入（沒有重算），只看品質（§2.2 讀法 A） |
| **讀取機率** | 這一段的 FP8 備份到底有沒有被讀到 | Cake 實際還原，逐 block 記錄來源（§2.2 讀法 B） |
| **速度** | FP8 讓搬運變快，會合點往前移 | 限速層 × GPU 閒／忙的還原時間（§4） |

**這週不做**：500K、VLM、訓練任何東西、預測器、容量掃描、新的「寫入時 vs 延後」比較，以及強規則（除非 §2.4 的「穩定差距」成立）。§R3 會重跑第一階段的 B 主設定，那只是用同樣的程式確認換機器後方向不變，不是新的比較。

**也不做、但要記著的對照**：CacheGen 式「讀取時才選精度」——每個 block 同時存 BF16 和 FP8（存量 1.5 倍），還原時依當下狀況挑〔判讀，依 [cards/P02](cards/P02_CacheGen_mechanism.md)〕。它的存量不同，不符合「同樣資源」，所以不放進這週的比較；但如果位置策略活下來，它是必須面對的上界。

| 長度 | context 64 個 block × 512 token＝32,768 token；問題和答案另外接在後面 | 老師：≤32K |
| block | 512 token。每 token 的 KV：Llama＝32 層 × 2 × 8 head × 128 × 2 B＝128 KiB，一個 block＝64 MiB；Qwen＝28 層 × 2 × 4 head × 128 × 2 B＝56 KiB，一個 block＝28 MiB（BF16）〔算術，HF config；開跑前用實際 config 核對〕 | 沿用第一階段的粒度 |
| FP8 codec（預設） | e4m3fn。scale＝每個（block, 層, K/V, KV head）的 amax ÷ 448，**編碼當下用這個 block 自己算**；FP8 block＝14 MiB＋scale 896 B〔算術〕。D1 可能換成更好的粒度（下一列） | 不會溢位；每個 block 自己校準，沒有「校準資料和實際資料不同」的問題 |
| 「正確校準」的定義 | D1 比 2–3 種 scale 粒度（每 block 每 head／每 channel／每 token），用 KV 重建誤差和 20 題小測挑**最好的一種**，之後所有 FP8 配置都用它。**要寫明兩件事**：scale 怎麼來（每 block 動態，不需要校準資料）；尾數只有 3 位這件事，任何 scale 都改不了 | 挑最強的 FP8 當端點，對停損是保守的方向（讓「全 FP8 就夠」比較容易成立）。vLLM 0.28 的原生 FP8 只有「checkpoint 的 per-tensor scale 或 1.0」兩種，`--calculate-kv-scales` 已移除〔程式碼，[cards/P04](cards/P04_vllm_fp8_calibration.md) §1〕，所以不拿它當端點 |
| INT4 codec（第 2 階才用，§2.5） | 4-bit 整數。D3 用 KV 重建誤差和 20 題小測，從兩種分組挑**最好的一種**：(a) 每 token 每 head 對稱（vLLM `int4_per_token_head` 的格式，不含旋轉）；(b) KIVI 式：K 每 channel、V 每 token，group 32。**不留全精度窗口**（那本身就是一條位置規則） | 和 FP8 同樣的原則：挑最強的均勻格式當端點，對停損是保守的方向 |
| 先量 K／V 的分布 | D0 花約 30 分鐘：BF16 權重的 Qwen，3–5 個 32K prompt，記錄 RoPE 之後每層、每 KV head、每 channel 的 max\|K\| 與平均 K，以及每層 max\|V\| | 外部量測（第三方 fork，GPTQ 權重）顯示 Qwen2.5-7B 的 max\|K\| 約 423（< 448），而且少數 channel 有很大的固定偏移（k_proj bias）〔文件，P04 §4〕。這決定 FP8 失敗是「溢位」還是「偏移 × 3 位尾數」 |
| torch 的 FP8 轉型 | 單元測試印出 `torch.__version__`，並檢查編碼後沒有 NaN／Inf、被截在 ±448 的比例為 0 | torch 2.13 溢位會截在 448，torch 2.9 會變 NaN〔程式碼，P04 §3〕 |
| attention 路徑 | 所有配置都一樣：FP8 block 載入後**先反量化成 BF16**，寫進同一個 BF16 KV 緩衝，再用同一個 attention kernel | 老師：codec 和 attention 計算方式要相同。不用 vLLM 原生的 FP8 attention，因為那會換 kernel |
| 儲存層 | CPU：pinned 記憶體，真的 H2D。「SSD／NFS」：同一份 pinned 記憶體加限速器（`m7_restore_harness.Tier`），**只叫「限速層 X GiB/s」** | 老師：SSD／NFS 是限速模擬，保留這個範圍 |
| 限速器的位元組 | **改成依每個 block 的實際位元組計時**（FP8 block 只算 14 MiB＋scale） | 現在的 `_load` 一律用 `chunk_bytes`（BF16），FP8 會被算錯（`code/m7_restore_harness.py` 的 `_load`） |
| GPU 忙 | `code/m7_busy.py` 背景 matmul；兩個狀態：閒、忙（調 duty 讓重算約慢 2 倍，實測倍數寫進結果） | 第一階段 C5 的做法。**和 Cake 不同**：Cake 用「token budget 佔比」模擬 GPU 忙（例：512 裡只給 Cake 256＝50%）〔原文 Cake ICML §5.1 / p.6，[cards/P01](cards/P01_Cake_quant_mechanism.md)〕。要寫明 |
| 會合方式 | 不事先規劃：重算線每算完一個 block 就看下一個是否已載入，兩條線交錯就停（harness 的 `cake` 模式） | 和 Cake 一樣：會合點是自然形成的，沒有估計器〔原文 Cake ICML App. A–B.2 / p.12–13〕 |
| I/O 粒度 | 載入與重算都用 512 token | **偏離 Cake**：Cake 的 I/O chunk 是 128 token、重算是 512〔原文 Cake ICML §5.1 / p.5〕。512 會讓會合點跳動變大（§5.3），要寫明 |
| 生成 | greedy（temperature 0），每題最多 64 個 token | 品質分數才可重現 |
| 版本 | H200 上的 conda 環境 `tiara`（Python 3.12、vLLM 0.28.0，和 3090 同版）；`torch`、CUDA、driver 的版本照實記錄（§R0）；harness 的 git commit、`SLURM_JOB_ID`、節點名寫進每個 run 的 `context.txt` | CLAUDE.md §4。vLLM 版本對齊，跨平台才有得對照 |

### 1.1 模型：兩個模型都跑端點，再照規則選主模型

**為什麼不直接用舊資料選**：九月的品質實驗有四個問題，不能拿來決定這週用哪個模型（細節見 [05 §3](05_QA.md#3-llama-全部-2020是不是實驗設計有問題)）：
1. 題目太簡單：單題撈針容易滿分，20/20 是天花板，不是「沒有損失」。同一批 Llama 的 GSM8K（120 題）BF16 80.8、FP8 75.8，差 5 分但在雜訊內〔實測 20260916-192213，D6 §4.5〕。
2. 題數太少：20 題，錯 1 題就是 5%。
3. 情境不同：九月是 vLLM 原生 FP8，第一次讀文件時每一層就讀 FP8，誤差會往後面的層傳〔判讀，依 [cards/P04](cards/P04_vllm_fp8_calibration.md) §2.1〕。這週測的是「存起來的那份是低精度、還原時讀一次」。
4. 混雜：3090 那次是 AWQ 權重、scale 1.0；MI300X 那次動態 FP8 換了 kernel。

**做法（寫死）**：
- **每一階精度的端點（E0、E1、E1s）都在兩個模型上跑**：Llama-3.1-8B-Instruct 和 Qwen2.5-7B-Instruct-1M，BF16 權重，同一套題目、同一個 codec、讀法 A＋第 2 輪。
- 選這兩個的理由：Llama 是 Cake（Table 6）、KIVI、ZipCache、SemKV 都用的模型，也是第一階段的模型，**代表性**最好；Qwen2.5 是 KVTuner、DiffKV 報告「Key 特別怕量化」的模型家族，是**壓力測試**。
- **主模型的規則**（端點結果出來後照表走，不看結果再改）：

| Llama 的 E1／E1s | Qwen 的 E1／E1s | 下一步 |
|:--|:--|:--|
| 過 | 過 | 這一階**兩個模型都不需要位置策略** → 往下一階（§2.5） |
| 過 | 不過 | 只在 Qwen 上做 Step 2b（換 codec）。過 → **停（K3）**；不過 → Step 2 在 Qwen 上做，論文寫明「只在 Key 怕量化的模型上才需要」 |
| 不過 | 任何 | 在 Llama 上做 Step 2b。過 → **停（K3）**；不過 → Step 2 在 **Llama** 上做（代表性比較好）。Qwen 不進混合配置 |

- 這樣**主比較（Step 2 之後）只有一個模型**，符合老師「同一個模型」的要求；兩個模型只出現在端點篩選。
- **長度**：兩個模型都用 32K。3090 上 Llama 32K 要 21–23 GB〔算術，沒量過；migration README §2.3〕會很緊；H200 有 141 GB〔規格，§R0 確認〕，這個顧慮不存在。**但範圍不變**：記憶體變大不代表這週要做更長的 context 或更大的模型。

**多花的成本**：端點多跑一個模型，約多半天 GPU〔推論〕。可以分到另一張空閒的卡平行跑。

**為什麼不改用 MHA 模型**（例如 Cake 主表用的 LongAlpaca-7B）：
- 兩個候選都是 GQA，KV 比較小：每 token Llama 128 KiB、Qwen 56 KiB；MHA 的 LongAlpaca-7B 是 512 KiB（Cake Table 1 的數字），是 Llama 的 4 倍〔算術〕。
- KV 小，代表搬運便宜、會合點偏前，FP8 省下的**絕對時間**比較少。但這週的頻寬是用「E0 的會合點落在 block 16、32、48」來選的（§4.1），不是用裝置名稱選。這樣三種會合情況在 GQA 上一樣都量得到，**相對比較不受 KV 大小影響**。MHA 只會讓 Cake 有用的頻寬帶整體往高頻寬移。
- 現在的主流模型（Llama-3、Qwen2.5、Mistral）都是 GQA；MHA 多半是舊模型。LongAlpaca-7B 長文能力比較弱，題目很難調到 60–95%〔推論〕（3090 上它最多只能跑 16K，H200 沒有這個限制，但長文能力的問題還在）。
- **要誠實報告的一件事**：GQA 模型在真實 CPU 層上，FP8 能省的還原時間可能只有幾十到幾百毫秒（時間＝位元組 ÷ 頻寬；32K 的 BF16 KV：Qwen 1.75 GiB、Llama 4 GiB；H200 的 CPU→GPU 頻寬 NOT_MEASURED，§R0 量）。這種情況下，FP8 的價值主要是**省空間**（同樣的 CPU／SSD 放 2 倍的對話），不是省時間。報告要分開寫。
- MHA 留到之後當穩健性檢查（第一階段第 1 輪在 MI300X 上已經量過 LongAlpaca 的重算曲線），不放進這週。

## 2. 規則、預測、判準（事先登記）

### 2.1 六個配置

所有配置都存滿 64 個 block，差別只在每個 block 存成 BF16 還是低精度。下面用 FP8（第 1 階）寫；到第 2 階（§2.5）時，同樣六個配置，把 FP8 換成 INT4，其他完全不變。

**先寫死的一條：控制 attention sink。** 除了端點 E1，**所有配置的 block 0（token 0–511）一律 BF16**。
- 理由：文獻支持的「前面要高精度」只有最前面 1–32 個 token（sink），全部落在 block 0 裡；「整個前段比較重要」沒有任何一篇在量化下量過（[02 §3](02_papers.md#3-位置敏感度文獻真正支持什麼)、[cards/P03](cards/P03_position_sensitivity_literature.md)）。
- 不控制的話，「前 25% 存 FP8」會連 sink 一起壓，前／後的比較就混了 sink 效應。老師說的「sink 不能推成整個前半段」就是這個。
- sink 本身的效果用 E1 對 E1s 單獨量。

**配置 E0（全 BF16，品質上限）**
- 輸入：64 個 block。輸出：全部標 BF16。

**配置 E1（全 FP8，老師的端點）**
- 輸入：64 個 block。輸出：全部標 FP8（§1 的 codec），包括 block 0。
- 這就是「Cake＋均勻量化」。Cake 原文只量了速度，沒量品質（[02 §1](02_papers.md#1-cake把量化當成資料雙向會合)）。

**配置 E1s（全 FP8，只有 block 0 保留 BF16）**
- 步驟：block 0 標 BF16，block 1–63 標 FP8。
- 這是文獻裡已知的「保護 sink」規則（KVQuant 保護第 1 個 token、Kitty 保護前 32 個），多存 1/64 的 BF16〔算術〕。它是位置策略要先贏過的「最簡單的位置規則」。

**配置 F25（壓前段，sink 除外）**
- 輸入：n＝64 個 block，比例 ρ＝0.25。
- 步驟：
  1. k ← ⌊ρ·n⌋＝16。
  2. block 1 到 16 標 FP8，其餘（含 block 0）標 BF16。
- 依據〔推論〕：Cake 從前面重算，前段的 FP8 多半不會被讀到；問題接在最後，最近的內容可能比較常被用到。

**配置 B25（壓後段）**
- 步驟：block 48 到 63 標 FP8，其餘標 BF16。
- 依據〔推論〕：後段一定被載入，壓後段才會讓搬運變快。

**配置 R25（隨機，簡單混精度對照）**
- 步驟：用 seed＝題號，從 block 1–63 隨機抽 16 個標 FP8，其餘標 BF16。
- 這是「不用位置資訊、同比例」的對照。位置策略要贏的是它。

**相同的部分**：F25、B25、R25 存的位元組完全相同（16 個 FP8 block＋48 個 BF16 block）；codec、反量化、attention kernel 完全相同。**不同的只有「實際讀到的位元組」**，那正是要量的結果。

**條件式配置（只在對應條件成立時才加）**：
- **Step 2b 的兩個「換 codec」診斷**（E1 和 E1s 都不過品質時才跑；block 0 一律 BF16）：
  - **E1-K0**：K 先減掉每（block, 層, head, channel）的平均，殘差做 FP8，平均另存 BF16，反量化時加回去（多存約 0.2%〔算術〕）。這已經不是純 e4m3，等於非對稱量化，要寫明。過了 → 失敗原因是「K 的固定偏移 × FP8 只有 3 位尾數」〔判讀，依 P04 §4.1〕。
  - **E1-INT8**：每 token 每 head 對稱縮放（和 vLLM 的 `int8_per_token_head` 同格式）。過了 → 同樣 8 bit，換格式就夠。
  - 兩個任何一個過了，都代表是 codec 的問題，不是位置的問題。
- **S25**（Step 3）：敏感度感知的強規則（§2.4 的「穩定差距」成立才做）。候選：每個 block 的風險＝最後 512 個 context token 對這個 block 的 attention 質量（除以能看到它的 query 數，去掉因果遮罩造成的前偏，ZipCache 的做法）× 這個 block 的 FP8 重建誤差（PatchKV 式，寫入時算得出來），從 block 1–63 挑風險最低的 16 個標 FP8。另在 50 題子集上做「逐 block 實測敏感度」當上限（不能部署，只當天花板）。

### 2.2 兩種讀法：把「不敏感」和「沒被讀到」分開

| 讀法 | 怎麼還原 | 回答什麼 |
|:--|:--|:--|
| **A：強制全載入** | 64 個 block 全部從儲存載入（harness 的 `load_only`，所有 block 都有存） | **敏感度**：FP8 放在這裡，答案會不會錯 |
| **B：Cake 實際還原** | 前段重算、後段載入，在 b 會合。b 由 §4 的速度實驗量出來（每個配置 × 頻寬 × GPU 狀態） | **實際品質**：在真實的會合點下，讀到的 FP8 有多少、品質掉多少 |

**每一次還原都逐 block 記錄來源**：`recompute`（重算，精確的 BF16）、`load_bf16`、`load_fp8`。

**讀法 B 的品質怎麼量（省 GPU 的做法，要先驗證）**：
- 重算出來的 KV，和原本 prefill 時存的 BF16 應該**逐位元相同**（同樣的切法、同樣的 kernel；第一階段 `test_m7_correctness.py` 驗過「重算兩次逐位元組相同」）。
- 所以讀法 B 可以「重放」：給定 b，block < b 用原本的 BF16，block ≥ b 用存的版本。
- **D3 先在 20 題上比「真的跑 Cake」和「重放」的輸出**：logits 要逐位元相同（或報最大差）。不相同就改成全部真的跑。

**回答老師的第一個問題**：如果 F25 在讀法 A 掉了品質，但在讀法 B（GPU 閒）沒掉，而且紀錄顯示 F25 的 FP8 block 一個都沒被讀到 → 答案是「**沒被讀到**」，不是「不敏感」。這時 F25 省下的只有儲存空間，重算時間照付（重算時間計入還原時間，§4）。

**附帶的觀察（要量，不要假設）**：Cake 只要重算線至少算完 block 0，sink 就自動是精確的 BF16。所以讀法 B 下 E1≈E1s，除非 GPU 忙到載入線一路載到 block 0〔判讀，依 [cards/P01](cards/P01_Cake_quant_mechanism.md) 第 8 點〕。

### 2.4 判準（開跑前寫死）

**品質要求 ε**（看到任何 FP8 結果之前可以改，改了要記錄）：
- 主判準：所有題目（T1–T5，第 1、2 輪合併），配置 X 對 E0 的**配對**正確率差，bootstrap 95% CI 的下界 > −2 個百分點（非劣性）。
- 輔助：任一任務族的點估計掉幅不超過 5 個百分點。
- 連續指標（答案的 log-prob、對 E0 的 KL）只報告，不進判定。
- **檢定力要求**：如果 E0 vs E1 的 CI 半寬 > 1.5 個百分點，代表題目不夠，先加題再判，**不能因為 CI 太寬就說「沒過」而繼續做**。

**速度「不輸」**：在每個（頻寬, GPU 狀態）格子裡，E1（或 E1s）的還原時間中位數 ≤ 最快的混合配置 ×（1＋δ*）。δ* 的定義見 §5.3。

**「這一階不需要位置策略」**（K1、K1s、K3 任何一條成立 → 這一階結束，照 §2.5 往下一階；已經在最後一階就整個停）：
- **K1**（老師的規則）：E1 在讀法 A 和讀法 B（閒、忙）、第 1 和第 2 輪都過 ε，而且速度不輸。
- **K1s**：E1 沒過，但 E1s 過了，而且速度不輸 → 位置只透過 sink 有用，而保護 sink 是已知規則。
- **K3**（只在 FP8 階，理由見 [01 §3](01_advisor_feedback.md#3-我們自己發現老師沒提但會影響計劃的一件事)）：E1、E1s 都沒過，但 E1-K0 或 E1-INT8 過了，而且速度不輸 → 同樣 8 bit，換 codec 就夠，問題不在位置。
- 兩個模型怎麼合併判斷，照 §1.1 的表。

**「位置沒有貢獻」**（成立就整個停）：
- **K2**：在「均勻不夠」的那一階，F25、B25 在品質對延遲的平面上都沒有勝過 R25（見下面的「穩定差距」）→ 位置沒有比「隨機同比例」多幫什麼，只剩「比例」這個旋鈕。

**穩定差距**（Step 3 的入場條件，三條都要成立）：
1. 同樣的存量位元組下，F25 或 B25 對 R25：讀法 B 的品質差 ≥ 2 個百分點，配對 CI 不含 0，至少在一個 GPU 狀態下成立；而且還原時間不比 R25 慢超過 δ*。
2. 方向在 3 個位置帶任務族（T1–T4 中至少 2 族）裡一致。
3. **換一批新題目（新 seed、同樣題數）重跑，方向和顯著性都重現**。

**繼續**：找到「均勻不夠」的一階，而且在那一階穩定差距成立 → Step 3（強規則對照）。只有「位置規則」和強規則差不多好（或更好）時，位置資訊才算有貢獻。

### 2.5 精度階梯：FP8 不需要，就往下一階（最多一階）

**為什麼要往下**：混精度只有在「最好的均勻低精度也不夠」時才有意義，也就是快掉下品質懸崖的地方。文獻裡的位置效應（保護開頭、保護最近的）也都在 2–4 bit 才量得到（[02 §3.3](02_papers.md#33-支持什麼不支持什麼)）。FP8 很可能還沒到懸崖，在那裡「位置沒用」只代表「FP8 這個工作點不需要位置策略」。

**階梯（寫死，不再加）**：

| 階 | 格式 | 什麼時候跑 |
|:--|:--|:--|
| 第 1 階 | FP8（老師指定） | 一定跑 |
| 第 2 階 | INT4（§1 的 INT4 codec） | 只在第 1 階「不需要位置策略」時才跑 |

**步驟**：
1. 在第 1 階跑端點（Step 1，兩個模型），不過就做 Step 2b（換 codec）。
2. 第 1 階「不需要位置策略」（K1、K1s 或 K3）→ 在第 2 階重跑端點（兩個模型，同樣的題目與判準）。
3. 第 2 階也「不需要位置策略」→ **整個停**：FP8 和 INT4 兩個工作點都不需要位置策略。
4. 任何一階「均勻不夠」→ 不再往下，就在那一階做 Step 2（F25、B25、R25），主模型照 §1.1。

**界線**：
- 只往下一階。2-bit 這週不做：那是 KIVI、KVQuant 的主場，保護開頭與最近的規則已經有人量過；要做必須另寫一份事先登記。
- 第 2 階的判準、題目、ε、δ* 和第 1 階完全相同，不因為第 1 階的結果調整。
- **和老師原話的差別**：老師說「全 FP8 過品質、速度不輸，就把位置策略停下來」。這裡改成「FP8 這一階停，再往下看一階」。理由是上面那段；限制只走一階、事先寫死，是為了避免「換個方式一直試到有結果」（CLAUDE.md §1 規則 2、4）。這個改動是 10/13 自己決定的，10/20 的報告要明講。

### 3.2 題數與難度

- 題數：T1–T4 各 3 個位置帶 × 60 題＝720 題，T5 60 題，共 **780 題**〔設計值〕。
- 為什麼這麼多：配對正確率差的標準誤約為 √(不一致比例 ÷ n)。不一致 5%、n＝780 時約 0.8 個百分點，95% CI 半寬約 1.6〔算術〕，剛好接近 §2.4 的檢定力要求。
- **難度要求（這就是「題目要多難」的答案）**：每個模型、每個任務族、每個位置帶的 **BF16 正確率都要落在 60–95%**。高於 95% 會碰天花板（九月撈針 20/20 的問題），低於 60% 代表模型本身就不會，掉分分不出是誰造成的。
- **怎麼調**（D1，**只跑 E0**）：調干擾數、跳數、段落數、值的數量。只看 BF16 調難度，不會偏向任何低精度配置。
- **兩個模型可以用不同的難度參數**：比較都是「同一個模型、同一題，對 E0 配對」，所以每個模型只要自己不碰天花板就好。參數在跑任何低精度之前凍結，寫進事先登記。
- **不會碰天花板的連續指標**：每題另外記標準答案的 log-prob、答案分布對 E0 的 KL。正確率還沒掉時，這兩個指標已經能看出誤差往哪裡累積（只報告，不進判定）。
- **調不到 60–95% 的任務族**：照實記錄，不進該模型的主判準，報告裡列出來。

### 3.3 每題怎麼跑（讀法 A）

1. 產生 prompt（Qwen 的 chat template），context 剛好 64 個 block。
2. chunk 化 prefill 一次，存下每個 block 的 BF16 版本和 FP8 版本（pinned 記憶體）。
3. 對每個配置（同一個 process 內依序）：
   1. 依配置把每個 block 的 BF16 或「FP8 反量化後」寫進 GPU 的 KV 緩衝。
   2. 算問題的 token，greedy 生成答案，計分。
   3. 用 teacher forcing 算標準答案的 log-prob，以及答案每個位置的分布對 E0 的 KL（E0 的 logits 留在記憶體，不存檔）。
   4. 記下每個 FP8 block 的重建誤差（相對 L2）。
4. 第 2 輪（§3.4）。

**GPU 時間估計**〔推論，沒量過〕：每題 prefill 約數秒，每個配置還原＋作答約 2–3 秒。780 題 × 6 個配置 × 2 輪大約 6–7 小時。品質實驗量的是分數，可以分到 2–3 張空閒的卡平行跑（CLAUDE.md §3：品質 run 污染時保留分數，作廢延遲欄）。

### 3.4 第 2 輪重用

- **用語**：這裡的「第 1 輪」是**還原之後**的第一個問題。原本那一輪（第一次 prefill）用的是 BF16，FP8 只影響存下、之後被載入的 block。vLLM 原生 FP8 則連第一次 prefill 都從量化後的 cache 讀〔程式碼，P04 §2.1〕。兩種協定量到的不是同一件事，報告要寫明。
- **歷史固定**：第 1 輪的回答改用**標準答案的文字**（所有配置相同），避免第 1 輪答錯讓第 2 輪的 context 不同。SCBench 的多輪模式也是這樣做〔原文，[cards/P05](cards/P05_closest_work_mixed_precision.md) §3〕。
- **第 2 輪問另一個位置帶的資訊**（例：第 1 輪問前段，第 2 輪問後段），兩輪的組合輪流。
- 第 1 輪新增的 token（問題＋回答）的 KV 存成 BF16。**存的 FP8 版本不變**，不會從反量化後的值再量化一次。
- 兩種第 2 輪：
  - (a) **留在 GPU 直接重用**：第 1 輪還原的 KV（含 FP8 誤差）原地接著用。
  - (b) **再還原一次**，而且第 2 輪的 GPU 狀態換成「忙」：b 往前移，F25 的前段 FP8 開始被讀到。這就是老師問的「GPU 忙起來改成多載入」。

## 4. 速度測試

### 4.1 怎麼選頻寬

不用「SSD 幾 GiB/s」這種裝置名稱，改用「讓 E0 的會合點落在哪裡」來選：
- 先量 H200 上的逐 chunk 重算曲線 f(i)（第一階段 C1 的做法，用 §5.2 修過的重算）。H200 重算比較快〔推論〕，算出來的 GiB/s 會和 MI300X、3090 不同；跨機器只比會合點，不比 GiB/s。
- 對目標會合點 b* ∈ {16, 32, 48}，取 B＝(64 − b*) × 28 MiB ÷ Σ_{i<b*} f(i)〔算術〕。
- 加一個錨點：CPU 層不限速、真的 H2D。這一組量的是真實 PCIe，最容易受 NUMA 位置和同節點鄰居影響（[H200_SLURM](../H200_SLURM.md) §5.3）；pinned 記憶體要配在 GPU 所在的 NUMA 節點（§R0 量出是哪一個），報告要註明。
- **限速層的下限**：harness 每讀一個 block 都真的做一次 H2D，等「模擬時間」和「真實複製」兩者較晚的那個（`code/m7_restore_harness.py` 的 `_load`）。所以三個 B 都要**明顯低於** §R0 量到的真實 pinned H2D 頻寬；每次讀取另記一欄 `copy_bound`（真實複製比模擬時間晚結束），有出現的格子要標出來。
- 這樣三個頻寬分別是「多半在搬」「一半一半」「多半在算」，結論不會綁在某一個裝置上。

### 4.2 格子與重複

- 6 個配置（E0、E1、E1s、F25、B25、R25）× 4 個頻寬（3 個限速＋CPU）× 2 個 GPU 狀態＝48 格。
- 每格：3 次重開 process × 每次 10 次重複；**同一次重複裡，6 個配置的順序隨機打散**（配對、抵消漂移）。
- 單位是一次還原約 1–5 秒〔推論〕，全部約 1 小時 GPU。
- 包在 `GpuWatcher` 裡；被污染的 run 整批作廢重跑（CLAUDE.md §3）。Slurm job 裡看不看得到同節點其他卡，由 §R0 決定；看不到時 `host_contention` 要回 `UNOBSERVABLE_HOST`，不能回 `QUIET`（CLAUDE.md 規則 7），另外每個 run 記一份同節點鄰居的快照（`squeue -w`）。

### 4.3 每次還原記什麼

- 會合點 b、每種來源的 block 數（`n_recompute`、`n_load_bf16`、`n_load_fp8`）、**存了幾個 FP8、讀到幾個 FP8**。
- 時間拆解（§5.4 的每一段）。
- 逐 block 的來源與開始／結束時間（給圖 B 的時間線用）。

## 5. 量測整理（老師點名的四件事）

### 5.1 SSD／NFS 只是限速模擬

- **做法不變**：限速層＝pinned 記憶體＋計時。這週不量真實 SSD。
- **寫法改**：所有圖表與文字一律寫「限速層 X GiB/s」，不寫「SSD 上」「NFS 上」。
- 第一階段 MI300X 的真實裝置錨點（本地 SSD、NFS）只在附錄引用，不和 H200 的數字放在同一張圖。
- H200 叢集的 `/work` 是整個叢集共用的檔案系統（類型由 §R0 量）。之後真的要錨點，要另外登記，而且要報鄰居負載。這週不做。

### 5.2 還原器為什麼比 vLLM 慢

**已知的事實**：
- harness 的重算是 HF 的模組加上自己寫的 attention 迴圈：eager 模式、每層一個 Python 迴圈、`F.scaled_dot_product_attention` 加 `causal_lower_right` 遮罩和 `enable_gqa=True`、每次 512 token（`code/m7_model.py` 的 `forward_span`）。
- 第一階段對照時，vLLM 的 chunked prefill 一次處理 16,384 token（07 §7 表註）；harness 是 512。
- MI300X 上，和預設 vLLM 比，harness 重算慢 1.7–2.0 倍（F1）。**H200 上：NOT_MEASURED**；§R2 先用沒改過的 harness 量一次，當作復現的一部分。

**要把慢拆成兩層**，因為意義完全不同：
1. **粒度造成的慢**：Cake 要逐 512 token 重算，才能在中間會合。每步的 GEMM 比較小、效率比較低。這是 Cake 天生要付的，**不算 harness 的錯**。
2. **實作造成的慢**：kernel 選擇、eager 模式、Python 開銷。這要修，不然 f(i) 偏大、會合點偏前，Cake 有效的頻寬帶會整個偏移。

**步驟**（D0）：
1. vLLM 0.28（H200 的 conda 環境，預設 attention backend，關 prefix caching；Hopper 上的預設 backend 可能和 Ampere 不同〔推論〕，從 vLLM 的 log 記下實際用的 backend 名稱）量只算的 TTFT：8K／16K／32K，各 6 次；兩種切法：預設、`--max-num-batched-tokens 512`。
2. harness 的 `compute_only`，同樣長度、同樣次數。
3. torch.profiler 拆 harness 的 chunk 0、31、63：attention、GEMM、逐元素運算、kernel 之間的空檔。確認 SDPA 實際用了哪個 kernel（看 kernel 名稱：flash／efficient／math）。
4. 依便宜到貴試修：強制 flash 後端；改用 `flash_attn_func(causal=True)`（seqlen_q ≠ seqlen_k 時是右下對齊，支援 GQA；vLLM venv 裡有 `vllm_flash_attn`，**介面要先查證**）；最後才考慮 `torch.compile`。
5. **接受條件**（寫死）：每個 chunk 的重算時間 ≤ vLLM（512 切法）同位置的 1.2 倍。達不到就照實報比例，並用 F7 的 f 縮放模擬當上下界。

**交付**：一張表，「harness ÷ vLLM(512)」（實作差）和「vLLM(512) ÷ vLLM(預設)」（粒度差）分開列。

### 5.3 6.2% 波動 vs 5% 判勝

- **舊的問題**：第一階段的雜訊底線 δ＝6.2%，但判勝門檻寫 5%（CORE_QUESTION §2）。介於 5% 和 6.2% 之間的「勝」其實分不出來。10/12 報告已經更正過一次：24 格裡 6 格 CI 不重疊，只有 3 格超過 δ（07 §5）。
- **6.2% 從哪裡來**：主要是**會合點的離散跳動**。同一個設定，重算線有時多拿一個 chunk（會合在 6 或 7），TTFT 就跳一階（07 §3.4）。這是 512 token 的粒度造成的，不是計時不準。
- **新規則**（寫死）：
  1. H200 上重量 δ：E0 在每個（頻寬, GPU 狀態）格子，3 次重開 process × 10 次。δ＝各格「3 次 process 的中位數，最大減最小，除以整體中位數」的最大值。
  2. 判勝門檻 δ*＝max(5%, δ)。
  3. 「贏」要同時滿足：中位數的差 > δ*，而且配對差的 bootstrap 95% CI 不含 0。
  4. 每格都報會合點 b 的分布。如果時間是雙峰，就分 b 報，不只報中位數。

### 5.4 0.03 ms 只是微基準

- 0.031 ms 是 MI300X 上、單獨一個 64 MiB chunk、反量化 kernel 的時間（F3，cold 中位數）。**H200 上：NOT_MEASURED**，而且 Qwen 的 block 是 28 MiB。
- 端到端要拆成這幾段，**每段都量**：

| 階段 | 發生在 | 怎麼量 |
|:--|:--|:--|
| 編碼（BF16→FP8，含算 scale） | 寫入時，GPU | CUDA event，每 block |
| D2H | 寫入時 | CUDA event＋位元組 |
| 寫入限速層 | 寫入時 | 限速器的佔用時間 |
| 讀取限速層 | 還原時 | 限速器 |
| H2D | 還原時 | CUDA event |
| 反量化 | 還原時，I/O stream 上（和重算搶 GPU） | CUDA event；另量「有沒有讓重算變慢」 |
| 等待 | 還原時 | 兩條線結束時間的差（harness 已有 `t_wait`） |
| 重算 | 還原時 | 已有 `t_recompute` |
| 新一輪的問題 prefill＋第一個 token | 還原後 | 已有 `new_turn` |

- 寫入時的成本（編碼、D2H、寫入）不在使用者等待的路徑上，但要報，因為它佔 GPU 和頻寬。

## 9. 風險與對策

| 風險 | 後果 | 對策 |
|:--|:--|:--|
| Qwen 在 harness 裡算不對（bias、RoPE 設定） | 所有數字作廢 | R1 先跑正確性測試（Llama、Qwen），D0 修完 attention 再跑一次；過了才往下 |
| torch 的 FP8 轉型溢位變 NaN 或飽和行為和預期不同（版本相依：torch 2.13 截在 448、2.9 變 NaN〔程式碼，P04 §3〕） | codec 靜默出錯 | 單元測試檢查 NaN 與飽和比例；不對就改用 uint8 位元表示自己寫轉換；報告寫明 |
| 想加 vLLM 原生 FP8 當參考點 | P04 的分析是 sm_86 的。H200（sm_90）上 vLLM 的 FLASH_ATTN 會用 FA3 收 FP8 KV〔程式碼，P04 §2 表〕；vLLM 部落格說 Hopper 的 FA3 是整個 attention 用 FP8 算，128K 撈針曾從 BF16 91% 掉到 13%，修正後 89%〔文件，P04 §2.1〕。這和我們「反量化成 BF16 再算」是不同的東西；Qwen 也沒有現成的 KV-only scale checkpoint | 這週不做。真要做：寫明 H200 上是「連 attention 都 FP8」；FlashInfer 在 sm_90 上的 FP8 路徑怎麼算〔未查證〕 |
| 任務太簡單（BF16 滿分）或太難 | 看不到差異，或 E0 本身就不可靠 | D1 用 BF16 調難度到 60–95% |
| 題數不夠，CI 太寬 | K1 判不下來 | §2.4 的檢定力要求：先加題再判 |
| 重算不是逐位元相同 | 讀法 B 的重放不能用 | 改成全部真的跑 Cake，GPU 時間約多 1 倍 |
| 同節點的鄰居（Slurm 看不到別人的卡） | 時間數字被 PCIe／host 記憶體爭用灌水，而且可能看不出來 | §R0 先確認可見性；`gpu_guard` 回 `UNOBSERVABLE_HOST`；每個 run 記鄰居快照；配置順序隨機打散、配對比較；報告寫明「只能部分觀測」。品質 run 保留分數 |
| 帳號核准、排隊 | 時程整個往後移 | 等帳號時先寫和機器無關的程式（§7）；lab 合計 4 張卡和同學共用，一次最多佔 2 張 |
| 單一 job 最長 48 小時 | 長的 run 被砍 | 每題算完就寫 CSV，重跑時跳過已完成的 `item_id` |
| 叢集資料「不保證永遠存在」 | run 目錄遺失 | 結果 CSV 每天 push；原始 run 目錄每天 rsync 回 Mac 或 3090 的 `/ssd7`（[H200_SLURM](../H200_SLURM.md) §5.4） |
| vLLM 0.28.0 的 wheel 和叢集的 driver 不合 | 環境裝不起來 | 照實記錄錯誤、停下來回報（CLAUDE.md 規則 2），不換版本硬裝 |
| 第一階段在 H200 上不重現 | 後面的速度實驗沒有可信的基準 | §R3 事先寫好怎麼判、不重現時做什麼 |
| 修 attention 後 f(i) 大變 | 第一階段的頻寬帶全部移位 | 預期中的事，這週的數字全部重量，不和 MI300X 混用 |
| 被說是挑模型 | 結論的範圍被質疑 | 兩個模型都跑端點，主模型照 §1.1 事先寫好的表決定；論文寫明範圍 |
