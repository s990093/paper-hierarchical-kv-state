# 03 瓶頸、空白，以及對第一階段的意義

> **一句話**：寫入的瓶頸有五種（`01` §2）。各篇大多只量到其中一兩種，而且幾乎都是全部寫、沒有比較寫入策略。所以「哪一種寫入時機、在什麼容量與裝置下最好」，在評測卡涵蓋的範圍內還沒有人系統性地回答〔複核修正：補範圍限定〕。這正是第一階段 B 實驗要做的；建議再加一個「選擇性寫入」的對照組。

## 2. 這個領域的空白（依評測卡涵蓋的論文）

1. **寫入幾乎都是「全部寫」。** E04 的 8 篇論文裡，只有 Strata 把寫入策略做成可切換的設定（延後寫、寫穿、選擇性）；MTDS 依重用排優先順序；Tutti 全寫但等空檔才寫；KVDrive 全寫 SSD 再往上提。CachedAttention、Bidaw、LMCache、Mooncake 都是全部寫（E04 共同模式 2〔判讀〕）。〔複核修正：原句沒有限定「E04 的 8 篇」。範圍放大到本資料夾讀的其他卡，還有：SGLang HiCache、vLLM `store_threshold`、Dynamo KVBM 的寫入策略可切換（E02，軟體而非論文）；HCache 依層決定有些層不存（E03）；AdaptCache、EvicPress 存入時決定壓縮與層（E05）〕
2. **沒有一篇比較「寫入策略 × 容量壓力」。** 連 Strata 也沒有做這個消融（E04 共同模式 2〔判讀〕，範圍是 E04 的 8 篇）〔複核修正：補範圍〕。
3. **沒有系統依「位置」上的重算成本 vs 傳輸成本決定不存或放哪。** 機制上的開關有，例如 LMCache 的 `skip_save`、`store_threshold`、HiCache 的 `write_back`，但決定的依據都不是成本（EVAL §2.4〔判讀〕，範圍是 E02 查的 5 個 KV 層系統）。〔複核修正：原寫「沒有系統依『重算成本 vs 傳輸成本』決定不存或放哪」，與 HCache 不符。HCache 在寫入時依離線量的傳輸與計算速度，決定每一層存 hidden state、KV 或不存（回來時從 token 重算），例：OPT-30B＝40 層 hidden＋8 層重算（HCache p.7 §4.1.2、§4.2，p.10 表 3；E03 共同模式 4 的複核修正）。所以「依成本在寫入時決定不存」已有前例，空白只剩「依 token 位置」這一點〕
4. **慢層常常沒有真的量到。** E04 的 8 篇裡，端到端真的讀 SSD 的只有 Bidaw、CachedAttention、Tutti，和部分的 KVDrive；Strata 只有一個 DeepSeek-V3 子實驗；Mooncake、LMCache 沒有 SSD 實驗（E04 共同模式 1）。E03 裡，HCache（4 顆 PM9A3）與 py-kvcache 用真實 NVMe；Cake 用延遲注入模擬（E03 共同模式 1）。〔複核修正：原把 Cake 引成 E04 共同模式 1（Cake 在 E03），並漏了 HCache、py-kvcache 與 Strata 的子實驗〕
5. **沒有重複、沒有誤差棒。** E04 的 8 篇都沒有寫重複次數（E04 共同模式 6）。

**要小心**：這些「沒有人做」都只限於評測卡涵蓋的範圍，不是完整的查新。動手前要再做一次查新（例如用 `novelty-check`）。〔複核修正：原寫「評測卡涵蓋的論文（54 篇論文與系統）」。EVAL_FOUNDATIONS 第 8 行的說法是 11 份卡共 54 篇論文，另有 5 個 KV 層系統、6 個工具等；而本資料夾只讀了 E02、E03、E04、E05、E07 五份卡。複核者另外抽查了 E06、E08 的「寫入時／prefill 後」相關段落，沒有看到依位置在寫入時決定層級的系統，但沒有逐張讀完〕

## 3. 對第一階段的意義

### 3.1 我們的策略對應到哪些系統

| 第一階段的策略 | 對應的寫入做法 | 實際系統 |
|:--|:--|:--|
| R0、S1 | 寫穿＋LRU | LMCache、SGLang 上游預設 |
| S0 | 全部寫到單一慢層 | Cake 的假設 |
| S2a、S3 | 寫了再刪、一開始不寫 | 老師點名；用來量「刪掉」的代價 |
| S2b | 寫穿＋成本感知逐出 | Pensieve、Fancy-eviction 的成本感知（不過它們是逐出時決定） |
| S4、S4+ | 延後寫 | Mooncake Store、HiCache／Strata 的 write-back |
| **S5** | **寫入時依位置決定狀態** | **評測卡範圍內目前沒有看到**（寫入時依層決定的有 HCache，依整段 context 的有 AdaptCache、EvicPress，依注意力重要度的有 KVDrive）〔複核修正：補範圍與最接近的前例〕 |

### 3.2 建議加一個對照組：選擇性寫入

**「命中 2 次才寫」**有幾種版本：Strata 論文的預設是存取次數超過門檻 2 才從 GPU **備份到 CPU**；Dynamo KVBM 是頻率 ≥2 才**寫進磁碟**；SGLang、vLLM 也有類似的開關〔10/8 修正：原寫「Strata 的預設」而未說明 Strata 備份的是 CPU 層，見 os_mapping 複核〕，但目前第一階段的 9 個策略裡沒有它。〔複核修正：原寫「都有的開關」。三者的計數語意不同：SGLang `write_through_selective` 門檻寫死為 2（E04 Strata 卡）；vLLM `store_threshold` 的 N 可設，v0.28.0 計的是被 `lookup()` 查到的次數，main 計的是被提議儲存的次數（EVAL §2.3）；Dynamo 磁碟層是「頻率 ≥2」，頻率初值 1、命中加倍、隨時間衰減（E02 B3）。對照組要寫明用的是哪一種〕建議加：

```
策略 S1s　寫穿＋選擇性（命中 2 次才寫 SSD）
寫入時：  1: 新 chunk 寫到 CPU
          2: chunk 第 2 次被命中時，才寫到 SSD
CPU 滿時：3: 刪掉最久沒用的 session 在 CPU 的那一份；如果它還沒寫過 SSD，就直接消失
SSD 滿時：4: 刪掉最久沒用的
回來時：  5: Cake 雙向還原
```

**為什麼要加**：老師問的是「簡單策略會不會追平」。選擇性寫入是業界最常見、也最簡單的「少寫」方法。如果它就能把多寫的 I/O 省掉，又不怎麼傷命中率，S5 就要贏過它才有意義。

**要不要加，請你決定。** 加了之後，B 實驗多一組策略，時間大約多 1/8（B 目前有 8 個策略：R0、S0、S1、S2b、S3、S4、S4+、S5，`phase1/05` §3 B〔計算〕）。

### 3.3 要多量的東西

- **總寫入量和寫入頻寬佔用**：每個策略都記錄寫了多少 GiB、平均和尖峰寫入速度。這是瓶頸 1 的直接證據。
- **讀寫並行時讀取變慢多少**：A2 已經有；建議 CPU 層也加一組「D2H 寫入同時 H2D 載入」，對應瓶頸 3。
- **延後寫入在逐出那一刻的寫入尖峰**：S4、S4+ 在 CPU 快滿時要一口氣寫一批，要記錄這一批寫多久、有沒有剛好擋到某個回來的使用者。這正是 S5 可能贏的地方（`01` §4）。
