# 01 寫入問題是什麼

> **一句話**：KV 算出來之後，系統要決定四件事：要不要存、存到哪、什麼時候寫、怎麼寫。寫入大多在背景進行，平常不會讓人等；但在五種情況下會。Cake 只研究讀取，前提是「KV 早就全部存好」，所以它沒有碰寫入，也只考慮從 SSD 或網路載入。

**出處**：論文的事實都取自 `docs/research_20261006_eval/cards/` 的評測卡（已讀原文並獨立複核），頁碼照卡片。標記：〔原文〕〔判讀〕〔計算〕〔二手〕。〔複核補充：2026-10-08 複核時回到原文 PDF 重查，有幾處頁碼與卡片的合併頁碼不同，已就地改正並標〔複核修正〕〕

## 1. KV 的一生：寫入在哪裡

![圖 1](figures/fig1_kv_lifecycle.svg)

一段 KV 從產生到被重新使用，會經過四步：

1. **產生**：prefill 讀輸入時算出來；decode 每生成一個 token，也會多一份。
2. **寫入**：決定要不要、要怎麼把它存到 GPU 以外的地方。
3. **存放與逐出**：CPU、SSD 的容量有限，放不下時要丟掉或往下搬。
4. **讀取還原**：使用者回來時把 KV 拿回 GPU，可以搬回來、重算，或兩者同時做（Cake）。

第 2 步「寫入」要做四個決定：

| 決定 | 問題 | 例子 |
|:--|:--|:--|
| **准入** | 要不要存？ | 全部存；命中 2 次才存；decode 的 KV 不存 |
| **放置** | 存到哪一層？ | CPU、SSD、遠端；全部先寫最慢的層 |
| **時機** | 什麼時候寫？ | 一產生就寫（寫穿）；被擠出時才寫（延後寫） |
| **路徑** | 怎麼寫？ | 同步或非同步；一次寫多大；誰來發 I/O；先壓縮再寫 |

現有系統怎麼做這四個決定，見 `02`。

## 2. 寫入什麼時候會讓人多等

寫入大多在背景進行。只要裝置有空、寫入不擋到別人，就沒有人會等它。會讓人等的是下面五種情況：

![圖 3](figures/fig3_write_bottlenecks.svg)

| # | 情況 | 白話 | 證據 |
|:--|:--|:--|:--|
| 1 | 寫入頻寬跟不上 | KV 產生得比 SSD 寫得還快，寫不完只好丟掉或卡住 | 3090 的 RUNLOG：toolagent trace 如果每個請求的 block 都寫磁碟，需要持續 7,172 MiB/s；QLC 實測持續寫入只有 181 MiB/s（RUNLOG，commit `9deda4f`；三次中位數、整機爭用 HEAVY 下量的，RUNLOG 稱為下界）。〔複核修正：原寫「每個新 block」。7,172 用的 202.9M token 是所有請求輸入 token 的總和（≈23,608 筆 × 平均 8,596；與 RUNLOG 同檔 12,694,731 次 block 存取 ×16 一致）〔計算〕，不是不重複的 block。只寫不重複 block（RUNLOG 同檔：5,457,182 個＝87.3M token）約需 3,086 MiB/s〔計算〕，仍是 181 MiB/s 的約 17 倍。RUNLOG 原句本身就寫「每個新 block」，用到這個數字時要一併更正〕 |
| 2 | 讀寫搶同一顆 SSD | 有人在寫的時候，別人從同一顆 SSD 讀就變慢 | Tutti 量到讀寫並行時，總頻寬降 60%（[T] p.6、Fig. 6；E04） |
| 3 | PCIe 雙向同時傳 | GPU→CPU 寫出去的同時，別人從 CPU→GPU 載入，兩邊都變慢 | Pensieve 量到雙向同時傳輸，兩個方向的吞吐各掉 18–20%（p.9 §5；E03）〔複核修正：原寫 p.6–7；這句在 arXiv v3 p.9 的「Prioritize data retrieval over eviction」段，p.6–7 是提前換出與逐層換入〕 |
| 4 | 同步寫入卡在關鍵路徑 | 要等寫完才能做下一步 | CachedAttention 的消融：非同步保存讓**整體執行時間**降 13–15%（prompt 1K–1.6K、decode 20 步的微基準；[CA] p.11；E04）〔複核修正：原寫「帶來 13–15% 的改善」，沒寫指標與條件。原文的對照是「整輪結束後一次寫完」〕。另一個證據：HCache 把 hidden state 直接寫 SSD（DirectIO）時，Llama2-7B、batch 16 的 TBT 高 34%，13B、batch 32 高 13%（HCache p.12 Fig. 14；E03）〔複核補充〕 |
| 5 | 搬運本身搶 GPU 資源 | 負責搬運的 kernel 會佔一點 GPU | Strata 的 I/O kernel 讓 prefill 慢不到 5%、decode 慢 10%（[S] p.6、Fig. 5；E04） |

**所以「多寫的 I/O 會不會讓人多等」的答案是：看有沒有碰到這五種情況。** 如果寫入都在背景、裝置也閒著，多寫一點就只是多佔空間；如果寫入的時候剛好有人在讀同一顆 SSD、或在用同一條 PCIe，就會拖慢那個人。

## 3. Cake 為什麼只寫到 SSD？為什麼不談 CPU？

先說結論：**Cake 不是「只寫到 SSD」，而是「完全不管寫入」**。它的研究範圍只有圖 1 的第 4 步。

**(1) 它假設 KV 早就全部存好了。** 原文明說：「we precompute and store all requests' KV cache in advance」（ICML p5；E03）。寫入發生在實驗開始之前，不算在量測裡。所以這也不是「冷啟動」：資料一直都在，只是放在慢的地方，Cake 研究的是怎麼最快把它拿回來。

**(2) 它選 SSD、網路當來源，因為那正是「雙向還原」有用的範圍。**

![圖 4](figures/fig4_cake_regime.svg)

- Cake 的 Fig. 3 把「GPU 重算」也換算成等效的搬運速度：A100 約 3.3 GB/s、H100 約 4 GB/s。這和 NVMe SSD（約 4 GB/s）、網路（約 1 GB/s）差不多（ICML p3–4；E03，圖讀值）。
- 兩邊速度差不多時，一邊算、一邊搬，各做一半，就比只做一邊快。原文也說，兩種資源相當時最有利（ICML p6；E03）。
- CPU 記憶體的頻寬約 25 GB/s（Cake Fig. 1 與 p2 正文；E03），比重算快很多。這時直接全部搬就好，雙向的好處很小〔判讀〕。〔複核修正：原寫「CPU 記憶體經 PCIe 約 25 GB/s」。原文只寫 CPU Memory「bandwidth: ∼25GB/s」，沒有說經 PCIe（「經 PCIe 搬到 GPU」是〔判讀〕）；而且 Fig. 1 圖說寫這些數字取自 LambdaLab GPU 伺服器的**規格**，不是 Fig. 3 那種「KV 大小 ÷ 處理時間」的等效吞吐，兩者不能放在同一把尺上直接比〕

**(3) 它引用「大部分命中在磁碟層」來支持這個場景，但要小心這句話。** Cake 轉述 AttentionStore 說約 80% 的命中在磁碟層（ICML p2 正文 §1；這是〔二手〕）〔複核修正：原寫「p2 Fig. 1」；80% 在 p2 的正文，不在 Fig. 1〕。但 CachedAttention（也就是 AttentionStore）自己的結果是：配合預取時，超過 99.6% 的命中發生在 DRAM（[CA] p.12 §4.3.3；E04）。〔複核補充：條件是 128 GB DRAM＋10 TB SSD、CA 的排程感知預取與逐出（總命中 86%）；同一設定下不預取的 LRU／FIFO，DRAM 命中只有約 0.6%／0.5%，幾乎都在磁碟（p.12）〕差別在於「KV 放在磁碟」和「從磁碟讀」是兩回事：資料可以多半放在磁碟，但讀之前先預取到 DRAM。

**(4) Cake 的 I/O 是模擬的。** 它用「延遲注入」模擬 7–100 Gbps 的頻寬，沒有和真實裝置校準（ICML p5 §5.1 的延遲注入、p6 Table 2 的頻寬點；E03）〔複核修正：原只寫 p5；7–100 Gbps 的頻寬點在 p6 Table 2〕。

**對本研究的意義**：Cake 的雙向還原只在「搬的速度 ≈ 重算速度」時有明顯好處。我們把後段放到 CPU，載入就會快很多，雙向還原的好處可能縮小，甚至接近「只搬」。這要在 `phase1` 的 A0、A1 量出來〔判讀〕。

## 4. 回到本研究：「多寫」是什麼

在 `phase1` 的 S5（寫入時依位置決定狀態）裡：
- 前段（預期會被重算）照樣寫進 SSD 當備份；
- 回來時如果 GPU 閒，Cake 會重算前段，這份備份就用不到。

所以前段的寫入多半是「多寫」，會佔用這些資源：
- PCIe 的 GPU→CPU 方向（第 3 種情況）；
- SSD 的寫入頻寬（第 1、2 種情況）；
- SSD 的容量。

現有系統降低寫入代價的做法（細節見 `02`）：
- **寫入不擋關鍵路徑**：非同步寫、讀取優先（CachedAttention、Pensieve、Tutti）；
- **少寫一點**：命中 2 次才寫（Strata、SGLang selective）、只寫新的 token（LMCache）；
- **晚點再寫**：被擠出時才寫（Mooncake Store、延後寫入）。

這幾種都是第一階段要比的簡單對手，或可以加進來的對手（`03` §3）。
