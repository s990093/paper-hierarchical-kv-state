\title{Does Deciding at Write Time Help?\\
KV Cache Placement and Precision Under Read-Adaptive Restore}

\author{\IEEEauthorblockN{Anonymous Author(s)}
\IEEEauthorblockA{Submission under review}}

\maketitle

\begin{abstract}
A user who returns to a long LLM conversation waits while the serving system restores the session's KV cache from CPU memory, from an SSD, or by recomputation.
Recent systems settle two properties of each KV block when they write it, the tier that holds it and the precision it keeps, and they often key both on token position.
Restore has meanwhile become adaptive: Cake recomputes the prefix on the GPU while it loads the suffix from storage, and the two streams meet at a point that only exists at read time.
We ask whether a write-time decision still buys anything that a later decision cannot, and we answer with two tests on an AMD MI300X.
A deferral test compares each write-time placement rule with the same rule applied at eviction, in the background, or by pre-cleaning: in 36 GPU comparisons, no write-time rule beat all of its deferred twins by 5\%, because position stays visible at eviction.
Read accounting fixes bytes, codec, and attention path, moves only the low-precision blocks, and logs which blocks each restore actually loads.
On slow tiers Cake almost never reads low-precision front blocks, so their harmlessness says nothing about sensitivity.
Under a forced full load, uniform FP8 keeps Llama-3.1-8B within 0.5 points of BF16; Qwen2.5-7B loses 32.8 points and recovers fully once its keys are mean-centered, while sink protection recovers at most 0.5.
Uniform INT4 meets a 2-point bound on both models, and 25\% INT4 placed in front, middle, or back stays within 0.33 points of random placement.
Both decisions can wait until demotion or read time.
\end{abstract}

\section{Introduction}\label{sec:intro}
% Stakes: returning sessions put KV restore on the TTFT path.
Long LLM conversations pause and resume.
When a user returns, the serving system must rebuild the KV cache of the whole earlier context before it emits the first token.
For Llama-3.1-8B~\cite{llama3_2024}, a 32K-token context holds 4\,GiB of KV in BF16, more than GPU memory can keep for every idle session.
Serving systems therefore move idle KV to CPU memory or SSD and restore it when the user returns~\cite{cachedattention2024,pensieve2025,mooncake2025,lmcache2025}.
The restore time adds directly to the returning request's time to first token (TTFT).

% Two decisions are made when a block is written.
Every stored KV block carries two decisions: the tier that holds it and the precision it keeps.
Several recent designs make both decisions when they write the block, and many key on token position.
Krul compresses a conversation's KV when the conversation goes idle, keeps a hardware-calibrated share of each layer, and recomputes the rest on restore~\cite{krul2025}.
TierKV splits each request's tokens by position into uncompressed, low-rank, and flash-resident ranges before decoding starts~\cite{tierkv2026}.
Lachesis places context segments in HBM or flash when it allocates them~\cite{lachesis2026}.
On the precision side, KV quantizers keep the first few ``sink'' tokens and a window of recent tokens at high precision~\cite{kivi2024,kvquant2024,skvq2024,qevict2026}.

% Reads became adaptive.
Restore has become adaptive at the other end.
Cake recomputes blocks from the start of the context on the GPU while it loads blocks from the end over I/O, and the two streams meet where they cross~\cite{cake2025}.
The meeting point moves with GPU load and tier bandwidth, so it exists only at read time.
CacheGen similarly chooses a compression level for each chunk when it sends that chunk, from the bandwidth it measures at that moment~\cite{cachegen2024}.

% Gap and approach, told in the order we did the work: placement first, then precision.
This combination raises a question that prior work leaves open: \emph{when the reader adapts, does deciding at write time buy anything that a later decision cannot?}
We answer it in two steps, one per decision.

% Step 1: placement and the deferral test.
\textbf{Step 1: placement.}
Write-time placement designs compare against position-blind baselines and rarely against the same rule applied later, at eviction or in the background.
A write-time rule that beats LRU may therefore owe its whole gain to the rule, with timing playing no part.
The \emph{deferral test} (\cref{sec:method-placement}) closes this gap: a write-time rule must beat each of its \emph{deferred twins} by at least 5\% on the GPU, namely the same rule applied when the CPU tier fills, the same rule applied in the background, a pre-cleaning copy, and write-through.
No write-time rule passes, because token position never changes and the deferred twin sees it at eviction as well.

% Step 2: precision, the remaining candidate, and read accounting.
\textbf{Step 2: precision.}
Once placement can wait, precision becomes the strongest remaining case for deciding early: a block stored in FP8 cannot return to BF16 without a second copy, and quantizers commonly protect tokens by position.
Existing evaluations of position-aware precision, however, ignore which blocks the reader loads.
Under Cake the GPU recomputes the prefix in exact BF16 whatever copy sits in storage, so a low-precision front that costs no accuracy may be insensitive, or the restore may never read it.
\emph{Read accounting} (\cref{sec:method-precision}) separates the two explanations.
It fixes the stored bytes, the codec, and the attention path, changes only where the low-precision blocks sit, and logs for every block whether the restore recomputed it, loaded it in BF16, or loaded its low-precision copy.
Two read modes then separate sensitivity from read probability: a forced full load exposes every stored copy, and a real Cake restore reads only the copies past the meeting point.

We run both steps on one AMD MI300X with a KV harness that checks every restore bit for bit, and we commit decision rules and analysis code before we collect any result they judge.

% Contributions as claims, with section pointers.
This paper makes four contributions.
\begin{enumerate}
\item \textbf{Placement can wait (\cref{sec:placement}).}
In 36 GPU comparisons, no write-time placement rule beat all of its deferred twins by 5\%.
The strongest write-time rule ran 18.9\% faster than the best position-blind policy but only 0.7\% faster than its own deferred twin, because position stays visible at eviction.
Deferral loses only under a sustained SSD write backlog with a bounded queue, which a single GPU does not produce: a pre-registered rerun on ten fresh seeds found 0 of 216 winning cells.
\item \textbf{Read accounting separates ``insensitive'' from ``unread'' (\cref{sec:reads}).}
On rate-limited tiers, Cake reads 0 of 16 low-precision front blocks at the balanced meeting point and all 16 back blocks.
On the real CPU tier it meets after 1--3 blocks and reads almost every copy.
\item \textbf{Precision does not need position (\cref{sec:precision}).}
Under a forced full load, uniform FP8 keeps Llama-3.1-8B within 0.5 points of BF16.
Qwen2.5-7B-1M loses 32.8 points; protecting sink and recent blocks recovers at most 0.5 points, while mean-centering its keys before FP8, or storing INT8, recovers all of it.
Uniform INT4 meets a 2-point bound on both models, and 25\% INT4 placed in the front, middle, or back stays within 0.33 points of random placement.
\item \textbf{Low precision buys time only on slow tiers (\cref{sec:speed}).}
INT4 cuts restore time by 36--57\% on rate-limited tiers but slows the real CPU tier by up to 2.2$\times$, because dequantization competes with recomputation on the GPU.
\end{enumerate}

% Thesis and scope.
Together the two steps give one answer.
When restore adapts at read time, a system can write every block to CPU memory in BF16, defer demotion and quantization until space runs out, and let the reader choose what to recompute.
Choosing a low-precision format is a question of codec and ratio, and position adds nothing we can measure.
Our evidence covers one GPU type, two GQA models, 32K-token contexts for quality, rate-limited slow tiers, and a single-request GPU harness; \cref{sec:threats} lists what these limits leave open.

\section{Background}\label{sec:bg}
Two facts set up the question: restore time sits on the returning request's critical path, and Cake fixes the split between recomputation and loading only at read time.

\subsection{Restoring a returning session}
We split a context into \emph{blocks} of 512 tokens.
A Llama-3.1-8B block holds 64\,MiB of BF16 KV (128\,KiB per token) and a Qwen2.5-7B block holds 28\,MiB, because Qwen has 28 layers with 4 KV heads where Llama has 32 layers with 8.
When a session goes idle, the system keeps its blocks in a fast but small tier (CPU DRAM), a slow but large tier (local SSD or network storage), or nowhere, in which case it recomputes them on return.
We call the request that resumes a session the \emph{returning request} and report its TTFT.

\subsection{Read-adaptive restore}\label{sec:bg-cake}
Cake restores $n$ blocks with two concurrent streams~\cite{cake2025}.
The GPU recomputes blocks $0,1,2,\dots$ and the I/O path loads blocks $n{-}1,n{-}2,\dots$; the streams stop where they meet, at block $b$.
Blocks before $b$ come from recomputation and blocks from $b$ on come from storage.
Recomputing block $i$ costs $f(i)$, which grows with $i$ because attention covers the whole prefix.
On our platform $f$ rises from 28.9\,ms for the first block to 98.8\,ms at block 80, about 0.89\,ms per block.
Loading a block costs $\ell$, set by tier bandwidth: 1.76\,ms from CPU memory at 35.4\,GiB/s and 188.8\,ms from a 0.331\,GiB/s network tier.
Given $f$ and the tier bandwidth, a simple two-pointer simulation predicts the measured meeting point within one block in 28 of 28 cells we tested.
The meeting point therefore depends on two quantities that only the reader sees: how busy the GPU is and how fast the tier delivers.

\subsection{Two write-time decisions and their deferred twins}\label{sec:bg-twins}
A write-time \emph{placement} decision assigns a block to a tier when the system writes the block.
Its deferred twin writes the block to the CPU tier and applies the same assignment when the CPU tier fills.
The twin sees the same token position, because position never changes after the write.
A write-time \emph{precision} decision stores the block in a low-precision format when it writes the block.
Its deferred twin keeps BF16 in the CPU tier and quantizes the block when it demotes the block to a slower tier.
Both orders reach the same final layout; the deferred order costs some extra CPU space until demotion and gives an early return a BF16 copy.

\subsection{Why recomputation hides precision}\label{sec:bg-hide}
Cake's split creates a confound for any position-aware precision rule (\cref{fig:concept}).
Recomputation regenerates a block from tokens, so a recomputed block is exact BF16 regardless of the stored copy.
Only blocks past the meeting point expose their stored precision to the model.
A configuration that stores the front in low precision and shows no accuracy loss under Cake therefore admits two explanations.
The front may be insensitive to quantization error, or the restore may never have read it.
Separating the two requires knowing, block by block, what each restore read.

\section{Methodology}\label{sec:method}
Both steps share one platform, one harness, and one rule: each experiment changes a single variable.
Step~1 changes when a placement rule runs; Step~2 changes where low-precision blocks sit and holds bytes, codec, and attention path fixed.

\subsection{Platform and harness}\label{sec:method-platform}
All measurements run on one AMD Instinct MI300X (192\,GiB HBM3, PCIe Gen5 x16) with ROCm 7.2.2, PyTorch 2.10, and Transformers 5.17.
We use Llama-3.1-8B-Instruct for both steps and add Qwen2.5-7B-Instruct-1M~\cite{qwen25_1m_2025} for the precision study, all in BF16 weights.
We add Qwen as a stress case: KVTuner reports that Qwen2.5-3B and 7B-Instruct degrade sharply when keys drop to 4 or 2 bits~\cite{kvtuner2025}.
Both models use grouped-query attention.
A self-managed KV harness reuses the Hugging Face weights and rotary embedding but owns attention and the KV buffer, so it can time every block and run Cake's two streams concurrently.
Recomputing a block twice yields identical bytes, a GPU$\to$pinned$\to$GPU round trip yields identical bytes, and every experiment compares the restored KV against the stored copy; all experiments report zero corrupted blocks.

The harness recomputes 1.7--2.0$\times$ slower than default vLLM: a full 32K prefill takes 3.76\,s in the harness against 2.24\,s for a 33K prefill in vLLM~0.28 with its default attention kernel, and 0.645\,s against 0.318\,s at 8K.
Slower recomputation pushes the meeting point toward the front and leaves a write-time rule less to decide, which biases Step~1 toward our conclusion.
\Cref{sec:placement-fast} tests that bias in simulation.

\subsection{Tiers}
The CPU tier is pinned host memory with real host-to-device copies (52.9\,GiB/s raw H2D).
Slow tiers reuse pinned memory behind a rate limiter that charges each block by its actual bytes; we call them ``rate-limited tiers'' and do not claim they behave like a particular device.
Step~1 sets the limiter from the slowest measured value of two real devices times 0.9: a local SSD (6.98\,GiB/s read, 1.91\,GiB/s write) and an NFS mount (0.331 and 0.601\,GiB/s).
A real-device calibration sets how much a concurrent write slows reads (3.31$\times$ on the SSD, 1.67$\times$ on NFS, 1.16$\times$ on the CPU tier).
The limiter tracks its set rate within 0.3\% from 0.25 to 40\,GiB/s.

\Cref{tab:policies} lists the policies.
A write-time idea passes the deferral test only if, on the GPU and across at least three workload seeds, it beats every deferred twin by at least 5\%; we call 15\% strong.
A rule that beats only some twins counts as a good rule, and its timing earns no credit.
The test follows from a simple argument.
A write-time decision can win only if it uses information that disappears after the write, saves a resource that deferral must spend, avoids work that deferral can only do in idle time the system lacks, or fixes a format that limits what the reader can do.
Token position satisfies none of these on its own.

Step~1 serves eight sessions one request at a time.
In the \emph{chat} workload each turn appends 8K tokens for up to four turns; in the \emph{doc} workload the first turn writes 32K tokens and later turns ask short questions.
A workload seed sets which sessions return and in what order.
The CPU tier holds 25\%, 50\%, or 100\% of the working set.
Under \emph{free} release, demotion frees CPU space at once; under \emph{hold}, a request waits until the demotion write completes.
The metric is the median TTFT of returning requests.

A simulator shares the policy code and the rate limiter with the GPU harness and replaces time with a virtual clock.
It reproduces all 114 first-phase cells within 10\% (median error 0.4\%, maximum 5.0\%) and 47 of 50 later GPU cells within 10\% (median 3.1\%).
Its error on the gap \emph{between} two policies is larger, about 5--6 percentage points, so we use it only to pick candidates for the GPU and screen at a 10\% threshold.
A separate concurrency simulator adds 32 sessions, Poisson or bursty arrivals, a GPU queue, an SSD write queue, and drop-on-full admission; no GPU run validates it.

\textbf{Configurations.}
\Cref{tab:configs} lists the configurations.
Every mixed configuration keeps block 0 in BF16, because the sink tokens that published rules protect, the first one to five tokens~\cite{streamingllm2024,kvquant2024,skvq2024}, all fall inside block 0; without that control a front placement would also quantize the sink.
Sinks can also emerge beyond the initial tokens~\cite{kvsink2025}; like the published rules, \cfg{All+S} protects only the start.
\cfg{All} versus \cfg{All+S} measures the sink on its own.
The restore dequantizes every low-precision block into the same BF16 KV buffer and runs the same attention kernel, so the attention path never changes.

\textbf{Two read modes.}
The \emph{full-load} read loads all 64 blocks from storage and measures sensitivity.
The \emph{Cake} read recomputes blocks before the measured meeting point and loads the rest, and measures the accuracy a user would get.
Because recomputed KV equals the BF16 KV stored at prefill bit for bit, we evaluate the Cake read by replay: blocks before $b$ take the BF16 copy and blocks from $b$ on take the stored copy.
On 120 items (50 Llama FP8, 50 Qwen FP8, 20 Qwen INT4, meeting points 15--36) the replay matches a real Cake restore exactly in KV and in logits.
We evaluate the Cake read with the GPU idle, with the GPU busy, and on a second turn restored under a busy GPU after an idle first turn.

\textbf{Tasks.}
We use RULER-style synthetic tasks~\cite{ruler2024} with the needed information placed in a chosen position band: multi-value needle retrieval (T2), variable tracking (T3), two-hop QA that inserts the two HotpotQA gold paragraphs~\cite{hotpotqa2018} into the band (T4), and common-word extraction over the whole context (T5).
The bands are blocks 1--16, 24--39, and 48--63, aligned with the mixed configurations so that answer position and low-precision position cross.
A multi-key needle task saturates under BF16 on both models, so the decision rules exclude it.
Each model answers 600 items (180 each for T2--T4 and 60 for T5); T2--T4 have a second turn, for 1,140 scored rows per condition.
We tune difficulty on BF16 only: every model, task, and band sits between 60\% and 95\% BF16 accuracy before any low-precision run.

\textbf{Formats.}
We pick formats on 20 separate items using only the KL divergence of next-token distributions, never accuracy.
FP8 is E4M3~\cite{fp8formats2022} with a scale per block and per token (Llama) or per head (Qwen).
INT4 follows KIVI, with keys quantized per channel and values per token in groups of 32~\cite{kivi2024}.
Two 8-bit diagnostics test whether a failure belongs to the format: \cfg{FP8-K0} subtracts each key channel's mean within a block before FP8 and stores the mean in BF16, and \cfg{INT8} stores symmetric INT8 with a scale per token and head.

\textbf{Speed.}
We pick slow-tier bandwidths by where BF16's meeting point lands, $b^\ast\in\{16,32,48\}$: 5.27, 1.47, and 0.42\,GiB/s for Llama and 2.77, 0.76, and 0.22\,GiB/s for Qwen.
A busy GPU runs a background matrix multiply at 0.7 duty cycle, which slows recomputation 2.07$\times$.
Each cell takes three process launches of ten repetitions with configurations shuffled within each repetition.

\textbf{Decision rules.}
A configuration meets the quality bound $\varepsilon$ if its paired accuracy difference against \cfg{BF16}, bootstrapped over items 10,000 times, has a 95\% CI lower bound above $-2$ points and no task-and-turn point estimate below $-5$, in all four read conditions.
A configuration is not slower if, in every tier and GPU state, its median restore time stays within $(1{+}\delta^\ast)$ of the fastest mixed configuration, where $\delta^\ast=\max(5\%,\text{measured noise})$: 5\% for Llama and 9.43\% for Qwen.
The rules then branch in a fixed order.
If uniform low precision restores no faster than BF16 anywhere, precision has nothing to offer and we stop.
If \cfg{All}, \cfg{All+S}, or an 8-bit codec change meets both rules, the level needs no position policy and we move one level down, from FP8 to INT4, and stop after that level.
At a level where uniform fails, a position placement wins only if it beats \cfg{Rand} by at least 2 points with a CI that excludes zero at $b^\ast=32$ and is not slower; otherwise position adds nothing and we stop.

\subsection{Measurement hygiene}\label{sec:method-hygiene}
Run-to-run noise in Step~1 is 6.2\% (95\% CI half-width over median), mostly from the meeting point jumping between adjacent blocks.
A process monitor checks every timed run for foreign GPU processes; one Qwen FP8 speed grid recorded one suspicious sample, and we re-measured the whole grid and judged on the re-measurement.
Quality runs execute several processes at once, so we discard their latency fields and keep only their scores.
Greedy decoding makes those scores deterministic: on Llama, 2,620 rows that read no low-precision block reproduce the BF16 baseline's text and answer log-probabilities bit for bit across separate batches.
We committed the precision study's rules and analysis code before generating any low-precision answer, and the concurrency rerun of \cref{sec:placement-idle} froze its code by hash before it ran.

\section{Step 1: Placement Can Wait}\label{sec:placement}
This section shows that a write-time placement rule never beats the same rule applied later, and it locates the one regime where deferral could lose.

\subsection{Cake pays off in a bandwidth band}\label{sec:placement-cake}

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{figures/cake_band.pdf}
\caption{\textbf{Cake pays off between 0.3 and 4\,GiB/s.} Speedup of Cake over the faster of recompute-only and load-only, per context length; one run per cell, median of six restores.}
\label{fig:cake}
\end{figure}

Read-adaptive restore is worth the most where loading a block costs about as much as recomputing it (\cref{fig:cake}).
At 32K tokens Cake beats the faster single path by 1.38--1.93$\times$ between 0.33 and 3.73\,GiB/s, with the peak at 0.82\,GiB/s.
Above that band the gain shrinks: 1.17$\times$ at 6.98\,GiB/s and 1.05$\times$ at 11.6\,GiB/s.
Against recompute-only, longer contexts gain more at all seven bandwidths.
One of 28 cells reverses: at 4K tokens and 11.6\,GiB/s Cake is 5.6\% slower than load-only (78 versus 74\,ms).
Because our harness recomputes slowly, the band's absolute position would shift to higher bandwidth on a faster engine; its shape is what Step~1 relies on.

The band also bounds what a write-time placement rule can decide.
On the CPU tier a block loads 16$\times$ faster than the cheapest block recomputes, so the meeting point sits at block 0--3 and a rule that sends ``the part Cake will recompute anyway'' to SSD has almost nothing to send.

\textbf{First phase: identical behavior.}
The write-time rule and its deferred twin differ only in when they apply the position split, and they finish within $-3.0\%$ to $+0.3\%$ of each other in all 15 configurations.
At CPU speed the computed meeting point covers 0--3 blocks, so the write-time rule places almost every block in CPU memory and then behaves exactly like its twin.
In 22 of 22 write-time/twin pairs under free release the two differ by less than 5\%.
When capacity is tight, position-based eviction itself hurts: at 25\% capacity LRU-style policies beat the position rules by 12--33\%, because evicting every session's front strands the front of the next returning session on the slow tier.

\textbf{Ablation: the rule wins, the timing does not.}
We then combined every condition we expected to favor a write-time rule: a slow CPU tier (3.69\,GiB/s, set from vLLM's measured CPU offload throughput on this machine), hold release, the doc workload, and 50\% capacity.
The best write-time rule beat the best position-blind policy by 18.9\% and its deferred twin by only 0.7\%.
On the next workload seed the same rule lost to write-through by 6.8\%.

\textbf{Simulator survivor: gone on the GPU.}
Of 64 simulated Llama configurations, one passed the four-twin screen on at least three of five seeds, with a predicted 7.6\% gain; four survivors of a second, MHA model could not run on the GPU because the doc workload exceeds that model's 32K-token limit.
On the GPU it passed on zero of five seeds; it stayed within $\pm3.5\%$ of both its deferred twin and the best position-blind policy.
The predicted gain was the size of the simulator's relative bias (\cref{sec:method-placement}).

\subsection{Write-time decisions go stale}
A write-time decision bakes in assumptions about a future read, and the reader often sees a different world.
A policy that does not store the front at all and recomputes it on return gains nothing when the user returns after the writes complete (0 of 24 cells).
When the user returns before the writes finish, it is faster in 6 of 24 cells (by 3.7--13\%), and only 3 of those exceed the 6.2\% run-to-run noise.
When the GPU is busy, the same policy runs 13--66\% slower than storing every block at 16K tokens and beyond, because a busy GPU should shift the meeting point forward and the missing front blocks forbid that shift.
The position split itself carries the same risk: computed for an idle GPU, it makes the write-time rule 37\% slower than keeping everything in CPU memory on the NFS tier with a busy GPU at 32K (546 versus 400\,ms).

\subsection{Return order picks the winner}
The best policy depends on which sessions return and in what order more than on hardware constants.
In simulation, keeping the hardware fixed and changing only the workload seed leaves the best non-write-time policy unchanged across five seeds in 17 of 64 Llama configurations.
On the GPU, three seeds of the same first-phase configuration spread the policies by 29.5\%, 32.6\%, and 0.1\%, and five seeds of the simulator survivor produced four different winners.
A rule that predicts the winner from the recompute-to-load cost ratio therefore cannot work for the write side; such a rule does predict Cake's read-side gain (median error 4.1\%).

\subsection{Deferral needs idle time, and one GPU leaves enough}\label{sec:placement-idle}
A deferred twin needs time to move blocks after the fact, so it can lose only when the SSD write path never drains.
We define write load $\rho_\mathrm{KV}$ as the rate at which the system wants to write KV to SSD divided by the SSD's write bandwidth.
Across 34,560 concurrency simulations on one GPU (0.05--0.4 sessions/s, five seeds), $\rho_\mathrm{KV}$ never exceeds 0.99, and its peak on the local SSD is 0.34.

The pre-registered analysis first reported a winner in 5 of 192 cells.
Two modeling errors in the twins explained all five: a twin labeled ``deferred'' evicted in a different order than its write-time rule, and the drop model never let a policy evict a newly arriving block, unlike the GPU harness.
With both fixed, no cell passed.
Because we fixed them after seeing the winners, we re-registered the corrected setup, froze the code by hash, and reran it on ten fresh seeds.
Among the 216 cells without sustained backlog ($\rho_\mathrm{KV}<1$), neither write-time candidate passed in any cell, under the median, the mean, or the 90th percentile.

Write-time placement survives only in an overloaded corner that we had to assume: eight GPUs sharing one local SSD (0.239\,GiB/s write each, not measured), a bounded write queue of 16, and $\rho_\mathrm{KV}\approx2.1$.
There, one of five earlier winning cells reproduced on 7 of 10 fresh seeds with a median gain of 14.2\% at a median returning TTFT of 11.2\,s, and one new cell passed on 6 of 10 seeds at 12--32\,s.
Under the mean or the 90th percentile, none of these cells wins.

Real systems confirm that a single GPU does not starve deferral.
vLLM~0.28 with a CPU tier at 50\% of the working set skipped 0 of 133,504 blocks offered for offload, and 0 of 200,256 at 25\%: when a store fails, its scheduler retries later.
The operating system adds another deferral buffer: files written with buffered I/O remain 100\% in the page cache 30\,s after the write, on the local SSD and on NFS.

\subsection{Faster recomputation does not revive write-time placement}\label{sec:placement-fast}
Because our harness recomputes slowly (\cref{sec:method-platform}), we reran the simulator with recomputation $2\times$ and $1.67\times$ faster against the full twin set.
Under free release no configuration survived at either speed (0 of 32; largest lead 4.9\%).
Under hold release one configuration survived the 10\% screen, but it split by seed: it won by 22--30\% on three seeds and lost to write-through by 20--27\% on two.
No GPU run confirms these simulations.

Position is one of several signals a system knows at write time, and \cref{tab:signals} shows that deferral recovers each of the ones we tested.

This section shows that the case fails under Cake.
Position mostly controls whether the restore reads a low-precision copy at all, uniform formats meet the quality bound once the codec fits the model, and a fixed ratio placed by position does no better than the same ratio placed at random.

We read the failure as a format mismatch: Qwen's keys carry a large constant offset per channel, which stretches FP8's per-head scale and leaves its 3 mantissa bits too coarse for the small differences that attention uses~\cite{fp8formats2022}.
\cfg{FP8-K0} misses the speed rule on the busy CPU tier (16.4\% slower than the fastest mixed configuration, against a 9.43\% allowance) because adding the mean back costs an extra dequantization step, so INT8 is the 8-bit format that passes both rules.

\subsection{Uniform INT4 keeps quality on both models}\label{sec:int4}
Since the FP8 level needed no position policy on either model, the rules move one level down to INT4 (KIVI layout).
Uniform INT4 meets the quality bound on both models in all 24 model, configuration, and condition cells; the lowest CI bound is $-0.8$ points.
Qwen, which lost 32.8 points under FP8, loses nothing under INT4.
KIVI quantizes keys per channel with a per-channel zero point, which removes the same constant offset that \cfg{FP8-K0} removes, so we attribute both recoveries to one cause.
One cell, Llama \cfg{All} under the full load, shows a CI that excludes zero on the positive side ($+1.1$); among 24 cells we expect about one such cell by chance, and we do not read it as INT4 beating BF16.

INT4 does leave a mark below the decision threshold.
Its outputs match BF16 verbatim in 74.6\% (Llama) and 73.9\% (Qwen) of rows, against 82--91\% for the 8-bit formats, and the log-probability of the reference answer drops slightly (Qwen common-word extraction: $-0.0275\pm0.0051$ per token).
At 32K tokens these shifts do not flip answers; whether they do at 64K and 128K is \pending{pre-registered long-context study, 64K and 128K}.

Uniform INT4 fails only the speed rule, and only on the real CPU tier (Llama busy: 1.13--1.15$\times$ the fastest mixed configuration against 1.05; Qwen: 1.14$\times$ idle and 2.10$\times$ busy against 1.094).
By the frozen rules that failure sends INT4 to the position test, which we run on Llama, the model the rules select when both models fail.

Under read-adaptive restore, a block's position mostly predicts whether the restore reads its low-precision copy; the codec decides how much the copy hurts.
Once the codec fits the model's key distribution, uniform low precision meets the quality bound at both levels we tested, and a fixed ratio placed by position matches the same ratio placed at random.

\section{Discussion}\label{sec:disc}
Both steps point to one design, and our data leave a few places where an early decision could still pay.

\subsection{Write simply, demote lazily, decide at read time}
Both parts point to the same design.
Write every block to the CPU tier in BF16.
When the CPU tier fills, demote blocks to the slow tier and quantize them on the way, choosing which blocks by recency.
At read time, let the restore split recomputation from loading according to the GPU load and bandwidth it observes.
This order never writes more bytes to the slow tier than a write-time rule would, because the slow tier receives the same low-precision copy; it costs CPU space until demotion, and a user who returns early gets BF16.

\subsection{Where an early decision could still pay}
Our data leave four openings.
First, a sustained SSD write backlog with a bounded queue: the one reproduced simulated cell needs eight GPUs per SSD, a regime we did not measure, and gains only on the median.
Second, information that disappears after the write: hybrid attention--SSM models overwrite intermediate states during prefill, so a cache must choose checkpoints while it prefills~\cite{marconi2025}; this choice depends on content.
Third, a write path open only at write time, such as GPU-direct writes to an SSD that bypass host memory; we could not measure it on our platform.
Fourth, admission when the CPU tier is tiny (at most 10\% of the working set), where knowing reuse in advance avoids SSD writes altogether.

\subsection{On a fast tier, low precision buys capacity}
On the real CPU tier low precision saves little time (\cref{sec:speed}), but it multiplies capacity.
A 32K-token session takes 4\,GiB in BF16 and 1.25\,GiB in INT4 (KIVI, including scales) for Llama, and 1.75\,GiB and 0.55\,GiB for Qwen.
One TiB of host memory therefore holds 256 Llama sessions in BF16 and 819 in INT4, and 585 and 1,872 for Qwen, 3.2$\times$ more in both cases.
Capacity decides when sessions spill to the slow tier, where low precision does save time; a measured two-tier restore (CPU in BF16, slow tier in INT4) is \pending{two-tier restore grid, stage 44}.

\subsection{Pitfalls we hit}
Four measurement errors would each have produced a false positive for early decisions.
\emph{Unread copies.} A Cake read at the balanced point reads no front copy (\cref{sec:reads}); reporting only that read would call the front insensitive.
\emph{Post-hoc rivals.} We added several twins after seeing a write-time winner; a fresh-seed, hash-frozen rerun of the corrected setup (\cref{sec:placement-idle}) is what lets us keep the conclusion.
\emph{Simulator bias.} The simulator predicts absolute TTFT within a few percent but the gap between two policies with an error near 5 points, the size of the one survivor's predicted gain.
\emph{Kernel swaps.} vLLM~0.28 on ROCm drops its default ROCM\_ATTN kernel whenever a deployment configures any KV connector, because that kernel's KV layout is not blocks-first~\cite{vllm_pr43660}; an open issue reports the same exclusion for disaggregated decoding~\cite{vllm_issue60316}.
On our machine the engine fell back to a Triton kernel.
With CPU offload enabled, new 33K-token requests ran 96\% slower on 3 of 3 seeds; the kernel swap alone explained most of that, attention time for one prefill rose from 1.37 to 3.28\,s, and registering K and V as separate views restored the default kernel and removed 45--74\% of the extra time.
An early version of our own comparison had judged the harness fast by comparing it against this slowed vLLM.

\subsection{Energy changes the read-side answer}
Measured in GPU energy instead of time, Cake loses its advantage on fast tiers.
The MI300X draws 726.4\,W while recomputing and 168.9\,W while waiting for I/O, so load-only restore uses 62--70\% less GPU energy than Cake on the CPU and local-SSD tiers at a cost of 4--43\% more restore time; on the NFS tier Cake wins both.
This result comes from one seed and covers only the GPU board.

\section{Related Work}\label{sec:related}
Prior KV systems decide either at read time or at write time, and few compare a write-time decision against the same decision made later.

\textbf{Read-adaptive restore.}
Cake meets recomputation and loading in the middle and assumes that the system computed and stored the full KV beforehand~\cite{cake2025}.
CacheGen chooses a compression level per chunk when it streams the chunk and can fall back to sending text~\cite{cachegen2024}.
KVPR overlaps partial recomputation with transfer~\cite{kvpr2025}, CacheFlow plans recomputation and loading at restore time~\cite{cacheflow2026}, and HCache restores from hidden states, splitting the work by layer~\cite{hcache2025}.
Pensieve swaps KV from GPU to CPU memory and, when CPU memory fills, drops the chunks with the lowest ratio of recomputation cost to idle time, which favors the leading tokens of idle conversations; it recomputes dropped tokens on return~\cite{pensieve2025}.
It is a deferred form of ``do not keep the front.''
These systems decide at read time or on eviction; we show that write time adds nothing to them.

\textbf{Write-time placement and admission.}
Krul~\cite{krul2025}, TierKV~\cite{tierkv2026}, and Lachesis~\cite{lachesis2026} decide placement when they write, EfficientAgent decides admission to the host tier~\cite{efficientagent2026}, and a CXL memory rack skips writes when its buffer fills~\cite{hymcache2026}.
AdaptCache~\cite{adaptcache2025} and EvicPress~\cite{evicpress2025} choose a lossy compression level and a tier for each entry when they store it and revisit the choice as tiers fill, and KVDrive persists all KV to SSD at prefill and keeps attention-selected entries in HBM and DRAM~\cite{kvdrive2026}.
Serving engines and KV layers such as vLLM~\cite{vllm2023}, SGLang~\cite{sglang2024}, LMCache~\cite{lmcache2025}, and Mooncake~\cite{mooncake2025} keep KV in CPU memory or storage for reuse across requests.
A recent study of placement policies across GPU, CPU, and SSD finds that tier capacity, more than policy, drives the gains~\cite{wherekvlive2026}.
Few of these designs compare a write-time rule against the same rule applied later; our deferral test makes that comparison.

\textbf{Position-aware and content-aware KV precision.}
KIVI keeps a full-precision residual of recent tokens~\cite{kivi2024}, KVQuant keeps the first token in fp16~\cite{kvquant2024}, SKVQ keeps a recent window and five sink tokens~\cite{skvq2024}, and QEvict~\cite{qevict2026} and PM-KVQ~\cite{pmkvq2025} combine both rules; all of them quantize KV inside GPU memory at low bit widths.
StreamingLLM identifies the attention sink under eviction~\cite{streamingllm2024}, and ZipCache corrects the bias of accumulated attention toward early tokens~\cite{zipcache2024}.
Content-aware schemes choose precision from attention, similarity, or internal metrics~\cite{diffkv2025,cocktail2025,semkv2026}, and KVTuner tunes precision per layer~\cite{kvtuner2025}.
PatchKV, the closest work, recomputes a predicted set of blocks and quantizes only the blocks it will load, with per-block precision frozen at offload from an attention-weighted risk score~\cite{patchkv2026}, and SparKV evaluates Cake with a quantized loaded segment as a baseline~\cite{sparkv2026}.
Our read accounting adds what these evaluations lack: a per-block record of which stored copies a read-adaptive restore actually reads.

\textbf{Multi-level caching and recomputable storage.}
Gill compared promoting data to a cache level as it passes against demoting it on eviction and found small differences when demotion is free~\cite{gill2008}, and DEMOTE, which returns blocks to the lower cache on eviction, approximates exclusive caching when the lower cache also discards the blocks it just sent up~\cite{wong2002}.
Tachyon uses lineage to checkpoint in the background without stalling writes, and it checkpoints synchronously once memory fills with files it has not yet persisted~\cite{tachyon2014}; a lack of idle time is likewise the only regime where our deferred twins lose.
TPP separates reclamation from allocation watermarks so that background demotion keeps headroom for bursts~\cite{tpp2023}.
Our results extend this line to KV caches, which a system can recompute and which an adaptive restore reads.

\textbf{Characterizing offload.}
A recent analysis derives the ratio of cached to new tokens beyond which offloaded prefill becomes transfer-bound, and measures on H100 that transfers take up to 99\% of a long request's latency~\cite{bottlenecks2026}.
On an H200, offloading under high KV pressure saves 14.4--31.9\% of idle-subtracted GPU energy per output token compared with recomputation after preemption~\cite{hotcarbon2026}; our energy measurement (\cref{sec:disc}) instead compares restore paths for one returning request.
We study a different axis: the timing of placement and precision decisions, given an adaptive reader.

\section{Scope and Threats to Validity}\label{sec:threats}
\textbf{One platform.} Every measurement comes from one MI300X; other GPUs change recompute speed and therefore the meeting point.
\textbf{Slow recomputation.} The harness recomputes 1.7--2$\times$ slower than default vLLM; faster recomputation moves the Cake band and the meeting points, and only simulation covers it (\cref{sec:placement-fast}).
\textbf{Rate-limited tiers.} Slow tiers are pinned memory behind a limiter; device effects such as write cliffs and file-system overhead are absent, and we name tiers by bandwidth.
\textbf{Single-request GPU harness.} Concurrency appears only in simulation without GPU validation, and per-GPU SSD bandwidth when several GPUs offload at once is not measured.
\textbf{Models and lengths.} Placement uses one GQA model on the GPU; precision uses two GQA models at 32K tokens with synthetic tasks; MHA models, longer contexts, and real conversations remain open (\pending{64K/128K study; LongBench subset}).
\textbf{Small samples where noted.} The vLLM drop count and the energy result each come from one seed.

\section{Conclusion}
Read-adaptive restore changes when a KV cache manager needs to decide.
Across 36 GPU comparisons, write-time placement never beat the same rule applied later, and under Cake the stored position of a low-precision block mostly decides whether the restore reads it, while the codec decides how much it hurts accuracy.
Uniform formats that fit the model's key distribution meet a 2-point bound at FP8 and INT4, and position adds nothing to a fixed ratio, so a system can write simply, demote and quantize lazily, and decide at read time.
